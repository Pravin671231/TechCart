## Feature-based structure

- `src/app/` is routing only — thin files that import and render from `src/features/<feature>/`. Next's file-system router requires `app/` for routes; that's the only thing that belongs there.
- `src/features/<feature>/` holds the actual UI/logic for that feature. `src/features/home/HomeContent.tsx` is the current worked example, rendered by `src/app/page.tsx`. `src/features/category/CategoryContent.tsx` (Issue #73 / M2.16) is a second, rendered by the first dynamic route in the repo, `src/app/category/[slug]/page.tsx` — `params` is a `Promise<{slug}>` in this Next version, `await`ed in an async Server Component route file that stays thin per the convention above. `src/features/products/`, `src/features/categories/`, and `src/features/brands/` are resource-named (not screen-named) features — each owns exactly one backend resource's types/`api.ts`, reusable by any screen that needs that resource, distinct from screen-composition features like `home/`/`category/`.
- This mirrors `backend/src/modules/<feature>/`'s feature-based organization (see `backend/AGENTS.md`), adapted for Next's routing constraints — named `features` here rather than `modules`, since this is a different framework with its own conventions.
- `src/features/search/` (Issue #74 / M2.17) is a third screen-composition feature, rendered by `src/app/search/page.tsx` — `searchParams` is also a `Promise<{q?: string}>` in this Next version, `await`ed the same way `params` is on the category route. It reuses `products/`'s `ProductGrid`/`ProductCard` (home's grid shape, not category's row layout — the mock's card markup matches home's) and `Pagination`, but owns its own `SearchSortSelect` (adds a `relevance` option that only makes sense alongside a keyword, so it isn't merged into `products/SortSelect`) and its own `SearchFilterRail`/`SearchEmpty` — the former adds a category filter search doesn't have a fixed scope for, the latter renders one of two distinct copy strings per `FR-CAT-067` depending on whether the empty result is the keyword's fault or a filter's.
- `src/features/productDetail/` (Issue #75 / M2.18) is a fourth screen-composition feature, rendered by `src/app/products/[slug]/page.tsx` (a second dynamic route). `ProductGallery` and `VariantSelector` are the two pieces with real client state: a variant switch swaps the displayed price/availability/images from the *already-fetched* `useGetProductBySlugQuery` response's `variants[]` array — no refetch, per `FR-CAT-064` — computed via a `pickVariant()` helper matching the current `selectedAttributes` against each variant's own `attributes[]`. Both `ProductGallery`'s image-index reset and `ProductDetailContent`'s default-variant-on-load reset use React's documented "adjust state during render on a prop/data change" pattern (a guarded `setState` call in the render body, not inside a `useEffect`) — `react-hooks/set-state-in-effect` (part of this workspace's `eslint-config-next` rule set) rejects the effect-based version of the same reset.
- `src/features/authentication/auth/` (Issue #146 / M3.8) is `buyer-app`'s first auth surface — no password field anywhere: `GoogleSignIn.tsx` (Google Identity Services script, an auto-triggered One Tap prompt plus a rendered "Sign in with Google" button), `OtpSignIn.tsx` (email entry → 6-digit code entry with a 30s resend cooldown, distinct inline messages for `GOOGLE_ACCOUNT_IS_ADMIN`/`INVALID_OTP`/`OTP_EXPIRED`), and `SignInContent.tsx` (composes both, redirects home once `getSession` reports an existing session) — rendered by `src/app/sign-in/page.tsx`. `api.ts`'s `getSession` query (hitting the real `GET /api/auth/get-session`, not the SRS's illustrative `/api/auth/session`) bootstraps `src/components/layout/AuthStatus.tsx` (rendered in `Header.tsx`) with signed-in/signed-out header state. A bearer token, read off the `set-auth-token` response header on every sign-in mutation (the cross-domain mechanism from the original M3.8 build, unchanged by the backend rewrite), persists in `localStorage` via `tokenStorage.ts` and is attached to every request through `store/api.ts`'s `prepareHeaders` — this is the first feature to make `store/api.ts` auth-aware. **`INVALID_OTP` is the code the backend's `auth.service.ts` `verifyBuyerOtp` throws** for a wrong or already-consumed code — an earlier version checked for `OTP_INVALID` (reversed), so a wrong code never triggered the custom message; found and fixed during a later audit, alongside a second bug in `handleResendOtp`'s error unwrapping that used the wrong error shape and always showed a generic resend-failure message. ## State management (`src/store/`)

- `src/store/` (Issue #71 / M2.14) is a third top-level `src/` directory, peer to `app/` and `features/` — Redux Toolkit + RTK Query infrastructure shared by every feature, not a feature itself. See `docs/architecture.md`'s "State management / data fetching" section for full detail on the envelope-unwrap/error-normalization design and the env fail-loud mechanics.
- `src/store/api.ts` defines **no endpoints of its own** (`endpoints: () => ({})`) and only `tagTypes` (`["Product", "Category", "Session", "Cart"]` — `"Session"` added by #147, `"Cart"` by #152). Add new endpoints via `api.injectEndpoints({...})` inside the owning feature's own `src/features/<feature>/api.ts` — never by editing `src/store/api.ts` directly, except to extend its own `baseQuery`/`meta` machinery (e.g. Issue #72 / M2.15 threaded `pagination` through via `meta` once a real list endpoint needed it) or add a `tagType`.
- `src/features/cart/api.ts` (Issue #152) is the first consumer to use **optimistic `dispatch(cartApi.util.updateQueryData("getCart", undefined, draft => …))`** patches in `onQueryStarted` — each cart mutation patches the cache immediately, then replaces it with the mutation's own full-cart response once it resolves (`.undo()` on rejection). The default MSW handlers in `__tests__/mocks/handlers.ts` now include a signed-out `GET /api/auth/get-session` and an empty `GET /api/cart` so any component test that renders the Header or a product card works without wiring auth; tests that render those also need a `vi.mock("next/navigation", …)` stub (`AddToCartButton`/`CartIndicator` use `useRouter`/`usePathname`).
- `NEXT_PUBLIC_API_URL` (`src/store/env.ts`) fails the build/dev-server loudly if unset — copy `.env.example` to `.env.local` and fill it in before running `dev`/`build`/`test` locally that need a real backend.
- `src/features/products/` (Issue #72 / M2.15) is the shared, cross-screen product-listing feature — `ProductCard`, `ProductGrid`, `Pagination`, `SortSelect`, and the loading/empty/error state components all live here, plus `api.ts` (the `getProducts`/`getCategoryProducts`/`searchProducts`/`getProductBySlug` endpoints — the latter two added by #74/#75) and `types.ts` (matching `backend`'s `PublicProductListItem`/`PublicProductDetail` exactly). `src/features/home/` only composes these into the home screen's toolbar/grid/pagination layout — later listing screens (category, search) are expected to reuse this feature's components/hooks rather than duplicating them. `getProductBySlug` (detail, not a list) stayed in `products/api.ts` rather than moving to `productDetail/` — same "same resource, different query" precedent `getCategoryProducts` already set.

### `isLoading` vs `isFetching` for query-driven screens (`fix/buyer-app-ui-bug`, no issue)

- **Rule**: an RTK Query consumer that drives a list/content area gates its **skeleton** on `isLoading` (the first-ever fetch of a cache key, no data yet) and shows a **dimmed "Updating…" indicator** for any *subsequent* fetch — a page / filter / sort / search-term change — via `isFetching && !isLoading`. RTK Query keeps the previous `data` visible across an arg change, so the subsequent-fetch case is a silent swap otherwise. Buyer-app counterpart to `admin-app`'s `Table`/`DataTable` async-state rule.
- **`src/components/ui/FetchingOverlay.tsx`** is the shared wrapper: `relative` container, `aria-busy`, dims (`opacity-50`) its children while `isFetching`, and renders a `role="status"` "Updating…" pill (spinner + text). Wrap the *populated* branch of the loading conditional in it — never the `isLoading` skeleton branch.
- Wired into `CategoryContent`, `SearchContent`, and `OrderHistoryContent` (the three user-paginated list screens). `HomeContent` already covers this via `InfiniteScrollFooter`'s own `isFetching`-driven "Loading more…" line. Detail pages, cart, checkout, addresses, and session guards are deliberately out of scope — they remount on the arg change or a refetch cue there is noise.
- **`Pagination` (`src/features/products/Pagination.tsx`) smooth-scrolls the window to the top on any page change** (`window.scrollTo`, `behavior: "auto"` under `prefers-reduced-motion`), for every screen that renders it — the numbered pager also now no-ops a click on the already-active page. `vitest.setup.ts` stubs `window.scrollTo`/`matchMedia` (jsdom has neither).

## Dev-only RTK Query request/response logging (Issue #253)

- **`src/store/api.ts`'s `baseQueryWithEnvelope`** logs every request/response through it, gated behind `process.env.NODE_ENV !== "production"` (Next's own statically-replaced build-time flag, so this is dead-code-eliminated from production the same way `admin-app`'s Vite-based equivalent is — no headers logged, `"[RTK Query]"`-prefixed, verified absent from a production build via grep). Same shape as `admin-app`'s (see `admin-app/AGENTS.md`'s matching section for the full design rationale): a collapsed per-request `console.group` (`request` →, for a mutation only, a copy-paste-ready `mutation input` JSON block → `response`), plus a separate, `setTimeout`-deferred group logging the full RTK Query cache slice after the result actually commits.

## Availability badge and insufficient-stock error (Issue #192 / M10.4, SRS v0.10)

Wires `buyer-app` up to two backend changes from M10 (Inventory Management, Issues #189/#190): a real per-variant `availability` field on buyer-facing product responses, and a new `409 INSUFFICIENT_STOCK` a cart mutation can throw. No new feature directory — this issue touches `products/`, `productDetail/`, and `cart/` in place.

- **`products/types.ts`'s `ProductAvailability` narrowed to the real 2-state `"in_stock" | "out_of_stock"`** — this type (and `productDetail/AvailabilityBadge.tsx`) predate #102's removal of stock system-wide and had sat dormant with a 3-state `"out_of_stock" | "low_stock" | "in_stock"` shape ever since; `low_stock` never existed on any real backend response and is dropped. `PublicProductListItem.availability` stays optional (a card's own best-across-active-variants figure); `PublicProductDetail`'s **top-level** `availability` field is removed outright — it never actually existed on the real API response (availability only ever lives per-variant, on `PublicProductVariant.availability`, which stays required).
- **`AvailabilityBadge` finally wired into `ProductDetailContent.tsx`** — previously a commented-out line waiting on this exact backend field (`{selectedVariant && <AvailabilityBadge availability={selectedVariant.availability} />}`, rendered next to price).
- **`AddToCartButton.tsx` gains an `availability?: ProductAvailability` prop**: `"out_of_stock"` renders a disabled "Out of stock" button in place of the normal control — the same early-return branch shape the existing `!variantId` → "Unavailable" case already used — never a raw stock number anywhere (`FR-INV-007`). Card call sites (`ProductCard` on home/search, `CategoryProductCard`) pass their list item's own `availability`; the PDP passes the currently selected variant's.
- **`AddToCartButton`/`CartLineRow`'s mutation calls switch from a bare, silently-swallowed `.catch(() => {})` to `.unwrap().catch((err: NormalizedApiError) => …)`**, checking `err.code === "INSUFFICIENT_STOCK"` and rendering `err.message` (the backend's own "naming the available count" wording, e.g. "Only 2 unit(s) available for this item.") inline via a small local `insufficientStockMessage` state — a `role="alert"` paragraph under the control. Every *other* mutation rejection on these two components still rolls back silently through the existing optimistic-cache `.undo()` with no inline copy; `INSUFFICIENT_STOCK` is the one case worth surfacing, since a cart quantity increase or a repeat add can genuinely outrun the warehouse it was allocated to (`FR-INV-009`–`011`) and a silent rollback there would leave the buyer with no idea why their click did nothing.
- **Two pre-existing flaky tests and one pre-existing lint failure, all unrelated to this issue, were fixed in the same PR** since each was blocking the `lint`/`test (buyer-app)` CI checks required for any buyer-app PR to merge (confirmed by reproducing both with this issue's own changes stashed out — identical failures on `main`): `addToCartButton.test.tsx`'s "flips to 'Go to Cart'" test could fire its click before `getSession`/`getCart` had resolved, making a signed-in click look signed-out — fixed by waiting on both RTK Query cache entries' `status` reaching `"fulfilled"` before clicking; `orders.test.tsx`'s cancel-order test waited for the "Cancel order" button to disappear, which its own transient "Cancelling…" in-flight label already satisfies before the mutation has actually resolved — fixed by waiting for the "Cancelled" status badge instead; `CheckoutContent.tsx`'s default-address effect called `setState` synchronously inside a `useEffect` (`react-hooks/set-state-in-effect`) — fixed via the render-time derived-state pattern `ProductDetailContent`'s own default-variant reset already established in this workspace, rather than an effect.
- Test layout: `addToCartButton.test.tsx` gained an out-of-stock-badge render test and an `INSUFFICIENT_STOCK`-on-add inline-message test; `cart.test.tsx` gained an `INSUFFICIENT_STOCK`-on-quantity-increase inline-message test; `productDetail.test.tsx`'s fixtures updated for the narrowed `ProductAvailability` and the removed top-level `PublicProductDetail.availability` field.

## Testing

- Stack: Vitest (`environment: "jsdom"`) + React Testing Library + MSW, wired via `vitest.config.ts` + `vitest.setup.ts`. Path aliases (`@/*`) resolve via the `vite-tsconfig-paths` plugin — `backend/vitest.config.ts`'s `resolve: { tsconfigPaths: true }` is not a real Vite/Vitest option (confirmed by reproducing the failure there), so it isn't mirrored here.
- Test files live in `__tests__/` at the workspace root (not colocated inside `src/`), e.g. `__tests__/home.test.tsx`, `__tests__/store/api.test.ts`.
- The shared MSW server lives at `__tests__/mocks/server.ts` (built from `__tests__/mocks/handlers.ts`) and is started/stopped once for the whole run via `vitest.setup.ts`. New feature tests that need to mock a request add handlers to `handlers.ts`, or call `server.use(...)` inside the test itself for a one-off override.
- A component using RTK Query hooks needs a manual `<Provider store={makeStore()}>` wrapper (`@/store/store`) when rendered directly with RTL — `layout.tsx`'s `StoreProvider` isn't part of the tree for a component rendered in isolation from its route.
- `npm run test --workspace buyer-app` runs the suite once (`vitest run`, not watch mode).
