## Feature-based structure

- `src/app/` is routing only — thin files that import and render from `src/features/<feature>/`. Next's file-system router requires `app/` for routes; that's the only thing that belongs there.
- `src/features/<feature>/` holds the actual UI/logic for that feature. `src/features/home/HomeContent.tsx` is the current worked example, rendered by `src/app/page.tsx`. `src/features/category/CategoryContent.tsx` (Issue #73 / M2.16) is a second, rendered by the first dynamic route in the repo, `src/app/category/[slug]/page.tsx` — `params` is a `Promise<{slug}>` in this Next version, `await`ed in an async Server Component route file that stays thin per the convention above. `src/features/products/`, `src/features/categories/`, and `src/features/brands/` are resource-named (not screen-named) features — each owns exactly one backend resource's types/`api.ts`, reusable by any screen that needs that resource, distinct from screen-composition features like `home/`/`category/`.
- This mirrors `backend/src/modules/<feature>/`'s feature-based organization (see `backend/AGENTS.md`), adapted for Next's routing constraints — named `features` here rather than `modules`, since this is a different framework with its own conventions.
- `src/features/search/` (Issue #74 / M2.17) is a third screen-composition feature, rendered by `src/app/search/page.tsx` — `searchParams` is also a `Promise<{q?: string}>` in this Next version, `await`ed the same way `params` is on the category route. It reuses `products/`'s `ProductGrid`/`ProductCard` (home's grid shape, not category's row layout — the mock's card markup matches home's) and `Pagination`, but owns its own `SearchSortSelect` (adds a `relevance` option that only makes sense alongside a keyword, so it isn't merged into `products/SortSelect`) and its own `SearchFilterRail`/`SearchEmpty` — the former adds a category filter search doesn't have a fixed scope for, the latter renders one of two distinct copy strings per `FR-CAT-067` depending on whether the empty result is the keyword's fault or a filter's.
- `src/features/productDetail/` (Issue #75 / M2.18) is a fourth screen-composition feature, rendered by `src/app/products/[slug]/page.tsx` (a second dynamic route). `ProductGallery` and `VariantSelector` are the two pieces with real client state: a variant switch swaps the displayed price/availability/images from the *already-fetched* `useGetProductBySlugQuery` response's `variants[]` array — no refetch, per `FR-CAT-064` — computed via a `pickVariant()` helper matching the current `selectedAttributes` against each variant's own `attributes[]`. Both `ProductGallery`'s image-index reset and `ProductDetailContent`'s default-variant-on-load reset use React's documented "adjust state during render on a prop/data change" pattern (a guarded `setState` call in the render body, not inside a `useEffect`) — `react-hooks/set-state-in-effect` (part of this workspace's `eslint-config-next` rule set) rejects the effect-based version of the same reset.
- `src/features/authentication/auth/` (Issue #146 / M3.8) is `buyer-app`'s first auth surface — no password field anywhere: `GoogleSignIn.tsx` (Google Identity Services script, an auto-triggered One Tap prompt plus a rendered "Sign in with Google" button), `OtpSignIn.tsx` (email entry → 6-digit code entry with a 30s resend cooldown, distinct inline messages for `GOOGLE_ACCOUNT_IS_ADMIN`/`INVALID_OTP`/`OTP_EXPIRED`), and `SignInContent.tsx` (composes both, redirects home once `getSession` reports an existing session) — rendered by `src/app/sign-in/page.tsx`. `api.ts`'s `getSession` query (hitting the real `GET /api/auth/get-session`, not the SRS's illustrative `/api/auth/session`) bootstraps `src/components/layout/AuthStatus.tsx` (rendered in `Header.tsx`) with signed-in/signed-out header state. A bearer token, read off the `set-auth-token` response header on every sign-in mutation (the cross-domain mechanism from the original M3.8 build, unchanged by the backend rewrite), persists in `localStorage` via `tokenStorage.ts` and is attached to every request through `store/api.ts`'s `prepareHeaders` — this is the first feature to make `store/api.ts` auth-aware. **`INVALID_OTP` is the code the backend's `auth.service.ts` `verifyBuyerOtp` throws** for a wrong or already-consumed code — an earlier version checked for `OTP_INVALID` (reversed), so a wrong code never triggered the custom message; found and fixed during a later audit, alongside a second bug in `handleResendOtp`'s error unwrapping that used the wrong error shape and always showed a generic resend-failure message. Issue #262 / M3.24 re-verified `auth/` and `account/` end-to-end against the custom hand-rolled backend (`backend/src/modules/authentication/auth/` on the custom session engine — Better Auth is fully removed, Issues #257–#261): routes, request bodies, the `set-auth-token` bearer flow, and the `GOOGLE_ACCOUNT_IS_ADMIN`/`INVALID_OTP`/`OTP_EXPIRED`/`RATE_LIMITED` codes all still line up. The one fix needed: `getSession`'s `transformResponse` now null-guards the response, since the backend's signed-out reply is `data: null` (not `data: { user: null }` — the shape the MSW mocks had always assumed and which masked the latent crash that left the header with no "Sign in" link and `/account` un-redirected for signed-out users).
- `src/features/authentication/account/` (Issue #147 / M3.9) is the buyer-facing half of `M3.6`'s backend profile endpoint — a view/edit form for `name`/`phone` (`ProfileForm.tsx`; email is rendered read-only, not editable, matching the backend's own `updateProfileSchema`) composed by `AccountContent.tsx`, rendered by `src/app/account/page.tsx`. No mock-ui wireframe exists for this screen (unlike home/category/search/product-detail), so its layout follows `SignInContent.tsx`'s established form-card visual style directly rather than translating a mock. `AccountContent.tsx` mirrors `SignInContent.tsx`'s own `useGetSessionQuery`-driven redirect, just inverted — no session redirects to `/sign-in` instead of home — then fetches the authoritative profile via a new `getProfile`/`updateProfile` pair in `api.ts` (`GET`/`PATCH /api/account/profile`), both tagged `"Session"` (the same tag `auth/api.ts`'s `getSession` already uses, not a new `"Account"` tag) so a successful edit also refreshes `AuthStatus.tsx`'s header name with no extra wiring. `AuthStatus.tsx`'s signed-in name is now a `next/link` to `/account` — previously plain text with no way to reach this screen. `ProfileForm.tsx` deliberately does no client-side pre-submit validation, letting an empty `name` reach the real backend and displaying its actual `VALIDATION_ERROR` response — consistent with `OtpSignIn.tsx`'s own "let the server validate" precedent.
- Screen-level design reference: [`mock-ui/`](../mock-ui/) — static wireframes per feature's SRS doc, not a workspace of its own. Consult it before building a feature's UI.
- Brand tokens (`primary`/`accent` color scales, `Inter` as `font-sans`) are wired into `src/app/globals.css` via a Tailwind `@theme` block. [`mock-ui/brand-kit.html`](../mock-ui/brand-kit.html) is the visual reference; `globals.css` is the source of truth if they ever drift.
- `src/app/loading.tsx` (Issue #119) is the root Next.js `loading.js`-convention special file — auto-wraps every route in a `<Suspense>` boundary, rendering a placeholder brand-token spinner during navigation. Fonts (`Inter`, `Plus Jakarta Sans`) are self-hosted via `next/font/google` in `layout.tsx` (not the old Google Fonts CDN `@import` — don't re-add it), feeding `globals.css`'s `--font-sans`/`--font-display` through a separate `@theme inline` block via CSS variables. See `docs/architecture.md`'s "State management / data fetching" section for the full detail.
- `src/components/layout/` (Issue #122) is a new top-level directory, peer to `app/`/`features/`/`store/` — cross-route chrome, not feature-owned code. `Header.tsx`/`Footer.tsx`/`AppShell.tsx` are translated directly from `mock-ui/buyer-app/`'s own header/footer (byte-identical across all 4 page mocks) and wired into `src/app/layout.tsx`, so every route gets the shell automatically without each feature needing its own copy. The header's search box is a static link to `/search`, not a functional input (no search-input feature exists yet); the mock's Cart icon and "All Categories" dropdown are omitted since neither has a real feature or route behind it. Every other placeholder mock link (footer's Customer Service links, social icons, Privacy/Terms) uses a plain `<a href="#">`, not `next/link`, since `next/link` is for real internal routes and these aren't. `PageContainer.tsx` (Issue #123) joined it — the `mx-auto max-w-7xl ...` page-shell `<main>` wrapper repeated across all 8 return sites in Home/Search/Category/ProductDetail's content components, now composed as `<PageContainer className="flex flex-col">`/`<PageContainer>` instead.
- `src/components/ui/` (Issue #123) is a sibling to `components/layout/` for generic, feature-agnostic primitives — added only after a direct-code survey found 6 pieces of markup/logic genuinely duplicated across 2+ features, not speculatively. `PriceDisplay` (price/MRP/discount-badge; `size`/`stacked` props) takes pre-formatted `price`/`mrp` **strings** rather than raw numbers specifically so this directory never imports from `src/features/*` — callers still call `features/products/money.ts`'s `formatPrice()` themselves. `NotFoundState` (message prop) supersedes the deleted, byte-identical `productDetail/ProductNotFound.tsx`/`category/CategoryNotFound.tsx`. `Checkbox` and `PriceRangeInput` (the latter owns the min/max local-state + blur/Enter commit logic, not just markup) replace duplicated code in `CategoryFilterRail`/`SearchFilterRail`. `SkeletonBox` (sizing/rounding via `className`) replaces the repeated shimmer leaf across all 3 skeleton components. Along the way, `ProductDetailContent`'s error branch — previously a hand-rolled duplicate of `products/ProductListError` with different copy ("...this product." vs. "...products.") — was fixed to reuse `ProductListError` via a new optional `message` prop instead of duplicating its markup.

## State management (`src/store/`)

- `src/store/` (Issue #71 / M2.14) is a third top-level `src/` directory, peer to `app/` and `features/` — Redux Toolkit + RTK Query infrastructure shared by every feature, not a feature itself. See `docs/architecture.md`'s "State management / data fetching" section for full detail on the envelope-unwrap/error-normalization design and the env fail-loud mechanics.
- `src/store/api.ts` defines **no endpoints of its own** (`endpoints: () => ({})`) and only `tagTypes: ["Product", "Category"]`. Add new endpoints via `api.injectEndpoints({...})` inside the owning feature's own `src/features/<feature>/api.ts` — never by editing `src/store/api.ts` directly, except to extend its own `baseQuery`/`meta` machinery (e.g. Issue #72 / M2.15 threaded `pagination` through via `meta` once a real list endpoint needed it).
- `NEXT_PUBLIC_API_URL` (`src/store/env.ts`) fails the build/dev-server loudly if unset — copy `.env.example` to `.env.local` and fill it in before running `dev`/`build`/`test` locally that need a real backend.
- `src/features/products/` (Issue #72 / M2.15) is the shared, cross-screen product-listing feature — `ProductCard`, `ProductGrid`, `Pagination`, `SortSelect`, and the loading/empty/error state components all live here, plus `api.ts` (the `getProducts`/`getCategoryProducts`/`searchProducts`/`getProductBySlug` endpoints — the latter two added by #74/#75) and `types.ts` (matching `backend`'s `PublicProductListItem`/`PublicProductDetail` exactly). `src/features/home/` only composes these into the home screen's toolbar/grid/pagination layout — later listing screens (category, search) are expected to reuse this feature's components/hooks rather than duplicating them. `getProductBySlug` (detail, not a list) stayed in `products/api.ts` rather than moving to `productDetail/` — same "same resource, different query" precedent `getCategoryProducts` already set.

## Dev-only RTK Query request/response logging (Issue #253)

- **`src/store/api.ts`'s `baseQueryWithEnvelope`** logs every request/response through it, gated behind `process.env.NODE_ENV !== "production"` (Next's own statically-replaced build-time flag, so this is dead-code-eliminated from production the same way `admin-app`'s Vite-based equivalent is — no headers logged, `"[RTK Query]"`-prefixed, verified absent from a production build via grep). Same shape as `admin-app`'s (see `admin-app/AGENTS.md`'s matching section for the full design rationale): a collapsed per-request `console.group` (`request` →, for a mutation only, a copy-paste-ready `mutation input` JSON block → `response`), plus a separate, `setTimeout`-deferred group logging the full RTK Query cache slice after the result actually commits.

## Testing

- Stack: Vitest (`environment: "jsdom"`) + React Testing Library + MSW, wired via `vitest.config.ts` + `vitest.setup.ts`. Path aliases (`@/*`) resolve via the `vite-tsconfig-paths` plugin — `backend/vitest.config.ts`'s `resolve: { tsconfigPaths: true }` is not a real Vite/Vitest option (confirmed by reproducing the failure there), so it isn't mirrored here.
- Test files live in `__tests__/` at the workspace root (not colocated inside `src/`), e.g. `__tests__/home.test.tsx`, `__tests__/store/api.test.ts`.
- The shared MSW server lives at `__tests__/mocks/server.ts` (built from `__tests__/mocks/handlers.ts`) and is started/stopped once for the whole run via `vitest.setup.ts`. New feature tests that need to mock a request add handlers to `handlers.ts`, or call `server.use(...)` inside the test itself for a one-off override.
- A component using RTK Query hooks needs a manual `<Provider store={makeStore()}>` wrapper (`@/store/store`) when rendered directly with RTL — `layout.tsx`'s `StoreProvider` isn't part of the tree for a component rendered in isolation from its route.
- `npm run test --workspace buyer-app` runs the suite once (`vitest run`, not watch mode).
