# TechCart context

This is the `admin-app` workspace of a monorepo. Root-level decisions (monorepo layout, shared tooling, error contract, auth) live in root [`CLAUDE.md`](../CLAUDE.md), [`AGENTS.md`](../AGENTS.md), and [`docs/architecture.md`](../docs/architecture.md) — nothing here overrides those. Implementation detail for this workspace specifically is in [`docs/architecture.md`](docs/architecture.md).

## Feature-based structure

- `src/app/` holds Redux/RTK Query state only, split into two sibling subfolders (see "Redux store" section below): `app/store/{store.ts,authSlice.ts,hooks.ts}` (the store itself, the auth slice, and typed `useAppDispatch`/`useAppSelector` hooks) and `app/api/{baseApi.ts,baseQuery.ts,api.types.ts,apiResponse.ts,apiError.ts,apiToast.ts,ENDPOINTS.ts}` (the RTK Query `createApi` instance, its base-query/401-guard, the response-envelope types, the success-response unwrap helpers, the error-reading helper, the sonner-toast bridge (`apiToast.ts`, see "Confirmation dialogs and toast notifications" below), and `ENDPOINTS.ts` — now just a re-export of feature-owned endpoint constants, see below). Routing lives elsewhere: `src/App.tsx` is the top-level composition root (`Provider` > `BrowserRouter` > `AdminKeyGate` > `MainRoutes`, plus a sibling `<Toaster />`), and `src/routes/mainRoutes.tsx` holds the top-level `<Routes>`/`<Route>` tree, since there's no file-system router here (unlike `buyer-app`'s Next.js App Router).
- `src/features/<feature>/` holds the actual UI/logic for that feature. `src/features/landing/LandingPlaceholder.tsx` is the current worked example, rendered at `/` by `src/routes/mainRoutes.tsx`.
- This mirrors `backend/src/modules/<feature>/` and `buyer-app/src/features/<feature>/`'s feature-based organization (see `backend/AGENTS.md`, `buyer-app/AGENTS.md`), adapted for React Router instead of a file-system router.
- `src/features/product-catalog/` groups the 5 features that together implement the Product Catalog domain — `brands/`, `categories/`, `categorySpecifications/`, `categoryVariants/`, `products/` (incl. `products/productForm/`) — since they form one cohesive domain (matching the backend/SRS's own Product Catalog grouping) rather than sitting flat alongside single-purpose features like `adminKey/`, `uploads/`, `landing/`. Every section below that names one of these 5 (e.g. "Brand management") refers to its path as `src/features/product-catalog/<feature>/`.
- **`src/features/product-catalog/endpoints.ts`/`routePaths.ts`/`routes.tsx`** — the domain's own centralized constants and routing, owned by the feature rather than authored generically in `app/api/`/`routes/`. `endpoints.ts` exports `PRODUCT_CATALOG_ENDPOINTS` (backend API paths, namespaced per sub-feature, functions for dynamic segments — e.g. `PRODUCT_CATALOG_ENDPOINTS.products.detail(id)`); every sub-feature's `*Api.ts` imports it instead of inlining URL strings, and `app/api/ENDPOINTS.ts` re-exports it as the one canonical import path for anything outside the feature. `routePaths.ts` exports `PRODUCT_CATALOG_ROUTES` (frontend page paths, same per-sub-feature namespacing; dynamic entries carry both a `*Pattern` string for `<Route path>` and a builder function for `Link`/`navigate`, since React Router needs a literal `:id` in the former but a real id in the latter). `routes.tsx` exports `ProductCatalogRoutes()`, a function returning all 8 product-catalog `<Route>` elements (built from `routePaths.ts` + each page's own component) as a fragment; `src/routes/mainRoutes.tsx` mounts it via `{ProductCatalogRoutes()}` inside the `AppShell` layout route — called as a plain function, not `<ProductCatalogRoutes />`, since `<Routes>` only recognizes `<Route>` children directly, not nested custom components. `src/components/layout/navItems.ts` and the three `Link`/`navigate` call sites in `products/ProductList.tsx`, `products/ProductDetailPage.tsx`, and `products/productForm/ProductForm.tsx` all import `PRODUCT_CATALOG_ROUTES` directly rather than hardcoding path strings.
- `src/components/` holds cross-feature building blocks with no domain logic of their own, split by purpose rather than feature: `components/ui/` (generic reusable primitives — `Button`, `Card`, `ConfirmDialog`, `InlineAlert`, `LoadingState`, `Pagination`, `StatusBadge`, `Table`), `components/form/` (form-input controls — `Checkbox`, `FormField`, `SearchInput`), and `components/layout/` (app chrome and page structure — `AppShell`, `Sidebar`, `SidebarItems`, `Header`, `Footer`, `MainSection`, `navItems`, `PageHeader`, `TableLayout` — see "Admin shell & reusable layout components" below for the Issue #107 rework of this folder). `AppShell` is wired as a React Router layout route (`<Route element={<AppShell />}>` wrapping every page route) inside `src/routes/mainRoutes.tsx`, itself rendered by `AdminKeyGate` in `App.tsx`.
- Screen-level design reference: [`mock-ui/`](../mock-ui/) — static wireframes per feature's SRS doc, not a workspace of its own. Consult it before building a feature's UI.
- Brand tokens (`primary`/`accent` color scales, `Inter` as `font-sans`) are wired into `src/index.css` via a Tailwind `@theme` block. [`mock-ui/brand-kit.html`](../mock-ui/brand-kit.html) is the visual reference; `index.css` is the source of truth if they ever drift.

## Redux store, RTK Query, and the X-Admin-Key gate (Issue #76 / M2.19)

- `src/app/store/authSlice.ts` — holds `adminKey: string | null`, hydrated from `sessionStorage` (key `techcart_admin_key`, `ADMIN_KEY_STORAGE_KEY` exported) at module-init time, not a mount effect, so there's no flash of the key prompt on reload. `setAdminKey`/`clearAdminKey` sync `sessionStorage` inline in the reducer (plain synchronous browser API, no thunk needed).
- `src/app/api/` — split out of a single former `api.ts` into files by concern: `baseQuery.ts` (the `fetchBaseQuery` config plus a `baseQueryWithAdminKeyGuard` wrapper that dispatches `clearAdminKey()` whenever a request comes back `401` — the backend's `adminAuth` middleware is what actually enforces the key, this only reacts to its rejection), `baseApi.ts` (just the `createApi` instance every feature module `injectEndpoints` into — `reducerPath`, `tagTypes`, and the base query from `./baseQuery`), `api.types.ts` (the `Pagination`/`ApiSuccessEnvelope`/`ApiSuccessListEnvelope`/`ApiErrorEnvelope` types, no functions), `apiResponse.ts` (`unwrapData`/`unwrapList` helpers for endpoints' own `transformResponse`), `apiError.ts` (`getApiErrorEnvelope` — `fetchBaseQuery`'s `FetchBaseQueryError` already carries the raw `{success:false,code,message}` body as `error.data`, so no `transformErrorResponse` is needed either), `apiToast.ts` (`notifyApiSuccess`/`notifyApiError` — see "Confirmation dialogs and toast notifications" below), and `ENDPOINTS.ts` (a re-export of `PRODUCT_CATALOG_ENDPOINTS` from `src/features/product-catalog/endpoints.ts` — see "Feature-based structure" above; every product-catalog `*Api.ts` file builds its request URLs from that constant instead of inlining strings like `"/brands"`). `baseApi.ts`'s `fetchBaseQuery`'s `baseUrl` is `ADMIN_API_BASE_URL` (`${API_URL}/api/admin`, from `src/config/env.ts`), so endpoint `query` paths stay relative (`"/brands"`, not `"/api/admin/brands"`); `prepareHeaders` attaches `X-Admin-Key` only when `adminKey` is non-null (never sends a literal `"null"` header).
- `src/app/store/store.ts` — `configureStore` built from a `combineReducers` root (`auth` + the api slice), exposed as both a `createStore(preloadedState?)` factory and a `store` singleton. Tests that need an isolated store (rather than mutating the app's singleton) should use `createStore(...)`, not `store` directly — see `__tests__/utils/renderWithStore.tsx`. `store/` moved under `src/app/` (from a former standalone `src/store/`) so `app/` is the single container for Redux/state — see "Feature-based structure" above.
- `src/app/store/hooks.ts` — `useAppDispatch`/`useAppSelector`, the standard Redux Toolkit typed-hooks pair (`useDispatch<AppDispatch>()` / `useSelector` typed via `TypedUseSelectorHook<RootState>`). Components should use these instead of raw `react-redux` `useDispatch`/`useSelector` — e.g. `AdminKeyGate.tsx`, `AdminKeyPrompt.tsx`, and `SidebarNav.tsx` all consume these rather than the untyped hooks directly.
- `src/features/adminKey/` — `AdminKeyGate` wraps `<MainRoutes />` once in `App.tsx` (there are no public admin-app routes to leave unguarded); it renders `AdminKeyPrompt` (a minimal one-field form) until `state.auth.adminKey` is set. This is explicitly a **throwaway client-side convenience**, not a security boundary — real sessions replace it outright once v0.3 Authentication lands. Don't build on top of it expecting it to survive.
- `src/config/env.ts` — `API_URL` reads `import.meta.env.VITE_API_URL`, falling back unconditionally to `http://localhost:4000` (no "fail loudly if missing" — unlike `backend`'s `env.ts`, this app has no required-secret startup check). `src/vite-env.d.ts`'s `/// <reference types="vite/client" />` is what makes `import.meta.env` type-check at all; add to it if a second env var is introduced.
- **Testing gotcha**: `authSlice`'s `sessionStorage` read happens once, at ESM module-eval time. A test that needs a pre-authenticated render should dispatch `setAdminKey(...)` against the store directly (see `__tests__/app.test.tsx`'s `beforeEach`) — seeding `sessionStorage` and expecting an already-imported store to pick it up won't work, since the module was already evaluated. The one test that specifically verifies hydration (`__tests__/store/authSlice.test.ts`) works around this with `vi.resetModules()` + a dynamic `await import("@/app/store/authSlice")` after seeding `sessionStorage`.

## Brand management (Issue #77 / M2.20)

- `src/features/product-catalog/brands/` — the first feature module to `injectEndpoints` into the shared `api` instance. `brandsApi.ts`'s `getBrands` query and `createBrand`/`updateBrand`/`updateBrandStatus`/`deleteBrand` mutations all share one flat `"Brand"` tag (`providesTags`/`invalidatesTags: ["Brand"]`, no per-id scheme) — matching the issue's own literal spec, and appropriate here since the brand list is small and unpaginated. `src/app/api/baseApi.ts`'s `createApi` call now declares `tagTypes: ["Brand"]`; any future feature's own tag type must be added there too, since RTK Query requires tag types declared upfront on the base instance, not just referenced from `injectEndpoints`.
- **`updateBrand` cannot change `status`** — the backend's `PATCH /api/admin/brands/:id` Zod schema only accepts `name`/`description`/`logo`; status is exclusively `PATCH /api/admin/brands/:id/status` (`{status: boolean}`). `BrandForm` therefore has no status field at all — the list's own status badge (`BrandList.tsx`) is a clickable toggle calling `useUpdateBrandStatusMutation` directly. Don't try to fold status into the edit form; the API doesn't support it.
- **Delete-guard rejection is rendered inline, not as a modal or toast** — `BrandList.tsx` catches a blocked `deleteBrand` mutation's `409 BRAND_IN_USE` via `.unwrap()`, reads the message through `getApiErrorEnvelope()` (`src/app/api/apiError.ts`, new — pulls `error.data` off an RTK Query `FetchBaseQueryError`), and renders it in a `role="alert"` row scoped to that brand. The backend's message is plain text with an embedded count (`"Cannot delete brand: referenced by N product(s)."`) — there's no separate numeric field, so it's displayed verbatim rather than reformatted.
- **Logo upload is a three-step client flow**, not a single request: `src/features/uploads/uploadsApi.ts`'s `presignUpload` mutation (`POST /api/admin/uploads/presign`, `{purpose, contentType}`) returns `{uploadUrl, objectKey, publicUrl, expiresAt}`; the file is then `PUT` directly to `uploadUrl` via `putFileToPresignedUrl()` (plain `fetch`, not RTK Query — it targets R2, not `backend`, and needs no `X-Admin-Key`); only `objectKey` (not `publicUrl`) is sent back to `backend` in the brand's `logo: {objectKey, alt?}` field on create/update. The response shape differs by direction: a brand's `logo` field in a **request** is `{objectKey, alt?}`, but in a **response** it's `{url, alt?}` — these are deliberately different types (`BrandLogoInput` vs `BrandLogo` in `src/features/product-catalog/brands/types.ts`), not a typo. `uploadsApi.ts` is intentionally feature-agnostic (`UPLOAD_PURPOSES` already lists `"category-image"`/`"product-image"` alongside `"brand-logo"`) so later category/product-image issues reuse it rather than duplicating the presign flow.
- **No sidebar/nav shell exists yet** — `mock-ui/admin-app/brand-list.html` shows one, but building it was out of scope for this issue. `LandingPlaceholder.tsx` just gained a plain `Link` to `/brands` as the only way to reach it for now; a real nav shell is expected once more admin screens land (M2.21+).
- Test layout: one `__tests__/features/product-catalog/brands/BrandsPage.test.tsx` integration test (list render, create, edit, delete-guard rejection, status toggle, search, and the full presign→PUT→save logo flow), MSW handlers defined locally via `server.use(...)` per test rather than added to the shared `__tests__/mocks/handlers.ts` — same "one-off override" convention `__tests__/store/api.test.ts` already established.

## Category management (Issue #78 / M2.21)

- `src/features/product-catalog/categories/` — mirrors `brands/`'s file layout and `getCategories`/`create·update·delete·updateStatus` pattern almost exactly (same flat `"Category"` tag, same `unwrapData`/`getApiErrorEnvelope` conventions, same `objectKey`-in/`url`-out image shape via `src/features/uploads/uploadsApi.ts` — `ImageUploader.tsx` here is a near-copy of brands' `LogoUploader.tsx`, just using `purpose: "category-image"`). `src/app/api/baseApi.ts`'s `tagTypes` grew to `["Brand", "Category"]`.
- **The two-level hierarchy renders as one flat, indented table — not a nested tree/accordion.** `CategoryList.tsx`'s `orderAsTree()` groups the flat `CategoryListItem[]` response by `parentCategory` client-side (the backend's `GET /api/admin/categories` returns a flat array with no nesting or sort, confirmed from `categories.repository.ts`): root categories first (sorted by `sortOrder`/`name`), each immediately followed by its own children (same sort). A child row gets a `↳ ` prefix and `pl-8` indent; a dedicated `Parent` column names the parent for children and shows `—` for roots — matching `mock-ui/admin-app/category-list.html` exactly, which has no collapse/expand affordance either.
- **The parent-category picker is a plain `<select>` pre-filtered to root-level categories only** (`CategoryForm.tsx`'s `parentOptions`: any category with no `parentCategory` of its own, excluding the category currently being edited) — matching the mock's own caption, "Only top-level categories are selectable · FR-CAT-014". This client-side filter is a UX nicety, not the enforcement: the backend's `validateParentCategory` (`categories.service.ts`) is what actually rejects an invalid choice, across four distinct error codes the form must surface as inline, field-level text (not a toast) — `INVALID_PARENT_CATEGORY` (400, self-parent), `PARENT_CATEGORY_NOT_FOUND` (404), `PARENT_CATEGORY_TOO_DEEP` (400, parent already has a parent), `CATEGORY_HAS_SUBCATEGORIES` (400, update-only — the category being edited already has children of its own). All four reuse the same `saveError` (`getApiErrorEnvelope(createError ?? updateError)`) already established by `BrandForm`, just positioned directly under the parent `<select>` instead of at the bottom of the form, since three of the four are inherently about that field.
- **`parentCategory` is sent differently on create vs. update, matching the backend's own tri-state Zod schema**: create only accepts `undefined | string` (an empty picker selection is simply omitted from the payload); update accepts `undefined | null | string` and `CategoryForm` always sends either the picked id or explicit `null` on every save — never omits it. This is safe (not just simpler) because `validateParentCategory(null, ...)` short-circuits immediately, and a category that already has children can only ever have a `null` (root) parent locally in the first place (a subcategory can't itself have children, so `CATEGORY_HAS_SUBCATEGORIES` never fires on an always-`null` resend) — see the function's full logic in `backend/CLAUDE.md`'s Categories section if this needs revisiting.
- **The delete guard combines two independent conditions in one message**, not two separate errors: `409 CATEGORY_IN_USE`, with the backend joining whichever of "N product(s)" / "N subcategory(ies)" actually blocks via `" and "` — e.g. `"Cannot delete category: referenced by 1 product(s) and 1 subcategory(ies)."` when both apply. `CategoryList.tsx` displays it verbatim, identical inline-`role="alert"` placement to `BrandList.tsx`.
- No status field on `CategoryForm` either, same reasoning as brands — `updateCategory`'s Zod schema doesn't accept `status`; the list's status badge calls `useUpdateCategoryStatusMutation` directly.
- Test layout: one `__tests__/features/product-catalog/categories/CategoriesPage.test.tsx`, mirroring `BrandsPage.test.tsx`'s structure (`makeCategory`/`setupCategoryHandlers` local closures) but with dedicated cases for the tree-ordering/indentation, each of the four hierarchy-validation error codes individually, and the combined delete-guard wording.

## Category specification editor (Issue #79 / M2.22)

- `src/features/product-catalog/categorySpecifications/` — the first feature module built against `categorySpecifications`' `GET`/`PUT`/`PATCH`-only shape (no `POST`/`DELETE`, mirroring `backend/CLAUDE.md`'s Category Specifications section exactly). `src/app/api/baseApi.ts`'s `tagTypes` grew to `["Brand", "Category", "CategorySpecification"]`. `categorySpecificationsApi.ts` exposes three endpoints: `getCategorySpecifications` (query), `replaceCategorySpecifications` (the `PUT` full-replace), and `patchCategorySpecifications` (the `PATCH` discriminated-union op, typed as `SpecPatchOperation` — a direct mirror of backend's own union). The synthetic empty `{category, specificationGroups: []}` response before any `PUT` needs no special handling — it's a normal, successfully-loaded `data` value to RTK Query, so the editor just renders zero groups rather than a distinct "empty state."
- **Routed at `/specifications`, not a per-category dynamic route** — `CategorySpecificationsPage.tsx` owns an in-page category `<select>` (matching the mock's "Category: Smartphones ▾" control) rather than a URL param; `CategorySpecificationEditor` is mounted with `key={categoryId}`, so a category switch is a clean remount rather than a state-reconciliation problem.
- **Two different persistence strategies for the same document, chosen deliberately per action** — documented here because it's the one thing in this module a future reader could easily assume is a bug: bulk edits (adding/reordering groups or fields, editing a field's name/type/unit/options/required) stay purely in local React state until "Save schema" fires one `PUT` with the whole draft; but renaming a group, deleting a group/field, and toggling a field's `filterable` checkbox call the matching `PATCH` op **immediately**, whenever the group/field being acted on is already known to exist server-side (tracked via a `persisted` snapshot set alongside the draft `groups` state, refreshed only on initial load and on every successful mutation response — never by an incidental background refetch, which would otherwise clobber an in-progress, not-yet-saved local edit). Acting on a *not-yet-saved* group/field (e.g. deleting a group you just added locally and haven't saved yet) always stays local-only — there's nothing to `PATCH` against yet. `filterable` specifically gets immediate-persist treatment (not just delete/rename) because it's the one checkbox the mock's own callout box singles out as consequential (buyer-facing filter facet + card-display eligibility) — matching this codebase's established "a toggle persists immediately, a structural edit goes through a form-level Save" convention (`CategoryList.tsx`'s status toggle is the precedent).
- **Reorder is up/down buttons, not drag-and-drop** — a deliberate scope simplification versus the mock's `⣿` drag handles; functionally equivalent (any ordering is reachable), avoids a DnD library dependency for a low-traffic admin tool. Reordering is a local edit like any other, persisted only through "Save schema."
- **Type-dependent field inputs are a client-side mirror of backend's Zod `.refine()`s, for UX only** — `SpecificationGroupCard.tsx`'s `updateField` clears `options` whenever `type` isn't `"enum"` and forces `filterable: false` whenever `type` is `"text"`; the backend's own `specificationFieldSchema` refines are what actually enforce this on `PUT`/`PATCH updateField`, so a client bypass would just surface as a `VALIDATION_ERROR` on save, not a stored inconsistency.
- **In-use guard messages are rendered verbatim**, same convention as brands'/categories' delete guards (`getApiErrorEnvelope(err)?.message`) — `SPECIFICATION_FIELD_IN_USE` already names every blocking field and its count in one string on both `deleteField` and `deleteGroup`, so there's nothing to reformat client-side.
- Test layout: one `__tests__/features/product-catalog/categorySpecifications/CategorySpecificationsPage.test.tsx`, covering the synthetic-empty render, a full add-group+add-field-then-Save `PUT` flow, `renameGroup` and `updateField` (`filterable` toggle) each firing their own `PATCH`, and the in-use guard's exact message rendering on both a blocked field delete and a blocked group delete.

## Category variant-type editor (Issue #80 / M2.23)

- `src/features/product-catalog/categoryVariants/` — near-identical shape to `categorySpecifications/` (#79): same synthetic-empty-`GET`/full-replace-`PUT`/discriminated-union-`PATCH` pattern, same "bulk edits stay local until Save, a specific toggle persists immediately when already-persisted" convention. `src/app/api/baseApi.ts`'s `tagTypes` grew to `[..., "CategoryVariant"]`. Routed at `/variant-types`, same in-page category `<select>` + `key={categoryId}`-remount pattern as `CategorySpecificationsPage.tsx`.
- **Flat, not grouped** — `variants: VariantAxis[]` is one flat array (no `groupName` layer), so there's a single `VariantAxisRow`/table rather than `categorySpecifications/`'s per-group `SpecificationGroupCard`. Matched by `code`, not `name` — mirrors backend's own `VariantAxisPatchOperation` exactly, safe because this definition is admin-form-rendering guidance only, never enforced against stored variant attributes (`FR-CAT-037`).
- **The one deliberate divergence from `categorySpecifications/`: deleting an axis carries no in-use guard at all**, matching backend's `deleteAxis` (no `countBy...` call exists there, unlike `categorySpecifications.service.ts`'s `deleteField`/`deleteGroup`). `CategoryVariantEditor.tsx`'s `handleDeleteAxis` still routes an already-persisted axis's delete through the real `PATCH deleteAxis` (rather than optimistically removing it client-side first) specifically so the "no guard, always succeeds" behavior is exercised against the real backend, not simulated — but there's no guard-rejection branch to render, unlike `categorySpecifications/`'s `SPECIFICATION_FIELD_IN_USE` handling.
- **`required` is the toggle wired to immediate `PATCH updateAxis` persistence** (for an already-persisted axis) — the flat-axis analogue of `categorySpecifications/`'s `filterable`-triggers-`updateField` convention, chosen because it's the one boolean on this shape with a clear, singular meaning; every other property (name, code, type, options) stays local-only until "Save axes."
- **Options are edited as one `label/value, label/value` text field** (`VariantAxisRow.tsx`'s `formatOptions`/`parseOptions`), shown only when `type` is `select` or `color` — mirrors the mock's "Black / #000 · Silver / #c0c0c0" display exactly, and matches backend's Zod refine (`options` required for `select`/`color`, forbidden for `text`/`number`) as a client-side UX mirror only, same "not the real enforcement" caveat `categorySpecifications/`'s type-dependent inputs document.
- Test layout: one `__tests__/features/product-catalog/categoryVariants/CategoryVariantsPage.test.tsx` — synthetic-empty render, a full add-axis-then-Save `PUT` flow, an unguarded `deleteAxis` (asserting the `PATCH` call landed and no alert rendered), `updateAxis` via the `required` toggle, and the options editor's type-dependent visibility.

## Product list + read-only detail (Issue #81 / M2.24)

- `src/features/product-catalog/products/` — `productsApi.ts` adds `getProducts` (admin list, `Product` tag), `getProduct` (detail), `updateProductStatus`, and `updateProductStock` to the shared `api` instance (`tagTypes` grew to `[..., "Product"]`). Bundled as one issue per the issue body's own reasoning: the detail view is a read-only projection of data the list already fetches, not an independent write surface — that's `#82`/`M2.25`'s job (the create/edit form).
- **`brand`/`category` on a `Product` are raw ids, not populated** — confirmed directly from `backend/CLAUDE.md`: admin reads (`findById`/`listPaginated`) never `.populate()` them, unlike buyer-app's public product endpoints. `ProductList.tsx`/`ProductDetailPage.tsx` both resolve names client-side against the already-fetched `brands`/`categories` lists (`useGetBrandsQuery`/`useGetCategoriesQuery`, reused as-is from those features) — the same `nameById`-lookup convention `CategoryList.tsx` already established for its own parent-category name.
- **This is the first feature to introduce a real `react-router` `<Link>`/route param** beyond `App.tsx`'s own top-level `<Route>` declarations — `ProductList.tsx` links each row to `/products/:id` (`ProductDetailPage.tsx`, via `useParams`), rather than reusing brands'/categories' inline list-vs-form toggle. A dedicated route was chosen (over a drawer) because a product's detail view is dense enough (images, specs, variants) to want its own URL/back-button behavior; brands/categories's simpler forms don't carry that weight. Tests exercising this therefore wrap `<Provider>` in a `<MemoryRouter>` with both routes declared, rather than using the plain `renderWithStore` helper (which has no router) — see `ProductsPage.test.tsx`'s local `renderProductsApp()`.
- **List quick-actions call two different endpoints deliberately kept separate**: the inline stock editor (click the stock cell → text input + Save) calls `updateProductStock` (`PATCH .../stock`) — a dedicated stock-only path, independent of a future full edit form's own `stock` field (`FR-CAT-004`/`008`); "Archive"/"Restore" call `updateProductStatus` (`PATCH .../status`) directly from the row, no confirmation dialog (matches brands'/categories' delete-guard precedent of acting immediately, no modal).
- **"Restore" targets `draft`, not `published`** — an interpretive choice, documented here since the mock only shows the label "Restore" with no explicit target state: re-review before re-publishing is the safer default, and the detail page's own "Change status" `<select>` (all three states) is available for an admin who wants to restore straight to `published` instead.
- **The read-only detail view renders every stored field at any status** (`FR-CAT-006`), including fields with no admin write surface yet (`createdBy`/`updatedBy`, both reserved and stored as `null` until v0.3 auth — rendered as the literal string `"null"`, not blanked out, matching the mock's own treatment) — and **every variant regardless of `active`** (`FR-CAT-040`'s "never hard-removed" — an inactive variant's row is dimmed, not hidden).
- **Category breadcrumb-style label** (`"Electronics › Smartphones"`) is resolved the same way `buyer-app`'s `CategoryBreadcrumb.tsx`/`resolveBreadcrumb` do: look up the product's own category, then that category's `parentCategory` id, from the already-fetched flat `categories` list — no new endpoint needed.
- Test layout: one `__tests__/features/product-catalog/products/ProductsPage.test.tsx` covering list render with resolved names, independent `search`/`status`/`lowStock` composition in the request, the inline stock quick-edit, archive/restore, and navigating to the detail view (asserting every field renders, including both an active and an inactive variant).

## Product create/edit form (Issue #82 / M2.25)

- `src/features/product-catalog/products/productForm/` — the most complex admin screen, routed at `/products/new` (create) and `/products/:id/edit` (edit), both rendered by `ProductFormPage.tsx` (reads `useParams`, fetches the product via `useGetProductQuery` only when an `:id` is present, then hands `product: Product | null` to `ProductForm.tsx`). `productsApi.ts` grew `createProduct`/`updateProduct`/`addVariant`/`updateVariant` mutations (all `invalidatesTags: ["Product"]`) alongside #81's existing `getProducts`/`getProduct`/`updateProductStatus`/`updateProductStock`.
- **`sku` is disabled (not just non-editable), matching `FR-CAT-004`'s immutability**: the input has `disabled={Boolean(product)}`, and `UpdateProductInput` (`products/types.ts`) is `Partial<Omit<CreateProductInput, "sku">>` — a type-level guarantee alongside the UI one, mirroring how `backend`'s own `updateProductSchema` omits `sku` entirely rather than accepting-and-ignoring it.
- **A real accessible-name bug found and fixed while building this**: `getByLabelText`'s implicit-label matching only reads a `<label>`'s *direct child text nodes* (`getNodeText`'s default implementation filters to `nodeType === TEXT_NODE`), not nested elements' text — but it also breaks the other way: a `<label>` wrapping the control *plus* a trailing helper-text `<span>` (a pattern already used elsewhere, e.g. `BrandForm.tsx`'s slug caption) makes the label's matched text `"Category *Changing this re-validates…"`, not `"Category *"` alone, so `getByLabelText("Category *")` finds nothing. Both the `SKU`/`Category` fields (each has trailing caption text) restructure to explicit `<label htmlFor>`/`id` pairs with the caption living as a sibling `<span>`, not nested inside the `<label>` — a real bug this issue's own test-writing surfaced, not just a test-authoring workaround, and worth remembering for any future field that adds inline helper text.
- **Image editing has a real, unavoidable asymmetry between create and edit**, documented directly in the form's own JSX comment: a *stored* product image (`ProductImage`: `{url, alt, isPrimary}`) carries no `objectKey` — the presign flow's `objectKey` is consumed once at write time and never returned again — so an already-saved image literally cannot be resubmitted through `productImageSchema` (`objectKey` required). `ProductImagesEditor` (new, `min`/`max`-parameterized, reused for both the product's own 1–8 images and a variant's 0–2) therefore only ever holds *freshly uploaded* images; on edit, the product's current images render as an inert read-only preview grid above it, with copy explaining that uploading anything new **fully replaces** the set (never merges) — `images` is omitted from the `PATCH` body entirely when nothing new was uploaded, leaving the stored set untouched.
- **Specifications are rendered from the selected category's live schema**, not a fixed field list: `ProductSpecificationsFields.tsx` calls `categorySpecifications/`'s `useGetCategorySpecificationsQuery(categoryId)` (from #79) and renders one control per field by `type` (`enum`→`<select>` off `field.options`, `boolean`→checkbox, else text/number), matching `FR-CAT-033`'s required/type/enum-membership rules **client-side, for UX only** — same "mirrors the Zod schema, not shared code" caveat every prior admin form in this codebase already carries. Values are kept in one flat `Record<"groupName::fieldName", value>` map (`specificationValues.ts`'s `specKey`/`SpecificationValues`, split into their own module specifically to satisfy `react-refresh/only-export-components` — a component file may only export components); `ProductForm.tsx`'s `buildSpecificationGroups()` reconstructs the nested `ProductSpecificationGroup[]` backend shape from that flat map at submit time. **Changing the category clears `specValues` entirely** (`handleCategoryChange`) — a deliberate, documented simplification: carrying values across two different, unrelated schemas risked silently submitting values the new schema never defined.
- **The embedded variant editor only exists once the product itself has an id**: `ProductForm.tsx` renders `ProductVariantsEditor` only when `product` is non-null (a freshly-created product's response redirects to `/products/:id/edit` via `useNavigate`, landing the admin exactly where the section becomes available) — the backend's own `POST .../:id/variants` has nowhere to attach a variant before the parent document exists, so there's no create-time variant flow to build in the first place. `ProductVariantsEditor.tsx` renders each existing variant collapsed (a one-line summary, matching the mock's second variant row) with an "Edit" toggle that swaps it for the same `VariantForm` used by "+ Add variant" — one shared component for both flows, keyed by `variant?._id ?? "new"` so switching between add/edit/cancel always remounts with fresh local state.
- **One control per variant axis, chosen by the category's own `categoryVariants` axis `type`** (`useGetCategoryVariantsQuery`, from #80): `color`→swatch buttons keyed by the axis's own hex `options`, `select`→dropdown, `number`/`text`→a plain input — `AxisControl` in `ProductVariantsEditor.tsx`. Draft attribute state is keyed by axis **`code`** (not `name`) for stable React state even if two axes happen to share a display name, then mapped to `{name: axis.name, value}` pairs — matching `name` — at submit time, since that's what the backend's `ProductVariantAttribute` actually stores.
- **`sellingPrice` is live-computed client-side for both the product and each variant form**, mirroring `backend/src/utils/pricing.ts`'s exact formula (`mrp - floor(mrp * discount / 100)`) via a small `computeSellingPreview()` duplicated in `ProductForm.tsx` and `ProductVariantsEditor.tsx` rather than shared — two nearly-identical ~4-line pure functions, not worth extracting a shared util for (`src/lib/utils.ts`, added later for `cn()`, is a general-purpose className helper, not a place for this domain-specific formula). Labeled "preview — server-computed" everywhere it's shown; the actual submitted `mrp`/`discount` are what the backend recomputes from, same as every other admin form's pricing display in this codebase.
- **Every mutation error surfaces via the shared `getApiErrorEnvelope()`/inline `role="alert"` convention** (`SPECIFICATION_VALIDATION_FAILED`, `DUPLICATE_SKU`, `DUPLICATE_VARIANT_ATTRIBUTES`, and a generic Zod `VALIDATION_ERROR` fallback that joins the envelope's `errors` object when no top-level `message` exists) — `describeApiError()` in `ProductForm.tsx` is the one place that fallback lives; every named-guard error (the three explicitly listed above) already carries a `message` naming every offending field in one string, so there's nothing to reformat, only to render verbatim, same as every prior guard in this codebase.
- Test layout: `__tests__/features/product-catalog/products/ProductForm.test.tsx` (SKU disabled on edit, not on create; a category change re-fetching and re-rendering that category's own specification fields; a full create flow — including an actual `userEvent.upload()` through the presign→PUT mock — that redirects to the edit route; `SPECIFICATION_VALIDATION_FAILED` rendering its exact message; adding a variant through the embedded editor) plus `ProductsPage.test.tsx` (unchanged from #81). A second real timing bug surfaced while writing these: firing a `<select>`'s `change` event with a `target.value` that has no matching `<option>` yet (the options list hadn't finished loading from the async `GET /brands`/`GET /categories`) silently no-ops in jsdom exactly like a real browser — every test selecting a brand/category now first awaits that option's own text appearing before firing the change.

## Shared list/table state: search, filter, sort, pagination, loading

- **`src/hooks/`** — new top-level directory for cross-cutting, non-Redux React hooks (parallel to `src/lib/utils.ts` for non-Redux helpers; keep `app/store/hooks.ts` Redux-only). `useDebouncedValue(value, delayMs = 300)` returns a debounced copy of a value via a `setTimeout`/cleanup effect. `useListQueryState<TFilters extends object>(initialFilters)` generalizes the "filters + page, reset page to 1 on any filter change" pattern every list screen used to hand-roll independently — returns `{ filters, setFilter, page, setPage }`; `setFilter(key, value)` always resets `page` to `1`. Note the generic constraint is `object`, not `Record<string, unknown>` — a `TFilters` supplied as a named `interface` (e.g. Products' `ProductFilters`) has no implicit index signature and fails the stricter `Record<string, unknown>` constraint, while an inline object-literal type (e.g. Brands'/Categories' `{ search: string }`) does; `object` avoids that trap for both call shapes.
- **`src/components/ui/SortableHeader.tsx`** — a generic clickable `<th>` (`SortableHeader<TSort extends string>`) taking `sortKeyAsc`/`sortKeyDesc`/`currentSort`/`onSortChange`; toggles between the two sort keys on click and shows `⇅`/`↑`/`↓` via an `aria-hidden` glyph (so the button's accessible name is just the plain `label`, e.g. `"Name"` — tests must query by that, not `"Name ⇅"`).
- **`src/components/ui/Table.tsx` gained an `isFetching?: boolean` prop** — dims the `<table>` (`opacity-50`, `aria-busy`) and shows a small `role="status"` "Updating…" pill while true, without replacing the table (unlike the existing `isLoading ? <LoadingState/> : <Table/>` swap, which is still what covers the very first load). This closes a real pre-existing gap: RTK Query already keeps previous `data` around across an arg change while `isFetching` (not `isLoading`) goes true — every list was already silently swapping data on a filter/search/page change with zero visual feedback; the fix was destructuring and using a field that already existed, not new RTK Query config.
- **This pattern is now wired into all three list screens — Brands, Categories, Products** — not just built and demonstrated on one: each `*Page.tsx` uses `useListQueryState` instead of raw `useState`s (Products' four independent `useState`s + three `handle*Change` resetters collapsed into one `ProductFilters` shape), and each `*List.tsx` debounces its `search` prop via `useDebouncedValue` *before* passing it into its RTK Query hook (the Page's own `search` stays instant, for the controlled `<input>`; only the network arg lags ~300ms) and passes `isFetching` into `<Table>`. **Sorting was added to Products only** (`SortableHeader` on the Name/Price/Stock columns, wired to `getProducts`'s pre-existing but previously-unused `sort: ProductSort` param) — Brands/Categories have no backend `sort` param at all and deliberately got none added; Categories' existing `Sort` column still just displays `sortOrder` data, it is not a sort control.
- **Design call, if extending this further**: this is deliberately small composable hooks + one presentational primitive, not a monolithic `<DataTable columns=.../>` — every existing shared piece in `components/ui/` (`Pagination`, `SearchInput`, `Checkbox`, `StatusBadge`, `ConfirmDialog`) is single-purpose, and the three list screens' table *bodies* genuinely diverge (Brands' logo cell, Categories' tree-indentation, Products' inline stock editor) enough that a column-config abstraction would need a render-prop escape hatch per column anyway. What's actually identical across screens is the state orchestration, which is what got extracted.
- Test layout: no dedicated suite for `useListQueryState`/`SortableHeader`/`Table`'s `isFetching` prop (covered via each feature's integration test, matching the existing "no dedicated `components/ui/` suite" convention) — but `useDebouncedValue` does get one (`__tests__/hooks/useDebouncedValue.test.ts`, `renderHook` + `vi.useFakeTimers()`, including a "rapid changes coalesce to only the final value" case). Each of `BrandsPage.test.tsx`/`CategoriesPage.test.tsx`/`ProductsPage.test.tsx` gained a debounce-coalescing case and a refetch-indicator case (the latter via a locally delayed MSW handler, `delay()` from `msw`); `ProductsPage.test.tsx` also gained a sort-header-click case.

## Confirmation dialogs and toast notifications

- **`src/components/ui/ConfirmDialog.tsx`** — a controlled modal (`open`/`title`/`message`/`onConfirm`/`onCancel`/`isConfirming`), gating **delete-only** actions: `deleteBrand` (`BrandList.tsx`), `deleteCategory` (`CategoryList.tsx`), the `deleteGroup`/`deleteField` patch ops (`CategorySpecificationEditor.tsx`, via one dialog driven by a `PendingDelete` tagged union since only one can be open at a time), and the `deleteAxis` patch op (`CategoryVariantEditor.tsx`). Status toggles, stock updates, and every create/update/save stay immediate — no confirmation — this is a deliberate, narrow scope, not a general-purpose "confirm everything" pattern. Its overlay reuses `AppShell.tsx`'s mobile-drawer convention exactly — a full-bleed `<button aria-label="Cancel">` behind the panel, not a `<div onClick>` — for correct keyboard/AT semantics. Wiring is always the same shape: the row/button's `onClick` sets a local `pendingDelete` state instead of calling the mutation directly; the dialog's `onConfirm` reads that state, clears it, then calls the exact same handler function that existed before this convention (`handleDelete`, `handleDeleteGroup`, `handleDeleteField`, `handleDeleteAxis` are all unchanged) — only the trigger point moved.
- **`sonner`** (`<Toaster richColors position="top-right" />`, mounted in `App.tsx` as a sibling of `BrowserRouter` inside `Provider`) gives every product-catalog mutation a success/error toast, supplementing — not replacing — the existing `InlineAlert` convention: per-row delete-guard messages (`BRAND_IN_USE`, `CATEGORY_IN_USE`, `SPECIFICATION_FIELD_IN_USE`) and per-field form validation errors stay exactly where they were, anchored to their row/field; toast adds an app-wide layer on top and is what finally gives several previously-silent mutations (`updateBrandStatus`, `updateCategoryStatus`, `updateProductStatus`, `updateProductStock` — none had *any* error handling before this) user-visible feedback at all.
- **`src/app/api/apiToast.ts`** — `notifyApiSuccess(message)` (`toast.success`) and `notifyApiError(error, fallbackMessage)` (`toast.error(getApiErrorEnvelope(error)?.message ?? fallbackMessage)`, reusing the same envelope-reading helper every inline error already used).
- **Every product-catalog mutation fires its toast via RTK Query's `onQueryStarted`**, defined directly in the `*Api.ts` file's `injectEndpoints` call — not from the component that invokes it. This means adding toast coverage never touched any component's create/update/save logic (`onSaved()`, `navigate()`, `applyServerView()` are all untouched) and fires consistently regardless of which component calls the mutation. **Gotcha**: `onQueryStarted`'s `queryFulfilled` rejects with `{error, meta}`, not the raw error — unlike `.unwrap()` (which every component's own try/catch already awaits, and whose rejection *is* the raw `FetchBaseQueryError`) — so every hook's catch unwraps one level: `notifyApiError((err as {error: unknown}).error, fallback)`. Where one endpoint covers multiple logical operations (`patchCategorySpecifications`'s 4-way `SpecPatchOperation` union, `patchCategoryVariants`'s 2-way `VariantAxisPatchOperation` union, `updateProductStatus`'s 3-way `ProductStatus`), the hook branches on the mutation argument via a small `Record<Op, {success, errorFallback}>` lookup rather than a switch, so adding a new union tag is a compile error (missing property) if the message table isn't updated too.
- **The one exception to "toast lives in `*Api.ts`, not the component"**: `ProductImagesEditor.tsx`'s upload flow. The user-relevant outcome (upload success/failure) spans two steps — `presignUpload` (RTK Query) *and* the subsequent raw `fetch` PUT to R2 via `putFileToPresignedUrl` (plain `fetch`, invisible to `onQueryStarted`) — so `handleFileChange`'s own try/catch calls `notifyApiSuccess`/`notifyApiError` directly. This also fixed a pre-existing gap: the catch previously used a hardcoded string regardless of cause, bypassing `getApiErrorEnvelope` entirely; it now reads the real envelope like everywhere else, falling back to the same generic string only when the error isn't envelope-shaped (e.g. the raw PUT's own thrown `Error`).

## Component definition style

- **Every React component in `admin-app` is a named arrow-function `const`**, not a `function` declaration — `export const ComponentName = (props: Props) => { ... };`, including `App.tsx`'s default export (`const App = () => {...}; export default App;`) and every non-exported inner component (e.g. `ProductVariantsEditor.tsx`'s `AxisControl`/`VariantForm`, `ProductSpecificationsFields.tsx`'s `FieldInput`). This is enforced, not just a convention: `eslint.config.mjs` adds `eslint-plugin-react` and sets `react/function-component-definition` to `{namedComponents: "arrow-function", unnamedComponents: "arrow-function"}` (with `settings.react.version: "detect"` to silence the plugin's version-detection warning) — `npm run lint --workspace admin-app` fails on any component written as `function ComponentName(...)`.
- **This rule targets components only, not arbitrary functions** — plain helper functions (component-internal handlers like `handleSave`/`handleDelete`, and module-level utilities like `cn()`, `formatPrice()`, `getApiErrorEnvelope()`, `unwrapData()`) are unaffected and correctly stay as regular `function` declarations; the plugin distinguishes by detecting whether a function's name is PascalCase and it returns JSX.
- Applying this to the ~40 pre-existing component files was a mechanical, near-fully-automated migration: `eslint . --fix` converted all but one (`App.tsx`'s `export default function App()` — ESLint's fixer doesn't rewrite default-export function declarations, so that one was hand-converted to the `const`+`export default` form above), followed by `npx prettier --write` to reformat the handful of files the autofix left with non-Prettier-conformant line-wrapping. No component's runtime behavior changed — verified by the full existing test suite passing unchanged (48 tests) plus a clean `build`/`lint`.

## Shared UI component library styling (`cn()` / CVA)

- The components originally extracted into `src/components/ui/` (later split across `components/ui/`, `components/form/`, and `components/layout/` — see "Feature-based structure" above) build every className through `cn()` — `src/lib/utils.ts`'s `clsx` + `tailwind-merge` combinator (`twMerge(clsx(inputs))`) — instead of the hand-rolled `[..., className].filter(Boolean).join(" ")`/template-literal-ternary patterns they originally shipped with. `cn()` is the required way to build any conditional or externally-mergeable className anywhere in `admin-app`, not just inside these folders; it's a general-purpose helper, not folder-scoped, which is why it lives in `src/lib/`. The switch to `tailwind-merge` specifically fixes a real (if latent) bug the old pattern had no answer for: two conflicting Tailwind classes (e.g. a caller's `className="p-2"` against a component's own `p-4`) used to "resolve" by accident of compiled-stylesheet order, not by intentional last-wins precedence — `cn()` now guarantees the latter.
- `class-variance-authority` (`cva()`) is layered on top of `cn()` only where a component has a real variant prop map — `Button` (`variant`×`size`), `Card` (`padding`×`tone`×`dashed`), `StatusBadge` (`tone`×`shape`), `FormField`'s `ReadOnlyField` (`size`×`mono`×`bordered`), and `PageHeader` (`size`, two coordinated configs for its container and heading). Every other component (`Checkbox`, `SearchInput`, `Pagination`, `InlineAlert`, `Table`, `LoadingState`/`ErrorState`) uses plain `cn()` — no `cva()` config exists there and none should be added unless a real `variant`-style prop shows up; a single-branch map like `InlineAlert`'s `VARIANT_CLASS` stays a plain object until it grows a second entry. New components in `components/ui/`, `components/form/`, or `components/layout/` should default to `cn()` and only reach for `cva()` once they have their own multi-key variant map, matching this same rule.
- Every `cva(...)` config is a module-private `const`, never `export`ed from its component file — `eslint-plugin-react-refresh`'s `only-export-components` rule (already the reason `productForm/specificationValues.ts` was split out, see above) forbids a component file from also exporting a non-component value. Each component's public prop types (`variant?: Variant`, `size?: Size`, etc.) also stay hand-written unions rather than `VariantProps<typeof xVariants>`, so the public prop API can't silently drift from the `cva()` config's internal shape.
- This was a pure internal refactor: no component's public prop API or rendered output changed. There's no dedicated test suite for `components/ui/` itself, so regression coverage came entirely from each feature's existing integration tests (`BrandsPage.test.tsx`, `CategoriesPage.test.tsx`, `ProductForm.test.tsx`, etc.).

## Admin shell & reusable layout components (Issue #107)

- **`lucide-react`** is the one new dependency this issue adds — the previous shell (`AppShell`/`SidebarNav`, Issue #101) had no icon library at all (`AppShell.tsx`'s mobile hamburger was a hand-rolled inline `<svg>`); every icon below (nav items, hamburger, logout) now comes from it instead.
- **`navItems.ts`'s `NavItem` grew `icon: LucideIcon` and `group: string`** (both required, not optional) — every entry in `NAV_ITEMS` now names a `lucide-react` icon and a logical group (`"Overview"` for Dashboard, `"Catalog"` for Products/Categories/Brands/Specifications/Variant types). Any future nav item must supply both.
- **`SidebarNav.tsx` was decomposed into four focused components**, replacing the previous single file: `Header.tsx` (the brand mark — icon + "TechCart Admin" wordmark — used both in `AppShell`'s mobile topbar and at the top of the sidebar, so the markup exists in exactly one place instead of being duplicated across the two), `SidebarItems.tsx` (renders `NAV_ITEMS` grouped, one `NavLink` per item), `Footer.tsx` (the avatar/name/logout block, still a static "Admin User" placeholder — no real user identity exists until v0.3 Authentication), and `Sidebar.tsx` (composes the three, is what `SidebarNav.tsx` used to be end-to-end). `AppShell.tsx` itself kept its name (not renamed to `AdminShell` — the issue's "AdminShell" heading names the shell *concept*, not a required file rename) and now renders `<Sidebar>` + a new `MainSection.tsx` (a trivial extraction of the previous inline `<Outlet>` wrapper div).
- **The sidebar is `w-20` (80px) at tablet and `lg:w-50` (200px) at desktop** (`md:flex`, same breakpoint as before — only the width changed, from `w-64`) — revised after review from Issue #107's literal "100px at every breakpoint" text, which cramped the desktop icon+label rail. 200px at desktop lands closer to the ~240–280px "labeled sidebar" convention common in dashboard UIs generally (see the web-search note further up this doc's history); 80px at tablet stays a deliberately compact icon-only rail, closer to VS Code's activity bar or Slack's channel rail than a full labeled nav.
- **`Header`/`SidebarItems`/`Footer` all take a rail-vs-drawer variant** (`Header`'s `compact` boolean; `SidebarItems`' `layout: "rail" | "list"`; `Footer`'s `variant: "rail" | "drawer"`; `Sidebar` threads one `variant` prop to all three) — the persistent rail hides item/name labels below `lg` (`hidden lg:block`/`hidden lg:inline`) so only icons show at tablet width, while the mobile slide-out drawer (`AppShell.tsx`, `<Sidebar variant="drawer">`) always renders full labels regardless of viewport width, since it's a different, wider surface with its own "normal navigation" requirement in the issue — a single width-driven `hidden lg:*` treatment could not serve both, since the drawer only ever appears well below the `lg` breakpoint. **Every icon-only control keeps an explicit `aria-label`** (`SidebarItems`' `NavLink`, `Footer`'s logout button) rather than relying on the visually-hidden label span for its accessible name — a real gap this issue's own build surfaced: Tailwind's `hidden` utility removes an element from the accessibility tree too, not just visually, so a nav item with no separate `aria-label` would have had no discernible name at all at tablet width.
- **`SidebarItems.tsx`'s tablet icon-only rail shows a hover/focus tooltip naming the item** — added after review, since the icon-only tablet width otherwise gave sighted (non-screen-reader) users no way to identify a nav item without clicking it. The tooltip can't use a plain CSS `group-hover` reveal: it must render outside `<nav>`'s `overflow-y-auto` box, since an absolutely-positioned descendant of a container with only `overflow-y` constrained still gets clipped/scrolled away (`overflow-x`'s computed value is forced away from `visible` once `overflow-y` isn't `visible`, a real CSS Overflow spec quirk, not a typo). Instead, `SidebarItems` tracks one local `{label, top, left} | null` state — set via each rail `NavLink`'s `onMouseEnter`/`onFocus` (`getBoundingClientRect()` of the target), cleared on `onMouseLeave`/`onBlur` — and renders one shared tooltip `<span role="tooltip">` with `position: fixed` (escapes ancestor clipping without a portal, since no ancestor sets `transform`/`filter`), gated `lg:hidden` so it never appears once the desktop label is already visible. Only wired for `layout === "rail"`; the drawer's `"list"` layout has no tooltip logic since its labels are already always visible.
- **`PageHeader.tsx` gained an optional `breadcrumbs?: { label: string; to?: string }[]` prop**, rendered below the title: every crumb but the last is a `Link`, the last is bold plain text with `aria-current="page"`, separated by `>` (not `/` — matches `buyer-app`'s existing category-breadcrumb convention). The container's responsive classes changed from `flex flex-wrap items-center justify-between` to `flex flex-col items-start gap-3 sm:flex-row sm:items-center sm:justify-between` so title+actions stack on mobile — a pure Tailwind-class change, backward compatible with every existing call site (none of which pass `breadcrumbs` yet).
- **This `breadcrumbs` prop is deliberately opt-in, not a default every page should adopt** — raised and settled after review. `admin-app`'s navigation is flat: the sidebar links straight to 5 top-level list pages, so a multi-level breadcrumb trail on any of them would just render one crumb with no real ancestor to show, which is decorative rather than navigational. The one level of real drill-in this app has (list → a specific record) already has its own, lighter pattern: `components/ui/BreadcrumbHeading.tsx` (a "‹ Products / Edit product"-style back-link heading, pre-existing since before #107, used by `ProductDetailPage`/`ProductForm`) — that stays the pattern for detail/edit pages. `PageHeader`'s `breadcrumbs` prop is reserved for a genuine future multi-level hierarchy (e.g. if category drill-down navigation is ever added); don't wire it into `BrandsPage`/`CategoriesPage`/`ProductsPage`/etc. just because it exists.
- **`TableLayout.tsx` (new) is the "Common Table Layout" the issue asks for** — composes `PageHeader` (title/breadcrumbs/`primaryAction`) with a responsive search+filter row (`search`: wraps `components/form/SearchInput`; `filters`: a free `ReactNode` slot) above a `children` table slot and an optional `pagination` slot. **It is built and unit-tested in isolation only — `BrandsPage`/`CategoriesPage`/`ProductsPage` still hand-roll their own `<main className="p-6">` + `PageHeader` + list layout and have not been migrated onto it.** That migration is a deliberate follow-up, not an oversight of this issue.
- Test layout: `__tests__/components/layout/Shell.test.tsx` — the first dedicated test suite for this folder (previous shell/`components/ui/` changes relied entirely on feature-page integration tests, which don't exercise the shell chrome itself). Covers nav item hrefs/active-state, the mobile drawer's open/close, logout still dispatching `clearAdminKey`, `PageHeader`'s breadcrumb rendering, and a `TableLayout` smoke render.

## Products/brands/categories: synced with the backend's variant-only + paginated-list contract (Issue #114)

Two backend-only SRS v0.2 amendments (`#102` Variant-Only Pricing, `#104` Shared Admin List Query Parsing — both documented in `backend/CLAUDE.md`) had shipped without `admin-app` ever being updated to match; this issue closes that gap across every affected screen.

- **`Product` carries no pricing/stock/images/sku of its own anymore** (`types.ts`) — every sellable, priced, imaged unit is a `ProductVariant` (which itself lost `stock`, removed system-wide). `CreateProductInput`/`UpdateProductInput` now match the backend's `createProductSchema`/`updateProductSchema` exactly: `name`/`description`/`brand`/`category`/`specifications?`/`isFeatured?`/`metaTitle?`/`metaDescription?`. `ProductForm.tsx` lost its entire "Images" and "Pricing & stock" cards and the `sku` field (SKU now lives only on a variant, and a variant's own SKU is *not* immutable, unlike the old product-level field). `ProductList.tsx` lost its SKU/Price/Stock columns and the stock quick-editor (`updateProductStock`/`PATCH .../stock` no longer exist — deleted outright by #102); its Actions column's "Archive"/"Restore" and the Name column's now-clickable link to the detail page are unchanged. `ProductDetailPage.tsx` lost its Images card and the SKU/MRP/Discount/Selling-price/Stock/Low-stock-threshold detail rows; the Variants table below it lost only its `Stock` column, since variants never had stock either.
- **`ProductVariantsEditor.tsx`'s images bound changed from `{min:0,max:2}` (with a "falls back to the product's" caveat) to `{min:1,max:2}`** — #102 removed the parent product's gallery entirely, so there's no fallback left; the label copy was corrected to match. A real, adjacent correctness bug was fixed in the same pass: the variant submit body used to omit `images` entirely whenever nothing new was uploaded, which is correct behavior on **update** (existing stored images stay untouched) but was silently wrong on **add** (a brand-new variant has no existing images to fall back to, so omitting the now-required field produced an ambiguous "missing key" case instead of a normal validation error) — the omit-when-empty behavior is now scoped to the edit path only; adding a variant always sends the array, even empty.
- **`ProductSort` narrows to `"createdAt" | "-createdAt" | "name" | "-name"`** (`mrp`/`stock` are no longer sortable — matches backend's `PRODUCT_SORT_FIELDS`), but is deliberately **kept as one combined string at the UI layer** — `productsApi.ts`'s `getProducts` is the one place a small `toSortByOrderBy()` helper splits it into the wire format the backend now expects (`?sortBy=`/`?orderBy=`, replacing the old `?sort=-field`). This meant `ProductList.tsx`'s existing `SortableHeader` wiring for the Name column needed no shape change at all — only the request-building translates. (A true 3-state sort UI was, at the time this issue shipped, out of scope — it landed shortly after, see Issue #108 below.)
- **`brandsApi.ts`'s `getBrands` / `categoriesApi.ts`'s `getCategories` both switch from returning a bare array to `{items, pagination}`** (`unwrapList()`, mirroring `productsApi.ts`'s `getProducts` — both admin list endpoints now paginate server-side too, default `limit: 20`, per #104). This surfaced **two different calling conventions for the same endpoint** across this codebase, not one: `BrandList.tsx`/`CategoryList.tsx` (the admin grids themselves) now pass real `{search, page}` and render the existing `Pagination` component from the response, with `BrandsPage.tsx`/`CategoriesPage.tsx` threading `page`/`setPage` from `useListQueryState` (the hook already returned them; these two pages just weren't consuming them before). Every other call site — `ProductList.tsx`/`ProductDetailPage.tsx`/`ProductForm.tsx`'s brand/category name-resolution and picker `<select>`s, `CategoriesPage.tsx`'s own `allCategories` (for `CategoryForm`'s parent picker), `CategoryVariantsPage.tsx`/`CategorySpecificationsPage.tsx`'s category picker — is a **lookup**, not a grid, and calls `useGetXQuery({limit: 100})` (the backend's own max) instead, unwrapping `data?.items ?? []`. This is a pragmatic cap, not a real "fetch everything," documented here as a known small-catalog limitation consistent with this codebase's other "accepted, documented gap" precedents (e.g. buyer-app's `PUBLIC_PAGE_SIZE_MAX`) — acceptable given `docs/architecture.md`'s own small-to-medium target scale.
- **`CategoryList.tsx`'s two-level tree ordering (`orderAsTree`) now only ever sees the current page's slice**, not every category — a child whose parent falls on a different page renders as an unindented "orphan" with an unresolved parent name. A known, accepted limitation of pairing pagination with a hierarchy view (documented inline at the call site); still strictly better than the previous silent hard-cap-at-20-with-no-pagination-at-all.
- Every MSW-backed integration test touching a product/brand/category fixture or list response was updated to match: `ProductForm.test.tsx`/`ProductsPage.test.tsx` fixtures drop the removed `Product`/`ProductVariant` fields, and `BrandsPage.test.tsx`/`CategoriesPage.test.tsx` gained a pagination-composition test case (mirroring `ProductsPage.test.tsx`'s existing filter-composition tests) verifying `page` reaches the request and `Pagination` renders from the response.

## Table, Pagination, SortableHeader, and AlertModal rework (Issue #108)

- **`SortableHeader.tsx` is now tri-state**: the click cycle changed from asc↔desc to `asc → desc → none → asc`, so a column can be returned to unsorted instead of being stuck toggling between the two directions forever. `onSortChange` widened from `(sort: TSort) => void` to `(sort: TSort | undefined) => void`; the indicator glyphs (`⇅`/`↑`/`↓`) were already correct for a "none" state once it became reachable again, so no visual change was needed there. `ProductList.tsx`'s `onSortChange` prop widened to match — the only cascading change, since `ProductsPage.tsx`'s `setFilter("sort", value)` already accepted `ProductSort | undefined` (its `ProductFilters.sort` was already optional).
- **`Pagination.tsx` gained the three-zone layout the issue asked for**: left keeps the existing record-range text; center replaces the old prev/next-only nav with windowed page-number buttons (first, last, current ±1, `…` for gaps — a standard windowing algorithm, not a literal reading of the issue's own `1 2 < 3 > 5 6` example, which isn't a real layout) plus the active page carrying `aria-current="page"` and a filled `primary-600` style; right is a new, **optional** page-size `<select>` (`pageSize`/`onPageSizeChange`, defaulting to `[10, 20, 50, 100]`). The render guard changed from "hide everything when `totalPages <= 1`" to "hide the whole bar only when `total === 0`; hide just the center nav when `totalPages <= 1`" — so the (currently unused) page-size selector can still show on a short, single-page list once something wires it up.
- **The page-size selector is deliberately unwired** — `ProductList.tsx` (the only real `Pagination` consumer) still calls it exactly as before, with no `pageSize`/`onPageSizeChange` passed, even though `productsApi.ts`'s `getProducts` already accepts a `limit` param server-side. This matches `TableLayout`'s own precedent from #107 ("built and unit-tested in isolation, not yet adopted") — wiring it into `ProductsPage` is left as a future, documented follow-up rather than folded into this issue.
- **`AlertModal.tsx` replaces `ConfirmDialog.tsx` outright**, not a wrapper — `variant: "deleted" | "warning" | "confirm"` (red/amber/green; amber, not literal yellow, matching `StatusBadge.tsx`'s existing warning-tone token), a colored header with a `lucide-react` `X` close icon (wired to the same `onCancel` as the overlay click), and a variant-colored confirm button (`Button`'s `className` override, resolved correctly by the existing `cn()`/tailwind-merge convention). All 4 previous `ConfirmDialog` call sites — `BrandList.tsx`, `CategoryList.tsx`, `CategorySpecificationEditor.tsx`, `CategoryVariantEditor.tsx` — needed only an import/tag rename: they all default to `variant="deleted"`, and `role="alertdialog"` plus the default `"Delete"` confirm label were both preserved exactly, so none of their existing delete-flow assertions needed to change.
- **`Table.tsx` gained an opt-in `fillHeight` mode** and `TableHeadRow` gained a `sticky` prop, together giving a "header stays put, body scrolls" table using the standard single-`<table>` sticky-`<thead>` technique (no separate scrolling `<tbody>`) — `fillHeight` fills 100% of whatever height its parent provides; there's no `AppShell`/`MainSection` change, so nothing above the table is aware of viewport height. Like the page-size selector, **no page opts into `fillHeight`/`sticky` yet** — same "component built, not adopted" scope as the rest of this issue.
- Test layout: one dedicated suite per reworked/new component — `__tests__/components/ui/{SortableHeader,Pagination,AlertModal,Table}.test.tsx` — the first time `components/ui/` primitives got their own tests rather than relying solely on feature-page integration coverage (previously true only of `Shell.test.tsx`'s `TableLayout` smoke render). The existing feature integration suites (`BrandsPage.test.tsx`, `CategoriesPage.test.tsx`, `CategorySpecificationsPage.test.tsx`, `CategoryVariantsPage.test.tsx`, `ProductsPage.test.tsx`) needed no changes — verified unchanged against `AlertModal`'s preserved `role`/label surface and `SortableHeader`'s still-passing asc/desc assertions.

## Testing

- Stack: Vitest (`environment: "jsdom"`) + React Testing Library + MSW, wired via `vitest.config.ts` + `vitest.setup.ts` — same shape as `buyer-app` (see `buyer-app/AGENTS.md`). Reuses the `@vitejs/plugin-react` and `vite-tsconfig-paths` devDependencies already present for the app's own `vite.config.ts`.
- Test files live in `__tests__/` at the workspace root, e.g. `__tests__/app.test.tsx`, which renders `App` directly (`src/App.tsx`, importing `@/App`) since routing is composed in-app via `react-router`'s `BrowserRouter` + `src/routes/mainRoutes.tsx` (unlike `buyer-app`, which has Next's routing external to the page component).
- The shared MSW server lives at `__tests__/mocks/server.ts` (built from `__tests__/mocks/handlers.ts`) and is started/stopped once for the whole run via `vitest.setup.ts`. New feature tests that need to mock a request add handlers to `handlers.ts`, or call `server.use(...)` inside the test itself for a one-off override.
- `__tests__/utils/renderWithStore.tsx` — shared helper for tests that need a Redux `<Provider>`: builds an isolated store via `createStore({auth:{adminKey}})` and renders inside it. Prefer this over wrapping `<Provider store={store}>` manually so tests don't share state with each other via the app's singleton.
- `npm run test --workspace admin-app` runs the suite once (`vitest run`, not watch mode).
