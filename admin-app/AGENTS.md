# TechCart context

This is the `admin-app` workspace of a monorepo. Root-level decisions (monorepo layout, shared tooling, error contract, auth) live in root [`CLAUDE.md`](../CLAUDE.md), [`AGENTS.md`](../AGENTS.md), and [`docs/architecture.md`](../docs/architecture.md) — nothing here overrides those. Implementation detail for this workspace specifically is in [`docs/architecture.md`](docs/architecture.md).

## Feature-based structure

- `src/app/` and `src/router/` are routing only, split by concern: `src/app/App.tsx` is just the `BrowserRouter` wrapper; `src/router/AppRoutes.tsx` holds the actual `<Routes>` tree rendering from `src/features/<feature>/`. Unlike `buyer-app`'s Next.js file-system router, routes here are declared explicitly.
- `src/features/<feature>/` holds the actual UI/logic for that feature. `src/features/dashboard/Dashboard.tsx` (rendered at `/`) and, under `product-catalog/`, `products/ProductsPage.tsx`, `categories/CategoriesPage.tsx`, and `brands/BrandsPage.tsx` are the real ones so far; `specifications/` and `variant-types/` are still placeholder pages wired into real routes and the `Sidebar` nav, following the same "coming soon" idiom until each gets its real implementation — grouped under `product-catalog/` because all five belong to SRS v0.2 (`docs/srs/features/0.2-product-catalog.md`), unlike `dashboard/` which doesn't.
- This mirrors `backend/src/modules/<feature>/` and `buyer-app/src/features/<feature>/`'s feature-based organization (see `backend/AGENTS.md`, `buyer-app/AGENTS.md`), adapted for React Router instead of a file-system router.
- `src/layout/` holds cross-cutting page chrome that every route mounts inside — kept separate from `src/features/<feature>/` because it isn't owned by any single feature, the same way `backend/src/middleware/` and `backend/src/utils/` sit alongside (not inside) `backend/src/modules/` for non-feature code. `AdminShell.tsx` composes the three region components (`Sidebar.tsx`, `MobileMenuBar.tsx`, `MainSection.tsx` — the last renders child routes via `<Outlet />`), kept as separate files so each region can grow its own real content independently later. There's no full-width `Header` — `MobileMenuBar.tsx` is intentionally minimal (`lg:hidden`, just the hamburger button that opens the sidebar drawer below `lg`); everything else a conventional header might hold (search, theme/fullscreen toggles, notifications) was removed rather than relocated, and the profile block (avatar + name/role) moved into the bottom of `Sidebar.tsx` (`<nav>` is `flex-1`, pushing it down) instead. `PageHeader.tsx` also lives here (breadcrumb + bold title + optional top-right action button) — it's per-page chrome a feature composes into its own content, not baked into `MainSection.tsx`, because different pages need different header shapes (`Dashboard`'s stat cards vs. a list page's breadcrumb+table). Reuse it for every future list page rather than re-deriving the same breadcrumb/title/button markup.
- `src/components/` holds generic reusable UI widgets that are neither page chrome (`src/layout/`) nor feature-specific (`src/features/`): `DataTable.tsx` (a `material-react-table` wrapper — search, per-column filters, sorting, pagination, sticky header with a bounded-height scrollable body all come from it for free; row selection, the per-column "⋮" actions menu, and the "Show/Hide columns" toolbar button are explicitly disabled/omitted — none are part of this app's UI), `muiTheme.ts` (the MUI theme `DataTable` uses, matched to the Tailwind design tokens), `StatusSelect.tsx` (a small MUI `Select` — `{ value, onChange, options }` — for a *row-editable* status column; use inside a Status column's `Cell`, bound to `row.original`), and `StatusBadge.tsx` (the read-only status pill — use where a status is displayed but not editable). Every column except the first/Name column should be center-aligned (`{ align: "center" }` on both `muiTableHeadCellProps`/`muiTableBodyCellProps`) — Name stays left. Every list page follows the same composition: `PageHeader` + `DataTable` (+ any page-specific control MRT has no native concept of, e.g. `ProductsPage`'s "low stock only" checkbox — a derived cross-field filter). If a column is row-editable (like Status), the page holds its data in local `useState` seeded from the mock import, not the import directly, so edits persist. **MUI must stay scoped to `DataTable.tsx`** — its `ThemeProvider` wraps only there, no `CssBaseline`, nothing app-wide — so it can't collide with the Tailwind styling everywhere else. Don't reach for MUI components outside `DataTable.tsx`; everything else in this app is Tailwind.
- Screen-level design reference: [`mock-ui/`](../mock-ui/) — static wireframes per feature's SRS doc, not a workspace of its own. Consult it before building a feature's UI.
- Visual design reference: [`docs/design.md`](docs/design.md) — colors, typography, radius, borders, spacing, breakpoints, and layout behavior (admin-app only; `buyer-app` has its own separate `buyer-app/docs/design.md`). [`docs/design-tokens.md`](docs/design-tokens.md) holds the remaining admin-specific implementation notes. Consult both alongside `mock-ui/` before styling a feature's UI.

## Testing

- Stack: Vitest (`environment: "jsdom"`) + React Testing Library + MSW, wired via `vitest.config.ts` + `vitest.setup.ts` — same shape as `buyer-app` (see `buyer-app/AGENTS.md`). Reuses the `@vitejs/plugin-react` and `vite-tsconfig-paths` devDependencies already present for the app's own `vite.config.ts`.
- Test files live in `__tests__/` at the workspace root, e.g. `__tests__/app.test.tsx`, which renders `App` directly since `src/app/App.tsx` _is_ the router here (unlike `buyer-app`, which has Next's routing external to the page component).
- The shared MSW server lives at `__tests__/mocks/server.ts` (built from `__tests__/mocks/handlers.ts`) and is started/stopped once for the whole run via `vitest.setup.ts`. New feature tests that need to mock a request add handlers to `handlers.ts`, or call `server.use(...)` inside the test itself for a one-off override.
- `npm run test --workspace admin-app` runs the suite once (`vitest run`, not watch mode).

### What to test at each layer

- **Utilities** (pure functions — formatters, validators, helpers): plain Vitest unit tests, no RTL/MSW involved. Live in `__tests__/` mirroring the source path (e.g. `src/features/catalog/format-price.ts` → `__tests__/catalog/format-price.test.ts`), asserting input/output pairs directly.
- **Form data / client-side validation**: per root `CLAUDE.md`, `admin-app` owns its own validation independent of the backend's Zod schemas (no shared validation package) — so it needs its own coverage. Validation logic gets unit tests asserting both accepted and rejected inputs and the exact error message shown per field, tested standalone from component rendering.
- **Custom API hooks** (data-fetching hooks, e.g. a future `useProducts`): tested with RTL's `renderHook`, backed by the shared MSW server. Cover the loading → success and loading → error transitions using `server.use(...)` per-test overrides.
- **Integration tests — page-wise rendering**: one test per page/route, rendering the full route through `<App />` (or a `MemoryRouter` pointed at that path) with MSW mocking every API call the page makes, asserting the rendered result matches its `mock-ui/admin-app/*.html` reference (key content present, no stray loading/error state). `__tests__/shell.test.tsx` is the first instance of this pattern; `__tests__/routes.test.tsx` extends it by clicking each `Sidebar` nav link and asserting the destination page renders; every future real screen (`product-list`, `product-form`, `category-list`, ...) follows the same shape.
