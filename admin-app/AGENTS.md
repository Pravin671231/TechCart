# TechCart context

This is the `admin-app` workspace of a monorepo. Root-level decisions (monorepo layout, shared tooling, error contract, auth) live in root [`CLAUDE.md`](../CLAUDE.md), [`AGENTS.md`](../AGENTS.md), and [`docs/architecture.md`](../docs/architecture.md) — nothing here overrides those. Implementation detail for this workspace specifically is in [`docs/architecture.md`](docs/architecture.md).

## Feature-based structure

- `src/app/` is routing only — thin files that set up `react-router` and render from `src/features/<feature>/`. Unlike `buyer-app`'s Next.js file-system router, routes here are declared explicitly in `src/app/App.tsx`.
- `src/features/<feature>/` holds the actual UI/logic for that feature. `src/features/landing/LandingPlaceholder.tsx` is the current worked example, rendered at `/` by `src/app/App.tsx`.
- This mirrors `backend/src/modules/<feature>/` and `buyer-app/src/features/<feature>/`'s feature-based organization (see `backend/AGENTS.md`, `buyer-app/AGENTS.md`), adapted for React Router instead of a file-system router.
- Screen-level design reference: [`mock-ui/`](../mock-ui/) — static wireframes per feature's SRS doc, not a workspace of its own. Consult it before building a feature's UI.
- Brand tokens (`primary`/`accent` color scales, `Inter` as `font-sans`) are wired into `src/index.css` via a Tailwind `@theme` block. [`mock-ui/brand-kit.html`](../mock-ui/brand-kit.html) is the visual reference; `index.css` is the source of truth if they ever drift.

## Redux store, RTK Query, and the X-Admin-Key gate (Issue #76 / M2.19)

- `src/store/authSlice.ts` — holds `adminKey: string | null`, hydrated from `sessionStorage` (key `techcart_admin_key`, `ADMIN_KEY_STORAGE_KEY` exported) at module-init time, not a mount effect, so there's no flash of the key prompt on reload. `setAdminKey`/`clearAdminKey` sync `sessionStorage` inline in the reducer (plain synchronous browser API, no thunk needed).
- `src/store/api.ts` — the one shared `createApi` instance every feature module will `injectEndpoints` into (none exist yet — this issue only sets up the plumbing). `fetchBaseQuery`'s `baseUrl` is `ADMIN_API_BASE_URL` (`${API_URL}/api/admin`, from `src/config/env.ts`), so endpoint `query` paths stay relative (`"/brands"`, not `"/api/admin/brands"`). `prepareHeaders` attaches `X-Admin-Key` only when `adminKey` is non-null (never sends a literal `"null"` header). A `baseQueryWithAdminKeyGuard` wrapper dispatches `clearAdminKey()` whenever a request comes back `401` — the backend's `adminAuth` middleware is what actually enforces the key; this only reacts to its rejection. Exports `unwrapData`/`unwrapList` helpers for future endpoints' own `transformResponse` (detail vs. paginated-list envelopes need different shapes, so there's no single global transform) — `fetchBaseQuery`'s `FetchBaseQueryError` already carries the raw `{success:false,code,message}` body as `error.data`, so no `transformErrorResponse` is needed either.
- `src/store/store.ts` — `configureStore` built from a `combineReducers` root (`auth` + the api slice), exposed as both a `createStore(preloadedState?)` factory and a `store` singleton. Tests that need an isolated store (rather than mutating the app's singleton) should use `createStore(...)`, not `store` directly — see `__tests__/utils/renderWithStore.tsx`.
- `src/features/adminKey/` — `AdminKeyGate` wraps `<Routes>` once in `App.tsx` (there are no public admin-app routes to leave unguarded); it renders `AdminKeyPrompt` (a minimal one-field form) until `state.auth.adminKey` is set. This is explicitly a **throwaway client-side convenience**, not a security boundary — real sessions replace it outright once v0.3 Authentication lands. Don't build on top of it expecting it to survive.
- `src/config/env.ts` — `API_URL` reads `import.meta.env.VITE_API_URL`, falling back unconditionally to `http://localhost:4000` (no "fail loudly if missing" — unlike `backend`'s `env.ts`, this app has no required-secret startup check). `src/vite-env.d.ts`'s `/// <reference types="vite/client" />` is what makes `import.meta.env` type-check at all; add to it if a second env var is introduced.
- **Testing gotcha**: `authSlice`'s `sessionStorage` read happens once, at ESM module-eval time. A test that needs a pre-authenticated render should dispatch `setAdminKey(...)` against the store directly (see `__tests__/app.test.tsx`'s `beforeEach`) — seeding `sessionStorage` and expecting an already-imported store to pick it up won't work, since the module was already evaluated. The one test that specifically verifies hydration (`__tests__/store/authSlice.test.ts`) works around this with `vi.resetModules()` + a dynamic `await import("@/store/authSlice")` after seeding `sessionStorage`.

## Brand management (Issue #77 / M2.20)

- `src/features/brands/` — the first feature module to `injectEndpoints` into the shared `api` instance. `brandsApi.ts`'s `getBrands` query and `createBrand`/`updateBrand`/`updateBrandStatus`/`deleteBrand` mutations all share one flat `"Brand"` tag (`providesTags`/`invalidatesTags: ["Brand"]`, no per-id scheme) — matching the issue's own literal spec, and appropriate here since the brand list is small and unpaginated. `src/store/api.ts`'s base `createApi` call now declares `tagTypes: ["Brand"]`; any future feature's own tag type must be added there too, since RTK Query requires tag types declared upfront on the base instance, not just referenced from `injectEndpoints`.
- **`updateBrand` cannot change `status`** — the backend's `PATCH /api/admin/brands/:id` Zod schema only accepts `name`/`description`/`logo`; status is exclusively `PATCH /api/admin/brands/:id/status` (`{status: boolean}`). `BrandForm` therefore has no status field at all — the list's own status badge (`BrandList.tsx`) is a clickable toggle calling `useUpdateBrandStatusMutation` directly. Don't try to fold status into the edit form; the API doesn't support it.
- **Delete-guard rejection is rendered inline, not as a modal or toast** — `BrandList.tsx` catches a blocked `deleteBrand` mutation's `409 BRAND_IN_USE` via `.unwrap()`, reads the message through `getApiErrorEnvelope()` (`src/store/api.ts`, new — pulls `error.data` off an RTK Query `FetchBaseQueryError`), and renders it in a `role="alert"` row scoped to that brand. The backend's message is plain text with an embedded count (`"Cannot delete brand: referenced by N product(s)."`) — there's no separate numeric field, so it's displayed verbatim rather than reformatted.
- **Logo upload is a three-step client flow**, not a single request: `src/features/uploads/uploadsApi.ts`'s `presignUpload` mutation (`POST /api/admin/uploads/presign`, `{purpose, contentType}`) returns `{uploadUrl, objectKey, publicUrl, expiresAt}`; the file is then `PUT` directly to `uploadUrl` via `putFileToPresignedUrl()` (plain `fetch`, not RTK Query — it targets R2, not `backend`, and needs no `X-Admin-Key`); only `objectKey` (not `publicUrl`) is sent back to `backend` in the brand's `logo: {objectKey, alt?}` field on create/update. The response shape differs by direction: a brand's `logo` field in a **request** is `{objectKey, alt?}`, but in a **response** it's `{url, alt?}` — these are deliberately different types (`BrandLogoInput` vs `BrandLogo` in `src/features/brands/types.ts`), not a typo. `uploadsApi.ts` is intentionally feature-agnostic (`UPLOAD_PURPOSES` already lists `"category-image"`/`"product-image"` alongside `"brand-logo"`) so later category/product-image issues reuse it rather than duplicating the presign flow.
- **No sidebar/nav shell exists yet** — `mock-ui/admin-app/brand-list.html` shows one, but building it was out of scope for this issue. `LandingPlaceholder.tsx` just gained a plain `Link` to `/brands` as the only way to reach it for now; a real nav shell is expected once more admin screens land (M2.21+).
- Test layout: one `__tests__/features/brands/BrandsPage.test.tsx` integration test (list render, create, edit, delete-guard rejection, status toggle, search, and the full presign→PUT→save logo flow), MSW handlers defined locally via `server.use(...)` per test rather than added to the shared `__tests__/mocks/handlers.ts` — same "one-off override" convention `__tests__/store/api.test.ts` already established.

## Category management (Issue #78 / M2.21)

- `src/features/categories/` — mirrors `brands/`'s file layout and `getCategories`/`create·update·delete·updateStatus` pattern almost exactly (same flat `"Category"` tag, same `unwrapData`/`getApiErrorEnvelope` conventions, same `objectKey`-in/`url`-out image shape via `src/features/uploads/uploadsApi.ts` — `ImageUploader.tsx` here is a near-copy of brands' `LogoUploader.tsx`, just using `purpose: "category-image"`). `src/store/api.ts`'s `tagTypes` grew to `["Brand", "Category"]`.
- **The two-level hierarchy renders as one flat, indented table — not a nested tree/accordion.** `CategoryList.tsx`'s `orderAsTree()` groups the flat `CategoryListItem[]` response by `parentCategory` client-side (the backend's `GET /api/admin/categories` returns a flat array with no nesting or sort, confirmed from `categories.repository.ts`): root categories first (sorted by `sortOrder`/`name`), each immediately followed by its own children (same sort). A child row gets a `↳ ` prefix and `pl-8` indent; a dedicated `Parent` column names the parent for children and shows `—` for roots — matching `mock-ui/admin-app/category-list.html` exactly, which has no collapse/expand affordance either.
- **The parent-category picker is a plain `<select>` pre-filtered to root-level categories only** (`CategoryForm.tsx`'s `parentOptions`: any category with no `parentCategory` of its own, excluding the category currently being edited) — matching the mock's own caption, "Only top-level categories are selectable · FR-CAT-014". This client-side filter is a UX nicety, not the enforcement: the backend's `validateParentCategory` (`categories.service.ts`) is what actually rejects an invalid choice, across four distinct error codes the form must surface as inline, field-level text (not a toast) — `INVALID_PARENT_CATEGORY` (400, self-parent), `PARENT_CATEGORY_NOT_FOUND` (404), `PARENT_CATEGORY_TOO_DEEP` (400, parent already has a parent), `CATEGORY_HAS_SUBCATEGORIES` (400, update-only — the category being edited already has children of its own). All four reuse the same `saveError` (`getApiErrorEnvelope(createError ?? updateError)`) already established by `BrandForm`, just positioned directly under the parent `<select>` instead of at the bottom of the form, since three of the four are inherently about that field.
- **`parentCategory` is sent differently on create vs. update, matching the backend's own tri-state Zod schema**: create only accepts `undefined | string` (an empty picker selection is simply omitted from the payload); update accepts `undefined | null | string` and `CategoryForm` always sends either the picked id or explicit `null` on every save — never omits it. This is safe (not just simpler) because `validateParentCategory(null, ...)` short-circuits immediately, and a category that already has children can only ever have a `null` (root) parent locally in the first place (a subcategory can't itself have children, so `CATEGORY_HAS_SUBCATEGORIES` never fires on an always-`null` resend) — see the function's full logic in `backend/CLAUDE.md`'s Categories section if this needs revisiting.
- **The delete guard combines two independent conditions in one message**, not two separate errors: `409 CATEGORY_IN_USE`, with the backend joining whichever of "N product(s)" / "N subcategory(ies)" actually blocks via `" and "` — e.g. `"Cannot delete category: referenced by 1 product(s) and 1 subcategory(ies)."` when both apply. `CategoryList.tsx` displays it verbatim, identical inline-`role="alert"` placement to `BrandList.tsx`.
- No status field on `CategoryForm` either, same reasoning as brands — `updateCategory`'s Zod schema doesn't accept `status`; the list's status badge calls `useUpdateCategoryStatusMutation` directly.
- Test layout: one `__tests__/features/categories/CategoriesPage.test.tsx`, mirroring `BrandsPage.test.tsx`'s structure (`makeCategory`/`setupCategoryHandlers` local closures) but with dedicated cases for the tree-ordering/indentation, each of the four hierarchy-validation error codes individually, and the combined delete-guard wording.

## Category specification editor (Issue #79 / M2.22)

- `src/features/categorySpecifications/` — the first feature module built against `categorySpecifications`' `GET`/`PUT`/`PATCH`-only shape (no `POST`/`DELETE`, mirroring `backend/CLAUDE.md`'s Category Specifications section exactly). `src/store/api.ts`'s `tagTypes` grew to `["Brand", "Category", "CategorySpecification"]`. `categorySpecificationsApi.ts` exposes three endpoints: `getCategorySpecifications` (query), `replaceCategorySpecifications` (the `PUT` full-replace), and `patchCategorySpecifications` (the `PATCH` discriminated-union op, typed as `SpecPatchOperation` — a direct mirror of backend's own union). The synthetic empty `{category, specificationGroups: []}` response before any `PUT` needs no special handling — it's a normal, successfully-loaded `data` value to RTK Query, so the editor just renders zero groups rather than a distinct "empty state."
- **Routed at `/specifications`, not a per-category dynamic route** — `CategorySpecificationsPage.tsx` owns an in-page category `<select>` (matching the mock's "Category: Smartphones ▾" control) rather than a URL param; `CategorySpecificationEditor` is mounted with `key={categoryId}`, so a category switch is a clean remount rather than a state-reconciliation problem.
- **Two different persistence strategies for the same document, chosen deliberately per action** — documented here because it's the one thing in this module a future reader could easily assume is a bug: bulk edits (adding/reordering groups or fields, editing a field's name/type/unit/options/required) stay purely in local React state until "Save schema" fires one `PUT` with the whole draft; but renaming a group, deleting a group/field, and toggling a field's `filterable` checkbox call the matching `PATCH` op **immediately**, whenever the group/field being acted on is already known to exist server-side (tracked via a `persisted` snapshot set alongside the draft `groups` state, refreshed only on initial load and on every successful mutation response — never by an incidental background refetch, which would otherwise clobber an in-progress, not-yet-saved local edit). Acting on a *not-yet-saved* group/field (e.g. deleting a group you just added locally and haven't saved yet) always stays local-only — there's nothing to `PATCH` against yet. `filterable` specifically gets immediate-persist treatment (not just delete/rename) because it's the one checkbox the mock's own callout box singles out as consequential (buyer-facing filter facet + card-display eligibility) — matching this codebase's established "a toggle persists immediately, a structural edit goes through a form-level Save" convention (`CategoryList.tsx`'s status toggle is the precedent).
- **Reorder is up/down buttons, not drag-and-drop** — a deliberate scope simplification versus the mock's `⣿` drag handles; functionally equivalent (any ordering is reachable), avoids a DnD library dependency for a low-traffic admin tool. Reordering is a local edit like any other, persisted only through "Save schema."
- **Type-dependent field inputs are a client-side mirror of backend's Zod `.refine()`s, for UX only** — `SpecificationGroupCard.tsx`'s `updateField` clears `options` whenever `type` isn't `"enum"` and forces `filterable: false` whenever `type` is `"text"`; the backend's own `specificationFieldSchema` refines are what actually enforce this on `PUT`/`PATCH updateField`, so a client bypass would just surface as a `VALIDATION_ERROR` on save, not a stored inconsistency.
- **In-use guard messages are rendered verbatim**, same convention as brands'/categories' delete guards (`getApiErrorEnvelope(err)?.message`) — `SPECIFICATION_FIELD_IN_USE` already names every blocking field and its count in one string on both `deleteField` and `deleteGroup`, so there's nothing to reformat client-side.
- Test layout: one `__tests__/features/categorySpecifications/CategorySpecificationsPage.test.tsx`, covering the synthetic-empty render, a full add-group+add-field-then-Save `PUT` flow, `renameGroup` and `updateField` (`filterable` toggle) each firing their own `PATCH`, and the in-use guard's exact message rendering on both a blocked field delete and a blocked group delete.

## Testing

- Stack: Vitest (`environment: "jsdom"`) + React Testing Library + MSW, wired via `vitest.config.ts` + `vitest.setup.ts` — same shape as `buyer-app` (see `buyer-app/AGENTS.md`). Reuses the `@vitejs/plugin-react` and `vite-tsconfig-paths` devDependencies already present for the app's own `vite.config.ts`.
- Test files live in `__tests__/` at the workspace root, e.g. `__tests__/app.test.tsx`, which renders `App` directly since `src/app/App.tsx` _is_ the router here (unlike `buyer-app`, which has Next's routing external to the page component).
- The shared MSW server lives at `__tests__/mocks/server.ts` (built from `__tests__/mocks/handlers.ts`) and is started/stopped once for the whole run via `vitest.setup.ts`. New feature tests that need to mock a request add handlers to `handlers.ts`, or call `server.use(...)` inside the test itself for a one-off override.
- `__tests__/utils/renderWithStore.tsx` — shared helper for tests that need a Redux `<Provider>`: builds an isolated store via `createStore({auth:{adminKey}})` and renders inside it. Prefer this over wrapping `<Provider store={store}>` manually so tests don't share state with each other via the app's singleton.
- `npm run test --workspace admin-app` runs the suite once (`vitest run`, not watch mode).
