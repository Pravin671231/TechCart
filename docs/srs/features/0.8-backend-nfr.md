# SRS v0.8 — Backend Non-Functional Requirements

**Status:** Draft — awaiting review
**Last Updated:** 2026-08-21
**Depends on:** everything built in M2–M7 (v0.2–v0.7) — this version audits and hardens existing code rather than adding new business logic.

---

## 1. Feature Overview

Every feature doc from v0.2 through v0.7 shipped a deliberately **lightweight** Baseline NFR checklist (§4 item 3 of the template in `SRS.md`) and pointed the exhaustive, system-wide version here. This version collects on that: full rate-limiting policy across every route (not just auth), `helmet`, an exhaustive session-cookie audit, database resilience and index verification, structured logging with request correlation, Sentry, graceful shutdown, and a real load-test baseline.

This is an **audit-and-harden pass**, not a new feature with its own collections or endpoints — its acceptance criteria (§8) is largely "verify X across the whole existing codebase and fix what's found," applied retroactively to every route built since M0 (`FR-NFR-BE-028`).

## 2. Functional Requirements

### 2.1 Performance and scalability

- `FR-NFR-BE-001`: Every list/paginated endpoint across every feature has a documented p95 latency target under 300ms at the "small-to-medium catalog store" scale fixed in [`SRS.md`](../SRS.md) §2.5, measured against a seeded dataset representative of that scale (e.g. 5,000 products, 10,000 orders).
- `FR-NFR-BE-002`: The MongoDB connection pool size and timeout settings are explicitly configured, not left at driver defaults, and documented in `backend/.env.example`.
- `FR-NFR-BE-003`: A lost MongoDB connection triggers automatic reconnection with exponential backoff; a request arriving during a reconnection window fails fast with a specific `503`, rather than hanging until a client-side timeout — the real retry policy v0.2 §3 explicitly deferred here ("do not fail silently" was the only requirement then).
- `FR-NFR-BE-004`: Redis is available as a general-purpose response-cache utility (beyond Dashboard's existing use, `FR-DASH-013`) with a documented key-naming and TTL convention, so later modules adopt one pattern instead of inventing their own.
- `FR-NFR-BE-005`: A load test runs against the three highest-traffic buyer endpoints (product listing, product detail, search) at a target concurrency (50 concurrent users) before this version is considered complete, with results recorded in `backend/docs/architecture.md`.

### 2.2 Database

- `FR-NFR-BE-006`: Every index declared across every feature's SRS doc (v0.2 §3 through v0.7 §3) is audited against the actually deployed indexes (`db.collection.getIndexes()`), and any drift is corrected.
- `FR-NFR-BE-007`: Every collection's primary query paths are confirmed to use an index — no full collection scan — except the two already-documented, deliberately accepted exceptions (`FR-CAT-050`–`052`'s admin name-search regex).
- `FR-NFR-BE-008`: A database backup/restore procedure is documented (MongoDB Atlas's built-in continuous backup, per the managed-platform-only hosting decision, [`SRS.md`](../SRS.md) §2.5) and a restore is test-run at least once against a non-production cluster.

### 2.3 Security

- `FR-NFR-BE-009`: `helmet` is applied to every response, setting standard security headers (`X-Content-Type-Options`, `X-Frame-Options`, a baseline `Content-Security-Policy`) — deferred from [`docs/architecture.md`](../../architecture.md) §6 until this version.
- `FR-NFR-BE-010`: Every route in the system — not only auth (`FR-AUTH-032`–`033`) — has a rate-limit policy sized to its risk: strictest on auth/checkout/payment/webhook routes, more permissive on public catalog browsing, all on the existing Redis instance.
- `FR-NFR-BE-011`: Every session cookie's `httpOnly`/`secure`/`sameSite` attributes are audited against the production deployment's actual TLS/origin configuration and confirmed correct — closing the "exhaustive cookie-attribute audit" both v0.3 §3 and [`docs/architecture.md`](../../architecture.md) §6 deferred here.
- `FR-NFR-BE-012`: The existing CORS allowlist (`backend/src/middleware/cors.ts`) is audited to confirm it rejects every non-allowlisted origin, including wildcard-subdomain and protocol-mismatch attempts.
- `FR-NFR-BE-013`: Every admin-writable endpoint across every feature is confirmed, route by route, to require both authentication and the correct role (`FR-AUTH-023`–`025`) — not just the routes that existed when v0.3 shipped.
- `FR-NFR-BE-014`: Dependency vulnerabilities are scanned (`npm audit` or equivalent) in CI, failing the build on a high/critical finding with an available fix.
- `FR-NFR-BE-015`: A repo-wide audit confirms no secret (Razorpay keys, R2 credentials, Better Auth session secret, Resend API key) is ever logged, committed, or returned in any API response.

### 2.4 API and error handling

- `FR-NFR-BE-016`: Every error response across every feature is verified against `{ success: false, code, message }` by a system-wide integration-test pass, not merely claimed compliant in each feature's own checklist.
- `FR-NFR-BE-017`: The backend process handles `SIGTERM` with a graceful shutdown — stop accepting new connections, drain in-flight requests up to a timeout, close the MongoDB connection cleanly — required for zero-downtime deploys on Render.
- `FR-NFR-BE-018`: The existing `/health` endpoint (from M0) is deepened to report actual dependency health (MongoDB and Redis connection state), not just process liveness, so a deploy platform's health check can distinguish "process is up" from "process can serve traffic."
- `FR-NFR-BE-019`: API responses are gzip/brotli compressed above a minimum payload-size threshold.

### 2.5 Observability

- `FR-NFR-BE-020`: Pino structured JSON logging is wired for every request, including a request ID correlating a single request's log lines, per [`docs/architecture.md`](../../architecture.md) §6's already-stated intent.
- `FR-NFR-BE-021`: No `console.log` call exists in any request-handling code path anywhere in `backend`, enforced by a lint rule rather than a one-time manual pass.
- `FR-NFR-BE-022`: Sentry is wired for `backend`, capturing unhandled exceptions and unhandled promise rejections with request ID, route, and non-PII context.
- `FR-NFR-BE-023`: A structured audit log records every admin-privileged mutation (catalog writes, order status changes, refunds, admin user management) with who/when/what — separate from Pino's general request logging, since this is a compliance/support artifact, not a debugging tool.
- `FR-NFR-BE-024`: Logging never includes a password, session token, payment signature, or the full request body of a payment/webhook endpoint — enforced by an explicit redaction list at the logger configuration level, not left to individual call sites.

### 2.6 Configuration and operations

- `FR-NFR-BE-025`: Environment-variable validation (`env.ts`, live since v0.2) covers every secret/config value introduced by every feature since; a missing required variable fails startup loudly, never silently defaulting in production.
- `FR-NFR-BE-026`: A documented API-versioning stance is recorded — either "no versioning needed at this scale, breaking changes coordinate frontend/backend deploys directly" or an actual `/api/v1` prefix decision — closing an open item that has implicitly hung over the project since M1.
- `FR-NFR-BE-027`: BullMQ queues have a documented dead-letter/failure-visibility mechanism — a job that exhausts its retries is logged at minimum and ideally surfaced to Sentry, never silently dropped.
- `FR-NFR-BE-028`: Every requirement in this section applies retroactively to every route/module built in M2–M7 — this version's acceptance criteria audits the whole existing codebase, not only code written after this version starts.

## 3. Baseline Non-Functional Requirements

This version *is* the exhaustive NFR pass every prior feature deferred to; it has no further "lightweight, feature-scoped" subset to defer to itself. §2 above **is** this feature's NFR content, organized by area rather than by CRUD behavior.

## 4. User Stories

- As the **operator of this system**, I want confidence that a lost database connection degrades gracefully instead of hanging every in-flight request, so that a transient Atlas blip doesn't look like a full outage.
- As the **operator of this system**, I want every admin-privileged action logged with who/when/what, so that a disputed refund or an unexpected catalog change can be traced back to a real actor.
- As the **operator of this system**, I want to know my actual latency and error-rate baseline under realistic load before real traffic arrives, so that a launch-day surprise doesn't come from something a load test would have caught.
- As a **future contributor to this codebase**, I want a documented API-versioning stance and rate-limit policy, so that I don't have to reverse-engineer conventions from scattered code.

## 5. Verification Surface

No new collections or endpoints. What this version actually touches:

| Area | Mechanism | Cites |
| --- | --- | --- |
| Rate limiting | Redis-backed, per-route policy | `FR-NFR-BE-010` |
| Security headers | `helmet` middleware | `FR-NFR-BE-009` |
| Reconnection | MongoDB driver retry/backoff config | `FR-NFR-BE-003` |
| Logging | Pino + request-ID middleware | `FR-NFR-BE-020`–`024` |
| Error tracking | Sentry SDK (`backend`) | `FR-NFR-BE-022` |
| Health check | Deepened `/health` route (existing, from M0) | `FR-NFR-BE-018` |
| Audit log | New lightweight `adminAuditLog` collection (append-only, no update/delete) | `FR-NFR-BE-023` |
| Load test | k6 or Artillery script + recorded results | `FR-NFR-BE-005` |

## 6. UI/UX Requirements

None — this version is entirely backend. Any frontend-visible effect (a graceful `503` during a reconnect window, a rate-limit `429`) is an existing error-contract case both frontends already handle generically; no new UI state is introduced.

## 7. Out of Scope

- **Multi-region/multi-cluster database architecture** — one Atlas cluster per environment, per [`docs/architecture.md`](../../architecture.md) §7; this version hardens the connection to it, not its topology.
- **A dedicated APM/tracing product beyond Sentry** — Sentry's own performance monitoring is used where relevant (`FR-NFR-FE-023` on the frontend side); no separate distributed-tracing system is introduced.
- **Autoscaling policy** — Render's own scaling configuration is an infra/ops decision outside this SRS's scope.
- **Penetration testing** — a full third-party security audit is a Launch Readiness (v1.0) concern, not this version's.
- **Microservice extraction or queue-based decoupling beyond the existing BullMQ worker** — explicitly out of scope per [`SRS.md`](../SRS.md) §2.5's "avoid premature microservices" constraint.

## 8. Acceptance Criteria

**Performance and database**

- [ ] The three highest-traffic buyer endpoints meet their documented p95 target under the recorded load test. — `FR-NFR-BE-001`, `FR-NFR-BE-005`
- [ ] Every index from every prior feature's SRS doc exists in the deployed database; any drift found is corrected and re-verified. — `FR-NFR-BE-006`
- [ ] A simulated MongoDB disconnect results in automatic reconnection and a `503` (not a hang) for requests during the gap. — `FR-NFR-BE-003`
- [ ] A documented backup restore succeeds against a non-production cluster. — `FR-NFR-BE-008`

**Security**

- [ ] Every response carries `helmet`'s standard security headers. — `FR-NFR-BE-009`
- [ ] Every route category (auth, checkout, payment, webhook, public browsing) has a rate limit appropriate to its risk, verified by exceeding each and observing a `429`. — `FR-NFR-BE-010`
- [ ] A request from a non-allowlisted origin is rejected by CORS. — `FR-NFR-BE-012`
- [ ] A route-by-route audit confirms every admin-writable endpoint enforces both auth and role. — `FR-NFR-BE-013`
- [ ] A repo-wide secret-leak search (logs, committed files, API responses) finds nothing. — `FR-NFR-BE-015`

**API, observability, and operations**

- [ ] A system-wide test pass confirms every error response matches the standard contract. — `FR-NFR-BE-016`
- [ ] Sending `SIGTERM` to the running process drains in-flight requests and exits cleanly, without dropping a request mid-flight. — `FR-NFR-BE-017`
- [ ] `/health` reports MongoDB/Redis connection state, not just process liveness. — `FR-NFR-BE-018`
- [ ] Every log line for a request carries a request ID that correlates its other log lines. — `FR-NFR-BE-020`
- [ ] No `console.log` exists in a request-handling path — enforced by a lint rule that fails CI on violation. — `FR-NFR-BE-021`
- [ ] A deliberately thrown unhandled exception appears in Sentry with request context. — `FR-NFR-BE-022`
- [ ] An admin-privileged mutation (e.g. a status change) produces a corresponding `adminAuditLog` entry. — `FR-NFR-BE-023`
- [ ] A password or payment signature never appears in a log line, verified by a targeted test. — `FR-NFR-BE-024`
- [ ] Removing a required environment variable fails startup with a clear error, in every environment. — `FR-NFR-BE-025`

## 9. Dependencies

- **Every feature built in M2–M7** — this version's entire acceptance criteria is an audit of existing code; there is nothing to verify against without it.
- **Sentry, MongoDB Atlas (backup feature), Upstash Redis** — all already-provisioned per earlier features' dependencies; this version configures them more thoroughly rather than introducing new external services.

### Resolved during drafting

- **Whether this version needs its own "Baseline NFR" subsection distinct from its Functional Requirements** — no; unlike every prior feature, this version's FRs *are* the exhaustive NFR content those features deferred to, so §3 states that explicitly rather than duplicating §2.
- **Whether to introduce distributed tracing or an APM product** — no; Sentry (already adopted) covers error tracking and basic performance monitoring at this scale, and a dedicated tracing product is deferred until profiling data shows it's actually needed, per [`docs/architecture.md`](../../architecture.md) §9's "revisit if profiling shows the backend as the bottleneck" stance.
