# SRS v0.10 — Inventory Management

**Status:** Spec drafted
**Depends on:** [v0.2 Product Catalog](0.2-product-catalog.md) (amended), [v0.3 Authentication](0.3-authentication.md), [v0.4 Shopping Cart](0.4-shopping-cart.md) (forward reference only — not yet implemented)

---

## 1. Feature Overview

Introduces a small, fixed set of warehouses (2–3) and tracks `stock` per product variant *per warehouse*, reinstating the inventory concept that [Issue #102](https://github.com/Pravin671231/TechCart/issues/102) deliberately removed from the Product Catalog feature ("this system tracks no inventory quantity at all") — but this time splitting stock across locations rather than as a single field on the variant.

Admin gets one flat inventory table (product × variant × warehouse) to view and edit stock directly — no adjustment history, no reason codes, no low-stock thresholds or alerting. Buyer-facing availability stays a simple `in_stock`/`out_of_stock` signal, summed across warehouses; warehouses themselves are never exposed to buyers.

Cart quantity drives stock: adding an item to the cart decrements a warehouse's stock immediately (not deferred to order confirmation); removing or reducing the cart line restores it. This is a deliberate simplification for this portfolio project, not the conventional reserve-at-checkout pattern — see §10.

## 2. Functional Requirements

### 2.1 Warehouses

- `FR-INV-001`: A small, fixed set of warehouses exists (`name`, `code`, `active`) — admin can create and list warehouses. The system is designed for 2–3 warehouses, not an arbitrary number.
- `FR-INV-002`: Every unit of stock belongs to exactly one warehouse — there is no "unassigned" stock.

### 2.2 Inventory data

- `FR-INV-003`: For every (variant, warehouse) pair, the system tracks a `stock` count (integer, ≥ 0). A variant's total stock is the sum of `stock` across all warehouses.
- `FR-INV-004`: Admin can view a single inventory table listing every (product, variant, warehouse, stock) row, filterable by warehouse and by product/SKU keyword, paginated.
- `FR-INV-005`: Admin can directly edit the `stock` value for a given (variant, warehouse) row from that table — a plain absolute update; no history is kept.
- `FR-INV-006`: `stock` cannot be set below 0; the API rejects a negative value with a validation error.

### 2.3 Buyer — availability

- `FR-INV-007`: Buyer-facing availability is a simple derived state — `in_stock` if the variant's summed stock across all warehouses is greater than 0, else `out_of_stock`. Per-warehouse detail and raw counts are never exposed to the buyer.
- `FR-INV-008`: A variant with total stock equal to 0 is shown as out of stock and cannot be added to the cart.

### 2.4 Cart ↔ stock

_All FRs in this subsection depend on [v0.4 Shopping Cart](0.4-shopping-cart.md), which has no implemented `cart` backend module yet — these are forward-referencing specifications, not buildable until Cart ships._

- `FR-INV-009`: When a buyer adds a variant to their cart with quantity _n_, the system picks one warehouse whose `stock >= n` (first match, by warehouse creation order) and decrements that warehouse's `stock` by _n_. The chosen `warehouseId` is stored on the cart line so it can be restored later.
- `FR-INV-010`: If no single warehouse can fulfill the requested quantity, the add/increase is rejected with `INSUFFICIENT_STOCK`, naming the largest available single-warehouse quantity. Splitting one cart line's fulfillment across multiple warehouses is explicitly not supported.
- `FR-INV-011`: Increasing a cart line's quantity re-checks the same warehouse it was originally allocated to; decreasing it or removing the line restores `stock` to that same warehouse.
- `FR-INV-012` _(Open Question — not fully specced, see §10)_: Stock is decremented at cart-add time with no expiry/restore job for abandoned carts. This is a known simplification for this portfolio project, not production behavior.

### 2.5 Requirements by Workspace

Per this repo's architecture (`CLAUDE.md` — "One backend, two frontends"), all business logic and data live in `backend/`; `buyer-app/` and `admin-app/` only consume its API and render UI. Every `FR-INV-NNN` above is listed here under the workspace(s) that implement it, so implementation issues can be split cleanly by workspace as this feature moves to milestone/issue breakdown.

**`backend/`** — owns every FR outright (schema, validation, business logic, all endpoints in §5's API list):

- `FR-INV-001`, `FR-INV-002` — `warehouses` collection + create/list endpoints.
- `FR-INV-003` — `inventory` collection (per variant × warehouse `stock`).
- `FR-INV-004` — `GET /api/admin/inventory`: pagination, `warehouseId`/`search` filtering.
- `FR-INV-005`, `FR-INV-006` — `PATCH /api/admin/inventory/:inventoryId`: absolute stock update, negative-value rejection.
- `FR-INV-007` — computes `availability` (`in_stock`/`out_of_stock`) server-side on buyer-facing product/variant reads.
- `FR-INV-008` — enforces that an out-of-stock variant cannot be added to cart (rejected at the API, not just hidden client-side).
- `FR-INV-009`–`FR-INV-011` _(blocked on Cart v0.4)_ — warehouse-allocation logic inside the future `POST/PATCH/DELETE /api/cart/items[...]` endpoints: pick a warehouse, decrement/restore `stock`, reject with `INSUFFICIENT_STOCK`.
- `FR-INV-012` — the accepted gap (no restore job) is a backend design decision, not a frontend concern.
- All of §3's NFRs (auth guard, atomic `$inc`, error codes, indexes) are backend-only.

**`admin-app/`** — UI only, no logic of its own, consuming the endpoints above:

- `FR-INV-001` — "Warehouses" screen: list + create form, calling `GET`/`POST /api/admin/warehouses`.
- `FR-INV-004` — Inventory table screen: product/SKU/warehouse/stock columns, warehouse filter, keyword search, pagination — reuses `TableLayout`/`Pagination`/`SortableHeader` (Issue #107/#108) — calling `GET /api/admin/inventory`.
- `FR-INV-005`, `FR-INV-006` — inline-editable stock cell calling `PATCH /api/admin/inventory/:inventoryId`, surfacing `NEGATIVE_STOCK_REJECTED` inline.
- Corresponds to all "Admin:" bullets in §6.

**`buyer-app/`** — UI only, no logic of its own, consuming the endpoints above:

- `FR-INV-007`, `FR-INV-008` — availability badge / "Out of stock" state on the product detail page (`productDetail`, M2.18), reading the `availability` field; disables add-to-cart when `out_of_stock`.
- `FR-INV-009`–`FR-INV-011` _(blocked on Cart v0.4)_ — cart quantity controls that call the future `/api/cart/items` endpoints and surface `INSUFFICIENT_STOCK` inline, naming the available count.
- Corresponds to all "Buyer:" bullets in §6.

## 3. Baseline Non-Functional Requirements

- Inventory edit and warehouse-management endpoints require the existing admin-auth guard (today `X-Admin-Key`; `catalog-manager` role once v0.3 Authentication ships).
- `stock` updates — both admin edits and cart-driven changes — use atomic `$inc`/`$set` operations at the database level to avoid lost updates under concurrent cart adds.
- Error contract: reuse the existing `{ success: false, code, message }` envelope; new codes `NEGATIVE_STOCK_REJECTED`, `INSUFFICIENT_STOCK`.
- Unique index on `{ variantId: 1, warehouseId: 1 }` on the `inventory` collection, supporting both lookup and the table query.

## 4. User Stories / Use Cases

- As an admin, I can see one table of every variant's stock across all warehouses and edit any cell.
- As an admin, I can add a warehouse when the business opens a new one.
- As a buyer, I can't add more of an item to my cart than is actually in stock, without needing to know which warehouse it ships from.
- As a buyer, I see "out of stock" instead of being able to buy something unavailable everywhere.

## 5. Data Model / API Contract

### API list (summary)

| Method | Path | Owner | Purpose |
| --- | --- | --- | --- |
| `POST` | `/api/admin/warehouses` | Inventory | Create a warehouse |
| `GET` | `/api/admin/warehouses` | Inventory | List warehouses |
| `GET` | `/api/admin/inventory` | Inventory | Paginated inventory table (product × variant × warehouse × stock), filterable by `warehouseId`/`search` |
| `PATCH` | `/api/admin/inventory/:inventoryId` | Inventory | Edit one row's `stock` |
| `GET` | `/api/products` | Catalog (existing) | Buyer list — gains `availability` per variant |
| `GET` | `/api/products/:slug` | Catalog (existing) | Buyer detail — gains `availability` per variant |
| `GET` | `/api/categories/:slug/products` | Catalog (existing) | Buyer category list — gains `availability` per variant |
| `GET` | `/api/products?inStock=true` | Catalog (existing) | Buyer listing filter — reused query param, no new route |
| `POST` | `/api/cart/items` | Cart v0.4 (future) | Add to cart — allocates a warehouse, decrements `stock` |
| `PATCH` | `/api/cart/items/:id` | Cart v0.4 (future) | Change cart quantity — adjusts `stock` at the allocated warehouse |
| `DELETE` | `/api/cart/items/:id` | Cart v0.4 (future) | Remove cart line — restores `stock` at the allocated warehouse |

### Schema

New collection `warehouses`:

```ts
{
  _id: ObjectId;
  name: string;
  code: string;
  active: boolean;
  createdAt: Date;
}
```

New collection `inventory` — one row per (variant, warehouse):

```ts
{
  _id: ObjectId;
  productId: ObjectId;   // ref Product, denormalized for the table query
  variantId: ObjectId;   // matches ProductVariant._id
  warehouseId: ObjectId; // ref Warehouse
  stock: number;         // integer, >= 0, default 0
}
```

Unique index on `{ variantId, warehouseId }`. `ProductVariant` itself gains no `stock` field — stock lives entirely in `inventory`, keyed off the variant.

### Endpoints

`POST /api/admin/warehouses` / `GET /api/admin/warehouses` — create/list warehouses

```
POST Request  { "name": "Bengaluru DC", "code": "BLR-1" }
POST Response { "success": true, "data": { "_id": "...", "name": "Bengaluru DC", "code": "BLR-1", "active": true } }
```

`GET /api/admin/inventory?warehouseId=&search=&page=&limit=` — the inventory data table

```
Response { "success": true,
  "data": [ { "inventoryId": "...", "productId": "...", "productName": "...", "variantId": "...",
              "sku": "...", "warehouseId": "...", "warehouseName": "Bengaluru DC", "stock": 25 }, ... ],
  "pagination": { "page": 1, "limit": 20, "total": 48 } }
```

`PATCH /api/admin/inventory/:inventoryId` — edit one row's stock

```
Request  { "stock": 30 }
Response { "success": true, "data": { "inventoryId": "...", "stock": 30 } }
Errors   NEGATIVE_STOCK_REJECTED (400)
```

Buyer-facing reads (`GET /api/products`, `/api/products/:slug`, `/api/categories/:slug/products`) — each variant regains a computed field, warehouses/raw counts hidden:

```
"variants": [ { "sku": "...", "attributes": {...}, "sellingPrice": 999, "availability": "in_stock" } ]
```

Cart endpoints (owned by the future Cart v0.4 module, referenced not defined here) call into an internal inventory-allocate operation:

```
POST /api/cart/items        { variantId, quantity } → allocates a warehouse, decrements its stock, or 409 INSUFFICIENT_STOCK
PATCH /api/cart/items/:id   { quantity }             → adjusts stock at the line's already-allocated warehouseId
DELETE /api/cart/items/:id                            → restores stock at the line's warehouseId
```

Cart v0.4's own line-item schema will need a `warehouseId` field to remember the allocation — a cross-feature dependency this doc calls out but doesn't own.

## 6. UI/UX Requirements

- **Admin:** new "Inventory" nav section with one table view, reusing the existing `TableLayout`, `Pagination`, and `SortableHeader` components (Issue #107/#108) rather than a new one-off table. Columns: Product, SKU, Warehouse, Stock, with a warehouse filter dropdown and a keyword search box, mirroring the filter-chip pattern from M2.10.
- **Admin:** the stock cell is inline-editable (click → numeric input → save) — no separate modal or page.
- **Admin:** a small "Warehouses" management screen (list + create form) — simple, no edit/delete needed for 2–3 fixed locations at this scope.
- **Buyer:** an "Out of stock" label/badge replaces the add-to-cart control on a variant with total stock equal to 0, on the product detail page (`productDetail` feature, M2.18) — no warehouse information is ever shown.
- **Buyer:** attempting to add more than the available quantity to cart shows an inline error naming the available count — owned by the future Cart UI, specified here as a requirement it must satisfy.
- States to design: empty inventory table (no products/variants yet), and the inline validation error when an admin edit or buyer cart action is rejected.

## 7. Out of Scope

Adjustment audit log/reason codes; low-stock thresholds/alerts/reporting; suppliers; purchase orders; barcode/SKU scanning; bulk/CSV stock import; a cart-expiry stock-restoration job; order-time (as opposed to cart-time) stock deduction; splitting one order/cart line's fulfillment across multiple warehouses; warehouse-to-warehouse stock transfers; per-warehouse admin permissions; support for more than a handful of warehouses.

## 8. Acceptance Criteria

- [ ] Admin creates 2 warehouses and sets a variant's stock to 5 in Warehouse A, 0 in Warehouse B; the inventory table shows both rows correctly, and the buyer-facing product shows `in_stock`. — `FR-INV-001`, `FR-INV-003`, `FR-INV-004`, `FR-INV-007`
- [ ] Buyer adds 3 to cart → Warehouse A's stock becomes 2 (chosen since it had enough), and the cart line records `warehouseId = A`. — `FR-INV-009`
- [ ] Buyer tries to add 3 more (only 2 left in A, B has 0) → rejected with `INSUFFICIENT_STOCK`, naming 2 as available. — `FR-INV-010`
- [ ] Buyer removes the cart line → Warehouse A's stock is restored to 5. — `FR-INV-011`
- [ ] Admin attempts to set a row's `stock` to -1 → rejected with `NEGATIVE_STOCK_REJECTED`. — `FR-INV-006`
- [ ] A variant with total stock across all warehouses equal to 0 shows "Out of stock" on the buyer product page and cannot be added to cart. — `FR-INV-008`

## 10. Open Questions

- `FR-INV-012`: no expiry/restore job is specced for stock locked by an abandoned cart — accepted as a known gap for this portfolio project.
- Whether warehouse selection should ever consider proximity/priority beyond "first warehouse with enough stock, by creation order."
- Whether a 4th+ warehouse will ever need to be supported — out of scope today, assumed fixed at 2–3.
