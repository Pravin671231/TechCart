# SRS v0.9 — Frontend Non-Functional Requirements

**Status:** Draft — awaiting review
**Last Updated:** 2026-08-21
**Depends on:** every `buyer-app`/`admin-app` screen built in M2–M7 — this version audits and hardens existing UI rather than adding new screens. Mirrors v0.8's audit character on the frontend side.

---

## 1. Feature Overview

The buyer- and admin-facing counterpart to v0.8: Core Web Vitals targets, a responsive/browser-support baseline, an accessibility pass (WCAG 2.1 AA), a UX-consistency audit across every loading/empty/error state built since M2, a frontend security review, and Sentry wired into both clients. Like v0.8, this is primarily an **audit-and-fix pass** across `buyer-app`'s and `admin-app`'s existing screens (`FR-NFR-FE-024`), not a source of new screens.

Accessibility gets the deepest treatment here because it is the one area most likely to have silently drifted across eleven separately-built screens (`buyer-app` M2.14–18, `admin-app` M2.19–25, plus whatever M3–M7 add) — each shipped correct in isolation, but nothing has audited them together.

## 2. Functional Requirements

### 2.1 Performance

- `FR-NFR-FE-001`: `buyer-app`'s ISR-rendered routes (home, category, product detail, search — per [`docs/architecture.md`](../../architecture.md) §4.1) each meet a documented Core Web Vitals target (LCP < 2.5s, CLS < 0.1, INP < 200ms), measured via Lighthouse CI against a representative dataset.
- `FR-NFR-FE-002`: Every product/category/brand image in `buyer-app` uses `next/image` with explicit dimensions, never a bare `<img>` that can shift layout.
- `FR-NFR-FE-003`: `buyer-app`'s client bundle is code-split per route — checkout's Razorpay widget script, for instance, never loads on the home page.
- `FR-NFR-FE-004`: `admin-app`'s initial and largest-route bundle sizes are measured and recorded as a baseline in `admin-app/docs/architecture.md`; no specific target is enforced (it is not SEO/first-load sensitive the way `buyer-app` is, per [`docs/architecture.md`](../../architecture.md) §4.2's SPA rationale), only "no unbounded growth without justification."

### 2.2 Responsiveness and browser support

- `FR-NFR-FE-005`: Every `buyer-app` screen renders correctly at three baseline breakpoints — mobile (~375px), tablet (~768px), desktop (~1280px) — with no horizontal scroll and no clipped/overlapping content at any of them.
- `FR-NFR-FE-006`: Every `admin-app` screen renders correctly at the two-tier sidebar breakpoints Issue #107's shell already established (tablet icon-only, desktop icon+label), plus a functional mobile fallback.
- `FR-NFR-FE-007`: A documented browser-support matrix (current + 1 prior major version of Chrome, Firefox, Safari, Edge) is recorded, and every existing screen in both apps is smoke-tested against it at least once.
- `FR-NFR-FE-008`: No feature relies on a browser API outside that matrix's support without a documented fallback.

### 2.3 Accessibility

- `FR-NFR-FE-009`: Every interactive element across both apps is reachable and operable via keyboard alone, with a visible focus indicator — audited screen by screen, not spot-checked.
- `FR-NFR-FE-010`: Every image carries meaningful `alt` text actually rendered by the frontend (variant images already carry it server-side per `FR-CAT-084`); every purely decorative image is marked `alt=""` rather than omitted entirely.
- `FR-NFR-FE-011`: Every form across both apps associates its labels with their inputs programmatically, and surfaces validation errors in a way assistive technology can announce.
- `FR-NFR-FE-012`: Color contrast across both apps meets WCAG AA (4.5:1 normal text, 3:1 large text/UI components), audited against the actual rendered palette.
- `FR-NFR-FE-013`: Every modal/dialog (e.g. `admin-app`'s `AlertModal` from Issue #108) traps focus while open and returns it to the triggering element on close.
- `FR-NFR-FE-014`: This version's accessibility baseline is WCAG 2.1 AA — not AAA — a deliberate, bounded commitment appropriate to a small-to-medium commercial storefront.

### 2.4 UX consistency

- `FR-NFR-FE-015`: Every data-fetching screen across both apps has all three of a loading state, an empty state, and an error state, audited against every screen built in M2–M7 — several were built independently across many issues and could have drifted from each other.
- `FR-NFR-FE-016`: Every destructive admin action (delete, deactivate, cancel, refund) confirms via the existing `AlertModal` pattern rather than executing immediately on click, audited across every admin screen — not just the call sites that existed when `AlertModal` shipped.
- `FR-NFR-FE-017`: Every error message shown to a user is a specific, actionable string derived from the backend's `code`/`message` — never a raw stack trace, a generic "Something went wrong," or an unhandled promise rejection visible in the UI.

### 2.5 Frontend security

- `FR-NFR-FE-018`: Neither app's built client bundle contains any secret beyond the public Razorpay key ID and the already-public `NEXT_PUBLIC_API_URL` — audited by inspecting the actual built bundle, not just the source.
- `FR-NFR-FE-019`: No component in either app uses `dangerouslySetInnerHTML` (or an equivalent raw-HTML-injection pattern) without a documented, reviewed justification and sanitization step.
- `FR-NFR-FE-020`: A baseline Content-Security-Policy is set on both `buyer-app` and `admin-app` (coordinated with, but configured separately from, `FR-NFR-BE-009`'s backend headers, since both are independently hosted Vercel deployments), restricting script/style sources to trusted origins.
- `FR-NFR-FE-021`: Session/auth state is never persisted client-side in a form exfiltratable via XSS — the `httpOnly` cookie from v0.3 remains the sole source of truth; any client-side "signed in" flag is a UI convenience derived from `FR-AUTH-009`'s session-check call, never a stored credential.

### 2.6 Observability

- `FR-NFR-FE-022`: Sentry is wired for both `buyer-app` and `admin-app` — the client-side half of `FR-NFR-BE-022` — capturing unhandled exceptions with route/breadcrumb context and no PII beyond what's already visible in the UI.
- `FR-NFR-FE-023`: A Real User Monitoring signal (Vercel Analytics or Sentry's performance product) is enabled for `buyer-app` to track `FR-NFR-FE-001`'s Core Web Vitals targets against real traffic, not only synthetic Lighthouse runs.

### 2.7 Retroactive scope

- `FR-NFR-FE-024`: This version's accessibility, UX-consistency, and frontend-security requirements apply retroactively to every screen built in M2–M7 across both apps — its acceptance criteria audits the existing codebase, not only screens built after this version starts.
- `FR-NFR-FE-025`: Any fix made under this version that changes an existing screen's markup or behavior is re-verified against that screen's originating feature's own acceptance criteria (e.g. v0.2 §8, v0.5 §8) to confirm no regression was introduced while closing an NFR gap.
- `FR-NFR-FE-026`: A documented list of accepted, deliberately-not-fixed gaps (e.g. a third-party widget like Razorpay's own checkout iframe, which cannot be fully controlled for accessibility) is recorded rather than silently left unaddressed.

## 4. User Stories

- As a **buyer on a mobile connection**, I want pages to load quickly and not jump around as images load, so that shopping doesn't feel sluggish or frustrating.
- As a **buyer using a screen reader or keyboard-only navigation**, I want every page to actually be usable that way, so that I'm not excluded from shopping on this site.
- As a **catalog/order manager**, I want every destructive action to ask for confirmation, so that a misclick doesn't delete or cancel something by accident.
- As the **operator of this system**, I want to know about a frontend crash before a user has to report it, so that I can fix it proactively.

## 6. UI/UX Requirements

This version's own §2 largely *is* its UI/UX requirement — it does not add a separate screen inventory the way v0.2–v0.7 do. Any visible change is a fix to an existing screen (a missing `alt`, a trapped-focus modal, a corrected contrast ratio), not a new one.

---

## 7. Out of Scope

- **New screens or features** — this version fixes existing ones; any missing screen entirely (as opposed to an existing screen's NFR gap) belongs to whichever feature version owns it.
- **Native mobile apps** — responsive web only, per the stack fixed in `SRS.md` §1.5's Technology Blueprint.
- **Internationalization/localization** — single-market (India), English-only, per `SRS.md` §2.5.
- **A full WCAG AAA commitment** — AA is the bar (`FR-NFR-FE-014`).
- **Third-party widget accessibility beyond what Razorpay itself controls** — documented as an accepted gap where applicable (`FR-NFR-FE-026`), not fixed by this codebase.

## 8. Acceptance Criteria

**Performance**

- [ ] Lighthouse CI reports LCP/CLS/INP within target on `buyer-app`'s four ISR routes. — `FR-NFR-FE-001`
- [ ] No `<img>` tag renders a catalog image in `buyer-app`; every one goes through `next/image`. — `FR-NFR-FE-002`
- [ ] `admin-app`'s bundle sizes are recorded as a baseline in its architecture doc. — `FR-NFR-FE-004`

**Responsiveness and browser support**

- [ ] Every screen in both apps is visually verified at each documented breakpoint with no horizontal scroll or clipped content. — `FR-NFR-FE-005`, `FR-NFR-FE-006`
- [ ] The browser-support matrix is documented and every screen has been smoke-tested against it at least once. — `FR-NFR-FE-007`

**Accessibility**

- [ ] An automated axe-core scan against every screen in both apps reports zero critical/serious violations. — `FR-NFR-FE-009`–`012`
- [ ] Tabbing through any screen reaches every interactive element in a logical order with a visible focus indicator at each stop. — `FR-NFR-FE-009`
- [ ] Opening `AlertModal` traps focus inside it; closing it returns focus to the button that opened it. — `FR-NFR-FE-013`
- [ ] Every form's error state is confirmed announced by a screen reader in a manual test pass (automated scans alone don't catch this). — `FR-NFR-FE-011`

**UX consistency and security**

- [ ] Every data-fetching screen built in M2–M7 is confirmed to have loading/empty/error states, with any gap found and fixed. — `FR-NFR-FE-015`
- [ ] Every destructive admin action across every admin screen routes through `AlertModal`. — `FR-NFR-FE-016`
- [ ] Inspecting both apps' built bundles finds no secret beyond the public Razorpay key ID and `NEXT_PUBLIC_API_URL`. — `FR-NFR-FE-018`
- [ ] A repo-wide search finds no unjustified `dangerouslySetInnerHTML` usage. — `FR-NFR-FE-019`
- [ ] A deliberately thrown frontend exception appears in Sentry for both apps. — `FR-NFR-FE-022`
