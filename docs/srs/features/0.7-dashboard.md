# SRS v0.7 — Dashboard

**Status:** Draft — awaiting review
**Last Updated:** 2026-08-21
**Depends on:** Orders (v0.5) and Payments (v0.6) for revenue/order figures; Product Catalog (v0.2) for catalog and top-product figures; Authentication (v0.3) for role-scoped access; Inventory Management (v0.10) for the out-of-stock count folded into catalog-summary (`FR-DASH-023`–`024`). Introduces no new primary collection of its own — every endpoint here reads and aggregates data already owned by an earlier feature.

---

## 1. Feature Overview

Dashboard is a read-only aggregation layer, not a new domain: `order-manager`/`super-admin` get an operational view of sales and orders, `catalog-manager` gets a catalog-health view scoped to their own domain, and a signed-in buyer gets a compact account-home summary distinct from — not a duplicate of — the full order history v0.5 already provides at `GET /api/orders`. Nothing here writes anything; every endpoint is a query.

Role scoping mirrors the boundary v0.5 already drew rather than inventing a new one: revenue and order figures are `order-manager`/`super-admin` territory, catalog figures are `catalog-manager`/`super-admin` territory, and `super-admin` sees everything. There is no low-stock or threshold-based alerting widget anywhere in this version — [SRS v0.10 Inventory Management](0.10-inventory-management.md) reinstated only a binary `in_stock`/`out_of_stock` signal and deliberately keeps low-stock thresholds/alerts/reporting out of scope (v0.10 §7), so catalog-summary surfaces nothing more than a live out-of-stock count on that axis. _(Amended by SRS v0.10: catalog-summary, §2.2, gains a live out-of-stock count — `FR-DASH-023`–`024` — superseding this doc's original claim that Dashboard had "nothing to surface" on the stock axis, which held only because v0.2 had removed the stock concept entirely at the time this doc was first drafted.)_

## 2. Functional Requirements

### 2.1 Admin sales and order summary

- `FR-DASH-001`: An `order-manager` or `super-admin` can view an operational summary via `GET /api/admin/dashboard/summary` — total orders, total revenue, and an order-count breakdown by status, scoped to a date range.
- `FR-DASH-002`: The date range is supplied via `from`/`to` query params; an invalid or reversed range is rejected, and an omitted range defaults to the last 30 days.
- `FR-DASH-003`: "Revenue" is the sum of `captured` payment amounts within the range, net of any refunds processed within that same range — never raw order `totalAmount`, since an order can be refunded after being counted (`FR-PAY-017`).
- `FR-DASH-004`: The summary's status breakdown covers every status in the order state machine (`pending_payment`, `paid`, `processing`, `shipped`, `delivered`, `cancelled`, `refunded`) for the selected range.
- `FR-DASH-005`: An `order-manager` or `super-admin` can view a revenue-over-time series via `GET /api/admin/dashboard/sales`, bucketed by day for ranges up to 31 days and by week for longer ranges.
- `FR-DASH-006`: An `order-manager` or `super-admin` can view a top-products-by-revenue list via `GET /api/admin/dashboard/top-products`, computed from captured order line items within the range, showing product name, units sold, and revenue.

### 2.2 Catalog summary

- `FR-DASH-007`: A `catalog-manager` can view catalog-only figures — product counts by status (`draft`/`published`/`archived`), category count, and brand count — via `GET /api/admin/dashboard/catalog-summary`, but is rejected `403` on every sales/revenue endpoint (`FR-DASH-001`, `005`, `006`), since revenue is `order-manager`/`super-admin` territory.
- `FR-DASH-020`: Catalog-summary counts are computed live from the `products`/`categories`/`brands` collections at request time — no denormalized counter table is introduced for this version.
- `FR-DASH-021`: `order-manager` is rejected `403` on the catalog-summary endpoint — the reciprocal of `FR-DASH-007`'s boundary, so dashboard role scoping introduces no capability either admin role didn't already have elsewhere.

_`FR-DASH-023`–`024` were added when [SRS v0.10 Inventory Management](0.10-inventory-management.md) was drafted (see §9 Dependencies). v0.10 is spec-drafted but not yet implemented as of this amendment, so these two requirements are not buildable until it ships — they're documented now so catalog-summary's contract doesn't need a second breaking change later._

- `FR-DASH-023`: A `catalog-manager` or `super-admin` additionally sees an out-of-stock count on the same `GET /api/admin/dashboard/catalog-summary` endpoint (`FR-DASH-007`) — the number of active variants, across `published` products only, whose stock summed across every warehouse is 0, i.e. whose buyer-facing `availability` (`FR-INV-007`) is `out_of_stock`. This is a plain count, not a threshold — no "low stock" figure exists, consistent with v0.10 keeping low-stock thresholds/alerts/reporting out of scope (v0.10 §7).
- `FR-DASH-024`: The out-of-stock count (`FR-DASH-023`) is computed live from v0.10's `inventory` collection at request time — grouped by `variantId`, summed across warehouses, filtered to active variants of `published` products — the same no-denormalized-counter-table approach `FR-DASH-020` already applies to the rest of catalog-summary. Until Inventory Management (v0.10) is implemented, this field is omitted from the response entirely rather than zero-filled, so a genuine zero is never confused with "not implemented yet."

### 2.3 Access scope

- `FR-DASH-008`: `super-admin` can view every dashboard endpoint regardless of the role scoping in `FR-DASH-007`/`021`.
- `FR-DASH-009`: Every dashboard endpoint is read-only — none of them accepts a write in this version.

### 2.4 Buyer account dashboard

- `FR-DASH-010`: A signed-in buyer can view an account-home summary via `GET /api/account/dashboard`, showing their profile essentials (name, email) and their 5 most recent orders (order number, date, status, total) — a compact view, not a second copy of v0.5's full paginated `GET /api/orders`.
- `FR-DASH-011`: The summary includes the buyer's lifetime order count and lifetime amount spent, computed net of refunds the same way as `FR-DASH-003`.
- `FR-DASH-012`: An unauthenticated request to the buyer dashboard endpoint is rejected `401` — no dashboard content is available to a guest.

### 2.5 Aggregation behavior

- `FR-DASH-017`: The top-products list (`FR-DASH-006`) is capped at 10 entries, ordered by revenue descending with units sold as the tiebreaker.
- `FR-DASH-018`: The sales-over-time series (`FR-DASH-005`) returns a zero-filled bucket for every day/week in range with no captured revenue, rather than omitting it — a chart consuming this response never has to fill gaps itself.
- `FR-DASH-019`: A date range longer than 1 year is rejected outright rather than silently clamped — an unbounded aggregation window is a performance risk this version chooses to reject, not degrade through.

### 2.6 Caching

- `FR-DASH-013`: Admin dashboard aggregation responses are cached in Redis for a 60-second TTL, keyed by the exact endpoint and query parameters — these are aggregation-heavy reads repeatedly hit by the same admin session loading the same screen.
- `FR-DASH-014`: A cached response is invalidated by TTL expiry only; there is no explicit cache-invalidation-on-write path in this version, accepting up to 60 seconds of staleness as a deliberate tradeoff against aggregation cost.

### 2.7 Response envelope

- `FR-DASH-015`: Every dashboard endpoint follows the existing `{ success, data }` contract; none is paginated in the list-endpoint sense — `top-products` returns a fixed-size top-N array (`FR-DASH-017`), not a paginated list.
- `FR-DASH-016`: Every monetary field in a dashboard response is an integer number of paise, consistent with every prior feature.
- `FR-DASH-022`: Every dashboard error follows `{ success: false, code, message }`, unchanged from every prior feature.

## 3. Baseline Non-Functional Requirements

**Validation**

- [ ] `from`/`to` range params are validated server-side (well-formed dates, `from` ≤ `to`, span ≤ 1 year per `FR-DASH-019`) before any aggregation query runs.

**Indexes**

- [ ] Dashboard aggregation reuses `orders`' and `payments`' existing indexes (`(user, createdAt)`, `status`, etc. from v0.5/v0.6), and — once Inventory Management (v0.10) ships — its unique index on `{ variantId, warehouseId }` on `inventory` for the out-of-stock aggregation (`FR-DASH-024`). No new collection or index is introduced solely for this feature, aside from what caching requires in Redis.

**Error handling and operations**

- [ ] Every endpoint follows `{ success: false, code, message }`, per [`docs/architecture.md`](../../architecture.md) §6.
- [ ] A range producing genuinely zero data (e.g. a brand-new deployment with no orders yet) returns a successful, zero-valued response — never an error.

**Security**

- [ ] Role checks on every admin dashboard endpoint reuse the exact `FR-AUTH-023`–`024` guard already applied to catalog and order routes — no bespoke authorization logic is written for this feature.
- [ ] Redis-cached dashboard responses carry no buyer-identifying detail beyond what the requesting admin's own role is already entitled to see — the cache key includes range/query params but the cached value contains only aggregate figures, never a raw buyer list.

## 4. User Stories

- As an **order manager**, I want to see total sales and order counts over a date range, so that I know how the store is performing without querying the database by hand.
- As an **order manager**, I want to see which products are selling best, so that I know what's actually driving revenue.
- As a **catalog manager**, I want to see how many products are published versus still in draft, so that I know how much of my catalog work is actually live.
- As a **super admin**, I want to see every figure either role can see, so that I have full operational visibility without needing a separate account.
- As a **registered buyer**, I want a quick summary of my recent orders when I land on my account page, so that I don't have to open the full order history just to check on my last purchase.

## 5. Data Model / API Contract

No new collection of its own. Every endpoint aggregates `orders`, `payments`, and `products`/`categories`/`brands`, plus — for the catalog-summary out-of-stock count (`FR-DASH-023`–`024`) — [v0.10](0.10-inventory-management.md)'s `inventory` collection. _(Amended by SRS v0.10: the first Dashboard figure sourced from a collection that didn't exist when this doc was originally drafted.)_

### API endpoints

| Method | Path                                     | Auth                                              | Purpose                                                    |
| ------ | ------------------------------------------ | ---------------------------------------------------- | -------------------------------------------------------------- |
| GET    | `/api/admin/dashboard/summary`            | session (`order-manager`/`super-admin`)              | Orders/revenue summary — `FR-DASH-001`–`004`                    |
| GET    | `/api/admin/dashboard/sales`              | session (`order-manager`/`super-admin`)              | Revenue-over-time series — `FR-DASH-005`, `018`                 |
| GET    | `/api/admin/dashboard/top-products`       | session (`order-manager`/`super-admin`)              | Top products by revenue — `FR-DASH-006`, `017`                  |
| GET    | `/api/admin/dashboard/catalog-summary`    | session (`catalog-manager`/`super-admin`)            | Catalog health counts — `FR-DASH-007`, `020`–`021`, `023`–`024`  |
| GET    | `/api/account/dashboard`                  | session (buyer)                                       | Buyer account-home summary — `FR-DASH-010`–`012`                |

## 6. UI/UX Requirements

**`admin-app`** — Recharts per [`docs/architecture.md`](../../architecture.md) §4.2, role-gated per §2.1–2.2 above; a `catalog-manager` sees only the catalog-summary widgets, an `order-manager` sees only the sales/order widgets, `super-admin` sees both.

- **Admin dashboard (order-manager/super-admin)**: summary cards (total orders, total revenue, orders-by-status), a revenue-over-time chart, a top-products table, and a date-range control (`FR-DASH-002`) that re-fetches all three on change.
- **Admin dashboard (catalog-manager)**: a narrower set of cards — product counts by status, category count, brand count, and (once Inventory Management v0.10 ships) an out-of-stock count (`FR-DASH-023`) — with no date-range control, since catalog-summary is a point-in-time snapshot, not a ranged query. _(Amended by SRS v0.10: the out-of-stock card is new; it is a plain count, not an alert — no threshold styling, no "low stock" badge.)_

**`buyer-app`** — client-rendered, session-gated.

- **Account home**: profile summary, a compact list of the 5 most recent orders (each linking to its full detail from v0.5), and lifetime order count/spend — a landing screen for the account section, distinct from and linking out to the full order-history page v0.5 already built.

## 7. Out of Scope

- **Any admin write action originating from the dashboard** — every dashboard endpoint is read-only (`FR-DASH-009`); actions like advancing an order's status still happen on v0.5's order detail screen, not here.
- **Real-time/live-updating dashboard** — figures refresh on page load and range change, subject to the 60-second cache (`FR-DASH-013`); no WebSocket/push updates.
- **Exportable reports** (CSV/PDF) — figures are viewed in-app only in this version.
- **Custom/configurable dashboard widgets** — the widget set per role is fixed, not user-arrangeable.
- **Marketing/traffic analytics** (page views, conversion funnels) — this dashboard covers orders/revenue/catalog only, not storefront traffic.
- **Low-stock threshold, alerting, or reporting widgets** _(amended by SRS v0.10)_ — [v0.10 Inventory Management](0.10-inventory-management.md) reinstated a raw/binary stock concept (per-variant, per-warehouse `stock` counts, and a computed `in_stock`/`out_of_stock` availability), so the original claim here — "no stock concept exists anywhere in this system" (v0.2 §1) — no longer holds; catalog-summary now surfaces a live out-of-stock count (`FR-DASH-023`–`024`). What remains out of scope is specifically anything threshold-based — low-stock thresholds, alerts, or reporting — since v0.10 itself excludes those (v0.10 §7). No per-warehouse or raw per-variant stock detail is exposed via Dashboard either, in any version — only the single aggregate out-of-stock count.

## 8. Acceptance Criteria

**Admin sales summary**

- [ ] The summary for a range with known orders returns correct totals, matching a manual aggregation of the same underlying `orders`/`payments` data. — `FR-DASH-001`, `FR-DASH-003`, `FR-DASH-004`
- [ ] Refunding an order after it was counted in a range's revenue reduces that range's revenue on the next request (subject to cache TTL), not just future ranges. — `FR-DASH-003`
- [ ] An omitted range defaults to the last 30 days; an invalid or reversed range is rejected; a range longer than 1 year is rejected. — `FR-DASH-002`, `FR-DASH-019`
- [ ] The sales-over-time series includes a zero-valued entry for a day/week with no revenue, not a gap. — `FR-DASH-018`
- [ ] The top-products list never exceeds 10 entries and is ordered by revenue descending. — `FR-DASH-017`

**Role scoping**

- [ ] A `catalog-manager` session is rejected 403 on `summary`, `sales`, and `top-products`; an `order-manager` session is rejected 403 on `catalog-summary`. — `FR-DASH-007`, `FR-DASH-021`
- [ ] A `super-admin` session succeeds on every dashboard endpoint. — `FR-DASH-008`

**Catalog summary**

- [ ] Once Inventory Management (v0.10) is live, the out-of-stock count on `catalog-summary` matches a manual count of active variants (of `published` products only) whose `inventory` stock sums to 0 across warehouses. — `FR-DASH-023`, `FR-DASH-024`
- [ ] Before v0.10 ships, `catalog-summary`'s response omits the out-of-stock field entirely rather than reporting a misleading zero. — `FR-DASH-024`

**Buyer dashboard**

- [ ] A signed-in buyer's account-home summary shows at most their 5 most recent orders and correct lifetime count/spend figures net of any refunds. — `FR-DASH-010`, `FR-DASH-011`
- [ ] An unauthenticated request to `/api/account/dashboard` is rejected 401. — `FR-DASH-012`

**Caching and envelope**

- [ ] Two identical requests within 60 seconds return identical figures even if underlying data changed in between; a request after 60 seconds reflects the change. — `FR-DASH-013`, `FR-DASH-014`
- [ ] Every response matches `{ success: true, data: {...} }` with monetary fields as integer paise; every error matches `{ success: false, code, message }`. — `FR-DASH-015`, `FR-DASH-016`, `FR-DASH-022`

## 9. Dependencies

- **Orders (v0.5)** and **Payments (v0.6)** — the source of every sales/revenue figure.
- **Product Catalog (v0.2)** — the source of catalog-summary counts and top-product names.
- **Inventory Management (v0.10)** — source of the out-of-stock count folded into catalog-summary (`FR-DASH-023`–`024`); Dashboard reads v0.10's `inventory` collection (summed per variant across warehouses) but owns no write path into it, consistent with every other Dashboard dependency being read-only aggregation.
- **Authentication (v0.3)** — role-scoped access, reusing the existing RBAC guard with no new authorization mechanism.
- **Upstash Redis** — dashboard response caching (`FR-DASH-013`–`014`), the same instance already used for rate limiting.

## 10. Open Questions

_None open — see "Resolved during drafting" below._

### Resolved during drafting

- **Whether the buyer dashboard duplicates v0.5's order history** — no; it is capped at 5 recent orders plus lifetime figures (`FR-DASH-010`–`011`), a landing summary that links out to the full history rather than replacing it.
- **Whether to invalidate the dashboard cache on every relevant write** — no; a flat 60-second TTL (`FR-DASH-013`–`014`) was chosen over wiring cache invalidation into every order/payment mutation, trading a small, bounded staleness window for not coupling Orders/Payments write paths to Dashboard's cache.
