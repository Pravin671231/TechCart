# SRS v0.3 — Authentication

**Status:** Draft — awaiting review
**Last Updated:** 2026-08-22 (amended, Issue #139 redo — added `FR-AUTH-046`, the buyer bearer-token session mechanism)
**Depends on:** Better Auth (MongoDB adapter, Google OAuth/One Tap provider, email-OTP plugin), Resend (OTP codes, admin password-reset emails), Upstash Redis (rate limiting), Google Cloud (OAuth client, Identity Services for One Tap). Replaces Product Catalog's temporary `X-Admin-Key` shared-secret guard (`FR-CAT-088`–`090`) outright.

---

## 1. Feature Overview

Authentication gives the system its first real identity: buyers who sign in with Google (OAuth or One Tap) or a passwordless email one-time code to place orders, and admins — `catalog-manager`, `order-manager`, `super-admin` — who sign in with an email/password step followed by a mandatory email-OTP step to a session-and-role-gated console instead of pasting a shared secret into every request. It replaces Product Catalog's `X-Admin-Key` guard exactly the way `FR-CAT-090` promised: a single middleware swap, no change to any catalog route path, controller, or service.

One `users` collection serves both apps — `role` is what separates a buyer from an admin, and which of the three admin roles an admin holds — per [`SRS.md`](../SRS.md) §2.3's User Classes and [`docs/architecture.md`](../../architecture.md) §5's data map. Every later feature depends on the identity this version establishes: Cart (v0.4) attaches a guest cart to a signed-in buyer, Orders (v0.5) records who placed an order, Payments (v0.6) and Dashboard (v0.7) both need a real `order-manager`/`super-admin` boundary that doesn't exist yet. Catalog writes have carried a reserved, always-`null` `createdBy`/`updatedBy` since v0.2 (`FR-CAT-013`) specifically so this version could populate them with no migration.

Buyers never have a traditional password in this version — every buyer entry point (Google OAuth, Google One Tap, email+OTP) is passwordless, resolving to one account per unique email regardless of which method was used. Admins are the only role with a password, and their password alone is never sufficient: a mandatory email-OTP step follows every successful password check before a session is established. Scope is otherwise deliberately narrow: no buyer address book (that belongs to Orders' checkout flow, v0.5), no non-Google social providers, no device-trust/remember-me exception to the admin OTP step — see §7.

## 2. Functional Requirements

### 2.1 Buyer authentication (Google + email OTP)

- `FR-AUTH-001`: A guest can sign in via Google OAuth (`POST /api/auth/sign-in/social` with `provider: "google"`, redirect flow, callback at `GET /api/auth/callback/google`), establishing a session on success.
- `FR-AUTH-002`: A guest can sign in via Google One Tap by posting the credential returned by Google Identity Services to `POST /api/auth/one-tap`; on successful verification this establishes a session identically to `FR-AUTH-001`.
- `FR-AUTH-003`: A guest can sign in passwordlessly with just an email: `POST /api/auth/email-otp/send` emails a single-use one-time code via Resend, and `POST /api/auth/email-otp/sign-in` verifies it and establishes a session.
- `FR-AUTH-004`: First-time use of any one of `FR-AUTH-001`–`003` auto-creates a `buyer` account from the email Google or the OTP flow provides — there is no separate registration step and no client-supplied `role` is ever trusted.
- `FR-AUTH-005`: A later sign-in through a _different_ one of the three buyer methods, using the same email, resolves to the same existing account rather than creating a duplicate — email is the sole identity key across all three.
- `FR-AUTH-006`: If the email resolved by any of `FR-AUTH-001`–`003` already belongs to an account whose `role` is not `buyer` (i.e. an admin), the sign-in is rejected with a specific, non-500 error — admins never authenticate through a buyer route.
- `FR-AUTH-007`: The email-OTP code (`FR-AUTH-003`) is single-use and expires 10 minutes after issuance; it is rejected once expired or once already used, even inside that window on a second attempt.
- `FR-AUTH-008`: A successful sign-in via any of `FR-AUTH-001`–`003` returns the resolved user's public profile (`id`, `name`, `email`, `role`).
- `FR-AUTH-046` _(added, Issue #139 redo)_: A buyer session established via any of `FR-AUTH-001`–`003` is additionally delivered as a bearer token — returned in a `set-auth-token` response header on sign-in, and accepted back as an `Authorization: Bearer <token>` request header on subsequent requests — alongside the session cookie, not instead of it. `buyer-app` and `backend` deploy to separate domains with no shared parent domain (`docs/architecture.md` §7); a cross-site cookie is not reliably sent back on a cross-origin `fetch` (and is blocked outright by Safari's third-party-cookie policy even at `sameSite=none`), so the buyer flow cannot depend on the cookie alone the way `FR-AUTH-015`'s admin-flow session does.

### 2.2 Admin authentication (password + OTP)

- `FR-AUTH-009`: A registered admin submits email and password to `POST /api/auth/sign-in/email`. Correct credentials do **not** establish a session directly — they return a short-lived sign-in challenge and trigger `FR-AUTH-011`.
- `FR-AUTH-010`: An unknown email or an incorrect password returns the same generic invalid-credentials error either way, so a failed attempt never reveals whether the email itself is registered.
- `FR-AUTH-011`: A valid password challenge (`FR-AUTH-009`) causes a one-time code to be emailed to the account's registered address via Resend.
- `FR-AUTH-012`: The admin submits that code together with the challenge to `POST /api/auth/email-otp/verify`; a correct, unexpired, unused code establishes the session. An incorrect code, an expired code, and an already-used code each return distinct error codes (`FR-AUTH-045`).
- `FR-AUTH-013`: The admin OTP is single-use and expires 10 minutes after issuance, mirroring `FR-AUTH-007`'s buyer OTP behavior.
- `FR-AUTH-014`: Neither the password step (`FR-AUTH-009`) nor the OTP step (`FR-AUTH-012`) alone establishes a session — both must succeed in sequence within the challenge's validity window.
- `FR-AUTH-015`: A session is a database-backed record (Better Auth's session model) referenced by an `httpOnly`, `secure`, `sameSite=lax` cookie — never a client-readable or client-storable token. _`admin-app` deploys to a separate domain from `backend` (`docs/architecture.md` §7) — the same cross-domain constraint `FR-AUTH-046` documents for the buyer flow applies here too, and this requirement will need the identical bearer-token amendment when the admin sign-in issue is redone (see `FR-AUTH-046`)._
- `FR-AUTH-016`: A session has a fixed maximum lifetime (30 days) after which it expires and re-authentication is required; activity extends it on a rolling basis within that ceiling, per Better Auth's default behavior.
- `FR-AUTH-017`: An admin can sign out via `POST /api/auth/sign-out`, which invalidates the current session server-side and clears the session cookie — a captured cookie from an already-signed-out session is rejected on its next use, not merely ignored client-side.

### 2.3 Session bootstrap

- `FR-AUTH-018`: `GET /api/auth/session` returns the current authenticated user's public profile and role, or a 401 if unauthenticated. Both frontends call this once on load to bootstrap client-side auth state, regardless of which sign-in path (buyer or admin) established the session.

### 2.4 Admin password reset

- `FR-AUTH-019`: An admin can request a password reset via `POST /api/auth/forgot-password` with their email. The response is identical whether or not that email is registered, so the endpoint cannot be used to enumerate accounts. (Buyers have no password and therefore no use for this endpoint.)
- `FR-AUTH-020`: A request matching a registered admin email sends a time-limited, single-use reset link by email through Resend.
- `FR-AUTH-021`: A reset link expires one hour after issuance and is rejected once expired or once already used, even if the expiry window hasn't elapsed.
- `FR-AUTH-022`: Completing a reset via `POST /api/auth/reset-password` invalidates every one of that admin's existing sessions, forcing re-authentication (password + OTP) on every device.

### 2.5 Admin account provisioning

- `FR-AUTH-023`: None of the three buyer sign-in routes (`FR-AUTH-001`–`003`) can ever produce an account with a non-`buyer` role.
- `FR-AUTH-024`: The first `super-admin` account is created by a one-time seed script that reads its email, name, and password from environment variables and is run manually during initial deployment — there is no in-app bootstrap flow, matching the "solo/small team" premise in [`SRS.md`](../SRS.md) §1.3.
- `FR-AUTH-025`: A `super-admin` can create an admin account of any of the three roles via `POST /api/admin/users`, setting its email, name, role, and an initial temporary password.
- `FR-AUTH-026`: A `super-admin` can update an admin account's role, or deactivate it (`status: false`), via `PATCH /api/admin/users/:id`. A deactivated account can no longer sign in — even with a correct password and a correct OTP — and any session it currently holds is invalidated within the same request that performs the deactivation, not on next expiry.
- `FR-AUTH-027`: A `super-admin` can view a paginated, searchable list of admin accounts via `GET /api/admin/users`, showing name, email, role, status, and last-sign-in timestamp.
- `FR-AUTH-028`: An admin account can never deactivate or delete its own account, preventing a single-`super-admin` deployment from locking itself out by mistake.
- `FR-AUTH-029`: A newly created admin account's first sign-in goes through the identical password-then-OTP flow (`FR-AUTH-009`–`017`) — there is no first-login bypass of the OTP step.

### 2.6 Role-based access control

- `FR-AUTH-030`: The admin sign-in flow (`FR-AUTH-009`–`017`) is the sole path to a session whose `role` is not `buyer`; `admin-app` treats any session whose `role` is `buyer` as unauthenticated for its own purposes, enforced both client-side (route guard) and server-side (`FR-AUTH-032`) — the server check is authoritative.
- `FR-AUTH-031`: Every route under `/api/admin/*` requires a valid, non-expired session; a request with no session or an expired one is rejected `401` before any controller or service code runs.
- `FR-AUTH-032`: Every route under `/api/admin/*` additionally declares which role(s) may call it; a valid session whose role is not among them is rejected `403`, a distinct outcome from `FR-AUTH-031`'s `401`.
- `FR-AUTH-033`: Every existing catalog endpoint (products, categories, brands, `categorySpecifications`, `categoryVariants`, uploads) accepts `catalog-manager` and `super-admin`; `order-manager` is rejected `403` on all of them, since catalog management isn't that role's concern.
- `FR-AUTH-034`: The `X-Admin-Key` shared-secret middleware (`FR-CAT-088`–`090`) is removed outright and replaced by the `FR-AUTH-031`–`033` session-and-role guard, mounted at the identical router-level location — no catalog route path, controller, or service changes, fulfilling the swap `FR-CAT-090` committed to.
- `FR-AUTH-035`: Every catalog write endpoint now populates `createdBy` and `updatedBy` with the authenticated admin's user ID, replacing the always-`null` placeholder `FR-CAT-013` reserved for this version. No schema migration is needed — the fields already accept an `ObjectId`.

### 2.7 Buyer account profile

- `FR-AUTH-036`: A signed-in buyer can view their own profile — name, email, phone — via `GET /api/account/profile`.
- `FR-AUTH-037`: A signed-in buyer can update their name and phone via `PATCH /api/account/profile`. Changing email is out of scope for this version (§7); buyers have no password, so there is no buyer change-password capability (§7).

### 2.8 Admin account self-service

- `FR-AUTH-038`: A signed-in admin can change their own password via `POST /api/account/change-password`, supplying their current password; an incorrect current password is rejected without further detail, the same enumeration-safety posture as `FR-AUTH-010`.
- `FR-AUTH-039`: A successful password change invalidates every one of that admin's other existing sessions (every device but the one used to make the change) — the same session-hygiene rule as `FR-AUTH-022`.

### 2.9 Abuse mitigation

- `FR-AUTH-040`: `POST /api/auth/sign-in/email` and `POST /api/auth/email-otp/verify` are rate-limited per IP and per email using the existing Upstash Redis instance; a client exceeding the limit receives a `429` following the existing error contract.
- `FR-AUTH-041`: The admin OTP-request triggered by `FR-AUTH-011` is rate-limited per email, independent of `FR-AUTH-040`, capping how often a code can be resent to one address.
- `FR-AUTH-042`: `POST /api/auth/forgot-password` is rate-limited per email, independent of `FR-AUTH-040`–`041`, to prevent reset-email flooding against one admin address.
- `FR-AUTH-043`: The buyer email-OTP request (`FR-AUTH-003`'s `POST /api/auth/email-otp/send`) is rate-limited per email, independent of the admin limits above, to prevent email-bombing a buyer's address.
- `FR-AUTH-044`: The Google OAuth callback and One Tap verify endpoints (`FR-AUTH-001`–`002`) are rate-limited per IP to bound automated account-creation spam, distinct from the credential-stuffing concern the other limits address.

### 2.10 Error contract

- `FR-AUTH-045`: Every authentication and authorization error follows the existing `{ success: false, code, message }` contract, with `code` specific enough that a frontend can branch on at least: invalid credentials, account deactivated, session expired, insufficient role, OTP required, OTP invalid, OTP expired, and "this email belongs to an admin account" — without parsing `message` text.

## 3. Baseline Non-Functional Requirements

Feature-scoped only — see [`SRS.md`](../SRS.md) §4 item 3; the exhaustive system-wide security/session posture (full rate-limiting policy, `helmet`, CORS hardening) lands once in v0.8/v0.9 per [`docs/architecture.md`](../../architecture.md) §6. This feature is where the auth-specific touchpoints that can't wait until then belong.

**Validation**

- [ ] `email` and `password` on every admin auth endpoint, and the Google-credential/OTP-code shape on every buyer/OTP endpoint, are validated server-side with Zod before reaching Better Auth or the database — malformed input never reaches the credential layer.
- [ ] Role values accepted by `POST /api/admin/users` and `PATCH /api/admin/users/:id` are restricted to the four-value enum (`buyer`, `catalog-manager`, `order-manager`, `super-admin`); an unrecognized value is rejected, not coerced.

**Indexes**

- [ ] `users`: unique index on `email` — the one index this feature's data model actually adds; Better Auth's own session/account/verification collections carry their adapter's default indexes.

**Session and cookie security**

- [ ] Session cookies are `httpOnly`, `secure` (production), and `sameSite=lax` from the moment sign-in is implemented — not deferred, unlike the exhaustive cookie-attribute audit v0.8 owns (`FR-AUTH-015`). _Amended, Issue #139 redo: for the buyer flow specifically, the cookie is additionally paired with a bearer token (`FR-AUTH-046`) — cross-domain `buyer-app`/`backend` deployment (`docs/architecture.md` §7) means the cookie alone cannot be relied on for an authenticated request to actually reach the backend with the session attached._
- [ ] Passwords and OTP codes are never logged, including inside error-handling and request-logging middleware — a login failure logs the attempted email, never the attempted password or OTP code.
- [ ] Deactivating an admin account invalidates its live session synchronously within the same request (`FR-AUTH-026`), not via a background job or on next token refresh.

**Error handling and operations**

- [ ] Every endpoint in this feature follows `{ success: false, code, message }`, per [`docs/architecture.md`](../../architecture.md) §6 — no ad-hoc error shape.
- [ ] The `X-Admin-Key` removal (`FR-AUTH-034`) ships as one PR that also removes `adminAuth.ts` and its env var, so no dead code or unused secret lingers.

**Security**

- [ ] Admin sign-in and OTP verification are rate-limited (`FR-AUTH-040`–`041`) before this feature ships, not as a v0.8 follow-up — credential-stuffing exposure starts the moment these endpoints exist.
- [ ] The admin password-reset-request endpoint (`FR-AUTH-042`) and the buyer email-OTP-request endpoint (`FR-AUTH-043`) are each rate-limited independently.
- [ ] No secrets committed — Better Auth's session secret, Resend's API key, and the Google OAuth client secret are sourced from environment variables, following the existing `.env.example` pattern.

## 4. User Stories

- As a **guest**, I want to sign in with my Google account without creating a new password to remember, so that I can check out and see my order history later.
- As a **guest**, I want to sign in with just my email and a one-time code if I'd rather not use Google, so that I still have a fast, no-password option.
- As a **registered buyer**, I want to update my profile, so that I can keep my account current.
- As a **super admin**, I want to create accounts for catalog managers and order managers, so that my team can work in the console without sharing one login.
- As a **super admin**, I want to deactivate an admin account immediately, so that a departing team member loses access right away, not at next login.
- As a **catalog manager**, I want my own admin session instead of a shared secret pasted into every request, so that catalog changes are properly attributed to me (`FR-AUTH-035`).
- As a **catalog manager**, I want a one-time code required after my password on every sign-in, so that a stolen password alone can't get into the console.
- As an **order manager**, I want to be blocked from catalog-management endpoints I have no business touching, so that the role boundaries in `SRS.md` §2.3 are actually enforced, not just documented.

## 5. Data Model / API Contract

### `users`

Per [`docs/architecture.md`](../../architecture.md) §5: one collection for both buyer and admin accounts, `role` carrying the distinction. Better Auth's MongoDB adapter additionally provisions its own `session`, `account`, and `verification` collections — implementation detail of the adapter, not modeled by hand here. In this version, `account` holds an admin's hashed password credential _or_ a buyer's Google provider linkage (`providerId`/`accountId`), and `verification` actively holds in-flight email-OTP state for both apps (no longer unused, unlike the prior draft).

| Field                     | Type                                                               | Notes                                                   |
| ------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------- |
| `_id`                     | ObjectId                                                           |                                                         |
| `name`                    | string, required                                                   |                                                         |
| `email`                   | string, required, unique                                           | identity key across all sign-in methods — `FR-AUTH-005` |
| `role`                    | enum `buyer` / `catalog-manager` / `order-manager` / `super-admin` | default `buyer` — `FR-AUTH-004`                         |
| `status`                  | boolean, default `true`                                            | admin-only meaning; deactivation — `FR-AUTH-026`        |
| `phone`                   | string, optional                                                   | buyer profile — `FR-AUTH-037`                           |
| `lastSignInAt`            | date, optional                                                     | `FR-AUTH-027`                                           |
| `createdAt` / `updatedAt` | timestamps                                                         |                                                         |

### Response envelope

Unchanged from v0.2 (`FR-CAT-093`–`095`); shown here for the flows this version adds.

```jsonc
// GET /api/auth/session — authenticated (either role)
{
  "success": true,
  "data": {
    "id": "66b1a2c3d4e5f6a7b8c9d0e1",
    "name": "Asha Rao",
    "email": "asha@example.com",
    "role": "buyer"
  }
}

// GET /api/auth/session — unauthenticated
{ "success": false, "code": "UNAUTHENTICATED", "message": "No active session." }

// POST /api/auth/sign-in/email — correct password, OTP now required
{
  "success": true,
  "data": { "challenge": "8f1c2e...", "expiresInSeconds": 600 },
  "code": "OTP_REQUIRED"
}

// POST /api/auth/email-otp/verify — wrong or expired code
{ "success": false, "code": "OTP_INVALID", "message": "Incorrect or expired code." }

// Google sign-in resolving to an existing admin account
{ "success": false, "code": "GOOGLE_ACCOUNT_IS_ADMIN", "message": "This email belongs to an admin account. Sign in from the admin console instead." }

// an order-manager calling a catalog endpoint
{ "success": false, "code": "FORBIDDEN_ROLE", "message": "This action requires the catalog-manager or super-admin role." }
```

## 6. UI/UX Requirements

**`buyer-app`**

- **Sign in**: one combined surface offering a "Continue with Google" button (with an auto-triggered One Tap prompt on page load) and an email-OTP path (email-entry field, then an OTP-entry step with a resend-with-cooldown control and an expired/invalid-code error state); no password field anywhere.
- **Account profile**: name/phone edit form with its own success/error state; no change-password screen, since buyers have no password.
- **Header/nav**: a signed-out state (sign in entry point) versus a signed-in state (account menu, sign out), driven by `GET /api/auth/session` on load.

**`admin-app`**

- **Sign in**: two screens in sequence — an email/password form, then (on success) an OTP-entry screen (code input, resend-with-cooldown, expired/invalid-code error state) before reaching the console; no sign-up link anywhere in the app (`FR-AUTH-023`); `INVALID_CREDENTIALS`, `OTP_INVALID`/`OTP_EXPIRED`, and `ACCOUNT_DEACTIVATED` each render distinct messages.
- **Route guard**: every route redirects to sign-in on a `401`/no session, and to a "you don't have access" state on a `403` from `FR-AUTH-032` — distinguishing the two per `FR-AUTH-045`'s code granularity, not one generic "access denied" screen.
- **Account self-service**: a signed-in admin's own change-password form, with its own success/error state (`FR-AUTH-038`–`039`).
- **Admin user management** (`super-admin` only, hidden entirely from the nav for other roles): a list (name, email, role, status, last sign-in), a create form, and role/deactivate controls; a `super-admin` never sees a delete/deactivate control on their own row (`FR-AUTH-028`).

## 7. Out of Scope

- **Buyer traditional email/password authentication** — replaced entirely by Google OAuth, Google One Tap, and passwordless email-OTP (§2.1); buyers never have a stored password in this version.
- **Non-Google OAuth providers** (Facebook, Apple, etc.) — Google only in this version; Better Auth supports adding providers later without a schema change to `users`.
- **Device-trust / "remember this device" OTP skip** — the admin OTP step is required on every sign-in, with no exception window or trusted-device state.
- **Configurable/optional two-factor authentication** — the admin OTP step is mandatory-by-design, not an opt-in 2FA feature; TOTP authenticator apps, SMS OTP, and any buyer-side 2FA all remain excluded.
- **Buyer email address changes** — deferred; changing the account's primary identifier interacts with in-flight OTP/session state and deserves its own design pass rather than a rushed addition here.
- **Buyer address book / multiple shipping addresses** — this is checkout territory, specified as part of Orders (v0.5), not account/profile territory.
- **CAPTCHA or other bot-detection beyond rate limiting** (`FR-AUTH-040`–`044`).
- **Buyer self-service account deletion.**
- **Admin self-service password reset without email access** — an admin who has lost both their password and their email access is a manual, out-of-band `super-admin` operation, not a product feature.
- **Full system-wide security hardening** (exhaustive rate-limit policy across all routes, `helmet`, CSRF strategy beyond `sameSite`) — owned by v0.8, per [`docs/architecture.md`](../../architecture.md) §6; this version ships only the auth-specific baseline in §3.

## 8. Acceptance Criteria

**Buyer sign-in**

- [ ] A guest can sign in with Google OAuth and is immediately signed in, receiving `role: "buyer"`. Repeating with the same Google account reuses the same account, not a duplicate. — `FR-AUTH-001`, `FR-AUTH-004`, `FR-AUTH-005`
- [ ] A guest can sign in with Google One Tap, with identical account-creation/reuse behavior to the OAuth path. — `FR-AUTH-002`, `FR-AUTH-004`, `FR-AUTH-005`
- [ ] A guest can sign in with email + OTP; requesting a code, then verifying it, establishes a session and creates the account on first use. — `FR-AUTH-003`, `FR-AUTH-004`
- [ ] A buyer OTP is rejected once expired (10 minutes) and rejected on reuse even inside that window. — `FR-AUTH-007`
- [ ] Signing in via a second buyer method (e.g. email-OTP after previously using Google) with the same email resolves to the original account. — `FR-AUTH-005`
- [ ] A Google or email-OTP sign-in attempt for an email already registered as an admin is rejected with `GOOGLE_ACCOUNT_IS_ADMIN`/equivalent, not silently allowed. — `FR-AUTH-006`

**Admin sign-in**

- [ ] Submitting a correct admin email/password returns an `OTP_REQUIRED` challenge, not a session. — `FR-AUTH-009`
- [ ] An incorrect password and an unregistered email both return the identical `INVALID_CREDENTIALS` error. — `FR-AUTH-010`
- [ ] Submitting the correct OTP against a valid challenge establishes a session; submitting an incorrect, expired, or already-used OTP is rejected with a distinct code and no session is created. — `FR-AUTH-012`, `FR-AUTH-013`
- [ ] Neither the password step alone nor the OTP step alone establishes a session. — `FR-AUTH-014`
- [ ] The session cookie is `httpOnly`, and `secure`+`sameSite=lax` in a production-like config. — `FR-AUTH-015`
- [ ] `GET /api/auth/session` returns the signed-in user's profile when authenticated (buyer or admin) and a 401 otherwise. — `FR-AUTH-018`
- [ ] Signing out invalidates the session server-side; replaying the old cookie after sign-out is rejected. — `FR-AUTH-017`

**Admin password reset**

- [ ] Requesting a reset for a registered and an unregistered admin email both return the same response shape. — `FR-AUTH-019`
- [ ] A registered admin email receives a reset link by email; completing the reset with a valid token changes the password and invalidates all existing sessions for that admin. — `FR-AUTH-020`, `FR-AUTH-022`
- [ ] A reset link is rejected after one hour, and rejected on a second use even inside that window. — `FR-AUTH-021`

**Admin provisioning and RBAC**

- [ ] None of the three buyer sign-in routes can ever produce an account with a non-`buyer` role, regardless of request shape. — `FR-AUTH-023`
- [ ] The seed script creates a working `super-admin` account from environment variables on a fresh database. — `FR-AUTH-024`
- [ ] A `super-admin` can create a `catalog-manager` and an `order-manager` account, each able to sign in immediately through the same password+OTP flow. — `FR-AUTH-025`, `FR-AUTH-029`
- [ ] Deactivating an admin account immediately invalidates its live session — a request made with that session's cookie fails on the very next call, not after expiry. — `FR-AUTH-026`
- [ ] A `super-admin` cannot deactivate or delete their own account; the attempt is rejected. — `FR-AUTH-028`
- [ ] Every `/api/admin/*` route rejects an unauthenticated request with 401 and an authenticated-but-wrong-role request with 403, verified as two distinct outcomes. — `FR-AUTH-031`, `FR-AUTH-032`
- [ ] A `catalog-manager` and a `super-admin` can both call every existing catalog endpoint; an `order-manager` is rejected 403 on all of them. — `FR-AUTH-033`
- [ ] `X-Admin-Key` no longer exists anywhere in `backend` — the env var, the middleware, and every reference to it are gone, and every catalog route/controller/service is byte-for-byte unchanged apart from the guard it's mounted behind. — `FR-AUTH-034`
- [ ] A product created by a signed-in `catalog-manager` stores that admin's real user ID in `createdBy`, not `null`. — `FR-AUTH-035`

**Buyer profile and admin self-service**

- [ ] A signed-in buyer can view and update their name/phone; an unauthenticated request to either endpoint is rejected 401. — `FR-AUTH-036`, `FR-AUTH-037`
- [ ] An admin changing their password with the correct current password succeeds and invalidates every other session for that admin, leaving the current one intact; an incorrect current password is rejected without extra detail. — `FR-AUTH-038`, `FR-AUTH-039`

**Abuse mitigation and error contract**

- [ ] Exceeding the admin sign-in/OTP-verify rate limit from one IP or for one email returns 429. — `FR-AUTH-040`
- [ ] Exceeding the admin OTP-resend limit for one email returns 429 without sending an additional code, independent of the sign-in limit. — `FR-AUTH-041`
- [ ] Exceeding the admin forgot-password rate limit for one email returns 429 without sending an additional reset email. — `FR-AUTH-042`
- [ ] Exceeding the buyer email-OTP-request rate limit for one email returns 429 without sending an additional code. — `FR-AUTH-043`
- [ ] Every error in this feature matches `{ success: false, code, message }`, and `INVALID_CREDENTIALS`, `ACCOUNT_DEACTIVATED`, `UNAUTHENTICATED`, `FORBIDDEN_ROLE`, `OTP_REQUIRED`, `OTP_INVALID`, `OTP_EXPIRED`, and the admin-email-on-buyer-route error are each distinguishable by `code` alone. — `FR-AUTH-045`

## 9. Dependencies

- **Better Auth** — session, credential storage, and cookie management; MongoDB adapter provisions its own collections alongside `users`. Configured with a Google OAuth/One Tap provider (buyer) and an email-OTP plugin (both apps) — the exact plugin/version is confirmed at implementation time (see §5's note). Chosen per [`docs/architecture.md`](../../architecture.md) §9 over Auth.js/Clerk specifically for built-in RBAC support.
- **Google Cloud (OAuth client + Identity Services)** — a Google OAuth 2.0 client (Client ID/Secret) for `FR-AUTH-001`, and the Google Identity Services browser library for the One Tap prompt (`FR-AUTH-002`). New dependency introduced by this version.
- **Resend** — sends three kinds of email: admin password-reset links (`FR-AUTH-020`), admin sign-in OTP codes (`FR-AUTH-011`), and buyer sign-in OTP codes (`FR-AUTH-003`) — the first feature to actually send email, ahead of Orders' (v0.5) transactional emails reusing the same client.
- **Upstash Redis** — admin sign-in/OTP-verify, admin OTP-resend, admin forgot-password, buyer OTP-request, and OAuth-callback rate limiting (`FR-AUTH-040`–`044`); the same instance `docs/architecture.md` §5 already designates for caching/queues.
- **Product Catalog (SRS v0.2)** — this version removes `FR-CAT-088`–`090`'s `X-Admin-Key` guard outright and backfills `FR-CAT-013`'s reserved `createdBy`/`updatedBy` fields; both are two-way dependencies, not just this feature depending on catalog.

## 10. Open Questions

_None open — see "Resolved during drafting" below._

### Resolved during drafting

- **One `users` collection vs. separate buyer/admin collections** — one collection with a `role` enum, matching `docs/architecture.md` §5's data map and keeping a single identity/session model for Better Auth to manage, rather than duplicating auth plumbing per app.
- **Whether admin sign-in needs its own endpoint(s)** — yes, split from the buyer flow: buyer sign-in is single-call (OAuth/One Tap/OTP-verify), admin sign-in is a two-call password-then-OTP flow, since one shared shape no longer fits both once admin OTP became mandatory (`FR-AUTH-030`).
- **Whether buyers keep a traditional password alongside Google** — no; buyer email/password was replaced outright by Google OAuth, Google One Tap, and passwordless email-OTP, so buyers never have a stored password in this version.
- **Whether the admin OTP step applies to every sign-in or only new/untrusted devices** — every sign-in, with no device-trust exception, to keep the admin console's security posture simple and unconditional for a small-team deployment.
- **Whether buyer address/contact details belong in this version** — no; kept deferred to Orders (v0.5) checkout, consistent with the address-book exclusion already in §7.
