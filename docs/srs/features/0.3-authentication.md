# SRS v0.3 — Authentication

**Status:** Draft — awaiting review
**Last Updated:** 2026-08-20
**Depends on:** Better Auth (MongoDB adapter), Resend (reset emails), Upstash Redis (rate limiting). Replaces Product Catalog's temporary `X-Admin-Key` shared-secret guard (`FR-CAT-088`–`090`) outright.

---

## 1. Feature Overview

Authentication gives the system its first real identity: buyers who register and sign in to place orders, and admins — `catalog-manager`, `order-manager`, `super-admin` — who sign in to a session-and-role-gated console instead of pasting a shared secret into every request. It replaces Product Catalog's `X-Admin-Key` guard exactly the way `FR-CAT-090` promised: a single middleware swap, no change to any catalog route path, controller, or service.

One `users` collection serves both apps — `role` is what separates a buyer from an admin, and which of the three admin roles an admin holds — per [`SRS.md`](../SRS.md) §2.3's User Classes and [`docs/architecture.md`](../../architecture.md) §5's data map. Every later feature depends on the identity this version establishes: Cart (v0.4) attaches a guest cart to a signed-in buyer, Orders (v0.5) records who placed an order, Payments (v0.6) and Dashboard (v0.7) both need a real `order-manager`/`super-admin` boundary that doesn't exist yet. Catalog writes have carried a reserved, always-`null` `createdBy`/`updatedBy` since v0.2 (`FR-CAT-013`) specifically so this version could populate them with no migration.

Scope is deliberately narrow: email/password only, no social login, no email-verification gate on sign-up, no buyer address book (that belongs to Orders' checkout flow, v0.5) — see §7.

## 2. Functional Requirements

### 2.1 Buyer registration

- `FR-AUTH-001`: A guest can register a buyer account with name, email, and password via `POST /api/auth/sign-up/email`.
- `FR-AUTH-002`: Email is required, must be a well-formed address, and is unique across every user regardless of role — a sign-up with an already-registered email is rejected with a specific, non-500 error.
- `FR-AUTH-003`: Password must be at least 8 characters. Better Auth's email/password provider hashes and stores it; the backend never logs or stores a plaintext password anywhere, including error messages.
- `FR-AUTH-004`: A successful sign-up immediately establishes an authenticated session — there is no email-verification gate blocking access (§7) — and returns the created user's public profile (`id`, `name`, `email`, `role`).
- `FR-AUTH-005`: `role` on sign-up is always `buyer`; a client-supplied `role` field on the sign-up request is ignored, never trusted.

### 2.2 Sign-in and session

- `FR-AUTH-006`: A registered user — buyer or admin — can sign in with email and password via `POST /api/auth/sign-in/email`, establishing a session on success. One endpoint serves both apps; `role` on the resulting session, not a separate endpoint, is what distinguishes an admin from a buyer (`FR-AUTH-022`).
- `FR-AUTH-007`: A sign-in with an unknown email or an incorrect password returns the same generic invalid-credentials error either way, so a failed attempt never reveals whether the email itself is registered.
- `FR-AUTH-008`: A session is a database-backed record (Better Auth's session model) referenced by an `httpOnly`, `secure`, `sameSite=lax` cookie — never a client-readable or client-storable token.
- `FR-AUTH-009`: `GET /api/auth/session` returns the current authenticated user's public profile and role, or a 401 if unauthenticated. Both frontends call this once on load to bootstrap client-side auth state.
- `FR-AUTH-010`: A session has a fixed maximum lifetime (30 days) after which it expires and re-authentication is required; activity extends it on a rolling basis within that ceiling, per Better Auth's default behavior.
- `FR-AUTH-011`: A user can sign out via `POST /api/auth/sign-out`, which invalidates the current session server-side and clears the session cookie — a captured cookie from an already-signed-out session is rejected on its next use, not merely ignored client-side.

### 2.3 Password reset

- `FR-AUTH-012`: A user can request a password reset via `POST /api/auth/forgot-password` with their email. The response is identical whether or not that email is registered, so the endpoint cannot be used to enumerate accounts.
- `FR-AUTH-013`: A request matching a registered email sends a time-limited, single-use reset link by email through Resend.
- `FR-AUTH-014`: A reset link expires one hour after issuance and is rejected once expired or once already used, even if the expiry window hasn't elapsed.
- `FR-AUTH-015`: Completing a reset via `POST /api/auth/reset-password` invalidates every one of that user's existing sessions, forcing re-authentication on every device.

### 2.4 Admin account provisioning

- `FR-AUTH-016`: The public sign-up endpoint (`FR-AUTH-001`) always creates a `buyer`; none of the three admin roles can be self-registered through it.
- `FR-AUTH-017`: The first `super-admin` account is created by a one-time seed script that reads its email, name, and password from environment variables and is run manually during initial deployment — there is no in-app bootstrap flow, matching the "solo/small team" premise in [`SRS.md`](../SRS.md) §1.3.
- `FR-AUTH-018`: A `super-admin` can create an admin account of any of the three roles via `POST /api/admin/users`, setting its email, name, role, and an initial temporary password.
- `FR-AUTH-019`: A `super-admin` can update an admin account's role, or deactivate it (`status: false`), via `PATCH /api/admin/users/:id`. A deactivated account can no longer sign in — even with a correct password — and any session it currently holds is invalidated within the same request that performs the deactivation, not on next expiry.
- `FR-AUTH-020`: A `super-admin` can view a paginated, searchable list of admin accounts via `GET /api/admin/users`, showing name, email, role, status, and last-sign-in timestamp.
- `FR-AUTH-021`: An admin account can never deactivate or delete its own account, preventing a single-`super-admin` deployment from locking itself out by mistake.

### 2.5 Role-based access control

- `FR-AUTH-022`: Admin sign-in reuses `FR-AUTH-006`'s single endpoint; `admin-app` treats a successfully authenticated session whose `role` is `buyer` as unauthenticated for its own purposes, enforced both client-side (route guard) and server-side (`FR-AUTH-024`) — the server check is authoritative.
- `FR-AUTH-023`: Every route under `/api/admin/*` requires a valid, non-expired session; a request with no session or an expired one is rejected `401` before any controller or service code runs.
- `FR-AUTH-024`: Every route under `/api/admin/*` additionally declares which role(s) may call it; a valid session whose role is not among them is rejected `403`, a distinct outcome from `FR-AUTH-023`'s `401`.
- `FR-AUTH-025`: Every existing catalog endpoint (products, categories, brands, `categorySpecifications`, `categoryVariants`, uploads) accepts `catalog-manager` and `super-admin`; `order-manager` is rejected `403` on all of them, since catalog management isn't that role's concern.
- `FR-AUTH-026`: The `X-Admin-Key` shared-secret middleware (`FR-CAT-088`–`090`) is removed outright and replaced by the `FR-AUTH-023`–`025` session-and-role guard, mounted at the identical router-level location — no catalog route path, controller, or service changes, fulfilling the swap `FR-CAT-090` committed to.
- `FR-AUTH-027`: Every catalog write endpoint now populates `createdBy` and `updatedBy` with the authenticated admin's user ID, replacing the always-`null` placeholder `FR-CAT-013` reserved for this version. No schema migration is needed — the fields already accept an `ObjectId`.

### 2.6 Buyer account profile

- `FR-AUTH-028`: A signed-in buyer can view their own profile — name, email, phone — via `GET /api/account/profile`.
- `FR-AUTH-029`: A signed-in buyer can update their name and phone via `PATCH /api/account/profile`. Changing email is out of scope for this version (§7).
- `FR-AUTH-030`: A signed-in buyer can change their password via `POST /api/account/change-password`, supplying their current password; an incorrect current password is rejected without further detail, the same enumeration-safety posture as `FR-AUTH-007`.
- `FR-AUTH-031`: A successful authenticated password change invalidates every one of that user's other existing sessions (every device but the one used to make the change) — the same session-hygiene rule as `FR-AUTH-015`.

### 2.7 Abuse mitigation

- `FR-AUTH-032`: `POST /api/auth/sign-in/email` and `POST /api/auth/sign-up/email` are rate-limited per IP and per email using the existing Upstash Redis instance; a client exceeding the limit receives a `429` following the existing error contract.
- `FR-AUTH-033`: `POST /api/auth/forgot-password` is rate-limited per email, independent of `FR-AUTH-032`, to prevent reset-email flooding against one address.

### 2.8 Error contract

- `FR-AUTH-034`: Every authentication and authorization error follows the existing `{ success: false, code, message }` contract, with `code` specific enough that a frontend can branch on "invalid credentials," "account deactivated," "session expired," and "insufficient role" without parsing `message` text.

## 3. Baseline Non-Functional Requirements

Feature-scoped only — see [`SRS.md`](../SRS.md) §4 item 3; the exhaustive system-wide security/session posture (full rate-limiting policy, `helmet`, CORS hardening) lands once in v0.8/v0.9 per [`docs/architecture.md`](../../architecture.md) §6. This feature is where the auth-specific touchpoints that can't wait until then belong.

**Validation**

- [ ] `email` and `password` on every auth endpoint are validated server-side with Zod before reaching Better Auth or the database — malformed input never reaches the credential layer.
- [ ] Role values accepted by `POST /api/admin/users` and `PATCH /api/admin/users/:id` are restricted to the four-value enum (`buyer`, `catalog-manager`, `order-manager`, `super-admin`); an unrecognized value is rejected, not coerced.

**Indexes**

- [ ] `users`: unique index on `email` — the one index this feature's data model actually adds; Better Auth's own session/account/verification collections carry their adapter's default indexes.

**Session and cookie security**

- [ ] Session cookies are `httpOnly`, `secure` (production), and `sameSite=lax` from the moment sign-in is implemented — not deferred, unlike the exhaustive cookie-attribute audit v0.8 owns (`FR-AUTH-008`).
- [ ] Passwords are never logged, including inside error-handling and request-logging middleware — a login failure logs the attempted email, never the attempted password.
- [ ] Deactivating an admin account invalidates its live session synchronously within the same request (`FR-AUTH-019`), not via a background job or on next token refresh.

**Error handling and operations**

- [ ] Every endpoint in this feature follows `{ success: false, code, message }`, per [`docs/architecture.md`](../../architecture.md) §6 — no ad-hoc error shape.
- [ ] The `X-Admin-Key` removal (`FR-AUTH-026`) ships as one PR that also removes `adminAuth.ts` and its env var, so no dead code or unused secret lingers.

**Security**

- [ ] Sign-in and sign-up are rate-limited (`FR-AUTH-032`) before this feature ships, not as a v0.8 follow-up — credential-stuffing exposure starts the moment these endpoints exist.
- [ ] The password-reset-request endpoint is rate-limited independently (`FR-AUTH-033`).
- [ ] No secrets committed — Better Auth's session secret and Resend's API key are sourced from environment variables, following the existing `.env.example` pattern.

## 4. User Stories

- As a **guest**, I want to create an account with my email and password, so that I can check out and see my order history later.
- As a **guest**, I want to sign in with an account I already have, so that I don't re-enter my details on every visit.
- As a **registered buyer**, I want to reset my password if I forget it, so that I'm not permanently locked out of my account.
- As a **registered buyer**, I want to update my profile and change my password, so that I can keep my account current and secure.
- As a **super admin**, I want to create accounts for catalog managers and order managers, so that my team can work in the console without sharing one login.
- As a **super admin**, I want to deactivate an admin account immediately, so that a departing team member loses access right away, not at next login.
- As a **catalog manager**, I want my own admin session instead of a shared secret pasted into every request, so that catalog changes are properly attributed to me (`FR-AUTH-027`).
- As an **order manager**, I want to be blocked from catalog-management endpoints I have no business touching, so that the role boundaries in `SRS.md` §2.3 are actually enforced, not just documented.

## 5. Data Model / API Contract

### `users`

Per [`docs/architecture.md`](../../architecture.md) §5: one collection for both buyer and admin accounts, `role` carrying the distinction. Better Auth's MongoDB adapter additionally provisions its own `session`, `account`, and `verification` collections to hold session records, the hashed email/password credential, and (unused in this version, per §7) verification tokens — implementation detail of the adapter, not modeled by hand here.

| Field                     | Type                                                                     | Notes                                          |
| ------------------------- | ------------------------------------------------------------------------- | ----------------------------------------------- |
| `_id`                     | ObjectId                                                                 |                                                 |
| `name`                    | string, required                                                        |                                                 |
| `email`                   | string, required, unique                                                | `FR-AUTH-002`                                   |
| `role`                    | enum `buyer` / `catalog-manager` / `order-manager` / `super-admin`      | default `buyer` — `FR-AUTH-005`                 |
| `status`                  | boolean, default `true`                                                 | admin-only meaning; deactivation — `FR-AUTH-019` |
| `phone`                   | string, optional                                                        | buyer profile — `FR-AUTH-029`                   |
| `lastSignInAt`            | date, optional                                                          | `FR-AUTH-020`                                   |
| `createdAt` / `updatedAt` | timestamps                                                               |                                                 |

### API endpoints

| Method | Path                          | Auth                       | Purpose                                                       |
| ------ | ----------------------------- | --------------------------- | --------------------------------------------------------------- |
| POST   | `/api/auth/sign-up/email`     | public                     | Buyer registration — `FR-AUTH-001`–`005`                       |
| POST   | `/api/auth/sign-in/email`     | public                     | Sign in, buyer or admin — `FR-AUTH-006`–`008`                  |
| GET    | `/api/auth/session`           | session (optional)        | Bootstrap current session — `FR-AUTH-009`                      |
| POST   | `/api/auth/sign-out`          | session                   | Invalidate current session — `FR-AUTH-011`                     |
| POST   | `/api/auth/forgot-password`   | public                     | Request reset email — `FR-AUTH-012`–`013`                      |
| POST   | `/api/auth/reset-password`    | public (valid reset token) | Complete reset — `FR-AUTH-014`–`015`                            |
| GET    | `/api/account/profile`        | session (buyer)            | View own profile — `FR-AUTH-028`                                |
| PATCH  | `/api/account/profile`        | session (buyer)            | Update name/phone — `FR-AUTH-029`                               |
| POST   | `/api/account/change-password`| session (buyer)            | Change password — `FR-AUTH-030`–`031`                           |
| GET    | `/api/admin/users`            | session (`super-admin`)    | Paginated, searchable admin list — `FR-AUTH-020`                |
| POST   | `/api/admin/users`            | session (`super-admin`)    | Create an admin account — `FR-AUTH-018`                         |
| PATCH  | `/api/admin/users/:id`        | session (`super-admin`)    | Update role or deactivate — `FR-AUTH-019`, `FR-AUTH-021`        |

### Response envelope

Unchanged from v0.2 (`FR-CAT-093`–`095`); shown here for the session bootstrap call both frontends make on load.

```jsonc
// GET /api/auth/session — authenticated
{
  "success": true,
  "data": {
    "id": "66b1a2c3d4e5f6a7b8c9d0e1",
    "name": "Asha Rao",
    "email": "asha@example.com",
    "role": "buyer"
  }
}

// GET /api/auth/session — unauthenticated
{ "success": false, "code": "UNAUTHENTICATED", "message": "No active session." }

// POST /api/auth/sign-in/email — wrong password or unknown email, identically
{ "success": false, "code": "INVALID_CREDENTIALS", "message": "Incorrect email or password." }

// an order-manager calling a catalog endpoint
{ "success": false, "code": "FORBIDDEN_ROLE", "message": "This action requires the catalog-manager or super-admin role." }
```

## 6. UI/UX Requirements

**`buyer-app`**

- **Sign up / Sign in**: two forms (or one with a mode toggle) per the mock, client-side validation mirroring the backend's Zod rules, an inline error for `INVALID_CREDENTIALS`/`EMAIL_ALREADY_REGISTERED`, a link between the two and to forgot-password.
- **Forgot / reset password**: an email-entry form showing the same confirmation regardless of whether the email exists (`FR-AUTH-012`); a token-driven reset form reached from the emailed link, with an expired/used-link error state.
- **Account profile**: name/phone edit form and a separate change-password form, each with its own success/error state; a session-refresh prompt is not needed since `FR-AUTH-031` only invalidates *other* sessions.
- **Header/nav**: a signed-out state (sign in / sign up links) versus a signed-in state (account menu, sign out), driven by `GET /api/auth/session` on load.

**`admin-app`**

- **Sign in**: a single form, no sign-up link anywhere in the app (`FR-AUTH-016`); `INVALID_CREDENTIALS` and `ACCOUNT_DEACTIVATED` render distinct messages.
- **Route guard**: every route redirects to sign-in on a `401`/no session, and to a "you don't have access" state on a `403` from `FR-AUTH-024` — distinguishing the two per `FR-AUTH-034`'s code granularity, not one generic "access denied" screen.
- **Admin user management** (`super-admin` only, hidden entirely from the nav for other roles): a list (name, email, role, status, last sign-in), a create form, and role/deactivate controls; a `super-admin` never sees a delete/deactivate control on their own row (`FR-AUTH-021`).

## 7. Out of Scope

- **Social/OAuth login** (Google, etc.) — email/password only in this version; Better Auth supports adding providers later without a schema change to `users`.
- **Email verification gate on sign-up** — an account is usable immediately (`FR-AUTH-004`); revisit if unverified accounts become a support or abuse burden.
- **Buyer email address changes** — deferred; changing the account's primary identifier interacts with in-flight password resets and deserves its own design pass rather than a rushed addition here.
- **Buyer address book / multiple shipping addresses** — this is checkout territory, specified as part of Orders (v0.5), not account/profile territory.
- **Two-factor authentication.**
- **CAPTCHA or other bot-detection beyond rate limiting** (`FR-AUTH-032`–`033`).
- **Buyer self-service account deletion.**
- **Admin self-service password reset without email access** — an admin who has lost both their password and their email access is a manual, out-of-band `super-admin` operation, not a product feature.
- **Full system-wide security hardening** (exhaustive rate-limit policy across all routes, `helmet`, CSRF strategy beyond `sameSite`) — owned by v0.8, per [`docs/architecture.md`](../../architecture.md) §6; this version ships only the auth-specific baseline in §3.

## 8. Acceptance Criteria

**Buyer registration and sign-in**

- [ ] A guest can register with a valid name/email/password and is immediately signed in, receiving `role: "buyer"`. — `FR-AUTH-001`, `FR-AUTH-004`, `FR-AUTH-005`
- [ ] Registering with an already-registered email is rejected with a specific error, not a 500. — `FR-AUTH-002`
- [ ] A password under 8 characters is rejected at sign-up. — `FR-AUTH-003`
- [ ] Signing in with a correct email/password establishes a session; an incorrect password and an unregistered email both return the identical `INVALID_CREDENTIALS` error. — `FR-AUTH-006`, `FR-AUTH-007`
- [ ] The session cookie is `httpOnly`, and `secure`+`sameSite=lax` in a production-like config. — `FR-AUTH-008`
- [ ] `GET /api/auth/session` returns the signed-in user's profile when authenticated and a 401 otherwise. — `FR-AUTH-009`
- [ ] Signing out invalidates the session server-side; replaying the old cookie after sign-out is rejected. — `FR-AUTH-011`

**Password reset**

- [ ] Requesting a reset for a registered and an unregistered email both return the same response shape. — `FR-AUTH-012`
- [ ] A registered email receives a reset link by email; completing the reset with a valid token changes the password and invalidates all existing sessions for that user. — `FR-AUTH-013`, `FR-AUTH-015`
- [ ] A reset link is rejected after one hour, and rejected on a second use even inside that window. — `FR-AUTH-014`

**Admin provisioning and RBAC**

- [ ] The public sign-up endpoint never produces an account with a non-`buyer` role, regardless of request body. — `FR-AUTH-016`
- [ ] The seed script creates a working `super-admin` account from environment variables on a fresh database. — `FR-AUTH-017`
- [ ] A `super-admin` can create a `catalog-manager` and an `order-manager` account, each able to sign in immediately. — `FR-AUTH-018`
- [ ] Deactivating an admin account immediately invalidates its live session — a request made with that session's cookie fails on the very next call, not after expiry. — `FR-AUTH-019`
- [ ] A `super-admin` cannot deactivate or delete their own account; the attempt is rejected. — `FR-AUTH-021`
- [ ] Every `/api/admin/*` route rejects an unauthenticated request with 401 and an authenticated-but-wrong-role request with 403, verified as two distinct outcomes. — `FR-AUTH-023`, `FR-AUTH-024`
- [ ] A `catalog-manager` and a `super-admin` can both call every existing catalog endpoint; an `order-manager` is rejected 403 on all of them. — `FR-AUTH-025`
- [ ] `X-Admin-Key` no longer exists anywhere in `backend` — the env var, the middleware, and every reference to it are gone, and every catalog route/controller/service is byte-for-byte unchanged apart from the guard it's mounted behind. — `FR-AUTH-026`
- [ ] A product created by a signed-in `catalog-manager` stores that admin's real user ID in `createdBy`, not `null`. — `FR-AUTH-027`

**Buyer profile**

- [ ] A signed-in buyer can view and update their name/phone; an unauthenticated request to either endpoint is rejected 401. — `FR-AUTH-028`, `FR-AUTH-029`
- [ ] Changing password with the correct current password succeeds and invalidates every other session for that user, leaving the current one intact; an incorrect current password is rejected without extra detail. — `FR-AUTH-030`, `FR-AUTH-031`

**Abuse mitigation and error contract**

- [ ] Exceeding the sign-in/sign-up rate limit from one IP or for one email returns 429 before Better Auth's own credential check runs. — `FR-AUTH-032`
- [ ] Exceeding the forgot-password rate limit for one email returns 429 without sending an additional reset email. — `FR-AUTH-033`
- [ ] Every error in this feature matches `{ success: false, code, message }`, and `INVALID_CREDENTIALS`, `ACCOUNT_DEACTIVATED`, `UNAUTHENTICATED`, and `FORBIDDEN_ROLE` are each distinguishable by `code` alone. — `FR-AUTH-034`

## 9. Dependencies

- **Better Auth** — session, credential storage, and cookie management; MongoDB adapter provisions its own collections alongside `users`. Chosen per [`docs/architecture.md`](../../architecture.md) §9 over Auth.js/Clerk specifically for built-in RBAC support.
- **Resend** — password-reset emails (`FR-AUTH-013`); the first feature to actually send an email, ahead of Orders' (v0.5) transactional emails reusing the same client.
- **Upstash Redis** — sign-in/sign-up and forgot-password rate limiting (`FR-AUTH-032`–`033`); the same instance `docs/architecture.md` §5 already designates for caching/queues.
- **Product Catalog (SRS v0.2)** — this version removes `FR-CAT-088`–`090`'s `X-Admin-Key` guard outright and backfills `FR-CAT-013`'s reserved `createdBy`/`updatedBy` fields; both are two-way dependencies, not just this feature depending on catalog.

## 10. Open Questions

_None open — see "Resolved during drafting" below._

### Resolved during drafting

- **One `users` collection vs. separate buyer/admin collections** — one collection with a `role` enum, matching `docs/architecture.md` §5's data map and keeping a single identity/session model for Better Auth to manage, rather than duplicating auth plumbing per app.
- **Whether admin sign-in needs its own endpoint** — no; `FR-AUTH-006` is shared, and role alone (checked both client-side for UX and server-side for enforcement, `FR-AUTH-022`/`024`) distinguishes an admin session from a buyer one.
- **Whether to gate sign-up on email verification** — deliberately not, to keep the buyer funnel to checkout short; see §7.
