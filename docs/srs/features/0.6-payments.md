# SRS v0.6 — Payments

**Status:** Draft — awaiting review
**Last Updated:** 2026-08-21
**Depends on:** Orders (v0.5) — every payment exists in relation to exactly one order, and this feature is the real caller of `FR-ORD-009`'s `pending_payment → paid` seam. Requires a provisioned Razorpay merchant account (`SRS.md` §2.6).

---

## 1. Feature Overview

Payments closes the loop v0.5 deliberately left open: it integrates Razorpay to actually move an order from `pending_payment` to `paid`, and gives `order-manager`/`super-admin` a way to refund one afterward. Razorpay confirms a payment two ways — synchronously, when the buyer's browser returns from its checkout widget, and asynchronously, via a server-to-server webhook — and this version treats **both as legitimate, idempotent paths to the same transition**, because the synchronous path alone is unreliable (a buyer who closes their browser mid-flow after paying successfully must not be left with an order stuck in `pending_payment`).

Money handling here inherits v0.2's and v0.5's conventions without exception: integer paise, server-computed, never trusted from a client. The two Razorpay secrets — the key secret and the webhook secret — never reach either frontend; `buyer-app` receives only a public key ID and a Razorpay order ID, neither of which can authorize a charge on its own.

## 2. Functional Requirements

### 2.1 Payment initiation

- `FR-PAY-001`: A signed-in buyer initiates payment for their own `pending_payment` order via `POST /api/orders/:id/payment`, which creates a corresponding Razorpay order (amount = the order's `totalAmount`, currency INR) and returns the Razorpay order ID and public key ID `buyer-app`'s checkout widget needs.
- `FR-PAY-002`: A payment-initiation request against an order that is not the requesting buyer's own, or that is not currently `pending_payment`, is rejected — the same ownership check `FR-ORD-012` uses, plus a status gate.
- `FR-PAY-003`: Each initiation creates, or reuses if one already exists and is still valid, exactly one `payments` document in status `created` referencing the order — never more than one live payment record per order at a time.
- `FR-PAY-004`: Initiating payment again for an order that already has a `created` or `authorized` payment record reuses that record's Razorpay order rather than creating a duplicate at the gateway.

### 2.2 Client-side verification

- `FR-PAY-005`: After the buyer completes payment in Razorpay's checkout widget, `buyer-app` submits the returned `razorpay_payment_id`, `razorpay_order_id`, and `razorpay_signature` to `POST /api/orders/:id/payment/verify`.
- `FR-PAY-006`: The backend verifies the submitted signature against Razorpay's HMAC scheme using the key secret before trusting any part of the payload; a signature that fails verification is rejected and the order remains `pending_payment`.
- `FR-PAY-007`: A successfully verified payment updates its `payments` document to `captured`, records `razorpayPaymentId`/`razorpaySignature`, and calls Orders' internal `paid`-transition seam (`FR-ORD-009`) — fulfilling the seam v0.5 left unimplemented.
- `FR-PAY-008`: The client-side verify call is a best-effort fast path only, not the sole route to `paid` — the webhook (§2.3) independently drives the identical transition, so a buyer who never returns to `buyer-app` after paying doesn't leave a genuinely successful payment stranded.

### 2.3 Webhook

- `FR-PAY-009`: The backend exposes `POST /api/webhooks/razorpay`, configured on the Razorpay dashboard, receiving asynchronous payment and refund lifecycle events.
- `FR-PAY-010`: Every webhook request's signature is verified against Razorpay's webhook secret before its payload is trusted or processed; an invalid signature is rejected before any database write.
- `FR-PAY-011`: Webhook processing is idempotent, keyed by Razorpay's event ID — a redelivered event (Razorpay retries on any non-2xx response or timeout) that was already successfully processed is acknowledged without reapplying its effect.
- `FR-PAY-012`: A `payment.captured` event drives the identical `payments`-status update and order-`paid` transition as `FR-PAY-007`; whichever of the client-verify path or the webhook arrives first performs the transition, and the second is a no-op by virtue of `FR-PAY-011`'s idempotency, not an error condition.
- `FR-PAY-013`: A `payment.failed` event updates the `payments` document to `failed` and leaves the order in `pending_payment`, allowing a retry (`FR-PAY-019`).
- `FR-PAY-014`: Every received webhook event — whether it changes anything or not — is appended to that payment's `webhookEvents` log with its type and timestamp, an audit trail independent of the derived `status` field.

### 2.4 Refunds

- `FR-PAY-015`: An `order-manager` or `super-admin` can initiate a full or partial refund on a `paid`-or-later, pre-`refunded` order via `POST /api/admin/orders/:id/refund`, specifying an amount (defaulting to the full remaining captured amount) and a required reason.
- `FR-PAY-016`: A refund request exceeding the order's captured amount minus any amount already refunded is rejected — no order is ever refundable beyond what it was actually paid.
- `FR-PAY-017`: A successful refund call creates a Razorpay refund against the original payment and records it on the `payments` document; the order transitions to `refunded` once the cumulative refunded amount equals the full captured amount. A partial refund is tracked on the payment record without a separate order-level `partially_refunded` status (§7).
- `FR-PAY-018`: Refund completion, like payment completion, is confirmed authoritatively by Razorpay's `refund.processed` webhook event, not solely by the synchronous admin call succeeding — the admin call creates the refund request; the webhook confirms it actually completed.

### 2.5 Failure and retry

- `FR-PAY-019`: A `pending_payment` order whose most recent payment attempt is `failed` can have a new payment attempt initiated against it (`FR-PAY-004`) without creating a new order — the buyer retries payment, not checkout.
- `FR-PAY-020`: An order already auto-cancelled by v0.5's 30-minute timeout (`FR-ORD-010`), or otherwise no longer `pending_payment`, cannot accept a new payment initiation — enforced by `FR-PAY-002`'s status gate.
- `FR-PAY-021`: A webhook event for a payment whose order is no longer eligible (already cancelled, or otherwise terminal) is logged (`FR-PAY-014`) and acknowledged, but does not force the order back into `paid` — the order's existing terminal state takes precedence.

### 2.6 Security

- `FR-PAY-022`: Razorpay's key secret and webhook secret are never exposed to either frontend; `buyer-app` receives only the public key ID and a Razorpay order ID (`FR-PAY-001`), neither of which can authorize a charge on its own.
- `FR-PAY-023`: The webhook endpoint's signature verification runs against the raw, unparsed request body — any body-parsing middleware mounted ahead of it must preserve the original bytes rather than re-serializing them, since Razorpay's HMAC is computed over the exact payload sent.
- `FR-PAY-024`: The webhook endpoint is exempt from the session/RBAC guard (`FR-AUTH-023`–`024`) — it authenticates by signature alone, since Razorpay has no session — and is additionally placed at a path never referenced by either frontend, as defense in depth beyond signature verification alone.

### 2.7 Response envelope and money handling

- `FR-PAY-025`: Every payment and refund endpoint follows the existing `{ success, data }` / `{ success: false, code, message }` contract.
- `FR-PAY-026`: Every stored monetary amount — payment and refund alike — is an integer number of paise, matching v0.2's and v0.5's convention; no floating-point currency field exists anywhere in this feature.
- `FR-PAY-027`: A `payments` document exists only in relation to an order; there is no cart-level or standalone payment concept, and a payment record is never deleted — only its status transitions, each one auditable.
- `FR-PAY-028`: A buyer sees their own payment status as a summary (`status`, amount, method) within their order detail response (`FR-ORD-012`), not via a separate payments-listing endpoint of their own.

## 3. Baseline Non-Functional Requirements

**Validation**

- [ ] Refund amount (`FR-PAY-015`) is validated server-side against the order's actual captured/refunded totals before any call reaches Razorpay — never trusted as an arbitrary client-supplied number.
- [ ] The client-submitted `razorpay_signature` (`FR-PAY-005`) is validated by cryptographic verification, not string comparison against a client-controlled expected value.

**Indexes**

- [ ] `payments`: unique index on `razorpayOrderId`, unique sparse index on `razorpayPaymentId`, index on `order`.
- [ ] Webhook idempotency (`FR-PAY-011`) is enforced by a unique index on processed Razorpay event IDs, not an application-level check-then-write that could race.

**Error handling and operations**

- [ ] Every endpoint follows `{ success: false, code, message }`, per [`docs/architecture.md`](../../architecture.md) §6.
- [ ] The webhook handler returns `200` for every event it successfully processes or safely ignores (`FR-PAY-011`, `FR-PAY-021`), and a non-2xx only for genuine processing failure — since Razorpay retries on anything else, an accidental non-2xx on a merely-uninteresting event would cause needless redelivery storms.

**Security**

- [ ] No secrets committed — the Razorpay key ID, key secret, and webhook secret are sourced from environment variables, following the existing `.env.example` pattern.
- [ ] The webhook endpoint is rate-limited independently of the general API rate-limit policy, since it is a public, unauthenticated-by-session endpoint that Razorpay itself calls at unpredictable volume.
- [ ] `payments` documents are never returned in full to `buyer-app` — only the summary in `FR-PAY-028` — since the full record carries gateway identifiers with no buyer-facing purpose.

## 4. User Stories

- As a **registered buyer**, I want to pay for my order through a trusted checkout flow, so that I can complete my purchase securely.
- As a **registered buyer**, I want my order to show as paid even if I close the browser right after paying, so that a successful payment is never lost from my side.
- As a **registered buyer**, I want to retry payment if it fails the first time, so that a declined card doesn't force me to rebuild my whole order.
- As an **order manager**, I want to refund a buyer fully or partially, so that I can resolve cancellations and disputes without a manual, out-of-band bank transfer.
- As a **super admin**, I want every payment and refund event logged, so that a support dispute can be traced back to exactly what Razorpay reported and when.

## 5. Data Model / API Contract

### `payments`

| Field                     | Type                                                                 | Notes                                                     |
| ------------------------- | ----------------------------------------------------------------------- | -------------------------------------------------------------- |
| `_id`                     | ObjectId                                                             |                                                            |
| `order`                   | ObjectId → `orders`, required                                        | `FR-PAY-003`, `FR-PAY-027`                                 |
| `razorpayOrderId`         | string, required, unique                                             | `FR-PAY-001`                                               |
| `razorpayPaymentId`       | string, optional, unique (sparse)                                    | set on capture — `FR-PAY-007`                               |
| `razorpaySignature`       | string, optional                                                     | set on verify — `FR-PAY-007`                                |
| `amount`                  | integer, required                                                    | paise — `FR-PAY-026`                                        |
| `status`                  | enum `created` / `authorized` / `captured` / `failed` / `refunded` / `partially_refunded` | `FR-PAY-007`, `FR-PAY-013`, `FR-PAY-017`                    |
| `refunds`                 | `[{ razorpayRefundId, amount, reason, status, createdAt }]`          | `FR-PAY-015`–`018`                                          |
| `webhookEvents`           | `[{ eventId, type, receivedAt }]`                                    | audit log — `FR-PAY-011`, `FR-PAY-014`                       |
| `createdAt` / `updatedAt` | timestamps                                                           |                                                            |

### API endpoints

| Method | Path                                  | Auth                             | Purpose                                                    |
| ------ | -------------------------------------- | ----------------------------------- | -------------------------------------------------------------- |
| POST   | `/api/orders/:id/payment`             | session (buyer, owner-only)         | Initiate/reuse a Razorpay order — `FR-PAY-001`–`004`            |
| POST   | `/api/orders/:id/payment/verify`      | session (buyer, owner-only)         | Client-side signature verify — `FR-PAY-005`–`008`               |
| POST   | `/api/webhooks/razorpay`              | signature only (no session)         | Async payment/refund events — `FR-PAY-009`–`014`, `020`–`021`  |
| POST   | `/api/admin/orders/:id/refund`        | session (`order-manager`/`super-admin`) | Initiate a refund — `FR-PAY-015`–`016`                     |

### Response envelope

```jsonc
// POST /api/orders/:id/payment
{
  "success": true,
  "data": {
    "razorpayOrderId": "order_QW7x9ZbK2mLpNr",
    "razorpayKeyId": "rzp_live_1a2b3c4d5e6f7g",
    "amount": 4000000,
    "currency": "INR"
  }
}

// POST /api/orders/:id/payment/verify — bad signature
{ "success": false, "code": "PAYMENT_SIGNATURE_INVALID", "message": "Payment could not be verified." }

// order detail's embedded payment summary (FR-PAY-028)
{
  "payment": { "status": "captured", "amount": 4000000, "method": "upi" }
}
```

## 6. UI/UX Requirements

**`buyer-app`**

- **Checkout — payment step**: replaces v0.5's "payment coming next" placeholder with Razorpay's checkout widget, launched using `FR-PAY-001`'s response; on the widget's success callback, calls verify (`FR-PAY-005`) and redirects to the order confirmation/detail view; a failure or dismissal returns the buyer to a retry state on the same order rather than forcing a fresh checkout.
- **Order detail**: shows the embedded payment summary (`FR-PAY-028`) — status, amount, method — alongside the existing status timeline from v0.5.

**`admin-app`** — role-gated to `order-manager`/`super-admin`, same boundary as v0.5's order screens.

- **Order detail — refund action**: a refund form (amount, defaulting to the full refundable balance, plus a required reason), disabled entirely on an order with no captured payment; shows refund history if any partial refunds already exist.

## 7. Out of Scope

- **Multiple payment attempts tracked as separate first-class records beyond the current one** — `FR-PAY-004` reuses the live payment record; a fully separate payment-attempt history beyond `webhookEvents`'s log is not modeled.
- **A distinct `partially_refunded` order status** — partial refunds are tracked on the `payments` document (`FR-PAY-017`); the order itself stays `paid`-or-later until refunded in full.
- **Non-Razorpay payment methods** (cash on delivery, other gateways) — single gateway, per `SRS.md` §2.5's India-first, Razorpay-only decision.
- **Saved payment methods / stored cards** — every checkout goes through Razorpay's widget fresh; no card-on-file feature exists.
- **Invoice/GST-compliant receipt generation** — deferred to Launch Readiness (v1.0), same as v0.5 §7.
- **Automatic refund-on-cancellation** — an admin explicitly initiates a refund (`FR-PAY-015`); cancelling an order never triggers one implicitly.

## 8. Acceptance Criteria

**Initiation and verification**

- [ ] Initiating payment on the buyer's own `pending_payment` order returns a Razorpay order ID and key ID; initiating on another buyer's order, or a non-`pending_payment` order, is rejected. — `FR-PAY-001`, `FR-PAY-002`
- [ ] Initiating twice in a row against the same still-valid payment reuses the same Razorpay order rather than creating a second one. — `FR-PAY-003`, `FR-PAY-004`
- [ ] Submitting a valid signature to verify transitions the payment to `captured` and the order to `paid`; submitting a tampered signature is rejected and the order stays `pending_payment`. — `FR-PAY-006`, `FR-PAY-007`

**Webhook**

- [ ] A webhook request with an invalid signature is rejected before any write occurs. — `FR-PAY-010`
- [ ] Redelivering the same `payment.captured` event twice results in exactly one `paid` transition and one webhook-log entry per delivery (two log entries, one effective transition). — `FR-PAY-011`, `FR-PAY-012`, `FR-PAY-014`
- [ ] Whichever of client-verify or webhook arrives first performs the `paid` transition; the second arrival is a no-op, not an error. — `FR-PAY-008`, `FR-PAY-012`
- [ ] A `payment.failed` event updates payment status to `failed` and leaves the order `pending_payment`. — `FR-PAY-013`

**Refunds**

- [ ] A full refund on a `paid` order succeeds and transitions the order to `refunded`. — `FR-PAY-015`, `FR-PAY-017`
- [ ] A partial refund succeeds, is recorded on the payment record, and the order remains its prior status (not `refunded`) until the cumulative refunded amount reaches the full captured amount. — `FR-PAY-017`
- [ ] A refund request exceeding the refundable balance is rejected. — `FR-PAY-016`

**Retry and eligibility**

- [ ] A failed payment attempt can be retried on the same order without creating a new order. — `FR-PAY-019`
- [ ] Initiating payment against an auto-cancelled order is rejected. — `FR-PAY-020`
- [ ] A webhook event for an order that's already terminal is logged and acknowledged without changing the order's status. — `FR-PAY-021`

**Security and envelope**

- [ ] Neither the Razorpay key secret nor the webhook secret ever appears in any `buyer-app`-facing response. — `FR-PAY-022`
- [ ] The buyer-facing order detail response includes only the payment summary fields, never the full `payments` document. — `FR-PAY-028`
- [ ] Every error in this feature matches `{ success: false, code, message }`. — `FR-PAY-025`

## 10. Open Questions

_None open — see "Resolved during drafting" below._

### Resolved during drafting

- **Whether the client-side verify call alone is sufficient to mark an order paid** — no; the webhook is treated as equally authoritative and the two paths are made idempotent against each other (`FR-PAY-008`, `FR-PAY-011`–`012`), because relying on the browser round-trip alone would lose genuinely successful payments whenever a buyer navigates away early.
- **Whether partial refunds need their own order status** — no; tracked on the `payments` document instead (`FR-PAY-017`), keeping the order state machine v0.5 already defined (`FR-ORD-008`) unchanged rather than adding a new terminal-adjacent status this late.
