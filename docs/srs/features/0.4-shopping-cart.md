# SRS v0.4 — Shopping Cart

**Status:** Draft — awaiting review
**Last Updated:** 2026-08-21
**Depends on:** Product Catalog (v0.2) for variant references and pricing; Authentication (v0.3) for the buyer session every cart endpoint requires.

---

## 1. Feature Overview

The cart is the bridge between browsing (Catalog, v0.2) and buying (Orders, v0.5): an authenticated buyer collects product variants here before checkout reads them. It is intentionally thin. There is no stock to reserve (v0.2 removed the stock/inventory concept from this system entirely, `FR-CAT-059`/`073`/`096`), no price to freeze at add-to-cart time (prices are always resolved live, since a stale cart price would silently diverge from what checkout actually charges), and no admin surface at all — nobody manages another person's cart.

A cart line item references a **variant**, never a bare product, matching v0.2's variant-only sellable-unit model exactly (`FR-CAT-039`–`044`). Building a cart requires signing in: there is no anonymous/guest cart. Browsing the catalog itself has no such gate — only the moment a visitor tries to add an item, or open the cart, is gated behind authentication, at which point `buyer-app` routes an unauthenticated visitor to Login rather than ever creating a cart for them.

## 2. Functional Requirements

### 2.1 Buyer cart identity

- `FR-CART-001`: A signed-in buyer has exactly one persistent cart, keyed by their user ID, created lazily on the first add-to-cart action; no empty cart record exists before that.
- `FR-CART-002`: Every cart endpoint requires an authenticated session; an unauthenticated request is rejected (401), never treated as an anonymous/guest cart.

### 2.2 Cart line items

- `FR-CART-003`: A cart line item references a specific product variant, never a bare product — a variant-less product cannot be added.
- `FR-CART-004`: Adding a variant already present in the cart increases that line's quantity rather than creating a duplicate line.
- `FR-CART-005`: Quantity per line item is a positive integer capped at 10 per variant; a request outside 1–10 is rejected outright, not clamped — this is a meaningful business rule (bulk-buy/scalping mitigation), unlike the display-only clamping catalog pagination uses.
- `FR-CART-006`: Buyer can update a line item's quantity via `PATCH`; setting it to `0` removes the line, equivalent to an explicit remove.
- `FR-CART-007`: Buyer can remove a line item explicitly via `DELETE`.
- `FR-CART-008`: Buyer can clear the entire cart in one call via `DELETE /api/cart`.
- `FR-CART-009`: Adding a variant ID that does not exist is rejected with a validation error, never silently ignored.

### 2.3 Pricing and availability

- `FR-CART-010`: Every cart read resolves each line item's price from the variant's **current** `mrp`/`discount`/`sellingPrice` — never a value captured at add-to-cart time, and never a client-supplied price.
- `FR-CART-011`: `subtotal` (sum of each line's live `sellingPrice × quantity`, excluding unavailable lines per `FR-CART-012`) is computed server-side on every read; it is never accepted from the client.
- `FR-CART-012`: A line item whose variant has since been deactivated (`active: false`), or whose parent product is no longer `published`, is retained in the cart response with `unavailable: true` and excluded from `subtotal` — never silently dropped, so the buyer can see why their total changed rather than just watching an item vanish.
- `FR-CART-013`: A line item whose quantity now exceeds the current per-variant cap (`FR-CART-005`, if that cap is ever lowered) is retained and flagged the same way as `FR-CART-012`, not silently reduced.
- `FR-CART-014`: `FR-CART-012`'s `unavailable` flag is the single source of truth checkout (v0.5) relies on to block those lines — checkout does not duplicate this availability check independently.

### 2.4 Expiry and retrieval

- `FR-CART-015`: An authenticated buyer's cart has no expiry; it persists until explicitly cleared (`FR-CART-008`).
- `FR-CART-016`: Buyer can retrieve the current cart via `GET /api/cart`, returning every line item (with pricing/availability flags) and the computed `subtotal`; a buyer who has added nothing yet receives an empty-cart shape, never a 404.
- `FR-CART-017`: A lightweight item-count value is included on every cart response (not a separate endpoint) so the `buyer-app` header badge needs no second request.

### 2.5 Response envelope

- `FR-CART-018`: Every cart response follows the existing `{ success, data }` envelope; `data` is always a single cart object — a cart has no independent listing/pagination concept, so `pagination` never appears on it.

### 2.6 UI access gating

- `FR-CART-019`: Clicking the header cart icon routes on session state alone: a signed-in buyer is taken to the Cart section; an unauthenticated user is taken to the Login section instead.
- `FR-CART-020`: Clicking "Add to Cart" — on a product card (grid/list quick-add) or the product detail page — as an unauthenticated user routes to the Login section instead of performing the add; the add-to-cart action is only ever invoked for an authenticated buyer, so no anonymous mutation is possible even transiently.
- `FR-CART-021`: For a signed-in buyer, a product card whose (sole/selected) variant is already a line item in their cart shows a "Go to Cart" control in place of "Add to Cart" — clicking it navigates to the Cart section rather than adding another line; the card reverts to "Add to Cart" if that line is later removed. This state is derived from the buyer's already-cached cart contents (`FR-CART-016`), not a per-card API call.

## 3. Baseline Non-Functional Requirements

**Validation**

- [ ] Every cart mutation (`variantId`, `quantity`) is validated server-side with Zod before touching the database; an out-of-range quantity (`FR-CART-005`) is rejected there, not clamped.
- [ ] `variantId` on every mutation is cross-checked against a real, existing variant before the line item is written — never trusted as an opaque string.

**Indexes**

- [ ] `carts`: unique index on `user` — every cart belongs to an authenticated buyer, so no sparse/guest variant of the index is needed.

**Error handling and operations**

- [ ] Every endpoint follows `{ success: false, code, message }`, per [`docs/architecture.md`](../../architecture.md) §6.
- [ ] Cart contents are never logged in full at `info` level in production.

**Security**

- [ ] Cart endpoints authenticate via the same session mechanism v0.3 established for the buyer; no separate cart-specific credential exists.

## 4. User Stories

- As a **guest browsing the catalog**, I want to be prompted to sign in when I try to add something to my cart, so that everything I add is saved to my account from the start.
- As a **registered buyer**, I want my cart to persist between visits, so that I can come back later and pick up where I left off.
- As a **registered buyer**, I want to see the current price for everything in my cart, so that I'm never surprised by a price that changed since I added an item.
- As a **registered buyer**, I want to be told clearly if something in my cart is no longer available, so that I understand why my total changed instead of just seeing an item disappear.
- As a **registered buyer**, I want a product card to show me when something is already in my cart, so that I don't accidentally add it twice and can jump straight to my cart instead.

## 5. Data Model / API Contract

### `carts`

| Field                     | Type                               | Notes                                                        |
| ------------------------- | ------------------------------------ | -------------------------------------------------------------- |
| `_id`                     | ObjectId                           |                                                               |
| `user`                    | ObjectId → `users`, required, unique | every cart belongs to an authenticated buyer — `FR-CART-001`   |
| `items`                   | `[{ variant: ObjectId, quantity: number }]` | `variant` references `products.variants._id` — `FR-CART-003`   |
| `createdAt` / `updatedAt` | timestamps                          |                                                                |

No `expiresAt`/price/availability fields are stored — pricing and availability are always derived live from the referenced variant at read time (`FR-CART-010`–`014`), never persisted on the cart document itself.

### API endpoints

| Method | Path                          | Auth                | Purpose                                                    |
| ------ | ------------------------------ | -------------------- | -------------------------------------------------------------- |
| GET    | `/api/cart`                    | session (required)   | Retrieve current cart — `FR-CART-016`–`017`                    |
| POST   | `/api/cart/items`               | session (required)   | Add a variant (or increase quantity) — `FR-CART-003`–`004`     |
| PATCH  | `/api/cart/items/:variantId`   | session (required)   | Update a line's quantity — `FR-CART-006`                       |
| DELETE | `/api/cart/items/:variantId`   | session (required)   | Remove a line — `FR-CART-007`                                  |
| DELETE | `/api/cart`                    | session (required)   | Clear the entire cart — `FR-CART-008`                           |

Every endpoint above requires an authenticated session and returns 401 without one (`FR-CART-002`); there is no anonymous entry point and no separate "create cart" endpoint — a cart is created lazily on first add for a buyer who doesn't already have one (`FR-CART-001`).

### Response envelope

```jsonc
// GET /api/cart
{
  "success": true,
  "data": {
    "id": "66c1a2b3c4d5e6f7a8b9c0d1",
    "items": [
      {
        "variant": {
          "id": "66a4f1c8e3b7a91d2c8f4f01",
          "sku": "NOVA-X5P-128-BLK",
          "product": { "id": "66a4f1c8e3b7a91d2c8f4e01", "name": "Nova X5 Pro 5G", "slug": "nova-x5-pro-5g" },
          "attributes": [{ "name": "Storage", "value": "128GB" }, { "name": "Color", "value": "Midnight Black" }],
          "primaryImage": { "url": "https://cdn.techcart.in/product-images/…webp", "alt": "Nova X5 Pro 5G in Midnight Black" }
        },
        "quantity": 2,
        "sellingPrice": 4000000,
        "lineTotal": 8000000,
        "unavailable": false
      },
      {
        "variant": { "id": "66a4f1c8e3b7a91d2c8f4f09", "sku": "OLD-SKU-DISCONTINUED", "product": { "id": "…", "name": "…", "slug": "…" }, "attributes": [], "primaryImage": null },
        "quantity": 1,
        "sellingPrice": 129900,
        "lineTotal": 0,
        "unavailable": true
      }
    ],
    "itemCount": 3,
    "subtotal": 8000000
  }
}
```

`itemCount` sums quantity across all lines including unavailable ones (`FR-CART-017`); `subtotal` excludes unavailable lines (`FR-CART-011`) — the two numbers are deliberately allowed to tell different stories, since one drives a header badge and the other drives what checkout will actually charge.

## 6. UI/UX Requirements

**`buyer-app`** — client-rendered per [`docs/architecture.md`](../../architecture.md) §4.1.

- **Header mini-cart**: item-count badge sourced from `itemCount` for a signed-in buyer, updating optimistically on add/remove; an unauthenticated visitor sees no badge. Clicking the icon routes to the Cart section if signed in, or the Login section otherwise (`FR-CART-019`).
- **Cart page**: line items with image/name/attributes/quantity stepper/remove, an inline "no longer available" treatment for `unavailable: true` lines (dimmed, excluded from the displayed subtotal, with a remove action), a subtotal summary, and a checkout button disabled when the cart has zero available lines. Empty-cart state distinct from the loading state.
- **Add-to-cart control**: present on product cards (grid/list quick-add) and on product detail (v0.2), scoped to the selected variant once variants exist — disabled or absent for a product with no active variants regardless of auth state. Clicking it as an unauthenticated visitor routes to the Login section instead of adding the item (`FR-CART-020`); for a signed-in buyer whose cart already contains that card's variant, the control instead reads "Go to Cart" and navigates to the Cart section (`FR-CART-021`).

**`admin-app`** — no cart-related screens exist; carts have no admin surface in this version (§7).

## 7. Out of Scope

- **Any admin visibility into carts** — no abandoned-cart admin view, no "carts" admin nav entry; that is Dashboard/Marketing territory, not this version's.
- **Anonymous/guest carts of any kind** — every cart requires an authenticated buyer session; there is no guest-cart identity, cookie, or merge-on-sign-in mechanism.
- **Saved-for-later / wishlist**, distinct from the active cart.
- **Multiple carts per buyer** (e.g. named lists) — exactly one cart per buyer, per §2.1.
- **Stock reservation of any kind** — v0.2 removed the stock/inventory concept from this system entirely; adding to a cart never reserves or decrements anything.
- **Cart-level coupons/promo codes** — pricing here is strictly the sum of live variant prices; discounting mechanics beyond a variant's own `discount` field are not designed in this version.
- **Cross-device real-time cart sync** (e.g. live push when a cart changes on another tab/device) — a buyer's cart is consistent on every fresh `GET`, not push-synced.

## 8. Acceptance Criteria

**Buyer identity**

- [ ] An unauthenticated user clicking the header cart icon lands on the Login section, not the Cart section. — `FR-CART-019`
- [ ] An unauthenticated user clicking Add to Cart (product card or detail page) lands on the Login section and no cart mutation occurs. — `FR-CART-020`
- [ ] A signed-in buyer's cart is retrievable by session alone. — `FR-CART-001`, `FR-CART-002`
- [ ] A product card whose variant is already in the signed-in buyer's cart shows "Go to Cart" instead of "Add to Cart," and clicking it navigates to the Cart section without adding a duplicate line. — `FR-CART-021`
- [ ] Removing that line from the cart reverts the card back to "Add to Cart." — `FR-CART-021`

**Line items**

- [ ] Adding the same variant twice results in one line with combined quantity, not two lines. — `FR-CART-004`
- [ ] Adding quantity 11, or updating an existing line to 11, is rejected; adding/updating to 0 through 10 succeeds, and updating to exactly 0 removes the line. — `FR-CART-005`, `FR-CART-006`
- [ ] Adding a nonexistent variant ID is rejected with a validation error. — `FR-CART-009`
- [ ] Removing a line and clearing the whole cart both work independently. — `FR-CART-007`, `FR-CART-008`

**Pricing and availability**

- [ ] Changing a variant's `mrp`/`discount` in the catalog after it's already in a cart changes the price shown on the next cart `GET`, with no cart-side update needed. — `FR-CART-010`
- [ ] Deactivating a variant already in a cart causes that line to appear with `unavailable: true` and be excluded from `subtotal` on the next `GET`, while remaining visible in `items`. — `FR-CART-012`
- [ ] `subtotal` recomputes correctly excluding unavailable lines; `itemCount` still includes them. — `FR-CART-011`, `FR-CART-017`

**Expiry and envelope**

- [ ] A brand-new buyer with nothing added receives a 200 with an empty `items` array, never a 404. — `FR-CART-016`
- [ ] Every response matches `{ success: true, data: {...} }` with no `pagination` key ever present. — `FR-CART-018`

## 9. Dependencies

- **Product Catalog (v0.2)** — every cart line references a `products.variants` subdocument; pricing is read live from it.
- **Authentication (v0.3)** — every cart endpoint requires the buyer session v0.3 issues (`FR-CART-002`); `buyer-app` gates the header cart icon and every Add-to-Cart control on that same session state (`FR-CART-019`, `FR-CART-020`).
- **Orders (v0.5, forward dependency)** — checkout reads a buyer's cart as its input and relies on `FR-CART-014`'s `unavailable` flag as the sole availability check; this version does not implement checkout itself.

## 10. Open Questions

_None open — see "Resolved during drafting" below._

### Resolved during drafting

- **Whether to freeze price at add-to-cart time or resolve it live** — resolved live, always (`FR-CART-010`). Freezing would let a cart silently understate what checkout actually charges once a price changes; re-deriving it from the variant on every read keeps the cart and checkout always in agreement.
- **Whether an unavailable line should be dropped or flagged** — flagged (`FR-CART-012`), never silently dropped, so a buyer understands why their subtotal changed rather than just noticing an item is gone.
- **Whether cart-building should support anonymous/guest use** — resolved to require authentication throughout (`FR-CART-002`, `FR-CART-019`, `FR-CART-020`); `buyer-app` routes any unauthenticated attempt to open the cart or add an item straight to Login instead. This reverses an earlier draft of this document, which treated a guest-cart-then-merge-on-sign-in flow as essential UX; the product decision going forward is to capture every added item directly against an authenticated buyer account from the outset, so no guest-cart identity, cookie, or merge step exists in this version.
