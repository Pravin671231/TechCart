# SRS v0.4 — Shopping Cart

**Status:** Draft — awaiting review
**Last Updated:** 2026-08-21
**Depends on:** Product Catalog (v0.2) for variant references and pricing; Authentication (v0.3) for the buyer session and cart-merge-on-login trigger.

---

## 1. Feature Overview

The cart is the bridge between browsing (Catalog, v0.2) and buying (Orders, v0.5): a buyer — signed in or not — collects product variants here before checkout reads them. It is intentionally thin. There is no stock to reserve (v0.2 removed the stock/inventory concept from this system entirely, `FR-CAT-059`/`073`/`096`), no price to freeze at add-to-cart time (prices are always resolved live, since a stale cart price would silently diverge from what checkout actually charges), and no admin surface at all — nobody manages another person's cart.

A cart line item references a **variant**, never a bare product, matching v0.2's variant-only sellable-unit model exactly (`FR-CAT-039`–`044`). A guest can build a cart with no account; signing in merges that guest cart into the buyer's own persisted one rather than discarding it — losing a guest's in-progress cart at the exact moment they commit to creating an account would be the single worst UX mistake this feature could make.

## 2. Functional Requirements

### 2.1 Guest and buyer cart identity

- `FR-CART-001`: A guest can add a product variant to a cart with no account, identified by an opaque, server-generated guest-cart token carried in an `httpOnly` cookie — never a value the client chooses or can read.
- `FR-CART-002`: A guest cart is created lazily on the first add-to-cart action; no empty cart record exists before that.
- `FR-CART-003`: A signed-in buyer has exactly one persistent cart, keyed by their user ID, created lazily the same way as `FR-CART-001`.
- `FR-CART-004`: A request carrying neither a guest-cart cookie nor an authenticated session is never rejected — it is treated as a new guest and a cart is created on first use. Cart-building never requires signing in first.

### 2.2 Cart line items

- `FR-CART-005`: A cart line item references a specific product variant, never a bare product — a variant-less product cannot be added.
- `FR-CART-006`: Adding a variant already present in the cart increases that line's quantity rather than creating a duplicate line.
- `FR-CART-007`: Quantity per line item is a positive integer capped at 10 per variant; a request outside 1–10 is rejected outright, not clamped — this is a meaningful business rule (bulk-buy/scalping mitigation), unlike the display-only clamping catalog pagination uses.
- `FR-CART-008`: Buyer/guest can update a line item's quantity via `PATCH`; setting it to `0` removes the line, equivalent to an explicit remove.
- `FR-CART-009`: Buyer/guest can remove a line item explicitly via `DELETE`.
- `FR-CART-010`: Buyer/guest can clear the entire cart in one call via `DELETE /api/cart`.
- `FR-CART-011`: Adding a variant ID that does not exist is rejected with a validation error, never silently ignored.

### 2.3 Pricing and availability

- `FR-CART-012`: Every cart read resolves each line item's price from the variant's **current** `mrp`/`discount`/`sellingPrice` — never a value captured at add-to-cart time, and never a client-supplied price.
- `FR-CART-013`: `subtotal` (sum of each line's live `sellingPrice × quantity`, excluding unavailable lines per `FR-CART-014`) is computed server-side on every read; it is never accepted from the client.
- `FR-CART-014`: A line item whose variant has since been deactivated (`active: false`), or whose parent product is no longer `published`, is retained in the cart response with `unavailable: true` and excluded from `subtotal` — never silently dropped, so the buyer can see why their total changed rather than just watching an item vanish.
- `FR-CART-015`: A line item whose quantity now exceeds the current per-variant cap (`FR-CART-007`, if that cap is ever lowered) is retained and flagged the same way as `FR-CART-014`, not silently reduced.
- `FR-CART-016`: `FR-CART-014`'s `unavailable` flag is the single source of truth checkout (v0.5) relies on to block those lines — checkout does not duplicate this availability check independently.

### 2.4 Merge on sign-in

- `FR-CART-017`: On sign-in, if the request carries a guest-cart cookie and the now-authenticated buyer also has an existing persisted cart, the two merge: matching variants combine quantities (capped at `FR-CART-007`'s maximum, never exceeding it), non-matching lines are appended.
- `FR-CART-018`: A merge is atomic — it either fully succeeds, leaving the buyer's cart with every guest line folded in, or fully fails, leaving the buyer's pre-existing cart completely untouched. It never partially applies.
- `FR-CART-019`: The guest-cart cookie and its underlying cart record are cleared after a merge attempt, successful or not, so a stale guest cart never resurfaces on a later anonymous visit from the same browser.
- `FR-CART-020`: If a signed-in buyer has no prior cart, a merge (`FR-CART-017`) is equivalent to simply adopting the guest cart as their own — no separate code path is needed for "first cart."

### 2.5 Expiry and retrieval

- `FR-CART-021`: A guest cart not merged into an authenticated cart is deleted automatically 30 days after its last update, via a TTL index — no application code runs the cleanup.
- `FR-CART-022`: An authenticated buyer's cart has no expiry; it persists until explicitly cleared (`FR-CART-010`).
- `FR-CART-023`: Buyer/guest can retrieve the current cart via `GET /api/cart`, returning every line item (with pricing/availability flags) and the computed `subtotal`; a buyer/guest who has added nothing yet receives an empty-cart shape, never a 404.
- `FR-CART-024`: A lightweight item-count value is included on every cart response (not a separate endpoint) so the `buyer-app` header badge needs no second request.

### 2.6 Response envelope

- `FR-CART-025`: Every cart response follows the existing `{ success, data }` envelope; `data` is always a single cart object — a cart has no independent listing/pagination concept, so `pagination` never appears on it.

## 3. Baseline Non-Functional Requirements

**Validation**

- [ ] Every cart mutation (`variantId`, `quantity`) is validated server-side with Zod before touching the database; an out-of-range quantity (`FR-CART-007`) is rejected there, not clamped.
- [ ] `variantId` on every mutation is cross-checked against a real, existing variant before the line item is written — never trusted as an opaque string.

**Indexes**

- [ ] `carts`: unique sparse index on `user` (authenticated carts only), unique sparse index on `guestToken` (guest carts only), TTL index on `updatedAt` scoped to guest carts (`FR-CART-021`) — an authenticated cart is structurally exempt from the TTL, not merely long-lived.

**Error handling and operations**

- [ ] Every endpoint follows `{ success: false, code, message }`, per [`docs/architecture.md`](../../architecture.md) §6.
- [ ] A merge failure (`FR-CART-018`) is logged with enough detail to diagnose without ever logging full cart contents at `info` level in production.

**Security**

- [ ] The guest-cart cookie is `httpOnly`, `secure` (production), and `sameSite=lax` — the same posture v0.3 established for the session cookie (`FR-AUTH-008`), since it is equally a bearer credential for someone's cart.
- [ ] The guest-cart token itself is cryptographically random, never derived from anything predictable (timestamp, sequential ID) that would let one guest enumerate another's cart.

## 4. User Stories

- As a **guest**, I want to add products to a cart without creating an account first, so that I can decide what I want before committing to sign up.
- As a **guest**, I want my cart to carry over automatically once I do sign in or register, so that I don't lose what I already picked out.
- As a **registered buyer**, I want my cart to persist between visits, so that I can come back later and pick up where I left off.
- As a **registered buyer**, I want to see the current price for everything in my cart, so that I'm never surprised by a price that changed since I added an item.
- As a **registered buyer**, I want to be told clearly if something in my cart is no longer available, so that I understand why my total changed instead of just seeing an item disappear.

## 5. Data Model / API Contract

### `carts`

| Field                     | Type                                              | Notes                                                        |
| ------------------------- | -------------------------------------------------- | -------------------------------------------------------------- |
| `_id`                     | ObjectId                                          |                                                               |
| `user`                    | ObjectId → `users`, nullable, unique (sparse)     | present only on an authenticated cart — `FR-CART-003`          |
| `guestToken`              | string, nullable, unique (sparse)                 | present only on a guest cart — `FR-CART-001`                   |
| `items`                   | `[{ variant: ObjectId, quantity: number }]`        | `variant` references `products.variants._id` — `FR-CART-005`   |
| `createdAt` / `updatedAt` | timestamps                                        | `updatedAt` drives the guest-cart TTL — `FR-CART-021`           |

No `expiresAt`/price/availability fields are stored — pricing and availability are always derived live from the referenced variant at read time (`FR-CART-012`–`016`), never persisted on the cart document itself.

### API endpoints

| Method | Path              | Auth               | Purpose                                                    |
| ------ | ------------------ | -------------------- | -------------------------------------------------------------- |
| GET    | `/api/cart`        | guest cookie/session | Retrieve current cart — `FR-CART-023`–`024`                    |
| POST   | `/api/cart/items`  | guest cookie/session | Add a variant (or increase quantity) — `FR-CART-005`–`006`     |
| PATCH  | `/api/cart/items/:variantId` | guest cookie/session | Update a line's quantity — `FR-CART-008` |
| DELETE | `/api/cart/items/:variantId` | guest cookie/session | Remove a line — `FR-CART-009` |
| DELETE | `/api/cart`        | guest cookie/session | Clear the entire cart — `FR-CART-010`                           |

The guest-cart cookie is issued transparently on any of the above when neither it nor a session is present (`FR-CART-004`); no separate "create cart" endpoint exists. Merge (`FR-CART-017`–`020`) is not its own endpoint — it runs as a side effect inside `POST /api/auth/sign-in/email` (v0.3), triggered whenever a guest-cart cookie accompanies that request.

### Response envelope

```jsonc
// GET /api/cart
{
  "success": true,
  "data": {
    "id": "66c1a2b3c4d5e6f7a8b9c0d1",
    "items": [
      {
        "variant": {
          "id": "66a4f1c8e3b7a91d2c8f4f01",
          "sku": "NOVA-X5P-128-BLK",
          "product": { "id": "66a4f1c8e3b7a91d2c8f4e01", "name": "Nova X5 Pro 5G", "slug": "nova-x5-pro-5g" },
          "attributes": [{ "name": "Storage", "value": "128GB" }, { "name": "Color", "value": "Midnight Black" }],
          "primaryImage": { "url": "https://cdn.techcart.in/product-images/…webp", "alt": "Nova X5 Pro 5G in Midnight Black" }
        },
        "quantity": 2,
        "sellingPrice": 4000000,
        "lineTotal": 8000000,
        "unavailable": false
      },
      {
        "variant": { "id": "66a4f1c8e3b7a91d2c8f4f09", "sku": "OLD-SKU-DISCONTINUED", "product": { "id": "…", "name": "…", "slug": "…" }, "attributes": [], "primaryImage": null },
        "quantity": 1,
        "sellingPrice": 129900,
        "lineTotal": 0,
        "unavailable": true
      }
    ],
    "itemCount": 3,
    "subtotal": 8000000
  }
}
```

`itemCount` sums quantity across all lines including unavailable ones (`FR-CART-024`); `subtotal` excludes unavailable lines (`FR-CART-013`) — the two numbers are deliberately allowed to tell different stories, since one drives a header badge and the other drives what checkout will actually charge.

## 6. UI/UX Requirements

**`buyer-app`** — client-rendered per [`docs/architecture.md`](../../architecture.md) §4.1.

- **Header mini-cart**: item-count badge sourced from `itemCount`, updating optimistically on add/remove.
- **Cart page**: line items with image/name/attributes/quantity stepper/remove, an inline "no longer available" treatment for `unavailable: true` lines (dimmed, excluded from the displayed subtotal, with a remove action), a subtotal summary, and a checkout button disabled when the cart has zero available lines. Empty-cart state distinct from the loading state.
- **Add-to-cart control**: present on product detail (v0.2) and, once variants exist, scoped to the selected variant — disabled or absent for a product with no active variants (there is nothing sellable to add).

**`admin-app`** — no cart-related screens exist; carts have no admin surface in this version (§7).

## 7. Out of Scope

- **Any admin visibility into carts** — no abandoned-cart admin view, no "carts" admin nav entry; that is Dashboard/Marketing territory, not this version's.
- **Saved-for-later / wishlist**, distinct from the active cart.
- **Multiple carts per buyer** (e.g. named lists) — exactly one cart per identity, per §2.1.
- **Stock reservation of any kind** — v0.2 removed the stock/inventory concept from this system entirely; adding to a cart never reserves or decrements anything.
- **Cart-level coupons/promo codes** — pricing here is strictly the sum of live variant prices; discounting mechanics beyond a variant's own `discount` field are not designed in this version.
- **Cross-device real-time cart sync** (e.g. live push when a cart changes on another tab/device) — a buyer's cart is consistent on every fresh `GET`, not push-synced.

## 8. Acceptance Criteria

**Guest and buyer identity**

- [ ] A guest can add an item with no account and no prior cookie; the response sets a guest-cart cookie and the item appears on a subsequent `GET`. — `FR-CART-001`, `FR-CART-002`, `FR-CART-004`
- [ ] A signed-in buyer's cart is retrievable by session alone, with no cookie exchange needed beyond the session cookie itself. — `FR-CART-003`

**Line items**

- [ ] Adding the same variant twice results in one line with combined quantity, not two lines. — `FR-CART-006`
- [ ] Adding quantity 11, or updating an existing line to 11, is rejected; adding/updating to 0 through 10 succeeds, and updating to exactly 0 removes the line. — `FR-CART-007`, `FR-CART-008`
- [ ] Adding a nonexistent variant ID is rejected with a validation error. — `FR-CART-011`
- [ ] Removing a line and clearing the whole cart both work independently. — `FR-CART-009`, `FR-CART-010`

**Pricing and availability**

- [ ] Changing a variant's `mrp`/`discount` in the catalog after it's already in a cart changes the price shown on the next cart `GET`, with no cart-side update needed. — `FR-CART-012`
- [ ] Deactivating a variant already in a cart causes that line to appear with `unavailable: true` and be excluded from `subtotal` on the next `GET`, while remaining visible in `items`. — `FR-CART-014`
- [ ] `subtotal` recomputes correctly excluding unavailable lines; `itemCount` still includes them. — `FR-CART-013`, `FR-CART-024`

**Merge on sign-in**

- [ ] Signing in with a guest-cart cookie present, where the buyer has no prior cart, results in the buyer's cart containing exactly the guest cart's lines. — `FR-CART-017`, `FR-CART-020`
- [ ] Signing in with a guest-cart cookie present, where the buyer already has a cart sharing one variant, results in that line's quantity combined (capped at 10) and the guest cart's other lines appended. — `FR-CART-017`
- [ ] After any sign-in, the guest-cart cookie no longer resolves to a cart, whether or not a merge actually occurred. — `FR-CART-019`
- [ ] Simulating a merge failure leaves the buyer's pre-existing cart completely unchanged, not partially merged. — `FR-CART-018`

**Expiry and envelope**

- [ ] A guest cart untouched for 30 days is absent from the database afterward, with no application code invoked. — `FR-CART-021`
- [ ] A brand-new guest/buyer with nothing added receives a 200 with an empty `items` array, never a 404. — `FR-CART-023`
- [ ] Every response matches `{ success: true, data: {...} }` with no `pagination` key ever present. — `FR-CART-025`

## 9. Dependencies

- **Product Catalog (v0.2)** — every cart line references a `products.variants` subdocument; pricing is read live from it.
- **Authentication (v0.3)** — the merge trigger is a side effect of `POST /api/auth/sign-in/email`; guest-vs-buyer identity depends on v0.3's session cookie existing to distinguish the two.
- **Orders (v0.5, forward dependency)** — checkout reads a buyer's cart as its input and relies on `FR-CART-016`'s `unavailable` flag as the sole availability check; this version does not implement checkout itself.

## 10. Open Questions

_None open — see "Resolved during drafting" below._

### Resolved during drafting

- **Whether to freeze price at add-to-cart time or resolve it live** — resolved live, always (`FR-CART-012`). Freezing would let a cart silently understate what checkout actually charges once a price changes; re-deriving it from the variant on every read keeps the cart and checkout always in agreement.
- **Whether an unavailable line should be dropped or flagged** — flagged (`FR-CART-014`), never silently dropped, so a buyer understands why their subtotal changed rather than just noticing an item is gone.
