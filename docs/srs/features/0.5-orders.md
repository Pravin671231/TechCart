# SRS v0.5 — Orders

**Status:** Draft — awaiting review
**Last Updated:** 2026-08-21
**Depends on:** Authentication (v0.3) for buyer identity and the `order-manager`/`super-admin` roles; Shopping Cart (v0.4) as checkout's input; Product Catalog (v0.2) for the variants an order's lines snapshot. Anticipates Payments (v0.6) as the real caller of the `pending_payment → paid` transition this version only stubs.

---

## 1. Feature Overview

Orders turns a cart into a durable, auditable record: checkout snapshots what was bought at what price, tracks it through a fixed status lifecycle, and gives both the buyer and `order-manager`/`super-admin` roles a place to see and act on it. It is the first feature whose records must survive the catalog changing underneath them — a renamed product, a repriced variant, or an archived listing must never alter or break an order placed before the change, so every order line is a frozen snapshot, not a live reference.

This version deliberately ships one load-bearing stub: the transition from `pending_payment` to `paid` is defined and exposed here, but has no real caller until Payments (v0.6) verifies an actual Razorpay payment against it. This is the same "ship the seam now, wire the implementation later" pattern v0.2's `X-Admin-Key` guard used ahead of v0.3's real RBAC (`FR-CAT-090`) — it lets Orders and Payments be built as two separate, independently testable milestones instead of one large one.

There is no stock or inventory concept anywhere in this system (`SRS.md` v0.2 §1, `FR-CAT-059`/`073`/`096`, Issue #102) — checkout's only availability check is that a variant is still `active` on a `published` product, not a quantity reservation.

## 2. Functional Requirements

### 2.1 Checkout

- `FR-ORD-001`: A signed-in buyer can create an order from their current cart via `POST /api/orders` (checkout); this endpoint is unavailable to guests — placing an order requires an account, even though building a cart does not (`FR-CART-004`).
- `FR-ORD-002`: Checkout is rejected if the cart has zero available line items (`FR-CART-016`'s `unavailable` flag); a cart containing only unavailable lines is treated as empty for checkout purposes.
- `FR-ORD-003`: An order's line items are copied from the cart at checkout as an immutable **snapshot** — product name, variant attributes, SKU, image, and price — never a live reference, since catalog entries can later be renamed, repriced, or archived and an order must not change retroactively when they are.
- `FR-ORD-004`: Checkout requires a shipping address in the same request — full name, phone, address lines, city, state, and a 6-digit Indian PIN code — validated server-side.
- `FR-ORD-005`: A successful checkout creates the order in status `pending_payment`, computes `totalAmount` server-side as the sum of the snapshotted line prices (never accepted from the client), and clears the ordered lines from the buyer's cart.
- `FR-ORD-006`: Checkout is atomic with respect to the buyer's cart — the order is created and the ordered lines are cleared together, or neither happens.
- `FR-ORD-007`: Each order is assigned a human-readable, sequential, unique order number, distinct from its `_id`, shown on every buyer-facing surface and in every notification email.
- `FR-ORD-025`: If a line item becomes unavailable between the buyer's last cart read and the moment checkout actually commits (a race condition), checkout re-validates every line at commit time; any newly-unavailable line is dropped from the created order and the response lists which lines were dropped, rather than silently including a stale line or failing the entire checkout.
- `FR-ORD-026`: A shipping address is captured per order, not stored in a reusable address book — v0.3 §7 deliberately deferred address-book management, so a returning buyer re-enters their address on each checkout in this version.
- `FR-ORD-027`: `totalAmount` and every line's snapshotted price are stored as integer paise, matching v0.2's pricing convention (`FR-CAT-085`); no floating-point currency field exists anywhere in this feature.

### 2.2 Order status lifecycle

- `FR-ORD-008`: An order's status follows a fixed state machine: `pending_payment → paid → processing → shipped → delivered`, with `cancelled` reachable only from `pending_payment` or `paid`, and `refunded` reachable only from `paid` or later. Any transition outside this graph is rejected.
- `FR-ORD-009`: The transition into `paid` is made through a dedicated, internal-only status endpoint reserved for Payments (v0.6) to call once it verifies a Razorpay payment. This version defines and exposes that endpoint but has no real caller until v0.6 ships — see §1.
- `FR-ORD-010`: An order left in `pending_payment` for more than 30 minutes with no successful payment is automatically transitioned to `cancelled` by a scheduled job. Nothing is released by this transition — there is no stock to free — it exists purely to keep buyer order history accurate rather than showing a payment attempt as perpetually pending.

### 2.3 Buyer order history and detail

- `FR-ORD-011`: A signed-in buyer can view a paginated list of their own orders via `GET /api/orders`, newest first, showing order number, date, status, item count, and total.
- `FR-ORD-012`: A signed-in buyer can view a single order's full detail via `GET /api/orders/:id`, including every snapshotted line item, the shipping address, and the full status history. A buyer requesting another buyer's order ID receives the identical not-found error a nonexistent ID would — never a 403, so order IDs can't be used to enumerate other buyers' purchases.
- `FR-ORD-013`: Every status transition is appended to the order's `statusHistory` with a timestamp, visible on the buyer's own detail view — a buyer sees when their order was paid or shipped, not only its current status.

### 2.4 Cancellation

- `FR-ORD-014`: A buyer can cancel their own order via `POST /api/orders/:id/cancel` only while it is `pending_payment` or `paid`; a request against an order already `processing` or later is rejected with an error naming the current status.
- `FR-ORD-015`: An `order-manager` or `super-admin` can cancel any order under the identical status restriction as `FR-ORD-014`, additionally required to supply a cancellation reason recorded on the order.
- `FR-ORD-016`: Cancelling a `paid` order does not itself process a refund — refunding is Payments' concern (v0.6). Cancellation here only changes order status; it is a precondition an admin (or, later, an automated flow) checks before a refund is triggered once v0.6 exists.

### 2.5 Admin order management

- `FR-ORD-017`: An `order-manager` or `super-admin` can view a paginated, sortable, status-filterable list of all orders via `GET /api/admin/orders`, searchable by order number or buyer email.
- `FR-ORD-018`: An `order-manager` or `super-admin` can view any single order's full detail via `GET /api/admin/orders/:id`, identical in shape to the buyer detail view (`FR-ORD-012`) plus the ordering buyer's identity.
- `FR-ORD-019`: An `order-manager` or `super-admin` can advance an order's status along the allowed state machine (`FR-ORD-008`) via `PATCH /api/admin/orders/:id/status` — e.g. `paid → processing → shipped → delivered` — with an optional carrier/tracking reference recorded on the transition into `shipped`.
- `FR-ORD-020`: A `catalog-manager` is rejected `403` on every `/api/admin/orders/*` route — order management belongs exclusively to `order-manager`/`super-admin`, the reciprocal boundary to the one v0.3 drew around catalog routes (`FR-AUTH-025`).

### 2.6 Notifications

- `FR-ORD-021`: A successful checkout enqueues an order-confirmation email (order number, items, total, shipping address) sent via Resend through the BullMQ worker process — never sent inline within the checkout request/response cycle.
- `FR-ORD-022`: Each subsequent buyer-relevant status transition (`paid`, `shipped`, `delivered`, `cancelled`) enqueues its own notification email through the same worker.
- `FR-ORD-023`: A notification email failing to send never fails or rolls back the status transition that triggered it — the transition is authoritative, the email is a best-effort side effect retried by BullMQ's normal retry policy.

### 2.7 Response envelope

- `FR-ORD-024`: Every order endpoint follows the existing `{ success, data[, pagination] }` / `{ success: false, code, message }` contract, unchanged from v0.2–v0.4.

## 3. Baseline Non-Functional Requirements

**Validation**

- [ ] Shipping address fields (`FR-ORD-004`) are validated server-side with Zod, including PIN code format — malformed addresses never reach the order document.
- [ ] `totalAmount` and every line price are always server-computed at checkout (`FR-ORD-005`, `FR-ORD-027`); a client-supplied value in the checkout request body is ignored, never trusted.

**Indexes**

- [ ] `orders`: unique index on `orderNumber`, index on `user`, index on `status`, compound index on `(user, createdAt)` for the buyer history list (`FR-ORD-011`).

**Error handling and operations**

- [ ] Every endpoint follows `{ success: false, code, message }`, per [`docs/architecture.md`](../../architecture.md) §6.
- [ ] An illegal status transition attempt (`FR-ORD-008`) returns a specific error naming both the current status and the attempted one, never a generic 400.
- [ ] The `pending_payment` auto-cancel job (`FR-ORD-010`) logs every order it cancels; a job run that finds nothing to cancel is not itself an error.

**Security**

- [ ] `GET /api/orders/:id` and `POST /api/orders/:id/cancel` verify the requesting buyer owns the order before returning or mutating anything (`FR-ORD-012`) — ownership is checked in the query itself, not filtered after a fetch by ID.
- [ ] The internal `paid`-transition endpoint (`FR-ORD-009`) is not reachable by any role — it is called only by trusted backend code (Payments, once v0.6 exists), never exposed as a public or admin-authenticated route.

## 4. User Stories

- As a **registered buyer**, I want to check out my cart with a shipping address, so that I can actually receive what I ordered.
- As a **registered buyer**, I want to see my past orders and each one's current status, so that I know what's on its way and what's already arrived.
- As a **registered buyer**, I want to cancel an order before it ships, so that I'm not stuck with something I no longer want.
- As an **order manager**, I want to see every order across all buyers and move it through its lifecycle, so that I can fulfill and ship what's been paid for.
- As an **order manager**, I want to search orders by order number or buyer email, so that I can quickly find the one a support request is about.
- As a **super admin**, I want the same order-management capability as an order manager, so that I can step in when needed.

## 5. Data Model / API Contract

### `orders`

| Field                     | Type                                                                                  | Notes                                                          |
| ------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| `_id`                     | ObjectId                                                                              |                                                                 |
| `orderNumber`             | string, required, unique                                                             | sequential, human-readable — `FR-ORD-007`                       |
| `user`                    | ObjectId → `users`, required                                                          | `FR-ORD-001`                                                    |
| `items`                   | `[{ product: {id,name,slug}, variant: {id,sku,attributes,image}, unitPrice, quantity, lineTotal }]` | frozen snapshot, no live refs — `FR-ORD-003`                     |
| `shippingAddress`         | `{ fullName, phone, line1, line2?, city, state, pincode }`                             | `FR-ORD-004`, `FR-ORD-026`                                       |
| `totalAmount`             | integer, required                                                                    | paise, server-computed — `FR-ORD-005`, `FR-ORD-027`               |
| `status`                  | enum `pending_payment` / `paid` / `processing` / `shipped` / `delivered` / `cancelled` / `refunded` | `FR-ORD-008`                                                    |
| `statusHistory`           | `[{ status, at, note? }]`                                                             | `FR-ORD-013`                                                    |
| `trackingReference`       | string, optional                                                                       | set on `shipped` — `FR-ORD-019`                                  |
| `cancellationReason`      | string, optional                                                                       | admin cancellations only — `FR-ORD-015`                          |
| `createdAt` / `updatedAt` | timestamps                                                                            |                                                                 |

### API endpoints

| Method | Path                                | Auth                             | Purpose                                                    |
| ------ | ------------------------------------ | ----------------------------------- | -------------------------------------------------------------- |
| POST   | `/api/orders`                       | session (buyer)                    | Checkout — `FR-ORD-001`–`007`, `025`–`027`                      |
| GET    | `/api/orders`                       | session (buyer)                    | Own order history — `FR-ORD-011`                                |
| GET    | `/api/orders/:id`                   | session (buyer, owner-only)        | Own order detail — `FR-ORD-012`–`013`                           |
| POST   | `/api/orders/:id/cancel`            | session (buyer, owner-only)        | Buyer cancellation — `FR-ORD-014`                                |
| GET    | `/api/admin/orders`                 | session (`order-manager`/`super-admin`) | Admin list, filterable/searchable — `FR-ORD-017`            |
| GET    | `/api/admin/orders/:id`             | session (`order-manager`/`super-admin`) | Admin detail — `FR-ORD-018`                                   |
| PATCH  | `/api/admin/orders/:id/status`      | session (`order-manager`/`super-admin`) | Advance status — `FR-ORD-019`                                 |
| POST   | `/api/admin/orders/:id/cancel`      | session (`order-manager`/`super-admin`) | Admin cancellation — `FR-ORD-015`                             |
| _internal_ | `markOrderPaid(orderId, paymentId)` | trusted server code only, no route | Reserved for Payments v0.6 — `FR-ORD-009`                     |

## 6. UI/UX Requirements

**`buyer-app`** — client-rendered, session-gated (`docs/architecture.md` §4.1).

- **Checkout**: order summary from the current cart (reusing v0.4's cart data), a shipping-address form, and a submit step that hands off to Payments (v0.6) once it exists — this version's checkout screen ends at order creation, with a "payment coming next" placeholder state until v0.6 lands. Any `droppedItems` in the response are surfaced clearly before the buyer is taken further.
- **Order history**: a list (order number, date, status badge, total) with pagination, reusing v0.4's empty/loading/error state patterns.
- **Order detail**: line items, shipping address, and a visual status timeline built from `statusHistory`; a cancel button shown only while `status` is `pending_payment` or `paid`.

**`admin-app`** — role-gated to `order-manager`/`super-admin`; a `catalog-manager` session never sees the Orders nav entry at all, matching the server-side 403 (`FR-ORD-020`).

- **Order list**: table (order number, buyer email, date, status, total), status filter, search, pagination — reusing the `Table`/`Pagination`/`SortableHeader` components from `admin-app`'s existing catalog grids.
- **Order detail**: full line items, shipping address, status timeline, a status-advance control constrained to the legal next states from `FR-ORD-008` (never a free-form status dropdown), and a cancel action with a required reason field.

## 7. Out of Scope

- **Payment capture and verification** — this version creates orders in `pending_payment` and defines the seam for Payments (v0.6) to call; it does not integrate Razorpay itself.
- **Refund processing** — cancellation changes order status only (`FR-ORD-016`); issuing money back is v0.6.
- **Buyer address book** — one ad-hoc address per checkout (`FR-ORD-026`); reusable saved addresses remain deferred from v0.3 §7.
- **Partial shipments / split orders** — one order ships as one unit in this version; splitting a single order across multiple shipments is not modeled.
- **Invoice/GST-compliant document generation** — deferred to Launch Readiness (v1.0), which explicitly owns India/Razorpay compliance pages.
- **Returns** (post-delivery), as distinct from pre-shipment cancellation (`FR-ORD-014`).
- **Order editing** — an order's line items and address are fixed at checkout; no add/remove-item-after-placement flow exists.

## 8. Acceptance Criteria

**Checkout**

- [ ] Checking out a cart with at least one available line creates an order in `pending_payment` with a unique, sequential order number, and clears the ordered lines from the cart. — `FR-ORD-001`, `FR-ORD-005`, `FR-ORD-006`, `FR-ORD-007`
- [ ] Checking out a cart with zero available lines is rejected. — `FR-ORD-002`
- [ ] Checkout without a complete, valid shipping address is rejected; a malformed PIN code is rejected specifically. — `FR-ORD-004`
- [ ] Archiving a product after an order containing it exists does not change that order's stored line item in any way. — `FR-ORD-003`
- [ ] A line that becomes unavailable between cart view and checkout commit is dropped from the created order and reported in `droppedItems`, while the rest of checkout still succeeds. — `FR-ORD-025`
- [ ] `totalAmount` submitted by the client on the checkout request has no effect — the stored value is always the server-computed sum. — `FR-ORD-005`, `FR-ORD-027`

**Status lifecycle**

- [ ] Every legal transition in `FR-ORD-008`'s graph succeeds; every illegal one (e.g. `pending_payment` → `shipped` directly) is rejected with an error naming both statuses. — `FR-ORD-008`
- [ ] An order left in `pending_payment` past the 30-minute window is auto-cancelled by the scheduled job, with the transition recorded in `statusHistory`. — `FR-ORD-010`

**Buyer surfaces**

- [ ] A buyer's order list shows only their own orders, newest first, paginated. — `FR-ORD-011`
- [ ] A buyer requesting another buyer's order ID receives the same error as a nonexistent ID. — `FR-ORD-012`
- [ ] An order's detail view shows a `statusHistory` entry for every transition it has undergone. — `FR-ORD-013`
- [ ] A buyer can cancel a `pending_payment` or `paid` order; cancelling a `processing` or later order is rejected, naming the current status. — `FR-ORD-014`

**Admin surfaces**

- [ ] An `order-manager` can list, search, filter, view, and advance the status of any order. — `FR-ORD-017`, `FR-ORD-018`, `FR-ORD-019`
- [ ] A `catalog-manager` session is rejected 403 on every `/api/admin/orders/*` route. — `FR-ORD-020`
- [ ] An admin cancellation without a reason is rejected; one with a reason succeeds under the same status restriction as buyer cancellation. — `FR-ORD-015`

**Notifications**

- [ ] A successful checkout enqueues exactly one confirmation email job; the checkout response itself does not wait on the email actually sending. — `FR-ORD-021`, `FR-ORD-023`
- [ ] Each of `paid`, `shipped`, `delivered`, and `cancelled` enqueues its own notification job when reached. — `FR-ORD-022`

## 9. Dependencies

- **Authentication (v0.3)** — buyer identity for checkout/history, `order-manager`/`super-admin` roles for admin endpoints.
- **Shopping Cart (v0.4)** — checkout's sole input; relies on `FR-CART-016`'s `unavailable` flag as the authoritative availability check.
- **Product Catalog (v0.2)** — the source of every snapshotted line item's original data at the moment of checkout.
- **Resend + BullMQ** — order notification emails (`FR-ORD-021`–`023`), the same infrastructure `docs/architecture.md` §3/§4.3 already designates for background workers.
- **Payments (v0.6, forward dependency)** — the real caller of `FR-ORD-009`'s `paid`-transition seam; until it ships, no order in this system can actually leave `pending_payment` except via cancellation or auto-cancel.

### Resolved during drafting

- **Whether checkout should hard-fail if any cart line is unavailable** — no; it drops just the unavailable lines and reports them (`FR-ORD-025`), so a race condition on one item doesn't block a buyer from buying everything else in their cart.
- **Where the `paid` transition seam lives** — an internal, routeless function (`FR-ORD-009`) rather than a callable-but-unsecured admin endpoint, since exposing it as any kind of HTTP route before v0.6's real signature verification exists would be an unguarded way to mark arbitrary orders paid.
