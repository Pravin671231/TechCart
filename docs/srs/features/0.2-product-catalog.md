# SRS v0.2 — Product Catalog

**Status:** Draft — open questions resolved 2026-07-22; data-model revision (embedded variants, flat mrp/discount/sellingPrice pricing, category/brand status + category image, restructured specifications, new `categoryVariants`, admin search/detail-view additions, buyer fuzzy search) resolved 2026-07-24 — see §10 Decisions #10–#17; full-document approval still pending before moving to milestone/issue breakdown.
**Depends on:** none for buyer-facing read paths; admin write paths are temporarily protected by a shared-secret header until Authentication (v0.3) replaces it with real RBAC — see Dependencies and Resolved Decisions.

---

## 1. Feature Overview

The Product Catalog is the system's source of truth for what's for sale: products organized into categories, browsable and searchable by buyers, fully managed by admins. It's the first feature built on top of the M0/M1 infrastructure and the first to touch MongoDB for real — `backend/src/config/db.ts` is currently a no-op stub, and this feature replaces it with a live Mongoose connection. Every later feature (Cart, Orders, Dashboard) references `products`/`categories`, so this version's data model is effectively load-bearing for the rest of the SRS. The catalog spans heterogeneous categories via category-governed specifications (`categorySpecification`), a first-class brand entity, and embedded sellable product variants (`products.variants`) with their own SKU/price/stock.

Scope is deliberately sized for the "small-to-medium catalog store" constraint already fixed in `SRS.md` §2.5: two-level category hierarchy, MongoDB Atlas Search for search/filtering (per `docs/architecture.md` §9's decision, revisit past ~50k SKUs). A product is single-SKU by default; a product needing a size/color matrix instead owns one or more embedded variants (`products.variants`), each an independently priced/stocked/SKU'd sellable item under a shared parent product — see §10 Decision #10 (supersedes Decision #7).

## 2. Functional Requirements

### Buyer-facing browsing, search, filtering

- `FR-CAT-001`: Buyer can view a paginated list of published products on a catalog listing page.
- `FR-CAT-002`: Buyer can view a paginated list of published products filtered to a single category (and, for a parent category, its subcategories).
- `FR-CAT-003`: Buyer can view a single product's detail page by its slug, showing all publicly visible fields (name, description, price, images, category, stock status).
- `FR-CAT-004`: Buyer can search products by keyword; results match against product name and description (case-insensitive, partial match). Search additionally applies fuzzy/typo-tolerant matching (via Atlas Search) so minor misspellings still surface relevant results — Decision #17.
- `FR-CAT-005`: Buyer can filter the catalog/search/category listing by a price range (min/max), applied against `sellingPrice`.
- `FR-CAT-006`: Buyer can sort listing results by: relevance (search only), price ascending, price descending (both against `sellingPrice`), newest first.
- `FR-CAT-007`: Listing/search/category endpoints are paginated with a fixed default page size and a server-enforced maximum page size.
- `FR-CAT-008`: A product with zero stock is still visible in listings and on its detail page, marked "out of stock," and excluded from any "in stock only" filter.
- `FR-CAT-009`: A product with status `draft` or `archived` is never returned by any buyer-facing endpoint, regardless of query parameters.
- `FR-CAT-010`: An empty result set (no matches for a search/filter combination) returns a valid empty response, not an error.

### Admin — product management

- `FR-CAT-011`: Admin (catalog-manager or super-admin) can create a product with: name, SKU, description, price, category, brand, stock quantity, and 1+ images.
- `FR-CAT-012`: SKU is unique across all products and their embedded variants (one shared namespace — see `products.variants`, Decision #10). Enforced via a unique index on `products.sku`, a separate unique multikey index on `products.variants.sku`, plus an application-level cross-check at write time (a single DB index can't span both fields). Creating or updating a product or variant with a duplicate SKU is rejected with a validation error.
- `FR-CAT-013`: Product slug is auto-generated from name at creation time; on collision with an existing slug, a numeric suffix is appended to keep it unique.
- `FR-CAT-014`: Admin can update any editable field of an existing product (name, description, price, category, stock, images, status).
- `FR-CAT-015`: Admin can set a product's status to `draft`, `published`, or `archived`.
- `FR-CAT-016`: Admin can delete a product; deletion is a soft delete (status → `archived`), not a hard row delete — later features (Orders) will reference products by ID and must not break on a deleted product.
- `FR-CAT-017`: Admin can view a paginated, searchable, sortable list of all products regardless of status (draft/published/archived all visible in the admin grid).
- `FR-CAT-018`: Price is stored as flat fields: `mrp` (integer, paise, required, > 0), `discount` (integer 0–99, default 0), `sellingPrice` (server-computed, see `FR-CAT-062`). No `currency` field — the market is India-only (`SRS.md` §2.5), documented as INR in prose. Validation rejects zero, negative, non-integer, or non-numeric `mrp`, and out-of-range/non-integer `discount`.
- `FR-CAT-019`: Stock quantity must be a non-negative integer; validation rejects negative or non-integer input.
- `FR-CAT-020`: Admin can adjust a product's stock quantity independently of other fields (a dedicated stock-update path, not just full-record edit).
- `FR-CAT-068`: Admin can view a single product's full detail (all fields, any status — draft/published/archived) via a dedicated read-only detail view, distinct from the create/edit form — backed by `GET /api/admin/products/:id` (Decision #17).

### Admin — category management

- `FR-CAT-021`: Admin can create a category with: name, and an optional parent category (max depth: one level — a category may have a parent, but a subcategory may not itself have children).
- `FR-CAT-022`: Category slug is auto-generated from name, unique, same collision-handling as `FR-CAT-013`.
- `FR-CAT-023`: Admin can update a category's name or parent.
- `FR-CAT-024`: Admin can delete a category only if it has zero products directly assigned to it and zero subcategories; deletion is rejected with a clear error otherwise (products/subcategories must be reassigned or removed first). A successful deletion also cascades to delete that category's `categorySpecification` **and `categoryVariants`** definitions.
- `FR-CAT-025`: Admin can view a list of all categories, showing parent/child structure and product count per category, and is searchable by name (case-insensitive partial match).
- `FR-CAT-026`: Buyer-facing endpoints can list all categories (for navigation menus), returning only the parent/child structure — no admin-only fields.
- `FR-CAT-063`: Admin can toggle a category's `status` (boolean, default `true`) without deleting it. `status: false` hides the category from the buyer-facing nav endpoint (`FR-CAT-026`); it does not bypass the delete guard (`FR-CAT-024`).
- `FR-CAT-064`: Admin can set/update a category's optional `image` (R2 URL) for buyer-facing nav display, uploaded through the existing presign flow using `purpose: category-image`.

### Images

- `FR-CAT-027`: Admin can upload product/brand images, stored via **Cloudflare R2** (S3-compatible object storage) per `docs/architecture.md`'s system diagram; the API stores the returned object URL(s), not raw image bytes.
- `FR-CAT-028`: A product must have at least 1 and at most 8 images; upload/edit requests violating this bound are rejected.
- `FR-CAT-029`: Uploaded images are restricted to JPEG, PNG, and WebP; other formats are rejected before reaching R2.

### Admin — temporary access control (pre-Authentication)

- `FR-CAT-030`: Every admin endpoint (all product, category, brand, specification, and variant create/update/delete/stock-adjust routes, plus the image-upload presign endpoint) requires a shared-secret header (e.g. `X-Admin-Key`) matching a server-side environment variable, checked by a single reusable Express middleware — not hand-rolled per route.
- `FR-CAT-031`: A request to an admin endpoint with a missing or incorrect shared-secret header is rejected with a 401, following the existing error contract, before it reaches any controller logic.
- `FR-CAT-032`: The shared-secret middleware is written as an isolated, swappable layer — replacing it with real session/role-based auth in v0.3 must not require changes to route paths, controllers, or services, only the guard itself.

### Admin — brand management

- `FR-CAT-033`: Admin can create a brand with name and optional logo/description.
- `FR-CAT-034`: Brand slug is auto-generated from name, unique, same collision-handling as `FR-CAT-013`.
- `FR-CAT-035`: Admin can update a brand's name, logo, or description.
- `FR-CAT-036`: Admin can delete a brand only if zero products of **any** status (draft/published/archived) reference it; rejected with a clear error otherwise.
- `FR-CAT-037`: Admin can view a list of all brands with product count per brand, and is searchable by name (case-insensitive partial match).
- `FR-CAT-038`: Buyer-facing endpoint lists all brands (for filter UI) — public, no admin-only fields.
- `FR-CAT-039`: Product create/update requires a valid `brand` reference; rejected if the brand doesn't exist. Brand is **required** on every product.
- `FR-CAT-040`: Buyer can filter a catalog/search/category listing by brand.
- `FR-CAT-065`: Admin can toggle a brand's `status` (boolean, default `true`) without deleting it. `status: false` hides the brand from the buyer-facing brand list (`FR-CAT-038`); it does not bypass the delete guard (`FR-CAT-036`).

### Admin — category-governed specifications

- `FR-CAT-041`: Admin can define a category's specification groups: one `categorySpecification` document per category, containing `specificationGroups: [{groupName, specifications: [{name, type (enum: text/number/boolean), unit, required flag}]}]`. There is no `enum`-type/`options` field anymore (Decision #14), and no `filterable` flag (`FR-CAT-045` removed, Decision #14).
- `FR-CAT-042`: Admin can update or delete a specification group, or an individual specification field within a group; deleting a specification field currently referenced by ≥1 product's specifications (matched by `groupName` + `name`) is rejected with a clear error — same in-use guard as before, now checked against the nested structure.
- `FR-CAT-043`: Product create/update performs structural validation of provided specifications against its own category's `categorySpecification` groups (all `required` specifications present, unknown spec-name keys rejected). Value type-checking and enum-options validation no longer apply — there is no type/options metadata left to check against (Decision #14). Values are stored generically: `specifications: [{groupName, values: [{name, value}]}]`, `value` is Mixed.
- `FR-CAT-044`: Buyer-facing product detail page shows all of a product's specification name/value pairs.
- `FR-CAT-045`: **Removed — moved to Out of Scope (§7); see Decision #14.** (Was: buyer-facing filter by a `filterable` specification.)

### Admin — category-governed variant types (UI-rendering guide)

- `FR-CAT-066`: Admin can define a variant-type field for a category (`categoryVariants`): `name`, `code`, `type` (enum: `text`/`select`/`color`/`number`, default `select`), `required` flag (UI hint only, default `false`), and `options` (`[{label, value}]`, relevant for `select`/`color` types). One `categoryVariants` document per category.
- `FR-CAT-067`: Admin can update or delete a category's variant-type field definition. Unlike `FR-CAT-042`'s specification-definition guard, deleting a variant-type definition is never blocked by in-use product variants — it is a UI-rendering guide only (drives `admin-app`'s dynamic variant-editor form, e.g. a color-swatch picker for a `color`-typed axis, a dropdown for `select`) and does not validate product variant `attributes` server-side, consistent with `FR-CAT-043`'s loosened specification-value validation. Deleting one simply means the admin-app variant editor falls back to generic text inputs for that category going forward.

### Admin — product variants (sellable, not tags)

- `FR-CAT-046`: Admin can add a variant to a product's embedded `variants` array: `sku` (required, shared uniqueness namespace with `products.sku` — `FR-CAT-012`), one or more attribute pairs (`{ name, value }`, e.g. `Color=Red` + `Size=L`), an optional `images` set (1–2 items when provided — not the product's 1–8 bound, not a single image; falls back to the parent product's images when absent), its own `mrp`/`discount`/`sellingPrice` (same rules as `FR-CAT-018`), its own `stock`, and an optional `weight`. No `barcode` field.
- `FR-CAT-047`: Admin can update a variant, or deactivate it (`active: false`, default `true` — a soft delete, mirroring `FR-CAT-016`'s rationale that future Order references must not break on a removed variant). Variants are never hard-deleted; they remain embedded on the product document even when inactive.
- `FR-CAT-048`: No two variants of the same product may share an identical attribute-pair combination; validated at the application layer by checking within the product's own `variants` array (no cross-collection query needed, now that variants are embedded).
- `FR-CAT-049`: A variant's price/stock fields follow the exact same validation as the product's own: `mrp` > 0 integer paise, `discount` 0–99, `sellingPrice` always server-computed, `stock` a non-negative integer.
- `FR-CAT-050`: A product with zero active variants is sold using its own `sku`/`price`/`stock` (original `FR-CAT-011`–`020` behavior, unchanged). A product with one or more active variants is sold **per-variant** — the base product's own `price`/`stock` become "starting from" display fields only, not the purchasable unit.
- `FR-CAT-051`: Buyer-facing product detail page defaults to displaying the first (or lowest-`sellingPrice`) active variant's price/stock/images when a product has variants; selecting a different variant updates the displayed price, stock, and images accordingly (falling back to the parent product's images if the selected variant has none of its own).
- `FR-CAT-052`: Buyer can filter a category listing by a variant attribute name/value (e.g. Color = Red), queried/indexed directly against `products.variants.attributes` of `active` variants only — no denormalized rollup or live join needed now that variants are embedded (supersedes the prior `availableVariantAttributes` rollup approach — see Decision #16).
- `FR-CAT-053`: A variant has no independent visibility status — it inherits entirely from its parent product's status. A draft/archived product's variants never appear buyer-facing, per the existing `FR-CAT-009` guarantee, regardless of the variant's own `active` flag.

### Images — Cloudflare R2 upload mechanics

- `FR-CAT-054`: Admin requests a short-lived presigned upload URL from the backend for each image before uploading directly to R2; the backend never receives raw image bytes.
- `FR-CAT-055`: The presigned-URL request declares the image's content-type and is rejected server-side if it isn't JPEG/PNG/WebP, before a presigned URL is issued (enforces `FR-CAT-029`).
- `FR-CAT-056`: The presign response returns a **server-generated** object key of the form `{purpose}/{uuid}.{ext}` (e.g. `product-images/{uuid}.webp`, `brand-logos/{uuid}.webp`, `category-images/{uuid}.webp`) — never a path keyed by the parent entity's ID, since the product/brand/category may not exist yet at upload time. The client cannot choose or influence the key.
- `FR-CAT-057`: Registering an uploaded image's URL against a product or brand validates that the object key was actually issued by a prior presign call (tracked server-side, not yet consumed) — arbitrary or unrecognized object URLs are rejected.
- `FR-CAT-058`: Presigned upload URLs expire 5 minutes after issuance.
- `FR-CAT-059`: The same presign endpoint serves product images, brand logos, and category images, parameterized by a `purpose` field (`product-image` | `brand-logo` | `category-image`) that determines the path prefix and any size/format constraints.
- `FR-CAT-060`: Registering uploaded image URLs against a product enforces the 1–8 image count bound (`FR-CAT-028`) server-side, regardless of how many presigned URLs were requested. A variant's `images` set (when provided) is bounded 1–2 instead — a distinct rule from `FR-CAT-046`.

### Price — computed price mechanics

- `FR-CAT-061`: `discount` is an integer percentage **0–99** (not 100 — a `discount: 100` would force `sellingPrice: 0`, violating the `> 0` rule); default `0` if omitted; validation rejects out-of-range or non-integer input.
- `FR-CAT-062`: `sellingPrice` is computed server-side as `mrp - floor(mrp * discount / 100)` on every create/update — never accepted directly from the client — guaranteeing it always stays consistent with `mrp`/`discount`, and (given the 0–99 discount bound) always `>= 1`.

## 3. Baseline Non-Functional Requirements

Feature-scoped only — see `SRS.md` §4 item 3 for why this isn't exhaustive (full system NFRs land in v0.8/v0.9).

- [ ] All admin write endpoints (create/update/delete on products and categories) validate input server-side with Zod schemas — this is the first feature to add a `zod` dependency to `backend`.
- [ ] All buyer-facing read endpoints validate query parameters (page, limit, price range, sort) server-side; invalid values are rejected or clamped, never passed through to the DB layer unvalidated.
- [ ] `products` collection indexes: unique index on `sku`, unique index on `slug`, index on `category`, index/text-or-Atlas-Search index supporting `FR-CAT-004`'s keyword search.
- [ ] `categories` collection indexes: unique index on `slug`, index on `parentCategory`.
- [ ] All endpoints follow the existing error contract (`{ success: false, code, message }`, per `docs/architecture.md` §6) — no ad hoc error shapes introduced by this feature.
- [ ] `backend/src/config/db.ts`'s Mongoose connection includes basic startup failure handling (the process should not silently serve traffic against a dead DB connection) — full connection-resilience/retry policy is deferred to v0.8, this is just "don't fail silently."
- [ ] No secrets (Cloudflare R2 credentials, admin shared-secret) committed to the repo; sourced from environment variables, following the existing `.env.example` pattern in `backend/`.
- [ ] The admin shared-secret guard (`FR-CAT-030`–`032`) is a single middleware applied at the router level, not duplicated per-controller — keeps the v0.3 swap-out a one-place change.
- [ ] `brands` collection: unique index on `slug`.
- [ ] `categorySpecifications` collection: unique index on `category` (one grouped document per category); uniqueness of spec names within a category's groups is an application-level check, not a DB index, since specs now live in nested arrays.
- [ ] `categoryVariants` collection: unique index on `category` (one document per category).
- [ ] Product/variant SKU shared namespace: unique index on `products.sku`, a separate unique multikey index on `products.variants.sku`, plus an application-level cross-check between the two at write time (`FR-CAT-012`, Decision #10) — a single DB index cannot span both fields. Duplicate attribute-combination prevention (`FR-CAT-048`) is an application-level check, not a DB index, since `attributes` is an array.
- [ ] `products.brand` indexed.
- [ ] `products.variants.attributes` indexed via Atlas Search `embeddedDocuments` (`active` variants only), backing `FR-CAT-052`'s filter directly — no denormalized rollup (Decision #16).
- [ ] **Atlas Search scope is deliberately narrow**: only free-text keyword search (`FR-CAT-004`, with fuzzy matching) and variant-attribute faceted filtering (`FR-CAT-052`) use Atlas Search. Category, brand, status, price-range, and in-stock filters remain plain indexed MongoDB queries.
- [ ] `sellingPrice` is never trusted from client input on either `products` or embedded variants — always recomputed server-side from `mrp`/`discount` on every write.
- [ ] `mrp`/`sellingPrice` are stored as integer paise to avoid float drift.
- [ ] R2 presigned URLs expire 5 minutes after issuance; object keys are server-generated (never client-chosen), and registering an image validates the key was actually issued and not yet consumed.

## 4. User Stories

- As a **guest**, I want to browse products by category, so that I can find things I'm interested in without creating an account.
- As a **guest**, I want to search for a product by name, so that I can quickly find something specific.
- As a **guest**, I want to filter and sort a product listing by price, so that I can shop within my budget.
- As a **guest**, I want to filter products by brand and by variant options like color or size, so that I can narrow down to exactly what I want.
- As a **registered buyer**, I want the same browsing/search/filtering as a guest (no catalog feature is gated behind login — that's a Cart/Checkout concern, not Catalog).
- As a **catalog manager**, I want to create and edit products with images, price, and stock, so that the storefront reflects what's actually available to sell.
- As a **catalog manager**, I want to organize products into categories, so that buyers can navigate the storefront logically.
- As a **catalog manager**, I want to define specification fields and add priced/stocked variants to a product, so that I can accurately represent products that come in multiple configurations.
- As a **catalog manager**, I want to mark a product out of stock or archive it, so that buyers don't see things that aren't purchasable, without losing the product's history.
- As a **super admin**, I want the same catalog-management capabilities as a catalog manager (role distinction here is only relevant once v0.3 RBAC exists).

## 6. UI/UX Requirements

Screen-level detail — layout, components, states, and the design language behind these requirements — lives in [`docs/ui/buyer-app.md`](../../ui/buyer-app.md) and [`docs/ui/admin-app.md`](../../ui/admin-app.md). This section stays the source of truth for _what_ the UI must do; those documents own _how_ it looks and behaves.

**`buyer-app`** (per `docs/architecture.md` §4.1's rendering strategy — catalog listing and product detail are both ISR):

- Catalog listing page: product grid, category filter, brand filter, variant-attribute facets, price-range filter, sort control, pagination controls. Loading state (skeleton grid), empty state ("no products match your filters"), error state (fetch failure — non-blocking, doesn't crash the page).
- Category page: same grid, pre-filtered to the category, breadcrumb showing parent category if any.
- Search results page: same grid, keyword shown, empty state distinct from the filter-empty state ("no results for '...'"); search applies fuzzy/typo-tolerant matching (`FR-CAT-004`) so close misspellings still surface results.
- Product detail page: images (gallery/carousel), name, price, description, category link, brand name/link, specification table (grouped by `specificationGroups`), stock-status badge (in stock / out of stock — no "add to cart" control yet, that's v0.4), and — when the product has variants — a variant selector (e.g. color swatches / size buttons) that updates the displayed price, stock, and images (1–2, falling back to the parent product's images), defaulting to the first/lowest-`sellingPrice` active variant.

**`admin-app`** (per `docs/architecture.md` §4.2 — TanStack Table for catalog grids):

- Product list: TanStack Table with columns (image thumbnail, name, SKU, brand, category, price, stock, status), search box, status filter, pagination.
- Product detail view: a read-only page showing all fields including draft/archived visibility, separate from the create/edit form — `FR-CAT-068`.
- Product create/edit form: all fields from the data model, client-side validation mirroring the backend Zod schema (per root `CLAUDE.md`'s "no shared validation package" decision — this is `admin-app`'s own separate validation, not shared code), image upload widget with preview and the 1–8 count constraint surfaced in the UI, a brand selector, dynamic spec fields grouped by `specificationGroups` rendered from the product's category's `categorySpecification` document, and a variant editor (add/edit/deactivate) where each variant has its own SKU, attribute pairs (rendered per the category's `categoryVariants` type definitions when present — color swatch / dropdown / etc. — falling back to generic text inputs otherwise), `mrp`/`discount`/`sellingPrice` (display-only, computed), stock, optional weight, an active toggle, and an optional 1–2 image picker.
- Category list: table (name, parent, product count, status), search box, create/edit form (including image upload and active toggle), delete blocked with an inline error if `FR-CAT-024`'s guard rejects it.
- Category variant-type editor: define a category's variant-type list (name, code, type picker — text/select/color/number, required toggle, options list for select/color types) driving the product variant editor's rendering; no delete-guard warning needed on removal.
- Brand list: table (name, logo, product count, status), search box, create/edit form (including active toggle), delete blocked with an inline error if `FR-CAT-036`'s guard rejects it.

## 7. Out of Scope

- Product variants (size/color) are now first-class sellable child records (own SKU/price/stock) embedded on a single parent product — but there is still no linking/grouping _between separate `Product` documents_. Two genuinely different products (even from the same brand) are never linked; a variant always belongs to exactly one parent product.
- Buyer-facing filtering by a curated `filterable` specification flag (former `FR-CAT-045`) — the simplified `categorySpecification` model has no `filterable` flag to curate which specs are facet-eligible, so spec-based faceted filtering is dropped from v0.2 scope; `FR-CAT-044` (showing all spec name/value pairs on the product detail page) is unaffected. Revisit in a later version if faceted spec filtering becomes a priority.
- Reviews and ratings.
- Wishlists / "save for later."
- Recommendation engine / "related products."
- Bulk import/export (CSV, etc.).
- Multi-warehouse / per-location inventory — a single global `stock` integer per product (or per variant, when variants exist) only.
- Category depth beyond two levels (parent + one level of children).
- Specification-axis inheritance from parent category to subcategory — `categorySpecification` definitions are scoped to the exact category a product is assigned to.
- R2 object cleanup on brand/product deletion — orphaned storage objects are not proactively deleted in this version (see §10 Resolved Decisions).
- Real RBAC enforcement on admin endpoints — protected by a temporary shared-secret header (`FR-CAT-030`–`032`) until v0.3 ships session/role-based auth.
- Cart/"add to cart" interaction — product detail page is read-only in this version (v0.4 territory).

## 8. Acceptance Criteria

- [ ] A guest can load the catalog listing page and see only `published` products, paginated.
- [ ] A guest can navigate to a category and see only products in that category (and its subcategories, if any).
- [ ] A guest can search a keyword and get correct, case-insensitive, partial-match results, including a correct empty-state for a no-match search.
- [ ] A guest can combine a price-range filter with sort (e.g., category + price ascending) and get correctly filtered, correctly ordered results.
- [ ] A product with `stock: 0` still appears in listings, marked out of stock, and is excluded when an "in stock only" filter is applied.
- [ ] A `draft` or `archived` product never appears on any public endpoint under any query combination — verified explicitly, not just by omission.
- [ ] An admin can create a product with all required fields; a request missing a required field, with a duplicate SKU, a non-positive price, or a negative/non-integer stock value is rejected with a validation error, not a 500.
- [ ] An admin can edit a product's status to `archived`; the product immediately disappears from all public endpoints while remaining visible in the admin grid.
- [ ] Deleting a product soft-deletes it (record persists with `status: archived`); no product is ever hard-deleted by this feature's endpoints.
- [ ] An admin can create a category, assign products to it, and see an accurate product count in the admin category list.
- [ ] Deleting a category with 0 products/subcategories succeeds; deleting one with either fails with a clear, actionable error message.
- [ ] Uploading a 9th image, or an image in an unsupported format, is rejected before reaching R2.
- [ ] A request to any admin endpoint with a missing or wrong `X-Admin-Key` header is rejected with 401 before any controller/service code runs.
- [ ] Price round-trips correctly as integer paise end-to-end (admin creates a product with `mrp: 49900` → buyer-facing detail/listing responses reflect the same `mrp`/`sellingPrice` with no float drift).
- [ ] `npm run test --workspace backend` includes integration tests (Supertest) covering at minimum: list/search/filter, product CRUD validation failures, category delete-guard, the draft/archived visibility boundary, and the admin shared-secret guard (missing/wrong/correct header) — mirroring the `health` module's existing test pattern.
- [ ] An admin can create a brand, assign products to it, and see an accurate product count (across all statuses) in the admin brand list; deleting a brand with ≥1 referencing product (any status) fails with a clear error.
- [ ] An admin can define a category's specification schema; creating a product with a missing required specification or an unknown spec-name key is rejected with a validation error, not a 500 (value type/enum-options checks no longer apply — Decision #14). Deleting that category cascades to remove its `categorySpecification` and `categoryVariants` definitions.
- [ ] An admin can add two variants to the same product's embedded `variants` array with different attribute combinations (e.g. Color=Red/Size=L and Color=Red/Size=M), each with its own SKU, price, and stock; adding a third variant with an attribute combination identical to an existing one is rejected.
- [ ] A buyer viewing a product with variants sees the first/lowest-`sellingPrice` active variant's price, stock, and images by default; selecting a different variant updates the displayed price, stock, and images (falling back to the parent product's images when the selected variant has none of its own).
- [ ] A buyer can filter a category listing by brand and by a variant attribute name/value, individually and combined with existing price/sort filters. (Filtering by a `filterable` specification — former `FR-CAT-045` — is removed from v0.2 scope, Decision #14.)
- [ ] Requesting a presigned upload URL for a disallowed content-type is rejected before any URL is issued; a presigned URL used after 5 minutes is rejected by R2 itself; registering an image URL with an object key the backend never issued is rejected; registering more than 8 image URLs against a product is rejected.
- [ ] Creating a product with `mrp: 99900, discount: 10` computes and stores `sellingPrice: 89910`; attempting `discount: 100` is rejected (would force `sellingPrice: 0`).
- [ ] Submitting a `sellingPrice` value directly in a create/update request (product or variant) has no effect — it is always server-recomputed from `mrp`/`discount`.
- [ ] Archiving a product hides all of its variants from every buyer-facing endpoint, without needing to touch each variant's own `active` flag.
- [ ] A variant `sku` colliding with any product's own `sku` (or vice versa, across any product) is rejected by the application-level cross-check, even though no single DB index spans both the `products.sku` and `products.variants.sku` indexes (`FR-CAT-012`).
- [ ] Deactivating a category or brand (`status: false`) hides it from the relevant buyer-facing endpoint immediately, remains visible in the admin list, and does not bypass the existing delete guard.
- [ ] An admin can define a category's variant-type list (e.g. a color-typed axis with swatch options); the admin-app product variant editor renders the corresponding input control per axis; deleting a variant-type definition succeeds unconditionally (no in-use guard), and the editor falls back to a generic text input for that axis going forward.
- [ ] Uploading a category image via the presign flow with `purpose: category-image` succeeds and the returned URL is accepted when registered against a category, same mechanics as `product-image`/`brand-logo`.
- [ ] Registering a variant with 3 images (exceeding the 1–2 bound) is rejected; registering with 0 is allowed (falls back to the parent product's images).
- [ ] An admin can search the category and brand admin lists by name and get correctly filtered results.
- [ ] An admin can view a single product's full detail (including draft/archived-only fields) via the dedicated admin detail view, distinct from the edit form.
- [ ] A buyer search for a mistyped keyword (a close misspelling of an existing product name) still returns relevant fuzzy-matched results.

## 10. Resolved Decisions

All open questions from the initial draft were resolved on 2026-07-22; a data-model revision round was resolved on 2026-07-24 (Decisions #10–#17). Kept here as a record of what was asked and decided, rather than silently rewriting requirements without a trace.

1. **Admin endpoints before Authentication exists.** M2 ships before M3 (Authentication) per the fixed milestone order in `docs/milestone.md`. **Decision: accepted, with temporary protection** — admin endpoints are gated by a shared-secret header (`FR-CAT-030`–`032`), not left open, until v0.3 replaces it with real RBAC.
2. **Product variants.** **Decision: superseded by Decision #7 below** — the original "no variant-matrix/grouping feature" call is revisited now that the catalog needs to represent products with multiple sellable configurations (size/color).
3. **Category depth.** **Decision: two-level hierarchy approved** (parent + one level of children, no grandchildren) — matches the original proposal, §2's `FR-CAT-021` and the data model are unchanged.
4. **Currency/price precision.** **Decision: integer paise** — see Decision #11 for the current shape.
5. **Brand.** New required top-level entity, own collection, full admin CRUD with delete-guard (counts products of any status), buyer-facing list + filter.
6. **Category-governed specifications, type-safe storage.** **Decision: superseded in part by Decision #14** — see below for the current, loosened shape.
7. **Product variants are real sellable items, not tags (supersedes Decision #2).** **Decision: superseded in part by Decision #10** — variants remain real sellable items with their own sku/price/stock, but are now embedded rather than a separate collection; see Decision #10.
8. **Image storage: Cloudflare R2 replaces Cloudinary.** Presigned direct-upload flow with a server-generated object key (`{purpose}/{uuid}.{ext}`, not entity-ID-keyed — avoids a chicken-and-egg problem for not-yet-created products/brands/categories), 5-minute expiry, and ownership validation before an uploaded URL is accepted. The same endpoint serves product images, brand logos, and category images. R2 objects are not proactively cleaned up on brand/product deletion in this version — accepted as a minor cost tradeoff at this scale, not a correctness gap.
9. **Price becomes a structured object.** **Decision: superseded by Decision #11** — see below for the current, flat shape.
10. **Product variants: embedded subdocuments, not a separate collection (supersedes Decision #7).** `products.variants` is an embedded array of subdocuments (`sku`, `images` [1–2 items when present, falls back to parent], `mrp`/`discount`/`sellingPrice`, `stock`, `weight`, `attributes`, `active`) — no `barcode` field. `active` (default `true`) preserves the soft-delete guarantee for future Cart/Orders references (`FR-CAT-047`) — variants are never hard-deleted. Because `sku` uniqueness now spans a top-level field and a multikey array field on the _same_ collection, no single DB index can cover both — enforcement is a unique index on `products.sku`, a separate unique multikey index on `products.variants.sku`, plus an application-level cross-check at write time (`FR-CAT-012`). The no-duplicate-attribute-combination rule (`FR-CAT-048`) is simpler now: an in-document array check, not a cross-collection query. Affects `FR-CAT-012`, `046`–`053`.
11. **Price: flat `mrp`/`discount`/`sellingPrice` fields (partially reinstates Decision #9).** Drops the nested `{mrp, currency, discount, sellingPrice}` object and the `currency` field, but **keeps** the server-computed `sellingPrice` mechanic and the 0–99 `discount` bound from the original design — these are flat top-level fields on both `products` and embedded variants, not wrapped in a `price` sub-object, and not the bare `price`/`salePrice` pair considered in an earlier revision round. `sellingPrice = mrp - floor(mrp * discount / 100)`, always server-recomputed, never client-settable (`FR-CAT-018`, `061`, `062`). All prices are INR (single-market product, `SRS.md` §2.5) — no currency field needed. Integer-paise remains the storage convention.
12. **Product status: 3-state enum reaffirmed.** Collapsing product `status` to a Boolean was considered and explicitly rejected — `status` stays `draft`/`published`/`archived` exactly as `FR-CAT-009`/`015`/`016` already describe. No FR/data-model change; recorded so the question isn't re-litigated.
13. **Category & Brand: lightweight `status` toggle, category `image`, `parent` → `parentCategory`.** `categories` and `brands` each gain their own simple `status: Boolean` (default `true`) — distinct from Product's 3-state enum, a plain active/inactive switch (`FR-CAT-063` category, `FR-CAT-065` brand). `status: false` hides a category from buyer-facing nav (`FR-CAT-026`) or a brand from the buyer-facing brand list (`FR-CAT-038`); it's a new, lighter-weight _alternative_ to deleting, and does **not** bypass the existing hard-delete guards (`FR-CAT-024` zero products/subcategories; `FR-CAT-036` zero referencing products of any status). Categories also gain an optional `image` (string URL, `FR-CAT-064`) for buyer-facing nav display, uploaded through the existing R2 presign flow (`FR-CAT-054`–`059`) by extending the `purpose` enum with `category-image` alongside `product-image`/`brand-logo` (`FR-CAT-059` updated in place). `categories.parent` is renamed `parentCategory` in the data model table to match intended naming — no behavior change, `FR-CAT-021`/`023` unaffected.
14. **`categorySpecification`: one grouped document per category, loosened validation (supersedes part of Decision #6).** `categorySpecification` becomes one document per category (unique on `category`) holding `specificationGroups: [{groupName, specifications: [{name, type: enum(text/number/boolean), required, unit}]}]` — no more `enum` type/`options`. `products.specifications` becomes generic `[{groupName, values: [{name, value: Mixed}]}]` (`FR-CAT-043` reworded) — structural validation only (required specs present, unknown spec-name keys rejected); value type-checking and enum-options validation are dropped, since there's no type/options metadata left to check against. `FR-CAT-045` (buyer-facing filter by a `filterable` spec) is **removed from v0.2 scope** — moved to §7 Out of Scope — since the simplified model has no `filterable` flag to curate facet-eligible specs; marked Removed, not renumbered. `FR-CAT-044` (product detail page shows all spec name/value pairs) is unchanged. Corresponding Atlas Search `embeddedDocuments`-by-`stringValue`/`numberValue`/`booleanValue` NFR bullets are dropped, since those fields no longer exist.
15. **New `categoryVariants` collection — admin-app UI-rendering guide only.** `{category (ref, required, unique), variants: [{name, code, type: enum(text/select/color/number) default select, required: Boolean default false, options: [{label, value}]}]}` — one document per category. Purpose is strictly to drive `admin-app`'s dynamic variant-editor form (e.g. a color-swatch picker for a `color`-typed axis, a dropdown for `select`) — `FR-CAT-066`, `067`. It does **not** validate product variant `attributes` server-side, deliberately consistent with Decision #14's loosened specification validation (inconsistent to make variants strict while specs are loose). No delete-guard on removing a `categoryVariants` definition — unlike `categorySpecification`'s in-use guard (`FR-CAT-042`) — since nothing depends on it for validation; removing one just means the admin form falls back to generic text inputs for that category going forward. Category deletion (`FR-CAT-024`) cascades to delete its `categoryVariants` doc too, same as it already cascades to `categorySpecification`.
16. **`products.availableVariantAttributes` rollup removed (consequence of Decision #10).** The denormalized rollup existed solely to avoid a live join against the old separate `productVariants` collection for `FR-CAT-052`'s buyer filter. Since variants are now embedded directly on the product document (Decision #10), there's no join to avoid — `FR-CAT-052` is reworded to filter/index `products.variants.attributes` directly, restricted to `active` variants only. The corresponding NFR bullet is updated to match (Atlas Search `embeddedDocuments` index on `products.variants.attributes`, not a separate rollup field).
17. **Admin search extended to Category/Brand; dedicated admin single-product detail view; buyer search gains fuzzy matching.** Three independent UX additions, decided 2026-07-24: (a) admin Category and Brand list endpoints become searchable by name, case-insensitive partial match, matching the existing Product admin grid (`FR-CAT-025`, `037`); (b) a new dedicated read-only admin product detail view (all fields, any status) is added alongside the existing create/edit form, backed by `GET /api/admin/products/:id` (`FR-CAT-068`); (c) buyer-facing keyword search (`FR-CAT-004`) additionally applies Atlas Search fuzzy/typo-tolerant matching on top of the existing case-insensitive partial match, with no new UI required.
