# SRS v0.2 — Product Catalog

**Status:** Draft — awaiting review
**Last Updated:** 2026-07-28
**Depends on:** MongoDB Atlas, MongoDB Atlas Search, Cloudflare R2. Admin write paths are temporarily protected by a shared-secret header until Authentication (v0.3) replaces it with real RBAC — see §9.

---

## 1. Feature Overview

The Product Catalog is the system's source of truth for what is for sale: products organised into categories, described by category-governed specifications, sold as single items or as priced/stocked variants, browsable and searchable by buyers and fully managed by admins.

It is the first feature built on top of the M0/M1 infrastructure and the first to touch MongoDB for real — `backend/src/config/db.ts` is currently a no-op stub, and this feature replaces it with a live Mongoose connection. Every later feature (Cart, Orders, Dashboard) references `products` and `categories`, so this version's data model is load-bearing for the rest of the SRS. Two consequences follow from that and are treated as hard rules throughout: catalog records are **never hard-deleted** once they can be referenced by an order, and money is **never stored as a float**.

Scope is sized for the "small-to-medium catalog store" constraint fixed in [`SRS.md`](../SRS.md) §2.5: a two-level category hierarchy, and MongoDB Atlas Search rather than a dedicated search vendor (per [`docs/architecture.md`](../../architecture.md) §8 — revisit past ~50k SKUs).

## 2. Functional Requirements

### 2.1 Admin — product management

- `FR-CAT-001`: Admin can create a product with name, SKU, description, brand, category, `mrp`, stock quantity, and at least one image.
- `FR-CAT-002`: Product slug is auto-generated from the product name at creation; on collision with an existing slug a numeric suffix is appended so the slug stays unique.
- `FR-CAT-003`: SKU is unique across all products **and** all embedded product variants — a single shared namespace. Creating or updating a product or variant with a SKU already in use anywhere is rejected with a validation error.
- `FR-CAT-004`: Admin can update any editable field of an existing product (name, description, brand, category, images, `mrp`, `discount`, stock, specifications, SEO fields, `isFeatured`, `lowStockThreshold`).
- `FR-CAT-005`: Admin can view a paginated, sortable list of all products regardless of status — `draft`, `published`, and `archived` products are all visible in the admin grid.
- `FR-CAT-006`: Admin can retrieve a single product by its ID, returning every field at any status, via a read-only detail view distinct from the create/edit form.
- `FR-CAT-007`: Admin can delete a product; deletion is a **soft delete** (`status` → `archived`), never a hard document removal, because Orders (v0.5) will hold product references that must not dangle.
- `FR-CAT-008`: Admin can adjust a product's stock quantity through a dedicated stock-update path, independently of a full-record edit.
- `FR-CAT-009`: Stock quantity must be a non-negative integer; negative, fractional, or non-numeric input is rejected with a validation error.
- `FR-CAT-010`: Admin can mark a product as featured (`isFeatured`, boolean, default `false`) for buyer-facing merchandising placements.
- `FR-CAT-011`: Admin can set a product's `lowStockThreshold` (non-negative integer, default `0`) and filter the admin product grid to products whose stock is at or below their own threshold. This field serves two purposes: it drives the admin low-stock filter here **and** the buyer-facing `low_stock` status in `FR-CAT-096`. The tension is accepted rather than designed away — a restock trigger and a buyer urgency trigger are not usually the same number, so raising the threshold to reorder earlier also makes more products read as low stock to buyers.
- `FR-CAT-012`: Admin can set a product's `metaTitle` and `metaDescription`; when either is absent, buyer-facing pages fall back to the product name and a truncation of its description.
- `FR-CAT-013`: Every catalog write records `createdBy` and `updatedBy`. In this version these fields are reserved and stored as `null` — there is no authenticated admin identity until v0.3 — so no migration is needed once real auth lands.

### 2.2 Admin — category management

- `FR-CAT-014`: Admin can create a category with a name and an optional parent category. The hierarchy is at most two levels deep: a category may have a parent, but a category that already has a parent may not itself be given children.
- `FR-CAT-015`: Category slug is auto-generated from the category name, unique, with the same collision handling as `FR-CAT-002`.
- `FR-CAT-016`: Admin can update a category's name, parent, image, `sortOrder`, and SEO fields.
- `FR-CAT-017`: Admin can view a list of all categories showing parent/child structure and the product count for each category.
- `FR-CAT-018`: Admin can retrieve a single category by its ID, returning every field including inactive categories — this is what backs the category edit form.
- `FR-CAT-019`: Admin can delete a category only if it has zero products directly assigned to it **and** zero subcategories; otherwise the request is rejected with an error naming which guard failed. A successful delete cascades to remove that category's specification definition and variant-type definition.
- `FR-CAT-020`: Admin can set a category's `sortOrder` (integer, default `0`); buyer-facing category listings are ordered by `sortOrder` ascending, then by name as a tiebreaker.
- `FR-CAT-021`: Admin can set an optional category `image`, uploaded through the presign flow with `purpose: category-image`, for buyer-facing navigation and category landing displays.
- `FR-CAT-022`: Admin can set a category's `metaTitle` and `metaDescription`, with the same fallback behaviour as `FR-CAT-012`.

### 2.3 Admin — brand management

Brands are a first-class entity because buyers filter by brand (`FR-CAT-064`); a filter cannot exist without a managed collection behind it.

- `FR-CAT-023`: Admin can create a brand with a name, an optional logo, and an optional description.
- `FR-CAT-024`: Brand slug is auto-generated from the brand name, unique, same collision handling as `FR-CAT-002`.
- `FR-CAT-025`: Admin can update a brand's name, logo, or description.
- `FR-CAT-026`: Admin can view a list of all brands with the product count for each brand.
- `FR-CAT-027`: Admin can retrieve a single brand by its ID, returning every field including inactive brands.
- `FR-CAT-028`: Admin can delete a brand only if zero products of **any** status (`draft`, `published`, or `archived`) reference it; otherwise the request is rejected with a clear error. Archived products still count — they may appear on historical orders.
- `FR-CAT-029`: Product create and update require a valid brand reference; a request naming a brand that does not exist is rejected with a validation error. Brand is required on every product.

### 2.4 Admin — category-based specifications

- `FR-CAT-030`: Admin can define a category's specification schema: one specification document per category, holding `specificationGroups`, each group having a `groupName` and a list of specification fields. Each field declares `name`, `type` (`text`, `number`, `boolean`, or `enum`), optional `unit`, `options` (required when `type` is `enum`), a `required` flag, and a `filterable` flag. `filterable` carries two effects, not one: it makes the field a buyer-facing facet (`FR-CAT-072`) **and** makes it eligible for display on category product cards (`FR-CAT-092`). Field declaration order is significant — it determines which fields reach the card when more than four are filterable.
- `FR-CAT-031`: Admin can update or delete a specification group, or an individual specification field within a group. Deleting a specification field currently referenced by at least one product — matched on `groupName` plus field `name` — is rejected with an error naming the blocking product count.
- `FR-CAT-032`: Product create and update validate the submitted specifications against the product's own category's specification schema: every `required` field must be present, unknown field names are rejected, each value must match its declared `type`, and an `enum`-typed value must be one of that field's `options`.
- `FR-CAT-033`: The product create/edit form renders specification inputs derived from the selected category's specification schema — a product inherits its relevant specification fields from its category rather than declaring its own ad-hoc field set.
- `FR-CAT-034`: Changing a product's category re-validates that product's specifications against the new category's schema; the update is rejected if the existing values do not satisfy it, with an error identifying the offending fields.
- `FR-CAT-035`: Only specification fields marked `filterable` are exposed as buyer-facing facets (`FR-CAT-072`) or displayed on category product cards (`FR-CAT-092`); non-filterable fields appear on the product detail page only. `filterable` may be set on `enum`, `boolean`, and `number` fields, and is rejected on `text` fields — free text is unbounded and produces neither a usable facet nor a scannable card value. `enum` and `boolean` fields yield value-list facets; `number` fields yield a range facet, the same shape `sellingPrice` already uses in `FR-CAT-068`.

### 2.5 Admin — category-based variant types

- `FR-CAT-036`: Admin can define a category's variant axes: one variant-type document per category, holding a list of axes, each declaring `name`, `code`, `type` (`text`, `select`, `color`, or `number`, default `select`), a `required` flag, and `options` as `{label, value}` pairs for `select` and `color` types.
- `FR-CAT-037`: Admin can update or delete a category's variant-axis definition. Unlike the specification guard in `FR-CAT-031`, deleting a variant axis is never blocked by in-use product variants — the definition drives admin form rendering only and is not enforced against stored variant attributes. Removing one means the variant editor falls back to plain text inputs for that axis.
- `FR-CAT-038`: The admin product variant editor renders an input control per axis according to the category's variant-type definitions — a swatch picker for `color`, a dropdown for `select`, a numeric input for `number`, a text input for `text` — falling back to text inputs where no definition exists.

### 2.6 Admin — product variants

- `FR-CAT-039`: Admin can add a variant to a product. A variant carries its own `sku` (in the shared namespace of `FR-CAT-003`), one or more attribute pairs such as `Color=Red` plus `Size=L`, its own `mrp`/`discount`/`sellingPrice`, its own `stock`, an optional `weight`, and an optional image set.
- `FR-CAT-040`: Admin can update a variant, or deactivate it by setting `active: false`. Deactivation is a soft delete for the same reason as `FR-CAT-007`; variants are never hard-removed from the product document.
- `FR-CAT-041`: No two variants of the same product may share an identical set of attribute pairs; a create or update producing a duplicate combination is rejected with a validation error.
- `FR-CAT-042`: A variant's price and stock fields follow exactly the same validation as the product's own — `mrp` a positive integer in paise, `discount` an integer 0–99, `sellingPrice` always server-computed, `stock` a non-negative integer.
- `FR-CAT-043`: A product with zero active variants is sold on its own SKU, price, and stock. A product with one or more active variants is sold **per variant**; the parent product's own price and stock become "starting from" display values and are not the purchasable unit.
- `FR-CAT-044`: A variant has no independent visibility state — it inherits its parent product's status entirely. A `draft` or `archived` product's variants never appear on any buyer-facing endpoint regardless of their own `active` flag.

### 2.7 Product, category, and brand status APIs

- `FR-CAT-045`: Admin can set a product's status to `draft`, `published`, or `archived` through a dedicated status endpoint, separate from the general product update path.
- `FR-CAT-046`: Admin can toggle a category's `status` (boolean, default `true`) through a dedicated status endpoint.
- `FR-CAT-047`: Admin can toggle a brand's `status` (boolean, default `true`) through a dedicated status endpoint.
- `FR-CAT-048`: Deactivating a category or a brand (`status: false`) hides it from the corresponding buyer-facing endpoint immediately while leaving it fully visible and editable in the admin console. It does **not** bypass the hard-delete guards in `FR-CAT-019` and `FR-CAT-028` — deactivation is an alternative to deletion, not a way around its preconditions.
- `FR-CAT-049`: Products belonging to a deactivated category, or carrying a deactivated brand, remain individually reachable by slug but are excluded from that category's and that brand's buyer-facing listings and facets.

### 2.8 Admin — search

- `FR-CAT-050`: Admin can search the product grid by keyword, matching product name and SKU, served by a plain indexed MongoDB query rather than Atlas Search. Name matching is case-insensitive and partial; SKU matching is exact or prefix-based so that pasting a full SKU returns that one product. This keeps all three admin list searches (`FR-CAT-050`–`FR-CAT-052`) on one mechanism, and confines Atlas Search to buyer-facing paths.
- `FR-CAT-051`: Admin can search the category list by name, case-insensitive partial match.
- `FR-CAT-052`: Admin can search the brand list by name, case-insensitive partial match.
- `FR-CAT-053`: Admin search results respect the admin visibility rule of `FR-CAT-005` — all statuses are searchable, and results can be further narrowed by a status filter.

### 2.9 Buyer — browsing

- `FR-CAT-054`: Buyer can view a paginated list of all `published` products; its cards follow the home card contract in `FR-CAT-091`.
- `FR-CAT-055`: Buyer can view a paginated list of `published` products within a single category; requesting a parent category includes products in its subcategories. Its cards follow the category card contract in `FR-CAT-092`.
- `FR-CAT-056`: Buyer can view a single product's detail page **by slug**, showing name, description, price, image gallery, brand, category, specifications, variants, and `availability` (`FR-CAT-095`). Slug rather than ID is the buyer-facing key because catalog pages are ISR-rendered and the slug is both the cache key and the SEO-visible URL.
- `FR-CAT-057`: Listing, category, and search endpoints are paginated with a fixed default page size and a server-enforced maximum page size; a request exceeding the maximum is clamped, not honoured.
- `FR-CAT-058`: An empty result set for any valid search or filter combination returns a successful, empty response — never an error and never a 404.
- `FR-CAT-059`: A product with zero stock remains visible in listings and on its detail page, reported as `availability: out_of_stock` (`FR-CAT-096`), and is excluded when the in-stock-only filter is applied.
- `FR-CAT-060`: A product with status `draft` or `archived` is never returned by any buyer-facing endpoint, under any combination of query parameters.
- `FR-CAT-061`: Buyer-facing endpoints can list active categories for navigation, ordered per `FR-CAT-020`, returning only the parent/child structure and display fields — no admin-only fields.
- `FR-CAT-062`: Buyer-facing endpoints can list active brands for the filter UI, returning public fields only.
- `FR-CAT-063`: The buyer product detail page displays all of a product's specification name/value pairs, grouped by their `groupName`, whether or not those fields are filterable.
- `FR-CAT-064`: When a product has active variants, the buyer product detail page defaults to the lowest-`sellingPrice` active variant and updates the displayed price, `availability`, and images as the buyer selects a different variant. A variant with no images of its own falls back to the parent product's images.

### 2.10 Buyer — search

- `FR-CAT-065`: Buyer can search products by keyword via MongoDB Atlas Search, matching product name and description, case-insensitive and partial, with fuzzy matching so close misspellings still return relevant results.
- `FR-CAT-066`: Buyer can search categories by name, case-insensitive partial match, served by a plain indexed query rather than Atlas Search — `categories` is a small collection and does not warrant a second search index.
- `FR-CAT-067`: Product search results can be narrowed by every filter in §2.11 and ordered by every sort option in `FR-CAT-075`.

### 2.11 Buyer — filtering and sorting

- `FR-CAT-068`: Buyer can filter a listing by price range (minimum and/or maximum), applied against `sellingPrice`.
- `FR-CAT-069`: Buyer can filter a listing by one or more brands.
- `FR-CAT-070`: Buyer can filter a listing by category, including a parent category's subcategories.
- `FR-CAT-071`: Buyer can filter a listing by a variant attribute name and value, such as `Color = Red`, matched against active variants of published products only.
- `FR-CAT-072`: Buyer can filter a listing by a `filterable` specification field, restricted to fields marked filterable per `FR-CAT-035`. `enum` and `boolean` fields filter by value match, such as `RAM = 8GB`; `number` fields filter by range, such as `Screen Size between 6.0 and 6.5`.
- `FR-CAT-073`: Buyer can restrict a listing to in-stock products only. A product with variants counts as in stock when at least one active variant has stock above zero.
- `FR-CAT-074`: Buyer can restrict a listing to discounted products only (`discount` greater than zero).
- `FR-CAT-075`: Buyer can sort listing results by relevance (search results only), price ascending, price descending, or newest first. Price sorting is applied against `sellingPrice`.
- `FR-CAT-076`: Filters compose — any combination of category, brand, price range, variant attribute, specification, in-stock, and on-sale filters can be applied together with a sort option and pagination, and the result respects all of them simultaneously.

### 2.12 Images — Cloudflare R2

- `FR-CAT-077`: Admin requests a short-lived presigned upload URL from the backend for each image and uploads directly to Cloudflare R2. The backend never receives raw image bytes (see `FR-CAT-097` for the one deliberate exception).
- `FR-CAT-078`: A presign request declares the image's content type and is rejected server-side unless it is JPEG, PNG, or WebP — the format check happens before any URL is issued, not after upload.
- `FR-CAT-079`: The presign response returns a **server-generated** object key of the form `{purpose}/{uuid}.{ext}`. The key is never derived from the parent entity's ID, because the product, brand, or category may not exist yet at upload time, and the client can neither choose nor influence it.
- `FR-CAT-080`: Presigned upload URLs expire five minutes after issuance.
- `FR-CAT-081`: One presign endpoint serves all image kinds, parameterised by a `purpose` field (`product-image`, `brand-logo`, or `category-image`) which determines the key prefix and any size constraints.
- `FR-CAT-082`: Registering an uploaded image URL against a product, brand, or category validates that the object key was actually issued by a prior presign call and has not already been consumed; arbitrary or unrecognised object URLs are rejected.
- `FR-CAT-083`: A product must carry between 1 and 8 images; a variant's optional image set is bounded at 1 to 2 when present. Both bounds are enforced server-side at registration time regardless of how many presigned URLs were requested.
- `FR-CAT-084`: Each product image carries `alt` text, and exactly one image per product is designated primary. The primary image is what listings, cards, and social previews use; if the designated primary is removed, the first remaining image is promoted automatically.
- `FR-CAT-097`: A second admin upload path, `POST /api/admin/uploads/direct`, accepts the image itself as `multipart/form-data` (a `file` field plus a `purpose` field) and uploads it to Cloudflare R2 from the backend, for clients that cannot perform a direct browser-to-R2 PUT. This is the one documented exception to `FR-CAT-077`.
- `FR-CAT-098`: The direct-upload path enforces the same content-type allow-list as the presigned path (`FR-CAT-078`) — JPEG, PNG, or WebP — rejecting any other type before the file reaches R2, and enforces a maximum file size of 5 MB, rejecting oversized uploads before any R2 call.
- `FR-CAT-099`: A successful direct upload returns the same server-generated object key format as the presigned path (`FR-CAT-079`) and a `publicUrl`; the object is tracked as an issued-but-unconsumed key exactly like a presigned upload, so image registration (`FR-CAT-082`) validates and consumes it identically regardless of which upload path produced it.
- `FR-CAT-100`: The direct-upload endpoint requires the same admin shared-secret guard as every other admin route (`FR-CAT-088`) and is subject to the same rate-limiting expectation as the presign endpoint, since it is a second path that can write into the R2 bucket.

### 2.13 Pricing

- `FR-CAT-085`: `mrp` is stored as an integer number of paise, is required, and must be greater than zero. Zero, negative, fractional, and non-numeric values are rejected. There is no `currency` field — the market is India-only per [`SRS.md`](../SRS.md) §2.5 — and all amounts are INR by definition.
- `FR-CAT-086`: `discount` is an integer percentage between 0 and 99 inclusive, defaulting to 0. 100 is excluded deliberately: it would force a `sellingPrice` of zero and violate `FR-CAT-087`.
- `FR-CAT-087`: `sellingPrice` is computed server-side as `mrp - floor(mrp * discount / 100)` on every create and update, for both products and variants. It is never accepted from the client; a submitted value is ignored, not rejected. Given the bound in `FR-CAT-086`, `sellingPrice` is always at least 1 and never exceeds `mrp`.

### 2.14 Temporary admin access control

M2 ships before M3 Authentication, so admin endpoints need protection that does not depend on a session layer that does not exist yet.

- `FR-CAT-088`: Every admin endpoint — all product, category, brand, specification, variant-type, variant, status, and presign/direct-upload routes — requires a shared-secret header matching a server-side environment variable, checked by a single reusable Express middleware rather than per-route code.
- `FR-CAT-089`: A request to an admin endpoint with a missing or incorrect shared secret is rejected with a 401 following the existing error contract, before it reaches any controller or service logic.
- `FR-CAT-090`: The shared-secret guard is written as an isolated, swappable layer. Replacing it with real session and role-based access control in v0.3 must require changes only to the guard itself — not to route paths, controllers, or services.

### 2.15 Buyer — product card content

The two buyer listing flows show different cards. Both are served by the same endpoint and the same response shape; the difference is a rendering choice in `buyer-app`, not a second API contract.

- `FR-CAT-091`: A card on the home page or any all-products listing shows the product's primary image, name, and `sellingPrice`. No specifications appear, regardless of which categories the listed products belong to — a mixed-category grid has no shared specification schema to draw on.
- `FR-CAT-092`: A card on a category listing shows the product's primary image, name, up to the first four `filterable` specification name/value pairs in schema declaration order (`FR-CAT-030`), and `sellingPrice`. A product carrying fewer than four filterable specifications renders only those it has; a category whose schema marks none filterable renders a card identical to the home variant. The limit of four is a display rule only — it never restricts how many fields a category may mark `filterable`, and admins choose which four reach the card by ordering the schema.

### 2.16 API response envelope and inventory visibility

- `FR-CAT-093`: Every successful response uses the envelope `{ "success": true, "data": ... }`, mirroring the existing error contract. `data` holds the resource itself — an object for detail endpoints, an array for list endpoints. No endpoint returns a bare array or bare object at the top level.
- `FR-CAT-094`: Paginated responses additionally carry a top-level `pagination` sibling to `data` — `{ "success": true, "data": [], "pagination": {} }` — containing `page`, `limit`, `total`, `totalPages`, and `hasNextPage`. Detail and other non-paginated responses omit the key entirely rather than sending it as `null` or `{}`.
- `FR-CAT-095`: Buyer-facing endpoints never return raw `stock`, nor `lowStockThreshold`, `status`, `createdBy`, or `updatedBy`. In place of a count they return `availability`, an enum of `in_stock`, `low_stock`, or `out_of_stock`, on the product and on each variant. Admin endpoints are unaffected and continue to return exact `stock`.
- `FR-CAT-096`: `availability` is derived server-side on every read and is never accepted from a client. For a unit carrying its own stock: `0` → `out_of_stock`; `0 < stock ≤ lowStockThreshold` → `low_stock`; anything greater → `in_stock`. The bound is inclusive, and because `lowStockThreshold` defaults to `0`, a product that never sets one simply never reports `low_stock` — it moves directly from `in_stock` to `out_of_stock`. For a product with active variants, product-level `availability` is the best state across those variants (`in_stock` > `low_stock` > `out_of_stock`), consistent with `FR-CAT-043`'s rule that the parent's own stock is not the purchasable quantity.

Exposing a status rather than a count is a deliberate consequence of the ISR rendering strategy in [`docs/architecture.md`](../../architecture.md) §4.1: a cached page's stock number is guaranteed to drift between revalidations, and a stale "42 in stock" is more damaging than a stale "In Stock". A coarse status degrades gracefully under caching where a precise number degrades into a falsehood. The authoritative stock check happens at checkout in v0.4/v0.5 regardless.

## 3. Baseline Non-Functional Requirements

Feature-scoped only — see [`SRS.md`](../SRS.md) §4 item 3 for why this is deliberately not exhaustive; full system NFRs land in v0.8/v0.9.

**Validation**

- [ ] Every admin write endpoint validates its input server-side with Zod schemas. This is the first feature to add `zod` as a `backend` dependency.
- [ ] Every buyer-facing read endpoint validates its query parameters (page, limit, price bounds, sort key, filter values) server-side; invalid values are rejected or clamped and never reach the data layer unvalidated.
- [ ] `sellingPrice` is never trusted from client input on either products or variants — always recomputed from `mrp` and `discount` on every write (`FR-CAT-087`).
- [ ] Money is stored exclusively as integer paise; no floating-point currency field exists anywhere in this feature.
- [ ] `availability` is likewise never trusted from client input — always derived server-side from `stock` and `lowStockThreshold` on every read, per the rule in `FR-CAT-096` (`FR-CAT-095`, `FR-CAT-096`).
- [ ] Buyer-facing response serialization is enforced at a shared response boundary, not left to each controller remembering to omit admin fields — `stock`, `lowStockThreshold`, `status`, `createdBy`, and `updatedBy` are structurally absent from every buyer payload, a property that is tested by asserting their absence rather than inferred from a passing happy-path test (`FR-CAT-095`).

**Indexes**

- [ ] `products`: unique index on `sku`, unique index on `slug`, index on `category`, index on `brand`, index on `status`.
- [ ] `products.variants.sku`: unique multikey index. Because SKU uniqueness spans a top-level field and an array field on the same collection, no single index can enforce `FR-CAT-003` — the two indexes plus an application-level cross-check at write time are jointly required.
- [ ] `categories`: unique index on `slug`, index on `parentCategory`.
- [ ] `brands`: unique index on `slug`.
- [ ] `categorySpecifications` and `categoryVariants`: unique index on `category` on each (one document per category).
- [ ] Duplicate variant attribute combinations (`FR-CAT-041`) are prevented by an application-level check within the product document, not a DB index, since `attributes` is an array.

**Search**

- [ ] Atlas Search scope is deliberately narrow and **buyer-facing only**: free-text keyword search (`FR-CAT-065`) and faceted filtering on variant attributes and filterable specifications (`FR-CAT-071`, `FR-CAT-072`), where `number`-typed specification facets are range queries rather than value lists. Category, brand, status, price-range, in-stock, and on-sale filters remain plain indexed MongoDB queries.
- [ ] The Atlas Search index must be provisioned and configured against the `products` collection as part of implementation — it is a real setup step, not an assumption.
- [ ] All three admin list searches (`FR-CAT-050`–`FR-CAT-052`) are plain MongoDB queries, not Atlas Search. The SKU half of product search rides the existing unique `sku` index; the name half is an unanchored case-insensitive regex, which cannot use an index and will collection-scan. That is accepted at this catalog's stated scale and is consistent across all three lists, but it is a known characteristic to revisit as the product count grows — the same threshold thinking [`docs/architecture.md`](../../architecture.md) §8 already applies to search generally.
- [ ] Category-card specification display (`FR-CAT-092`) needs no additional index or denormalisation — `products.specifications` is already embedded and returned with the listing document.

**Error handling and operations**

- [ ] Every endpoint follows the existing error contract, `{ success: false, code, message }`, per [`docs/architecture.md`](../../architecture.md) §6. This feature introduces no ad-hoc error shapes.
- [ ] Guard rejections (`FR-CAT-019`, `FR-CAT-028`, `FR-CAT-031`) return actionable messages naming what blocks the operation, not a generic conflict.
- [ ] Replacing `backend/src/config/db.ts`'s stub with a live Mongoose connection includes startup failure handling — the process must not silently serve traffic against a dead database connection. Full connection-resilience and retry policy is deferred to v0.8; this requirement is only "do not fail silently."

**Security**

- [ ] No secrets committed — Cloudflare R2 credentials and the admin shared secret are sourced from environment variables, following the existing `.env.example` pattern in `backend/`.
- [ ] The admin shared-secret guard is applied once at the router level, not duplicated per controller, so the v0.3 swap is a single-location change (`FR-CAT-090`).
- [ ] The presign and direct-upload endpoints are both rate-limited. Between them they are the only endpoints that can write into the R2 bucket, so leaving either unbounded is a storage-abuse vector even behind the shared secret (`FR-CAT-100`).
- [ ] Presigned URLs expire in five minutes, object keys are server-generated, and image registration validates that the key was issued and not yet consumed (`FR-CAT-079`, `FR-CAT-080`, `FR-CAT-082`).

## 4. User Stories

- As a **guest**, I want to browse products by category, so that I can find things I am interested in without creating an account.
- As a **guest**, I want to search for a product by name and still get results when I mistype it, so that a small spelling error does not leave me with an empty page.
- As a **guest**, I want to filter a listing by price, brand, specifications like RAM or storage, and variant options like colour or size, so that I can narrow a large category down to the few products that actually suit me.
- As a **guest**, I want to see a product's full specifications and pick a specific variant before deciding, so that I know exactly what I would be buying.
- As a **registered buyer**, I want the same browsing, search, and filtering as a guest — no catalog capability is gated behind login, which is a Cart and Checkout concern rather than a Catalog one.
- As a **catalog manager**, I want to create and edit products with images, price, and stock, so that the storefront reflects what is actually available to sell.
- As a **catalog manager**, I want to define the specification fields and variant axes for a category once, so that every product in that category is described consistently without me re-typing the field list.
- As a **catalog manager**, I want to organise products into categories and brands and control their display order, so that buyers can navigate the storefront logically.
- As a **catalog manager**, I want to deactivate or archive something instead of deleting it, so that buyers stop seeing it without me losing its history.
- As a **catalog manager**, I want to see which products are running low on stock, so that I can restock before they sell out.
- As a **super admin**, I want the same catalog capabilities as a catalog manager — the role distinction only becomes meaningful once v0.3 RBAC exists.

### Response envelope

Every response, success or failure, is wrapped (`FR-CAT-093`, `FR-CAT-094`). `data` always holds the resource itself, so a client unwraps detail and list responses identically.

```jsonc
// detail — data is an object, no pagination key
{ "success": true, "data": { "id": "…", "name": "…" } }

// list — data is an array, pagination sits beside it
{
  "success": true,
  "data": [],
  "pagination": { "page": 1, "limit": 24, "total": 137, "totalPages": 6, "hasNextPage": true }
}

// error — the existing contract, unchanged
{ "success": false, "code": "PRODUCT_NOT_FOUND", "message": "No product exists with that slug." }
```

### Field visibility — buyer vs admin

Buyer payloads are not admin payloads with fields blanked; they are a distinct projection (`FR-CAT-095`). These keys never appear on a buyer-facing endpoint:

| Field                     | Why it is admin-only                                                                     |
| ------------------------- | ---------------------------------------------------------------------------------------- |
| `stock`                   | Replaced by `availability`; a raw count publishes inventory and sales velocity to anyone |
| `lowStockThreshold`       | Operational tuning; also reveals the count indirectly                                    |
| `status`                  | Buyers only ever receive `published` products, so the field carries no information       |
| `createdBy` / `updatedBy` | Internal attribution, meaningful only once v0.3 populates it                             |

## 6. UI/UX Requirements

This section is the source of truth for _what_ the UI must do. Screen-level design — wireframes, components, spacing — is not specified in this version; see §10.

**`buyer-app`** — per [`docs/architecture.md`](../../architecture.md) §4.1, catalog listing and product detail are both ISR.

- **Home / catalog listing**: product grid whose cards show image, name, and price (`FR-CAT-091`); category filter, brand filter, price-range filter, variant-attribute facets, filterable-specification facets — value lists for `enum`/`boolean`, range inputs for `number` — in-stock and on-sale toggles, sort control, pagination. Loading state as a skeleton grid; empty state reading "no products match your filters"; error state that degrades without crashing the page.
- **Category page**: the same grid pre-filtered to the category, with a breadcrumb showing the parent category where one exists. Its cards additionally show up to four specification name/value pairs between the name and the price (`FR-CAT-092`), so cards stay uniform in height across the grid.
- **Search results**: the same grid with the keyword shown, and an empty state distinct from the filter-empty state — "no results for '…'" rather than "no products match your filters."
- **Product detail**: image gallery driven by the primary image and `alt` text, name, price, description, brand link, category link, specification table grouped by `groupName`, a three-state availability badge (`In Stock` / `Only a few left` / `Out of Stock`, driven by `availability` — `FR-CAT-095`, `FR-CAT-096`), and — when variants exist — a variant selector that updates price, stock, and images on selection. No add-to-cart control in this version; that is v0.4.

**`admin-app`** — per [`docs/architecture.md`](../../architecture.md) §4.2, TanStack Table backs the catalog grids.

- **Product list**: table with thumbnail, name, SKU, brand, category, price, stock, and status columns; keyword search; status filter; low-stock filter; pagination.
- **Product detail**: a read-only view of every field at any status, separate from the edit form (`FR-CAT-006`).
- **Product create/edit form**: all data-model fields, client-side validation mirroring the backend Zod schema (per the root `CLAUDE.md` "no shared validation package" decision — this is `admin-app`'s own separate validation, not shared code), an image upload widget with preview, primary-image selection, `alt` text entry, and the 1–8 bound surfaced in the UI; a brand selector; specification inputs rendered from the selected category's schema; and a variant editor whose controls follow the category's variant axes.
- **Category list and form**: table with name, parent, product count, sort order, and status; search; create/edit form including image upload, sort order, SEO fields, and an active toggle; delete blocked inline when `FR-CAT-019`'s guard rejects it.
- **Brand list and form**: table with name, logo, product count, and status; search; create/edit form with an active toggle; delete blocked inline when `FR-CAT-028`'s guard rejects it.
- **Category specification editor**: define groups and fields with type, unit, options, required, and filterable, with reorderable fields since declaration order decides which four reach a category card; the editor states both effects of `filterable` and previews which fields would appear on a card. Deleting an in-use field shows the blocking product count rather than a generic error.
- **Category variant-type editor**: define axes with name, code, type, required, and options; no delete warning is needed since removal is unguarded.

## 7. Out of Scope

- **Admin user profile section** — deferred to SRS v0.3 (Authentication). It is user identity, session, and role territory, and this version has no authenticated admin identity to build a profile against; see `FR-CAT-013`.
- Reviews and ratings, and therefore rating-based filtering and sorting.
- Wishlists and "save for later."
- Recommendation engine and "related products."
- Bulk import/export (CSV or otherwise) and bulk grid actions such as multi-select status change.
- Multi-warehouse or per-location inventory — a single global stock integer per product, or per variant where variants exist.
- Category depth beyond two levels.
- Specification or variant-axis inheritance from a parent category to its subcategories — definitions are scoped to the exact category a product is assigned to.
- Proactive R2 object cleanup when a product, brand, or category is deleted; orphaned storage objects are accepted at this scale.
- Real RBAC on admin endpoints — replaced by the temporary shared-secret guard until v0.3.
- Add-to-cart and any cart interaction; the product detail page is read-only in this version.

## 8. Acceptance Criteria

- [ ] An admin can change a product's stock through the stock-only endpoint without submitting any other field. — `FR-CAT-008`

## 10. Open Questions

1. **Screen-level UI design.** §6 specifies UI behaviour but not layout, components, or visual design. Whether that lives in a separate `docs/ui/` layer, and whether it is authored before or alongside implementation, is undecided.

### Resolved during drafting

- **Product card content** — the two buyer flows show different cards: home shows image, name, and price; a category listing shows image, name, specifications, and price. Card-eligible specifications are chosen by reusing the existing `filterable` flag rather than adding a `showOnCard` field, capped at the first four in schema declaration order. This is why `FR-CAT-035` admits `number` fields as filterable: restricting the flag to `enum` and `boolean` would have kept numeric specifications such as screen size and battery capacity off cards entirely, and forced admins to model them as enums at the cost of range filtering. See `FR-CAT-030`, `FR-CAT-035`, `FR-CAT-091`, `FR-CAT-092`.
- **Admin grid search mechanism** — plain indexed MongoDB queries rather than Atlas Search, putting all three admin list searches on one mechanism and confining Atlas Search to buyer-facing paths. See `FR-CAT-050`–`FR-CAT-052` and the §3 note on the unanchored-regex characteristic this accepts.
