## How to add a new module

1. Pick a location: a product-catalog domain entity module (governs a catalog resource — brands, categories, products, and their sub-resources) goes under `src/modules/product-catalog/features/<feature>/`; a cross-cutting/infra module with no catalog-domain meaning of its own (like `health`, `uploads`) stays flat at `src/modules/<feature>/`.
2. Create that `<feature>/` directory with:
   - `<feature>.routes.ts` — pure route definitions (method + path → controller)
   - `<feature>.controller.ts` — request/response shaping, calls the service
   - `<feature>.service.ts` — business logic, orchestrates the repository
   - `<feature>.repository.ts` — Mongoose queries only (skip if the module needs no DB access)
   - `<feature>.model.ts` — Mongoose schema (skip if the module owns no collection)
   - `<feature>.module.ts` — imports `<feature>.routes.ts`'s router, exports `{ path, router }`
   - `tests/` — colocated unit tests for this module
3. Wire it into `src/routes/index.ts`: import the module and add `router.use(<feature>Module.path, <feature>Module.router)`.
4. If the module needs end-to-end coverage, add a Supertest file under the workspace-root `__tests__/<feature>/` — nested under `__tests__/product-catalog/<feature>/` for a catalog module, flat for infra, mirroring the same split as step 1 (see `__tests__/health/health.api.test.ts` for the pattern).

`src/modules/health/` is the current worked reference for a module's internal shape — copy its shape regardless of which of the two locations above the new module lands in.

## Path aliases

`@/*` maps to `src/*` (`backend/tsconfig.json`'s `paths`). Use it for any import that would otherwise need `../` parent traversal (e.g. reaching `config/`, `middleware/`, `utils/`, `externalService/` from inside a module); same-directory or one-level-down-from-`src` imports stay relative. Works everywhere: `tsc` build (rewritten to relative paths by `tsc-alias`, run right after `tsc` in the `build` script), `tsx watch` dev server (native tsconfig-paths support), and Vitest via the `vite-tsconfig-paths` plugin in `vitest.config.ts` (there is no native `resolve.tsconfigPaths` option — an earlier version of this doc claimed there was, which was wrong and left `__tests__/health/health.api.test.ts` failing until Issue #8 fixed it) — one alias defined once in `tsconfig.json`.

## Error contract

- `src/utils/AppError.ts` — `class AppError extends Error { constructor(statusCode, code, message) }`
- `src/middleware/errorHandler.ts` — 4-arg Express error middleware. `AppError` instances → `{ success:false, code, message }` at `err.statusCode`; a `ZodError` (thrown directly from a controller, e.g. `schema.parse(req.body)`) → 400 `{ success:false, code:"VALIDATION_ERROR", errors }`, where `errors` is an object keyed by field path (`issue.path.join(".")`) with that field's own Zod message as the value — no `message` key on this response; a `MulterError` (thrown by the `multer` middleware itself, before a controller runs — e.g. an oversized file) → 400 `{ success:false, code, message }`, where `code` is `"FILE_TOO_LARGE"` for `LIMIT_FILE_SIZE` and `"UPLOAD_ERROR"` for every other Multer error code; anything else → always `console.error`'d server-side first, then 500 `{ success:false, code:"INTERNAL_ERROR", message:"Internal server error" }` — except when `env.NODE_ENV === "development"`, where the response instead includes the real `message`/`name`/`stack` for local debugging. Production, `test`, and any unrecognized `NODE_ENV` value all get the generic shape (fail-safe default) — `err.stack` is never leaked to a client outside development.
- `src/middleware/notFound.ts` — catch-all for unmatched routes → 404 `{ success:false, code:"NOT_FOUND", message:"Route not found" }`.

Both are mounted in `src/app.ts`, after all routes. Because Express 5 (already a dependency) auto-forwards a thrown or rejected error from an async route handler to this middleware, a controller can call `schema.parse(req.body)` directly with no manual `try`/`catch` — see `src/modules/uploads/uploads.controller.ts` for the pattern every later M2 admin endpoint should copy.

## Success envelope

`src/utils/apiResponse.ts`'s `successResponse(data)` / `successResponse(data, pagination)` is the one place every controller builds its success response from — mirrors the error contract's single-source-of-truth shape:

- Detail: `successResponse(data)` → `{ success: true, data }`, no `pagination` key at all.
- List: `successResponse(items, { page, limit, total, totalPages, hasNextPage })` → `{ success: true, data: items, pagination }`.

Built as two overloads returning a conditionally-constructed object literal (never `pagination: undefined`) specifically because `tsconfig.base.json` sets `exactOptionalPropertyTypes: true` — assigning `undefined` to an optional field is a type error there, and would violate the "omit entirely, never `null`/`{}`" rule anyway.

`health` predates this helper and still returns its own `{ success, code, message }` shape — left as-is; it isn't a catalog resource.

## Admin routes and auth

- `src/middleware/adminAuth.ts` — checks the `X-Admin-Key` request header against `env.ADMIN_API_KEY`; mismatch → `next(new AppError(401, "UNAUTHORIZED", ...))`, so it produces the exact same error-contract shape as everything else, not a one-off `res.json`.
- `src/routes/admin.routes.ts` — a dedicated router with `adminRouter.use(adminAuth)` applied once, mounted at `/api/admin` in `src/routes/index.ts`. Every M2 admin feature module (brands, categories, products, ...) mounts under this router as it lands (`adminRouter.use(<feature>Module.path, <feature>Module.router)`) — the guard never needs touching per-route, and the whole thing is swapped out in one place when v0.3 replaces it with real session/RBAC auth.
- Buyer-facing (non-admin) routes mount directly on the root aggregator router in `src/routes/index.ts`, same as `health` does today.

## CORS

`src/middleware/cors.ts` wraps the `cors` package and is mounted first in `src/app.ts`, ahead of the query-parser/`express.json()`/routes — pulled forward from the SRS v0.8 security-baseline bundle (`docs/architecture.md` §6 lists it alongside helmet/rate-limiting/session cookies, which stay deferred) since `buyer-app`/`admin-app` now deploy to different origins than `backend` and can't reach it at all without this.

- **Origins are env-driven, never hardcoded**: `env.CORS_ORIGINS` (`src/config/env.ts`) is a comma-separated string, split/trimmed into an array in `cors.ts`. Defaults to `http://localhost:3000,http://localhost:5173` (buyer-app/admin-app's local dev ports) so local dev needs no `.env` changes; Render's `render.yaml` declares the var `sync: false` (same pattern as `MONGODB_URI`/`ADMIN_API_KEY`/the R2 vars) — the real deployed Vercel URLs are typed into Render's dashboard by hand, not committed.
- **`credentials: true`** — anticipates the `httpOnly`/`secure`/`sameSite` session cookies `docs/architecture.md` already plans for v0.3 Authentication; harmless ahead of that since nothing currently sends cookies.
- **`methods`/`allowedHeaders` are the actual surface, not a wildcard**: `GET/POST/PUT/PATCH/DELETE` (every HTTP method any route in this codebase uses) and `Content-Type`/`X-Admin-Key` (the latter needed since `adminAuth.ts` reads it on every `/api/admin/*` request — omitting it would fail the browser's preflight for every admin call).
- Test: `__tests__/cors/cors.api.test.ts` — flat, cross-cutting-infra layout matching `__tests__/admin-auth/`, not nested under `product-catalog/`.

## R2 uploads

- `src/externalService/r2.ts` — the first client under `externalService/`. Wraps `@aws-sdk/client-s3` + `@aws-sdk/s3-request-presigner`: constructs an `S3Client` pointed at `https://{env.R2.ACCOUNT_ID}.r2.cloudflarestorage.com`, exports `createPresignedPutUrl(key, contentType)` returning a 5-minute presigned PUT URL, and `uploadObject(key, body, contentType)` — a plain `PutObjectCommand` sent via `client.send()`, used by the direct-upload path below. Presigning is a local signature computation — no network call — so it's fully unit-testable with dummy credentials; only actually uploading (through the presigned URL, or via `uploadObject`) touches the network.
- `src/modules/uploads/` — `POST /presign` (mounted as `/api/admin/uploads/presign`) and `POST /direct` (mounted as `/api/admin/uploads/direct`), the module's own model/repository/service pattern, plus reusable entity-agnostic exports from `uploads.service.ts` that later modules import directly rather than duplicating:
  - `POST /direct` (SRS amendment `FR-CAT-097`–`100`, the one deliberate exception to `FR-CAT-077`'s "backend never receives raw image bytes") accepts the image itself as `multipart/form-data` (a `file` field plus a `purpose` field), parsed in-memory by `multer` (`uploads.routes.ts`, `multer.memoryStorage()`, `limits.fileSize` capped at `MAX_DIRECT_UPLOAD_BYTES` — 5 MB), then uploads the buffer to R2 itself via `issueDirectUpload()` in `uploads.service.ts`. Same content-type allow-list as presign, same `{purpose}/{uuid}.{ext}` object key format, same `presignedUploads` tracking record — a product/brand/category registration consumes a direct-upload key identically to a presigned one, since `consumeImageKeys` doesn't distinguish which path produced the key.
  - Exists specifically for clients that can't perform a direct browser-to-R2 PUT (server-side tooling, scripts, classic form submission); the presigned path (`FR-CAT-077`–`081`) remains the default/preferred path for browser clients.
  - `consumeImageKeys(keys)` — validates each object key was issued by a prior presign call and not already consumed (`FR-CAT-082`); called by product/brand/category create-and-update paths once they exist.
  - `validateImageCount(images, { min, max })` — bounds check (`FR-CAT-083`); callers pass `{min:1,max:8}` for products, `{min:0,max:2}` for variants.
  - `normalizeImages(images)` — ensures exactly one `isPrimary: true`, auto-promoting the first image if none is marked (`FR-CAT-084`). Pure function, no I/O.
  - This module intentionally doesn't expose a `/products/:id/images`-style registration endpoint — brands/categories/products don't exist as collections yet. It builds the shared pieces; #27 (brands), #28 (categories), and #31 (products/variants) wire them into their own create/update controllers.
- Issued-but-unconsumed object keys are tracked in a `presignedUploads` MongoDB collection (`uploads.model.ts`), not in memory — a TTL index on `expiresAt` auto-deletes stale entries, and the choice avoids the correctness gaps an in-memory store would have (lost on restart, not shared across instances). `uploads.repository.ts`'s `consumeByKey` is an atomic `findOneAndDelete`; not-found collapses "never issued" and "already consumed" into one rejection, matching `FR-CAT-082`'s wording without needing to distinguish the two.
- New env vars are namespaced under `env.R2` in code even though the underlying `.env` entries are flat (env files can't nest keys) — see `src/config/env.ts`: `R2_ACCOUNT_ID`/`R2_ACCESS_KEY_ID`/`R2_SECRET_ACCESS_KEY`/`R2_BUCKET_NAME`/`R2_PUBLIC_URL_BASE` parse as flat fields, then get reshaped into `env.R2.ACCOUNT_ID` etc. before export. `R2_PUBLIC_URL_BASE` is the browser-accessible bucket URL (custom domain or `r2.dev`) used to build a registered image's stored `url`; it's distinct from the R2 API endpoint used to sign uploads, which is derived from `R2_ACCOUNT_ID`.

## Brands

`src/modules/product-catalog/features/brands/` (Issue #27 / M2.3, `FR-CAT-023`–`029`) is the first module with a real Mongoose collection beyond `uploads`' tracking one. Scope is deliberately just issue #27's own checklist — create/update/list-with-count/get/guarded-delete plus a public active-only list — not the status-toggle endpoint (`FR-CAT-047`, owned by #33) or admin search (`FR-CAT-052`, owned by #34); the SRS's endpoint table lists those near brands, but the project's issue breakdown defers them until brands+categories+products all exist, matching how categories (#28) is split too.

- **Two mount points, one module**: `brands.module.ts` exports `brandsAdminModule` (`path: "/brands"`, mounted under `adminRouter` → `/api/admin/brands`, guarded) and `brandsPublicModule` (`path: "/api/brands"`, mounted directly on the root router in `routes/index.ts`, unguarded) — the first module needing both an admin and a buyer-facing surface.
- **`src/utils/slug.ts`** (new, shared): `slugify(name)` + `generateUniqueSlug(name, slugExists)`, taking an injected `slugExists` checker rather than querying Mongoose directly, so it's DB-agnostic and reusable by categories/products. Suffixes collisions `-2`, `-3`, ... A brand's slug is generated once at create time and never touched on update (`FR-CAT-025` only lists name/logo/description as updatable).
- **`src/modules/product-catalog/features/products/` stub**: issue #31 (the real product module) doesn't exist yet, but `FR-CAT-026` (admin list's product count) and `FR-CAT-028` (delete guard) both need to query products. `products.model.ts` is a deliberately partial schema (`brand`, `status`, timestamps only — extend, don't replace, when #31 lands), and `products.repository.ts` exposes only `countByBrand(id)` / `countByBrandIds(ids)`, no service/controller/routes.
- **Cross-module repository import — the one layering exception**: `brands.service.ts` imports `countByBrand`/`countByBrandIds` directly from `@/modules/products/products.repository` rather than `brands.repository.ts` reaching into the `Product` model itself, or `brands.service.ts` skipping the repository layer entirely. Every module's repository still stays scoped to its own model; this is a peer service-to-repository import, narrow and commented where it happens.
- **`:id` route validation**: neither `health` nor `uploads` has an `:id` route, and `errorHandler.ts` has no `CastError` handling, so an invalid ObjectId string would otherwise fall through to a generic 500. `src/utils/objectId.ts`'s `parseObjectId()` checks `mongoose.isValidObjectId()` first and throws `AppError(400, "INVALID_ID", ...)` — note it also has to account for `req.params.id`'s real type, `string | string[] | undefined` (`ParamsDictionary`'s index signature under `noUncheckedIndexedAccess: true`), not just `string`. Originally inlined in `brands.controller.ts`; extracted to the shared util on categories (#28) becoming its second consumer — see Categories below.
- **`buildPublicUrl(objectKey)`**: extracted from `uploads.service.ts` (previously inlined twice) so brands' logo-URL construction, and later categories'/products' image-URL construction, doesn't duplicate the `${env.R2.PUBLIC_URL_BASE}/${objectKey}` interpolation a third and fourth time.
- **Known, accepted races (documented, not fixed)**: delete-guard TOCTOU (a product could be created between the count-check and the delete) and slug-uniqueness TOCTOU (two concurrent creates with the same name could both pass `slugExists` before either inserts, surfacing as a Mongo `E11000` → generic 500). No transactions or test-DB exist anywhere in this codebase yet; categories' `FR-CAT-019` guard will have the identical gap.
- Test layout follows the established split: `src/modules/product-catalog/features/brands/tests/brands.service.test.ts` (unit, repository/uploads-service mocked) and `__tests__/product-catalog/brands/brands.api.test.ts` (Supertest, same mocking, exercises the real Express app end-to-end).

## Categories

`src/modules/product-catalog/features/categories/` (Issue #28 / M2.4, `FR-CAT-014`–`022`) mirrors brands' layering almost exactly, but is the first module with a **hierarchy** (`parentCategory`, at most one level deep) and a **two-reason delete guard**. Scope is strictly issue #28's own checklist, same deferral as brands: no status-toggle (`FR-CAT-046`) or admin search (`FR-CAT-051`) — both owned by #33/#34, which explicitly cover brands+categories+products together.

- **`categories.description` exists even though the SRS's own schema table omits it** — added deliberately so `metaDescription`'s fallback (`FR-CAT-022`, "same behaviour as `FR-CAT-012`," which truncates a description) has something to truncate from; confirmed with the user before implementation.
- **List endpoints return a flat array with a `parentCategory` ref, not a nested tree** — despite the SRS endpoint table's "category tree" wording, matching brands' flat-array precedent; confirmed with the user since no consumer (buyer-app's catalog browsing, #35) exists yet to demand a specific nested shape.
- **Hierarchy validation — one shared `validateParentCategory(parentId, currentId?)` helper**, called from both create and update: `null` parentId is always valid; a `currentId` equal to `parentId` is a self-reference (`400 INVALID_PARENT_CATEGORY`); a parent that doesn't resolve is `404 PARENT_CATEGORY_NOT_FOUND`; a parent that itself already has a parent is `400 PARENT_CATEGORY_TOO_DEEP` (3-level chain from below). The **update-only** branch (only reachable when `currentId` is given): if the category being updated currently has subcategories of its own, assigning it a parent is `400 CATEGORY_HAS_SUBCATEGORIES` (3-level chain from above — parent → this category → its existing children). `createCategory` never hits this branch; a brand-new category can't have children yet.
- **`parentCategory` is the first tri-state field in this codebase**: absent (untouched), explicit `null` (promote to root), or an id (set/change parent) — every brands PATCH field is "if present, set" with no clear-to-null case. Validated in Zod as `objectIdString.nullable().optional()` on the update schema only, converted to `Types.ObjectId | null | undefined` in the controller before reaching the service, which distinguishes `undefined` from `null` explicitly under `exactOptionalPropertyTypes: true`.
- **`src/modules/product-catalog/features/products/products.repository.ts` grows `countByCategory`/`countByCategoryIds`**, identical shape to `countByBrand`/`countByBrandIds`; `products.model.ts` grows a required `category` field + index alongside `brand`, same extension pattern brands used first.
- **`categories.repository.ts` adds `countByParent(parentId)`** beyond brands' shape — a same-collection query (`Category.countDocuments({ parentCategory: parentId })`), used by both the update-time hierarchy guard and the delete guard. Not a cross-module exception like `countByBrand`/`countByCategory` — this one stays in-module because it queries `categories` against itself.
- **Delete guard — one combined `409 CATEGORY_IN_USE`**, not two separate throws: `Promise.all([countByCategory(id), countByParent(id)])`, then a message naming whichever of "N product(s)" / "N subcategory(ies)" actually blocks (both if both do). Matches this codebase's existing house style of reporting every blocking reason in one response (`errorHandler.ts`'s `ZodError` translation already does this for validation failures).
- **Cascade delete is deliberately not implemented**: `FR-CAT-019`'s "cascade-delete that category's specification and variant-type documents" has nothing to cascade to yet — #29/#30 don't exist. `deleteCategory` has a comment noting this is intentional, not an oversight, extend once they land.
- **Two shared utilities promoted on their second use**: `src/utils/objectId.ts`'s `parseObjectId()` (extracted out of `brands.controller.ts`, which now imports it too — no behavior change, brand tests stayed green) and `src/utils/text.ts`'s `truncate(text, maxLength = 160)` (word-boundary-safe, ellipsis-appended; reusable by products' identical `FR-CAT-012` fallback). Both follow the same "extract on second use" instinct that produced `buildPublicUrl` during brands.
- **A real bug found and fixed while building this**: `brands.repository.ts`'s `updateById` called `Brand.findByIdAndUpdate(id, patch, {new:true})` with a plain object — MongoDB treats an update document with no `$`-operator keys as a full **replacement**, not a partial update, silently dropping every field not in `patch` (including `slug`, which has no default). Both `brands.repository.ts` and `categories.repository.ts`'s `updateById` now wrap the patch in `{ $set: patch }`. No test caught this originally because every existing test mocks the repository layer entirely — worth remembering when writing repository-adjacent code, since this codebase has no real-DB test coverage to catch this class of bug.
- **A second, category-specific TOCTOU** beyond brands' delete-guard race: two concurrent `PATCH`es could each pass the has-no-children check on the same category before either write lands, both successfully assigning it a parent and producing a 3-level hierarchy despite each request validating individually. Documented in `categories.service.ts`, not fixed — no transactions or test-DB exist anywhere in this codebase.
- Test layout matches brands: `src/modules/product-catalog/features/categories/tests/categories.service.test.ts` (unit) and `__tests__/product-catalog/categories/categories.api.test.ts` (Supertest).

## Category Specifications

`src/modules/product-catalog/features/categorySpecifications/` (Issue #29 / M2.5, `FR-CAT-030`–`035`) governs what specification fields products in a category can carry, one document per category. Structurally unlike brands/categories: no `slug`, no `status`, no buyer-facing endpoint of its own, and its data is nested (groups of fields, not a flat document).

- **`GET`/`PUT`/`PATCH` only — no `POST`/`DELETE`**, matching the SRS endpoint table exactly (and the sibling `categoryVariants` resource, #30, has the identical shape). Deleting a group or field happens _through_ `PATCH`, not a separate route — the issue body's looser "POST/PATCH/DELETE routes" phrasing is not literal, same as how brands/categories already treated the SRS endpoint table as more authoritative than an issue body's phrasing in the opposite direction.
- **First single-mount-point module**: `categorySpecificationsAdminModule` only, no public counterpart — zero buyer-facing surface. Path is `/categories/:id/specifications`, a param segment mid-path rather than at the end, mounted directly on `adminRouter`; `categories.admin.routes.ts` is untouched (its own exact-match routes don't collide).
- **`Router({ mergeParams: true })` is required** — the one new, easy-to-miss bug this module introduces. Express routers don't inherit parent path params by default; without `mergeParams`, every handler's `req.params.id` would be `undefined` and every request would 400 `INVALID_ID`. Brands/categories never hit this since their `:id` was always declared inside their own router, never in a parent mount prefix. Copy this for any future module mounted the same way.
- **`GET` returns a synthetic empty default before any `PUT` has happened** — `{category, specificationGroups: []}`, no 404 (the `:id` is a _category_ id, already validated to exist; the sub-resource just hasn't been created yet). The response also drops `_id`/`createdAt`/`updatedAt` entirely, uniformly for both states — a deliberate, first-of-its-kind deviation from brands/categories' admin reads (which return the full record including those fields).
- **`PUT` is a full-replace upsert**; **`PATCH` takes one discriminated-union operation per call** (`renameGroup`/`deleteGroup`/`updateField`/`deleteField`) applied to the in-memory array and persisted through the _same_ full-replace repository function `PUT` uses — MongoDB positional-array update operators are brittle at this nesting depth for a low-traffic admin tool. Per FR-CAT-031's verbs ("update **or delete**," never "create"), `PATCH` only ever targets something that already exists; new groups/fields are added via `PUT`.
- **Deleting a group is guarded the same way deleting a field is**, even though `FR-CAT-031`'s guard sentence only names field-level deletion — resolved as an interpretive gap, not scope creep: it mirrors `FR-CAT-019`'s category-delete guard already being "blocked by what's nested beneath it," and group-deletion isn't optional scope the way brands'/categories' status-toggle and search were (deferred to #33/#34) — it's a mandatory operation whose safe-vs-unsafe behavior needed picking. `deleteGroup` iterates the group's fields through the same `countBySpecificationField` `deleteField` uses, and rejects (`409 SPECIFICATION_FIELD_IN_USE`, one code shared by both operations) naming every blocking field and its count.
- **Resolves `categories.service.ts`'s previously-deferred cascade comment**: `deleteCategory` now calls `categorySpecifications.service.ts`'s `deleteForCategory` before its own `deleteById` — safe without its own guard, since `deleteCategory`'s existing `productCount === 0` check already guarantees no product references any field in that category's schema. Variant-type cascade still waits for #30.
- **One deliberate exception to "cross-module calls go through the peer's service when one exists"**: `categorySpecifications.service.ts` validates category existence via `categories.repository.ts`'s `findById` directly, not `categories.service.ts`'s `getCategoryById` — going through the service would create a two-module circular import, since `categories.service.ts` already imports _from_ `categorySpecifications.service.ts` for the cascade. The dependency stays one-directional (categories → categorySpecifications for cascade; categorySpecifications → categories.repository for existence checks), keeping the module graph acyclic. `categorySpecifications.service.ts` throws its own `CATEGORY_NOT_FOUND` rather than reuse categories' internal helper.
- **Products stub grows a `specifications` field**, the third stub extension after `brand` (#27) and `category` (#28): `{ groupName, values: [{ name, value }] }[]`, where `value: string | number | boolean` — not just `string`, since the SRS's own worked example stores a number, a string, and a boolean in this same array. `products.repository.ts` gains `countBySpecificationField(categoryId, groupName, name)`; the `category` filter in that query is load-bearing, not defensive — two categories can each define a same-named field, and a product's specs are only ever valid against its own category's schema (`FR-CAT-034`).
- **Structural validation lives in Zod, not service-level `AppError`s**: `options` required when `type: "enum"`, `filterable` rejected when `type: "text"` are pure shape rules with no DB dependency, expressed as `.refine()` on the field schema (surfacing as `VALIDATION_ERROR`). Only rules needing the current stored document (rename collisions, not-found lookups, in-use guards) are service-level `AppError`s: `SPECIFICATION_GROUP_NOT_FOUND`, `SPECIFICATION_FIELD_NOT_FOUND`, `DUPLICATE_SPECIFICATION_GROUP`, `DUPLICATE_SPECIFICATION_FIELD`, `SPECIFICATION_FIELD_IN_USE`.
- Test layout matches brands/categories: `src/modules/product-catalog/features/categorySpecifications/tests/categorySpecifications.service.test.ts` (unit) and `__tests__/product-catalog/categorySpecifications/categorySpecifications.api.test.ts` (Supertest) — the latter also implicitly verifies `mergeParams: true` works, since a missing/broken mount would fail every test with `INVALID_ID`.

## Category Variant Types

`src/modules/product-catalog/features/categoryVariants/` (Issue #30 / M2.6, `FR-CAT-036`–`038`) governs what variant axes (e.g. `Color`, `Size`) the admin product-variant editor renders a control for, one document per category. Copies categorySpecifications' shape almost exactly, with one deliberate divergence.

- **Named `categoryVariants` (module folder, model, collection), not the issue body's `categoryVariantTypes`** — the SRS's own `categoryVariants` collection table (and its schema/index section, and a forward-reference comment already left in `categorySpecifications.model.ts` during #29) settled this name first; same "endpoint table/schema table over issue-body phrasing" call as categorySpecifications made for its own routes. The HTTP path is still `/variant-types` (`/api/admin/categories/:id/variant-types`), matching the SRS endpoint table.
- **Flat, not nested**: unlike `specificationGroups` (groups of fields), this document holds one flat `variants: VariantAxis[]` array — there's no group concept for variant axes. `VariantAxis` is `{ name, code, type: text|select|color|number (default select), required, options?: {label,value}[] }`.
- **`GET`/`PUT`/`PATCH` only — no `POST`/`DELETE`**, identical reasoning to categorySpecifications: deleting an axis happens through `PATCH`, not a separate route.
- **`Router({ mergeParams: true })`**, same requirement and same reason as categorySpecifications' router — mounted mid-path at `/categories/:id/variant-types`.
- **`GET` returns a synthetic empty default before any `PUT`** — `{category, variants: []}`, no 404 — identical to categorySpecifications' `GET` behavior.
- **`PUT` is a full-replace upsert; `PATCH` takes one discriminated-union operation** (`updateAxis` | `deleteAxis`) applied in-memory and persisted through the same full-replace repository function `PUT` uses. No `renameGroup`-equivalent op exists since there's no group layer; `updateAxis` alone covers renaming an axis (including its `code`), the same way categorySpecifications' `updateField` alone covers renaming a field.
- **Matched by `code`, not `name`**: an axis has both a display `name` and a `code`; `PATCH` operations key off `code`. Chosen over `name` specifically because `FR-CAT-037` makes it safe — this definition is never enforced against stored variant attributes, so renaming an axis (or its code) can't orphan anything downstream the way renaming a specification field could.
- **The one real behavioral divergence from categorySpecifications: `deleteAxis` (and `PATCH` generally) carries no in-use guard of any kind** — `FR-CAT-037` is explicit the definition drives admin form rendering only, never enforced against stored variant attributes, so deletion always succeeds even while products hold variants using that axis. No `products.repository.ts` query backs this module at all, unlike categorySpecifications' `countBySpecificationField`.
- **`options` structural validation mirrors categorySpecifications' `enum`/`text` split**: required (non-empty) when `type` is `select` or `color`, forbidden when `type` is `text` or `number` — expressed as two `.refine()`s on the Zod axis schema, not custom Mongoose validators, same split as categorySpecifications.
- **Resolves `categories.service.ts`'s remaining deferred cascade comment**: `deleteCategory` now also calls `categoryVariants.service.ts`'s `deleteForCategory` (alongside categorySpecifications' own, from #29) before its own `deleteById`. Needs no guard of its own to be safe — this document was never gated by product references in the first place.
- No `products.model.ts` stub growth this issue — variant axes are purely a rendering guide, so nothing on the product document references them.
- Test layout matches categorySpecifications: `src/modules/product-catalog/features/categoryVariants/tests/categoryVariants.service.test.ts` (unit) and `__tests__/product-catalog/categoryVariants/categoryVariants.api.test.ts` (Supertest).

## Products

`src/modules/product-catalog/features/products/` (Issue #31 / M2.7, `FR-CAT-001`–`013`, `FR-CAT-085`–`087`) is "the spine of M2" — the first module that's a real consumer of brands, categories, and categorySpecifications rather than just a stub they query. Scope is strictly issue #31's own checklist: no embedded-variant CRUD (`FR-CAT-039`–`044`, #32), no status-transition endpoint (`FR-CAT-045`, `PATCH .../status`, #33), no admin search (`FR-CAT-050`, #34), and no buyer-facing surface at all (`FR-CAT-054`–`056`, #35) — `products.module.ts` exports only `productsAdminModule`.

- **`sku` is immutable after create, exactly like `slug`** — `FR-CAT-004`'s editable-field list omits it, so `UpdateProductInput` has no `sku` field at all (a type-level guarantee, not just a runtime check); a client-submitted `sku` in a `PATCH` body is silently ignored by Zod's default "strip unknown keys" behavior, the same mechanism that makes a client-submitted `sellingPrice` have no effect.
- **`src/utils/pricing.ts`** (new, shared): `computeSellingPrice(mrp, discount)` implements `FR-CAT-087`'s formula (`mrp - floor(mrp * discount / 100)`) as a pure function with no I/O, deliberately placed outside the module (like `slug.ts`/`text.ts`) since #32's variant subdocuments will call the identical formula — a peer module importing into `products/` would be backwards.
- **SKU uniqueness needs two indexes plus an application-level check, not one** (`FR-CAT-003`): a unique index on `sku` and a separate unique multikey index on `variants.sku` (`productSchema.index({ "variants.sku": 1 }, { unique: true })`) can't jointly express "unique across both a scalar field and an array field on the same collection." `products.repository.ts`'s `skuInUse(sku, excludeId?)` runs `{ $or: [{ sku }, { "variants.sku": sku }] }` as the missing cross-check. `variants` was a deliberate partial stub at this point — only `{ sku: string }`, just enough to establish the index ahead of any variant-creation endpoint (an empty array contributes zero index entries, so declaring the index was safe before any variant existed); #32 fills in the rest of the subdocument — see Product Variants below.
- **Specifications validated via a peer service-to-service call in the opposite direction of the categories→categorySpecifications cascade**: `products.service.ts` imports `validateProductSpecifications` from `categorySpecifications.service.ts` (new export, alongside the existing `SpecPatchOperation` machinery). Safe without creating a cycle — `categorySpecifications.service.ts` only imports `products.repository.ts` (not `products.service.ts`), so the module graph stays acyclic: `products.service → categorySpecifications.service → products.repository`. The validator matches submitted `{groupName, name}` pairs against the category's schema, checks every `required` field is present, rejects unknown field names, and checks each value's runtime type against the field's declared `type` (`enum` also checks membership in `options`) — reporting every offending field in one `400 SPECIFICATION_VALIDATION_FAILED`, not just the first, matching this codebase's established "name every blocking reason" house style (`categories`' combined `CATEGORY_IN_USE`, `categorySpecifications`' combined field list).
- **`FR-CAT-034`'s re-validation runs whenever `category` _or_ `specifications` changes on update, not only when both do**: `updateProduct` fetches the existing product first specifically so it can fall back to the _other_ field's current stored value — moving `category` alone re-validates the product's existing (unchanged) specifications against the new schema; changing `specifications` alone re-validates the new values against the current (unchanged) category.
- **First module to actually consume `uploads.service.ts`'s `validateImageCount`/`normalizeImages`/`consumeImageKeys`** with real bounds (`{min:1, max:8}`, `FR-CAT-083`) — brands/categories only ever handled at most one image each, so this is the first `1–8` array case those functions were written for back in #26. Image-count bounds are enforced once, in the service via `validateImageCount` (surfacing `IMAGE_COUNT_OUT_OF_BOUNDS`), not duplicated as a Zod range check — `products.controller.ts`'s Zod schema validates each image's _shape_ only, so there's exactly one authoritative source for the bounds error rather than two competing error codes for the same rule.
- **The first paginated, sortable admin list in this codebase** (`FR-CAT-005`) — brands/categories/categorySpecifications all return their full list unpaginated. `GET /api/admin/products` uses `apiResponse.ts`'s existing `successResponse(items, pagination)` overload (defined since #25/M2.1, unused until now) for the first time. Query params: `page`/`limit` (Zod-clamped: `limit` max `100`, both integers ≥ 1 — an oversized `limit` is rejected with `VALIDATION_ERROR`, not silently clamped, an interpretive call since the SRS only specifies this behavior for _buyer_-facing pagination), and `sort` — an allow-listed enum (`createdAt`/`name`/`mrp`/`stock`, each with an optional `-` prefix for descending; default `-createdAt`) rather than free-form field/order params, since the SRS names no specific sort keys for the admin grid beyond "sortable." No `search` query param — that's `FR-CAT-050`'s admin-search scope (#34), same deferral brands/categories already made.
- **`lowStock` list filter** (`FR-CAT-011`, presence-based — `?lowStock=true`) is the one query filter beyond pagination/sort this issue adds, since the field is explicitly in `FR-CAT-001`–`013`'s range and would otherwise ship unused; implemented as `$expr: { $lte: ["$stock", "$lowStockThreshold"] }` in `products.repository.ts`'s `listPaginated`, since comparing two fields of the same document can't be a plain query-operator filter.
- **`DELETE` is an unconditional status flip to `archived`, not a guarded delete** — unlike brands/categories, nothing downstream references products yet (Orders is v0.5), so there's no in-use count to check. A nonexistent id `404`s (`PRODUCT_NOT_FOUND`) rather than silently succeeding — a deliberate difference from brands'/categories' guarded deletes, which silently succeed on a nonexistent id because their guard count is naturally zero either way; a plain status flip has no such "vacuous success" to fall back on.
- **`DUPLICATE_SKU` is `400`, not `409`** — modeled as an input-validation-style rejection (like categorySpecifications'/categoryVariants' `400 DUPLICATE_*` codes for a payload-level name collision), not a `409`-style "blocked by something that already depends on this" guard (`BRAND_IN_USE`, `CATEGORY_IN_USE`, `SPECIFICATION_FIELD_IN_USE`) — the two express different situations even though both are "already in use."
- **Brand/category reference validation reuses `brands.service.ts`'s `getBrandById`/`categories.service.ts`'s `getCategoryById` directly** (both already throw `BRAND_NOT_FOUND`/`CATEGORY_NOT_FOUND`) rather than re-implementing existence checks against their repositories — the first module to validate a foreign reference this way; safe for the same acyclic-graph reason as the specifications validator, since neither brands' nor categories' service imports `products.service.ts` (only `products.repository.ts`, for their own delete-guard counts).
- Test layout matches the established split: `src/modules/product-catalog/features/products/tests/products.service.test.ts` (unit, all five peer modules — `products.repository`, `uploads.service`, `brands.service`, `categories.service`, `categorySpecifications.service` — mocked) and `__tests__/product-catalog/products/products.api.test.ts` (Supertest; `uploads.service` is a _partial_ mock via `importOriginal` here, since the real Express app also boots `uploads.routes.ts`, which reads `UPLOAD_PURPOSES` off the same module at import time — a full replacement mock would crash route registration, not just this module's own tests).

## Product Variants

Issue #32 / M2.8 (`FR-CAT-039`–`044`) fills in the `variants` array `products.model.ts` stubbed to just `{ sku }` back in #31 — the full embedded subdocument (`attributes`, `images`, `mrp`/`discount`/`sellingPrice`, `stock`, `weight?`, `active`) — and adds `POST /api/admin/products/:id/variants` / `PATCH /api/admin/products/:id/variants/:variantId` to `products.admin.routes.ts`. No new module: variants live entirely inside `products.service.ts`/`.controller.ts`/`.repository.ts`, since they're embedded, not a standalone collection.

- **Both endpoints return the full updated product**, not a variant on its own — there's no standalone variant resource to `GET` independently; the response shape matches create/update's.
- **`products.repository.ts` grows `replaceVariants(id, variants)`**, a full-array replace — same reasoning as categorySpecifications'/categoryVariants' `replaceGroups`/`replaceAxes`: MongoDB positional array-update operators are brittle at this nesting depth for a low-traffic admin tool, so `products.service.ts` loads the product, mutates a plain in-memory copy of `variants`, and persists the whole array in one write. A new variant's `_id` is assigned explicitly via `new Types.ObjectId()` in the service rather than relied on from Mongoose's update-cast subdocument defaulting, which is unreliable for a `$set`-based array replacement (unlike `.push()` on a live document).
- **A variant's `sku` is editable, unlike the parent product's own** — `FR-CAT-004`'s editable-field list explicitly excludes the product's `sku`, but `FR-CAT-040`'s "admin can update a variant" names no such exclusion, so `UpdateVariantInput.sku` is present and optional, re-validated identically to create whenever it changes. A deliberate asymmetry, not an oversight — documented here specifically because it's easy to assume it should mirror the immutable product `sku`.
- **The SKU cross-check needs a three-part check, not just `skuInUse`** — `skuInUse(sku, excludeId)` excludes the _entire_ product document by id, so it correctly rules out every _other_ product's own `sku` and variants, but says nothing about collisions within the same product (the parent's own `sku`, or a sibling variant's `sku`) since those live inside the excluded document. `assertVariantSkuAvailable()` checks those two cases locally against the already-`findById`-fetched product before falling through to `skuInUse` for the "everywhere else" case — all three share one `400 DUPLICATE_SKU`.
- **Attribute-set duplication (`FR-CAT-041`) is checked via a canonical, order-independent key**: `attributeSetKey()` sorts each variant's `name=value` pairs and joins them, so `[Color=Red, Size=L]` and `[Size=L, Color=Red]` collide identically. Checked against every _other_ variant on the product regardless of `active` — the issue's own task list is explicit that both active and inactive variants count, unlike some of this codebase's guards that only consider live state.
- **Variant images reuse the product's own `resolveImages` shape but with a bespoke `resolveVariantImages` bound**: `{min: 1, max: 2}` only engages once at least one image is submitted (`FR-CAT-064`'s "0 or 1-2") — an empty array is valid and short-circuits before `validateImageCount` is even called, unlike the parent product's `images`, which is always required to be 1-8.
- **Deactivation is just `active: false` on the same `PATCH`**, not a separate endpoint or a `DELETE` — `FR-CAT-040` doesn't split it out, and a variant is never hard-removed from the document regardless of `active`'s value; the array length is unchanged either way.
- **`FR-CAT-043` (purchasability) and `FR-CAT-044` (visibility inheritance) are read-time, buyer-facing rules with no code added in #32 itself** — there's no buyer endpoint yet (`#35`) to compute "which unit is purchasable" or filter variants by the parent's `status` against. #32's job is limited to storing the data faithfully (`active`, per-variant `images`/pricing/`stock`) so `#35` can apply both rules once it exists — same deferral shape as `#30`'s `FR-CAT-038` (admin-editor rendering needed no backend code either).
- Tests are added to the existing files, not new ones — `addVariant`/`updateVariant` `describe` blocks in `products.service.test.ts`, and matching `POST`/`PATCH .../variants` blocks in `products.api.test.ts` — since this is an extension of the products module, not a new one.

## Variant-Only Pricing (Issue #102, SRS v0.2 amendment)

Issue #102 collapses the "zero-variant products sell on their own sku/price/stock, one-or-more-variant products sell per variant" model `#31`/`#32` originally shipped (`FR-CAT-043`) down to **variant-only**: `products.model.ts`'s `ProductDocument` drops `sku`/`images`/`mrp`/`discount`/`sellingPrice`/`stock`/`lowStockThreshold` entirely — a product is now pure metadata (name/description/brand/category/specifications/SEO/`isFeatured`). Stock/inventory tracking and the derived buyer-facing `availability` enum (`src/utils/availability.ts`, `FR-CAT-095`/`096`) are removed **system-wide**, not moved to the variant — this system tracks no inventory quantity at all, admin or buyer-facing.

- **A product needs ≥1 active variant to publish** (`FR-CAT-043`) — `updateProductStatus()` now does an extra `findById` + `variants.some(v => v.active)` check only when the target status is `"published"`, throwing a new `400 PRODUCT_HAS_NO_VARIANTS` otherwise. `"draft"`/`"archived"` transitions are unaffected — this is a publish-time guard, not a standing invariant enforced on every variant write, so deactivating the last active variant on an already-published product isn't separately blocked (a documented, accepted gap, same "TOCTOU documented, not fixed" treatment this module already gives other races).
- **Variant `images` is now schema-`required`, 1–2, unconditionally** (no more `default: []` on the schema, no more `resolveVariantImages`' empty-array short-circuit) — since the product no longer has any images of its own, there's no parent gallery left for a zero-image variant to fall back to (`FR-CAT-064`'s old last sentence is gone).
- **`skuInUse()` and `assertVariantSkuAvailable()` lose their product-`sku` half** — `FR-CAT-003`'s "shared namespace" collapses to `variants.sku` alone, now the sole SKU-uniqueness source (index and application-level check both). The `variants.sku` unique multikey index is technically sufficient on its own now; the application-level `skuInUse` check stays anyway, for a friendly `400 DUPLICATE_SKU` instead of a raw Mongo `E11000` surfacing as an uncaught `500`.
- **Buyer-facing list/detail mappers (`toPublicListItem`/`toPublicDetail`) source image and price from `selectDefaultVariant()` unconditionally** — no more `defaultVariant ? … : product.…` fallback branch, since there's no product-level value left to fall back to. `PublicProductListItem`'s `mrp`/`discount`/`sellingPrice`/`primaryImage` and `PublicProductDetail`'s `mrp`/`discount`/`sellingPrice`/`defaultVariantId` are all now optional, genuinely absent (not `null`/`0`) on the one edge case above (a published product that ends up with zero active variants). `PublicProductDetail` also drops its old top-level `sku`/`images` — both stay per-variant only (`variants[].sku`/`.images`), since a multi-variant product has no single unambiguous value for either.
- **`buildMatchStage()`'s price-range/on-sale filters move from top-level `sellingPrice`/`discount` fields into one `$elemMatch` on `variants`** (alongside `active: true`) — a single variant must satisfy price range **and** on-sale together when both are requested, not two different variants independently. `buildSearchFilters()`'s Atlas-only variant-attribute `embeddedDocument` filter gains the identical price/on-sale clauses inside its own `compound.filter` when combined with an attribute filter, so the plain and Atlas query paths stay semantically consistent.
- **Price sorting (`price_asc`/`price_desc`) is no longer a plain `.sort({sellingPrice})`** — there's no top-level field to sort by. Both `listPublicPaginated()` and `searchPublicPaginated()` gain a `priceSortStages()` case: `$addFields` a computed `sortPrice` (`$min` of each product's active variants' `sellingPrice` — the "starting from" price, same key for both directions, just the order flipped) then `$sort` on it. `listPublicPaginated()` branches into a small aggregation (`$match` → `priceSortStages` → `$facet`) only for this case; every other sort keeps the original plain `.find().sort()` path. A new shared `runFacetedAggregate()` helper (pull `$facet` items/count apart, then `Product.populate()` manually) is reused by this new branch and by `searchPublicPaginated()`'s pre-existing aggregation tail.
- **Admin list**: `?lowStock=` and the `mrp`/`stock` sort options are gone (`ProductSortField` is now just `"createdAt" | "name"`); `search`'s SKU half now targets `variants.sku` instead of the removed `sku` field.
- **`PATCH /api/admin/products/:id/stock` is deleted outright** — `updateStockSchema`/`updateStockHandler`/`updateStock()` (service) all removed, along with the route.
- **`backend/src/scripts/seed/generate.ts`** (local dev catalog seeding, predates this doc's own coverage) updated to the new shape — no product-level `sku`/`images`/`mrp`/`discount`/`stock`/`lowStockThreshold`, no variant `stock`.
- No index-field changes to `backend/atlas-search/products-search-index.json` — `sku`/`stock`/`sellingPrice` were never mapped fields there to begin with (only `name`/`description`/`variants.*`/`specifications.*` are).

Issue #34 / M2.10 (`FR-CAT-050`–`053`) adds a `?search=` query param to all three existing admin list endpoints. ## Shared Admin List Query Parsing

Issue #104 (SRS v0.2 amendment) extracts a shared `src/utils/parseQuery.ts` and uses it to bring categories'/brands' admin lists up to pagination/sort parity with products' — both had returned an unfiltered, unpaginated full array via the 1-arg `successResponse(data)` overload since #27/#28. Products' own sort wire format changes from a combined `?sort=-field` enum to two params, matching the new shared shape. No new modules — one new repository/service/controller signature change per module, same "extend, don't create" shape #32–#36 already established.

- **`parseQuery.ts` is pure and deliberately non-throwing** — `errorHandler.ts`'s `ZodError` branch is the only code path in this codebase producing `VALIDATION_ERROR` (with a field-keyed `errors` object); a hand-thrown `AppError(400,"VALIDATION_ERROR",...)` from inside a shared util would produce a different response shape for the identical code. So each controller's own Zod schema (`z.enum(<SORT_FIELDS>)` for `sortBy`, `z.enum(["asc","desc","none"])` for `orderBy`, `.max(100)` for `limit`) is what rejects bad input, exactly like products' pre-#104 `sort` enum already did — `parseQuery(search, pagination, sortBy, orderBy, field, filter?)` only ever shapes already-valid input into `{filter, sort?, page, limit}`; `field` (the caller's sortable-field allow-list) is consulted only as a redundant, unreachable-once-Zod-has-run defensive guard and to type the returned `sort`.
- **The returned `sort` shape, `{field, order}`, deliberately mirrors `ProductListSort` exactly** — `products.repository.ts`'s `listPaginated` needed no shape change to its `sort` parameter, only widening it to `| undefined` (`orderBy:"none"` means no `.sort()` call at all, not a fallback default).
- **Products' call passes `search: undefined`** — its search behavior (name: unanchored case-insensitive regex; sku: prefix-anchored, no case-insensitive flag) is asymmetric across fields and doesn't fit `parseQuery`'s generic same-regex-every-field merge, so that logic stays exactly as-is, untouched, inside `products.repository.ts`'s `listPaginated`. Only `sortBy`/`orderBy`/`field`/`pagination` are exercised for products' call; `PRODUCT_SORT_FIELDS = ["createdAt", "name"] as const` (new, exported from `products.repository.ts`) replaces the controller-local `SORT_VALUES`/`parseSort` as the single source of truth. Default `sortBy:"createdAt"`/`orderBy:"desc"` reproduces the old `-createdAt` default exactly.
- **Categories/brands _do_ use the generic `search`** (single field `["name"]`, functionally identical to their existing single-field regex match) — `CATEGORY_SORT_FIELDS = ["name", "sortOrder", "createdAt"] as const` and `BRAND_SORT_FIELDS = ["name", "createdAt"] as const` (new, exported from each repository; brands has no `sortOrder` field to sort by). `orderBy` defaults to `"none"` with no `sortBy` default on both — a deliberately conservative choice for a genuinely new capability, preserving each endpoint's pre-#104 "no guaranteed order" behavior when a caller sends nothing.
- **`categories.repository.ts`'s and `brands.repository.ts`'s `list()` both change shape**: from `list(search?: string): Promise<Record[]>` to `list(filter: QueryFilter<Document>, sort, page): Promise<{items, total}>` (`QueryFilter` is Mongoose's own exported type, not a `parseQuery.ts` addition) — filter (built by `parseQuery`, name search folded in) and sort now arrive pre-built from the controller, the same layering `products.repository.ts` already used. Confirmed each had exactly one caller (`listCategoriesForAdmin`/`listBrandsForAdmin`) before changing the signature. `listCategoriesForAdmin`/`listBrandsForAdmin` (service) now return `{items, pagination}` instead of a plain array, and their controllers switch to the 2-arg `successResponse(items, pagination)` overload.
- **`src/utils/apiResponse.ts` grows `buildPagination(page, limit, total): Pagination`** — extracted from `products.service.ts`, which had this exact formula duplicated twice already (a private buyer-facing copy and an inline copy in `listProductsForAdmin`) before this issue would have added a third and fourth for categories/brands. All four call sites now share the one implementation.
- **Known, accepted, documented gap: `admin-app` truncation risk.** `admin-app`'s `categoriesApi.ts`/`brandsApi.ts`/`CategoryList.tsx` currently expect the _entire_ unpaginated array back from `GET /api/admin/categories`/`GET /api/admin/brands` — now that both paginate with a default `limit: 20` (same default as products, for consistency across all three admin lists — a deliberate choice over a defensively-high default), `admin-app` will silently render only the first 20 categories/brands until a follow-up frontend issue updates it to actually page through results. This mirrors #102's own precedent of shipping a backend contract change ahead of its frontend consumer, except this one is a silent data-truncation risk on a screen that already exists and is in use today, not just a shape change on an unbuilt screen — flagged here prominently rather than left implicit.
- Test layout matches #34's precedent: new cases added to each module's existing `tests/*.service.test.ts` / `__tests__/*.api.test.ts` files (no new test files), plus a new `src/utils/tests/parseQuery.test.ts` (one `describe("parseQuery", ...)` block, mirroring `text.test.ts`'s per-behavior `it` style).

## Newest Sort By Primary Variant (Issue #121)

Issue #121 was filed against `buyer-app` (observed as inconsistent Home Page card ordering) but its actual fix is entirely here — the buyer-facing `?sort=newest` default has no product-level field to sort by reliably since `#102` made products variant-only.

- **The real bug, found while investigating**: `products.repository.ts`'s `replaceVariants(id, variants)` persists the _entire_ `variants` array in one `$set` every time `addVariant`/`updateVariant` runs. Empirically confirmed against a real product: every variant's `createdAt` was identical and matched the product's own `updatedAt` from the most recent variant write — Mongoose's subdocument-array casting re-stamps `createdAt`/`updatedAt` on every element that arrives without one, every time the whole array is `$set`, regardless of whether that element was actually touched. Also empirically confirmed: passing `{timestamps:false}` to `Product.findByIdAndUpdate` suppresses only the _document's_ own auto-timestamp bump, not the subdocument-array schema's own casting-time defaulting — it doesn't fix this on its own.
- **Fix: `replaceVariants` now goes through the raw MongoDB driver** (`Product.collection.updateOne(...)`, then a plain `findById`), deliberately bypassing Mongoose's schema casting entirely — verified empirically (a disposable test product, `create → add two variants → inspect → delete`) that this persists exactly what the caller supplies, nothing more. `addVariant`/`updateVariant` (`products.service.ts`) are the caller: a new variant gets fresh `createdAt`/`updatedAt`; an edited variant keeps its original `createdAt` but bumps `updatedAt`; untouched sibling variants are left exactly as fetched. `ProductVariant`'s TS type (`products.model.ts`) gained explicit `createdAt: Date`/`updatedAt: Date` fields to support this — both were always present at runtime via the subdocument schema's own `{timestamps:true}`, just untyped until now.
- **"Primary variant" has no prior definition in this codebase** (unlike images, variants have no `isPrimary` flag) — defined identically to the already-established `selectDefaultVariant()` (`products.service.ts`): the lowest-`sellingPrice` _active_ variant. A new shared `newestSortStages()` (`products.repository.ts`, mirroring `priceSortStages()`'s existing `$addFields`-then-`$sort` shape) reimplements that same selection rule in aggregation syntax via `$sortArray`/`$first` (MongoDB ≥5.2; confirmed 8.0 on this Atlas cluster), extracting that variant's `createdAt` into a computed `sortCreatedAt` field to sort on. A product with zero active variants gets a missing `sortCreatedAt` and sorts last under `-1` — not specially handled, consistent with how this codebase already treats that documented edge case elsewhere (e.g. `toPublicListItem`'s absent price/image fields).
- **Wired into both `listPublicPaginated`'s non-price-sort branch and `searchPublicPaginated`'s newest-fallback branch** — fixing only the former (Home Page's own literal path) would have left Search's "newest" fallback ordering the same products differently for the identical underlying reason, an inconsistency judged worse than the small extra diff of sharing the fix. `listPublicPaginated` is now always aggregation-based (the old plain `.find().sort({createdAt:-1})` path is gone) — both price sorts and newest now need a computed-per-product sort key derived from `variants`, since there's no top-level field left to sort by directly.
- **Deliberately out of scope**: the admin list's own `?sortBy=createdAt` (still the product's own top-level field) and exposing `createdAt` on the buyer API response (nothing renders it — this only ever affected sort order, not a displayed value) — both per an explicit scoping decision, not an oversight.
- Test coverage: two new cases in `products.service.test.ts`'s existing `addVariant`/`updateVariant` `describe` blocks, asserting the exact variant array passed to the (mocked) `replaceVariants` — a new variant's fresh/matching `createdAt`/`updatedAt`, an edited variant's preserved `createdAt` alongside a bumped `updatedAt`, and an untouched sibling's timestamps left exactly as they were. No dedicated `newestSortStages()` test — same as `priceSortStages()`, this codebase has no existing precedent for testing aggregation pipeline shape/output directly (the repository layer stays mocked everywhere else too); manually verified end-to-end instead, against the real database and running API, before merge.

## Buyer Browsing

Issue #35 / M2.11 (`FR-CAT-054`–`067`, `FR-CAT-095`–`096`) is the first buyer-facing surface for products — everything before this issue was admin-only (`productsAdminModule` was the only export from `products.module.ts`). No new module: buyer routes/handlers/service functions extend the existing `products`/`categories` modules, same "extend, don't create" shape #32–#34 already established, plus two new shared utilities.

- **`src/utils/availability.ts`** (new, shared): `deriveAvailability(stock, lowStockThreshold)` implements `FR-CAT-096`'s per-unit formula (`0` → `out_of_stock`; `0 < stock ≤ lowStockThreshold` → `low_stock`, inclusive; else `in_stock`) and `bestAvailability(states)` picks the best of a list (`in_stock` > `low_stock` > `out_of_stock`). Every buyer response substitutes this enum for the raw `stock`/`lowStockThreshold` fields it's never allowed to leak (`FR-CAT-095`). **Variants carry no `lowStockThreshold` of their own** — every per-unit calculation in this module, whether the unit is the product itself or one of its variants, reuses the _parent product's_ single threshold, since the schema has nowhere else to store one; a deliberate interpretive call, documented at each call site.
- **First use of Mongoose `.populate()` in this codebase**: every prior admin read was content with a raw `brand`/`category` ObjectId ref; buyer responses need the referenced document's own `name`/`slug`. `products.repository.ts` exports a `PopulatedRef` (`{_id, name, slug}`) and a `PublicProductDoc` type (`ProductRecord` with `brand`/`category` replaced by `PopulatedRef`), and every buyer-facing repository query chains `.populate("brand", "name slug").populate("category", "name slug")` before `.lean()`.
- **Two query shapes for listing, not one**: `listPublicPaginated(filter, page)` is a plain `.find({status:"published", ...})` — used for the flat `GET /api/products` (no `?q=`) and the category-scoped `GET /api/categories/:slug/products`. `searchPublicPaginated(q, filter, page)` (`FR-CAT-065`) is a genuinely different aggregation pipeline — `$search` must lead an aggregation, incompatible with layering onto a plain `.find()` — using `$facet` to run the paginated slice and the total count in one round trip, then `Product.populate()` on the raw aggregate result (aggregation doesn't run schema-level populate automatically the way `.find().populate()` does).
- **The Atlas Search index this depends on is a real Atlas-cluster provisioning step, not something this issue's code can create** — `backend/.env`'s local `MONGODB_URI` points at a plain `mongodb://localhost` instance, and Atlas Search is an Atlas-cluster-only feature (it doesn't exist against local/self-hosted MongoDB at all, Community Edition included). `backend/atlas-search/products-search-index.json` + `backend/atlas-search/README.md` check in the index definition (named `products_search`, `dynamic:false` over `name`/`description`) and the manual steps to apply it via the Atlas Console or CLI once pointed at a real cluster. Until then, `?q=` requests error at the database level — a known, accepted gap, same "documented, not fixed" treatment this codebase already gives its other infra-dependent gaps (e.g. brands'/categories' delete-guard TOCTOU races).
- **`GET /api/categories/:slug/products` (`FR-CAT-055`) is wired from `categories.public.routes.ts`, but its controller (`listProductsByCategorySlugHandler`) lives in `products.controller.ts`** — the response is product data, not category data, so the controller stays with the data it returns; only the route's _wiring_ crosses modules, imported directly into `categories.public.routes.ts`. Category resolution itself (`categories.service.ts`'s new `getActiveCategoryBySlug`/`listActiveSubcategoryIds`) is active-only and 404s as `CATEGORY_NOT_FOUND` on a miss — a deactivated category's slug shouldn't resolve to a buyer-visible product listing either, and categories are at most two levels deep, so "direct active children" already covers the whole subtree.
- **`GET /api/categories/search` (`FR-CAT-066`)** reuses `categories.repository.ts`'s `listActive(search?)` (already extended with an optional search param during #34) via a new `searchPublicCategoriesHandler`, distinct from the existing `listPublicCategoriesHandler` only in that `q` is _required_ here (this route exists specifically to search) versus optional on the plain list. Deliberately still a plain regex query, not Atlas Search — `FR-CAT-066`'s own wording: `categories` is too small a collection to warrant a second search index.
- **Buyer pagination clamps an oversized `limit` instead of rejecting it (`FR-CAT-057`)** — the opposite of the admin list's `.max(100)` → `VALIDATION_ERROR`. `products.controller.ts`'s buyer query schemas have no `.max()` at all; a new `clampLimit()` does `Math.min(limit, PUBLIC_PAGE_SIZE_MAX)` after parsing instead. `PUBLIC_PAGE_SIZE_DEFAULT`/`MAX` are `24`/`48` — the SRS's own worked JSON example uses `limit: 24`; no maximum is specified anywhere, so `48` (2×) is this issue's own interpretive choice.
- **List item shape follows the SRS's own worked example, minus `cardSpecifications`** — `FR-CAT-091`/`092` (card content: primary image, name, `sellingPrice`, and — on category cards — the first four `filterable` specifications in schema order) are explicitly **not** this issue's scope; the GitHub issue body's own `Implements` line names `FR-CAT-054`–`067`/`095`–`096` only. `PublicProductListItem` carries `_id, name, slug, brand{_id,name,slug}, primaryImage?, mrp, discount, sellingPrice, availability, isFeatured` — everything the worked example shows except `cardSpecifications`, which is `#36`'s job.
- **List-view vs. detail-view availability are deliberately different computations**, both reachable from `FR-CAT-096`'s single sentence: list items use `bestAvailability()` across every _active_ variant (`FR-CAT-096`'s literal "product-level availability is the best state across active variants" — one badge per card). The detail page's _initially-displayed_ availability (`FR-CAT-064`) is narrower: the state of whichever single unit is currently selected — the default variant if one exists, else the product's own stock — not a rolled-up best-of-everything value, since `FR-CAT-064` describes a value that changes as the buyer picks a different variant, not a static badge.
- **`FR-CAT-064`'s default-variant selection**: the lowest-`sellingPrice` _active_ variant (`selectDefaultVariant()`). Inactive variants are excluded from selection **and** from the buyer-facing `variants[]` array entirely — an interpretive call, since nothing in `FR-CAT-040` states whether an inactive variant is buyer-visible at all, and there's no reason to surface one the buyer can't select. When at least one active variant exists, the detail response's top-level `mrp`/`discount`/`sellingPrice`/`availability` reflect that default variant, not the parent product's own stored fields — matching `FR-CAT-064`'s "defaults to... and updates the displayed price/availability/images" literally. `defaultVariantId` is present only when a default variant exists; omitted (not `null`) otherwise, same `exactOptionalPropertyTypes: true` convention every other optional field in this codebase follows.
- **A variant with no images of its own falls back to the parent's images (`FR-CAT-064`'s last sentence)**, resolved server-side in `toPublicVariant()` so buyer-app consumers never duplicate the fallback themselves.
- **`FR-CAT-012`'s meta-description fallback is implemented for products for the first time here** — the field has existed on the schema since #31, but nothing read it until this issue built products' first buyer-facing read path. Identical formula to categories' own fallback (`metaTitle ?? name`, `metaDescription ?? truncate(description)`) via the same `src/utils/text.ts`; a product's `description` is always required (unlike categories', which is optional), so there's no further name fallback needed on that side.
- **`FR-CAT-063`: the detail page's `specifications` field is a verbatim pass-through of every stored group/value**, filterable or not — unlike list items, the detail response draws no distinction; filtering _which_ specs are filterable is `#36`'s concern (`FR-CAT-072`), not a detail-page display rule.
- **A new shared `src/utils/routeParams.ts`'s `parseSlugParam()`** mirrors `objectId.ts`'s `parseObjectId()` for this codebase's first `:slug`-based routes — same reasoning (validate the route param's shape before it reaches the service, and the same `string | string[] | undefined` real type under `noUncheckedIndexedAccess: true`), but a malformed/missing slug is `400 INVALID_SLUG`, not `404` — `404` stays reserved for a well-formed slug that simply doesn't match any record, so a client can tell "you sent garbage" apart from "that product doesn't exist."
- Test layout: new buyer-facing `describe` blocks added to each module's existing `tests/*.service.test.ts` / `__tests__/*.api.test.ts` files (no new test files, same #33/#34 precedent), plus a new `src/utils/tests/availability.test.ts`. The repository layer stays mocked in every test, same as every prior list endpoint — the Atlas Search aggregation pipeline's actual query shape is therefore unverified against a real Atlas cluster by this test suite, same "documented gap" as the index provisioning itself.

## Buyer Filtering & Sorting

Issue #36 / M2.12 (`FR-CAT-068`–`076`, `FR-CAT-091`–`092`) is the last M2 issue — it extends #35's two buyer listing endpoints (`GET /api/products`, `GET /api/categories/:slug/products`) with a full filter/sort surface and adds `cardSpecifications` to every list item. No new modules, same "extend, don't create" shape every M2 issue since #32 has followed.

- **Two query paths, same split #35 already drew, just with a richer boundary**: `buildMatchStage()` (new, `products.repository.ts`) builds the plain-MongoDB side of the filter — category/brand/price-range/in-stock/on-sale — shared by both `listPublicPaginated` and `searchPublicPaginated`'s post-`$search` `$match` stage. Variant-attribute (`FR-CAT-071`) and filterable-specification (`FR-CAT-072`) filters are Atlas-only (`buildSearchFilters()`), since matching "name X and value Y on the _same_ array element" needs `embeddedDocument`/`embeddedDocuments` operators Atlas Search provides and a plain query's `$elemMatch` can only approximate with more code — **submitting either one now forces the Atlas Search path even with no `?q=` at all**, a new routing condition beyond #35's original "only `?q=` triggers Atlas Search."
- **`in_stock` (`FR-CAT-073`)**: no variants → the product's own `stock > 0`; with variants → at least one _active_ variant has `stock > 0`. Expressed as a two-branch `$or` in `buildMatchStage()`, mirroring `FR-CAT-096`'s own availability rule (best state across active variants) but as a boolean gate rather than an enum.
- **Price sorting always targets `sellingPrice`, never `mrp`** (`FR-CAT-075`) — `sortSpec()`'s `price_asc`/`price_desc` cases. `"relevance"` only means something alongside `$search`'s own score order; both the plain `.find()` path and an Atlas query with no `q` (attribute/spec filters only, nothing to rank by) fall back to `newest` instead of trying to sort by a score that was never computed.
- **`?category=<slug>` is new on the _flat_ `GET /api/products`** (`FR-CAT-070`), resolved via the identical `getActiveCategoryBySlug`/`listActiveSubcategoryIds` pair the dedicated nested route already used — the two aren't duplicated, `listPublicProductsCore()` (new, `products.service.ts`) is the one implementation both `listPublicProducts`/`listPublicProductsByCategorySlug` now funnel into, differing only in whether `categorySlug` arrives via a query param or is already fixed by the route.
- **Filterable-specification filter validation is category-scoped, not global** (`FR-CAT-072`/`035`): `categorySpecifications.service.ts`'s new `getFilterableFieldsByCategory(categoryId)` is only consulted when the listing resolves to exactly one category (the nested route, or `?category=` on the flat one) — an unscoped, catalog-wide listing has no single schema to validate against, so a spec filter there is matched literally rather than rejected, a deliberate simplification (documented at `resolveSpecFilters()`) rather than a security gap: the filter can only ever narrow results, never expose more than a plain query already could. When a category _is_ known, an unfilterable or nonexistent field name, or a value/range shape mismatched to the field's actual type (`enum`/`boolean` → value match, `number` → range, per `FR-CAT-035`), is rejected as `400 INVALID_SPECIFICATION_FILTER`.
- **Spec filters matched by name alone, not `groupName` + name** — same simplification `categorySpecifications.service.ts`'s card-field lookup (below) already makes: the buyer-facing filter rail has no reason to expose group structure, and categorySpecifications' own duplicate-name guard is scoped to a single group, not the whole category, so this accepts a rare same-name-different-group collision rather than complicating the filter shape to rule it out.
- **`variantAttribute` is never validated against `categoryVariants`' axis definitions** — consistent with #30's own established rule that this definition drives admin form rendering only and is never enforced against stored variant attributes; a filter naming an axis that was never defined (or has since been renamed) just matches nothing, same as any other filter with no matches (`FR-CAT-058`).
- **`cardSpecifications` (`FR-CAT-091`/`092`) is always present on every list item**, even as `[]` on a home/all-products listing or a category with no filterable fields — per the SRS, home and category views share one response shape, and it's `buyer-app`'s job to ignore the field on the home grid rather than the API omitting it contextually. `categorySpecifications.service.ts`'s new `getCardFieldsByCategoryIds()` batch-fetches the first four filterable fields (in schema declaration order) for every distinct category on a result page in one query — `products.service.ts`'s `attachCardSpecifications()` — then `buildCardSpecifications()` looks up the _product's own_ value for each; a field the product carries no value for is skipped entirely, never padded with a placeholder, matching "a product carrying fewer than four filterable specifications renders only those it has."
- **`unit` is explicitly `null`, not omitted, on a `cardSpecifications` entry with no unit** — the one field in this codebase that breaks from the usual "omit an absent optional field" convention, chosen to match the SRS's own worked JSON example precisely (`"unit": null`) rather than this module's default.
- **A real, pre-existing bug found and fixed while building this**: Express 5's default query parser (`"simple"`, Node's built-in `querystring`) doesn't support the bracket notation (`?spec[RAM]=8GB`, `?spec[ScreenSize][min]=6`) this issue's dynamic specification filters need — Express 4's `"extended"` (`qs`-based) default was dropped, and `qs` is no longer bundled as a dependency. `src/app.ts` now calls `app.set("query parser", "extended")`, with `qs`/`@types/qs` added as explicit `backend` dependencies (previously only present transitively). No prior route needed structured/nested query params, so nothing else in this codebase depended on the old default.
- **The Atlas Search index definition (`backend/atlas-search/products-search-index.json`) grows two `embeddedDocuments`-typed fields**, `variants` and `specifications`, alongside #35's original `name`/`description` — see `backend/atlas-search/README.md` for the updated field-by-field explanation. Same unprovisioned-cluster caveat as #35: this repo has no Atlas access, so the index mapping and the `embeddedDocument` query operators `buildSearchFilters()` builds against it are this codebase's best-faith translation of Atlas Search's documented syntax, not verified against a live cluster.
- Test layout matches #35's precedent: new cases added to each module's existing `tests/*.service.test.ts` / `__tests__/*.api.test.ts` files (no new test files) plus new `describe` blocks in `categorySpecifications.service.test.ts` for the two new lookups. Same repository-stays-mocked caveat as #35 — the Atlas Search filter-clause construction is exercised only via the service/controller layers asserting the right filter object reaches the (mocked) repository call, never against a real index.

## Authentication (Buyer)

Issue #139 (`FR-AUTH-001`–`008`, `046`) — buyer sign-in via Google OAuth, Google One Tap, and email OTP, all resolving to one `users` collection by email. This is a **redo**: it shipped once (PR #202), was reverted the same day alongside two sibling admin-auth issues (#140/#141, PR #208) because login broke on deployed previews, then redone here with a fix. Scope is strictly buyer auth — no admin password/OTP sign-in, no `X-Admin-Key` replacement (both still #140/#141/#143, untouched by this issue).

- **Root cause of the original break, and why this redo uses a bearer token, not cookies alone**: `buyer-app` deploys to Vercel, `backend` deploys to Render (`docs/architecture.md` §7) — genuinely separate domains, no shared parent domain, no proxy. Better Auth's default session is a `sameSite=lax` cookie; a cross-site `fetch` from Vercel to Render won't reliably carry it back (and Safari blocks third-party/cross-site cookies outright regardless of `sameSite`), so this passed CI and worked locally while being broken in every real deployed environment. Fixed by adding Better Auth's official `bearer` plugin (`src/lib/auth.ts`) — additive alongside the existing cookie, not a replacement: sign-in returns the session token in a `set-auth-token` response header, and a client sends it back as `Authorization: Bearer <token>`. Documented as an SRS amendment, `FR-AUTH-046` (`docs/srs/features/0.3-authentication.md`), since the spec's original `FR-AUTH-015` said a session was "never a client-readable or client-storable token" — inert for buyer auth specifically since `#140` (admin, same cross-domain shape) hasn't been redone yet, but flagged there for when it is.
- **`src/lib/` is a new top-level directory** — this codebase's first constructed-third-party-singleton category, distinct from `src/config/`'s env/DB bootstrap and `src/externalService/`'s thin async-function SDK wrappers. `auth.ts` exports one `betterAuth(...)` instance (`mongodbAdapter` reusing `mongoose.connection.db`/`getClient()`, `transaction: false` — a confirmed, still-open upstream bug, [better-auth#10925](https://github.com/better-auth/better-auth/issues/10925), not a workaround for anything this feature's account-creation flows actually need).
- **`src/middleware/betterAuthHandler.ts`** bridges Better Auth's native Fetch-API `Request`/`Response` handler to Express and reshapes JSON responses to `{success:true,data}`/`{success:false,code,message}`. Wired in via **`src/modules/auth/`** (`auth.routes.ts` + `auth.module.ts`, exporting `{path:"/api/auth", router}`) — the same module shape `health`/`brands`/`categories`/`products` use, mounted through `src/routes/index.ts` like every other route, not a special case in `app.ts`. The one real constraint this forces: Better Auth needs the raw, unparsed request body, so `authModule` is registered **first** in `routes/index.ts`, ahead of that file's own `router.use(express.json())` — `express.json()` moved out of `app.ts` and into `routes/index.ts` specifically so the auth module could sit ahead of it while every other module still gets JSON parsing; `app.ts` itself is back to knowing nothing about auth. Forwards every response header except `set-cookie` (handled separately, since a single `Headers` entry can hold multiple `Set-Cookie` values `res.setHeader` would clobber) and `content-type`/`content-length` (set by `res.json()`/`res.send()` themselves) — not just `Set-Cookie` alone, which is what the original (reverted) version of this bridge did, silently dropping `set-auth-token` and making the whole bearer-token mechanism invisible until deployed.
- **`src/middleware/cors.ts`** gained `"Authorization"` in `allowedHeaders` (the Bearer header needs to survive preflight) and `exposedHeaders: ["set-auth-token"]` (without it, a browser receives the header but cross-origin `fetch(...).headers.get(...)` can't read it — the second silent-failure point in this mechanism). `origin` changed from a plain array to a matcher function (`src/utils/originMatch.ts`'s `matchesOrigin`) supporting a `*` wildcard segment per `CORS_ORIGINS` entry, so an operator can put e.g. `https://tech-cart-buyer-app-*.vercel.app` into Render's `CORS_ORIGINS` for staging to match Vercel's per-branch preview URLs (which change every deploy and can't be listed as static literals) — deliberately scoped to this project's own Vercel URL prefix, never a bare `*.vercel.app`, which would trust every Vercel-hosted app on the internet. Existing literal (non-wildcard) entries keep matching exactly.
- **`src/externalService/resend.ts`** — the second client under `externalService/`, same pattern as `r2.ts`: `new Resend(env.RESEND.API_KEY)` constructed once, one exported async function (`sendOtpEmail`).
- **`additionalFields`**: `role` (default `"buyer"`, `input:false` — blocks a client-supplied role, `FR-AUTH-004`), `status`, `phone`, `lastSignInAt` (`input:false`, stamped via `databaseHooks.session.create.after`).
- **`FR-AUTH-006` (reject a buyer sign-in on an email already registered as non-buyer)** is enforced two ways: `user.validateUserInfo` re-validates on every OAuth/One Tap sign-in (fresh provider identity each time); a `hooks.before` matcher (`rejectAdminEmailOnReturningOtpSignIn`) closes the one gap `validateUserInfo` doesn't cover — a _returning_ email-OTP sign-in for an already-existing account isn't re-validated through that hook, per Better Auth's own docs.
- **Known, documented limitation, out of scope for this backend-only issue**: Google OAuth is a full-page browser redirect, not a `fetch` call — a redirect response's headers (including `set-auth-token`) aren't readable by frontend JS the way a `fetch` response's are. One Tap and email-OTP are both direct JSON `fetch` calls and get the bearer token cleanly; whichever future issue wires `buyer-app`'s actual sign-in UI needs a specific technique (e.g. a token-exchange step after the redirect lands) for the OAuth path specifically. Pre-existing to the cross-domain premise, not introduced by this redo.
- **Route paths are Better Auth's own plugin-generated paths, confirmed against the installed `better-auth@1.7.1`** (not the SRS endpoint table's illustrative names, per that table's own footnote): `POST /api/auth/one-tap/callback`, `POST /api/auth/sign-in/social`, `GET /api/auth/callback/google`, `POST /api/auth/email-otp/send-verification-otp`, `POST /api/auth/sign-in/email-otp`, `GET /api/auth/get-session` (not `/api/auth/session`).
- **Test**: `__tests__/auth/auth.api.test.ts` — this codebase's first real-database test suite (`mongodb-memory-server`'s standalone `MongoMemoryServer`, not a replica set — sufficient since `transaction: false` means nothing here needs replica-set-only transaction support), needed because account-dedup/reject logic can't be trusted against a mocked adapter. Covers OAuth/One Tap/OTP account creation, cross-method dedup by email, no-client-supplied-role, OTP reuse/expiry rejection, and admin-email rejection — plus two tests specific to this redo's actual fix: one signs in and calls a _separate_ request with only `Authorization: Bearer <token>` and no cookies at all (the direct regression test for the bug that got this feature reverted — none of the other tests would have caught it, since Supertest's plain `request(app)` doesn't persist cookies across calls either way), and one asserts `Access-Control-Expose-Headers` actually includes `set-auth-token` when a request carries an `Origin` header.
- **CI**: `.github/workflows/ci.yml`'s `backend` test-matrix leg caches `~/.cache/mongodb-binaries` (`actions/cache`), since `mongodb-memory-server` downloads its own MongoDB binary on first use.

Also a **redo**: it shipped once (PR #205) alongside #139's first attempt, was reverted in the same PR #208 for the identical cross-domain cookie reason, and stayed unredone through #139's own redo (#209) since `admin-app`'s cross-domain shape needed its own verification. - **`src/scripts/seed/createAdminUser.ts`'s `provisionAdminUser()`** — shared by the CLI seed script (`npm run seed:admin --workspace backend` at the time this issue shipped; superseded by `npm run seed:super-admin`, see Admin Account Provisioning below) and the test suite, so "create a Better-Auth-compatible password credential" logic exists once. Rate limiting (`FR-AUTH-040`/`041`, Upstash Redis) is explicitly deferred too — no Redis dependency exists in this codebase yet.
- Test: `__tests__/auth/admin-sign-in.api.test.ts` (kept separate from `auth.api.test.ts` — the flow shape differs materially from buyer's single-call methods) — happy path, wrong-password/unknown-email identical error, password-alone-insufficient, wrong/expired/reused OTP, sign-out invalidation, cookie flags (`httpOnly`/`secure`/`sameSite=lax`), the bearer-token round-trip, and buyer-role rejection.

## Admin Password Reset

Issue #141 / M3.3 (`FR-AUTH-019`–`022`) — self-service recovery for an admin who forgets the password #140 introduced. Built on the same `emailAndPassword` plugin's own reset-password support, not hand-rolled token logic; extends `src/lib/auth.ts` again, plus one new small tracking collection. No `X-Admin-Key`/provisioning changes.

- **Real endpoint is `POST /api/auth/request-password-reset` (`requestPasswordReset` in `auth.api`), not `/forgot-password`** — neither the SRS/issue's illustrative name nor the plausible-sounding `/forget-password` exist in `better-auth@1.7.1`; found via a temporary diagnostic logging `Object.keys(auth.api)` after both guesses 404'd against real CI. `POST /api/auth/reset-password` matched as originally written.
- **`sendResetPassword` only actually sends an email for a non-buyer account** (re-queried via the raw driver, same pattern `rejectBuyerOnPasswordSignIn` already uses) — Better Auth's own response to the caller is identical either way, so `FR-AUTH-019`'s no-enumeration guarantee holds regardless of what this callback does; buyers just never receive a pointless reset link for a credential type they don't use for sign-in.
- **`src/lib/passwordResetTokens.ts`** (new): a small Mongoose model + `recordResetToken`/`consumeResetToken`, mirroring `uploads.model.ts`'s `presignedUploads` collection precedent exactly (DB-backed with a TTL index, not an in-process `Map`, so it survives restarts and works across instances) — `sendResetPassword` records `{token, userId}` at send time; `FR-AUTH-022`'s session-invalidation logic (below) consumes it.
- **Session invalidation (`FR-AUTH-022`) runs in `hooks.before`, not `after`** — an `after`-hook version was tried first (matching the same `ctx.path`/`ctx.body.token` pattern the working `before` hooks use) but confirmed via real CI to never actually delete a session; `ctx.body` in an `after` hook apparently isn't the original request body the way it reliably is in `before`. Runs before the real handler instead, resolving the affected userId via `consumeResetToken` and deleting every matching `session` document — a documented, accepted tradeoff (a token-valid-but-otherwise-rejected request, e.g. a rejected weak password, would revoke sessions slightly early) not chased further since CI is the only ground truth available here.
- **The delete query matches `session.userId` as both a plain string and an `ObjectId`** — a string-only match found zero documents in real CI even though the hook was confirmed running; this file's own `databaseHooks.session.create.after` already had precedent for exactly this ambiguity (converting `session.userId` to `ObjectId` to query `users` by `_id`), suggesting the `session` collection's own stored `userId` field isn't consistently the same type as the string ids arrive as at the API boundary.
- **The test's reset token is read back from `passwordResetTokens` directly, not parsed from the emailed URL** — Better Auth's reset `url` doesn't carry the token as a `?token=` query param the way the test originally assumed; reading it from this repo's own tracking collection sidesteps guessing Better Auth's URL format entirely.
- Test: `__tests__/auth/admin-password-reset.api.test.ts` (kept separate from `admin-sign-in.api.test.ts` — same "materially different flow shape" precedent) — registered-admin/registered-buyer/unregistered response equality (asserting `200` explicitly, not just equality between calls — two matching 404s would otherwise have passed the equality check trivially, which is exactly how the wrong endpoint path slipped past it twice), valid reset + new-password sign-in, expired/reused token rejection, session invalidation after reset.

## Admin Account Provisioning

Issue #142 / M3.4 (`FR-AUTH-024`–`029`) — the real admin-provisioning story #140's own `createAdminUser.ts` helper deliberately stopped short of: a super-admin can now create, list, and update further admin accounts over REST, and the CLI seed script is env-var-driven instead of hardcoded. New module (`src/modules/adminUsers/`) plus one new middleware; no changes to `X-Admin-Key`/`adminAuth.ts`.

- **`src/middleware/requireRole.ts`** (new) — this codebase's first identity-aware admin guard. Calls `auth.api.getSession({headers})` (via a new, shared `src/utils/fetchHeaders.ts`'s `buildFetchHeaders(req)`, extracted from `betterAuthHandler.ts`'s own inline header-conversion loop on its second use), 401s (`UNAUTHENTICATED`) with no session, 403s (`FORBIDDEN`) if `session.user.role` doesn't match the required role, otherwise attaches `req.adminUser = {id, role}` and calls `next()`. Mounted once at the top of `adminUsers.routes.ts` (`router.use(requireRole("super-admin"))`), the same "guard applied once, at mount" convention `adminAuth.ts` already established — **layered alongside** the existing router-level `X-Admin-Key` check, not a replacement; every other `/api/admin/*` route is untouched and still relies on `X-Admin-Key` alone. `auth.api.getSession({headers})`'s call shape worked against real CI on the first attempt — no iteration needed, unlike #140's `twoFactor` config or #141's `requestPasswordReset` endpoint name.
- **`src/modules/adminUsers/`** — raw MongoDB driver against the `users` collection (`adminUsers.repository.ts`), not a new Mongoose model, matching `auth.ts`'s own established reasoning for staying off Mongoose for this collection. `list()`/`findById()`/`findByEmail()` all scope to `role: {$in: ["catalog-manager","order-manager","super-admin"]}` — this module is the admin roster, never a general user directory, so a buyer account is structurally invisible to it.
  - **`createAdminUser(input)`** (service) generates a random, never-logged, never-returned temporary password (`crypto.randomBytes(24).toString("base64url")`), calls #140's `provisionAdminUser()` to create the account with the requested role and `twoFactorEnabled: true` — identical shape to every other admin account in this codebase — then immediately calls `auth.api.requestPasswordReset({body:{email}})`, reusing #141's real, already-proven flow end to end. The new admin's actual first sign-in still goes through #140's full password+OTP challenge with no bypass (`FR-AUTH-029`) — proven in the test suite by completing a real reset-password round trip and confirming the password step alone still doesn't establish a session.
  - **`listAdminUsers`** — pagination/search/role/status filtering via the shared `src/utils/parseQuery.ts` (#104), reused as-is with no changes needed.
  - **`updateAdminUser(id, patch, requesterId)`** — `400 CANNOT_MODIFY_OWN_ACCOUNT` if `id === requesterId` (`FR-AUTH-026`/`028`: an admin can never change their own role or deactivate themselves through this endpoint, whichever field the patch touches). On `status: false`, synchronously revokes every live session for that admin in the same request, via a newly extracted `src/utils/sessions.ts`'s `revokeSessionsForUser(userId)` — the identical string/`ObjectId` dual-match `deleteMany` logic #141's `auth.ts` hook already had, pulled out on its second use (this codebase's established "extract on second use" convention) and imported back into `auth.ts` too, replacing that inline copy with no behavior change.
  - **A real bug found and fixed while building this**: `adminUsers.repository.ts`'s `list()` originally spread the caller's own `filter` first and the module's `role: {$in: ADMIN_ROLES}` restriction second — since both use the same `role` key, the second spread silently clobbered a caller-supplied `?role=` filter every time, so `GET /api/admin/users?role=catalog-manager` actually returned admins of every role. Caught by the test suite (not a mock — this module's tests hit a real database), fixed by spreading the restriction first so a caller's own (already Zod-validated, already-a-subset-of-`ADMIN_ROLES`) role filter wins.
  - No `DELETE` route (`FR-AUTH-027`'s "an admin can be deactivated" doesn't extend to hard-deletion) — deactivation via `PATCH .../status: false` is the only removal path, consistent with brands'/categories'/products' own status-vs-delete distinction (Status Updates above).
- **`src/scripts/seed/superAdmin.ts`** (new) replaces `src/scripts/seed/admin.ts` (Issue #140's hardcoded stopgap, explicitly flagged in its own header comment as something to "rotate or remove entirely once real admin provisioning... exists") — reads `SUPER_ADMIN_EMAIL`/`SUPER_ADMIN_NAME`/`SUPER_ADMIN_PASSWORD` from `process.env` directly (CLI-only ad hoc config, not routed through the global `env.ts` schema, matching every other seed script's own inputs), falling back to `admin.ts`'s own literal defaults so local dev needs no `.env` changes. Calls `provisionAdminUser()` directly — idempotent, safe to run repeatedly. `package.json`'s `seed:admin` script is renamed `seed:super-admin`.

## Startup

`src/index.ts` exports an async `startServer()`: it awaits `connectDB()` first — on rejection it logs the error and calls `process.exit(1)` **without** calling `app.listen()`, so the process never silently serves traffic against a dead DB connection; only on success does it call `app.listen(env.PORT, ...)`. The unconditional call at the bottom of the file is guarded with `if (require.main === module) startServer();`, so requiring/importing `index.ts` (e.g. from a test) doesn't trigger a real startup as a side effect — only running it directly (`node`/`tsx src/index.ts`, which is what `npm run dev`/the compiled `dist/index.js` do) does. This is what makes the failure path unit-testable — see `src/tests/index.test.ts`, which imports `{ startServer }` and mocks `connectDB`.

## Dev workflow

- `npm run dev --workspace backend` — `tsx watch src/index.ts`
- `npm run build --workspace backend` — `tsc && tsc-alias`, must produce zero errors
- `npm run test --workspace backend` — `vitest run`
- `npm run test:coverage --workspace backend` — `vitest run --coverage` (v8 provider, text + HTML reporters; no enforced threshold yet)
- Copy `.env.example` to `.env` before running locally (`PORT`, `NODE_ENV`, `MONGODB_URI`, `ADMIN_API_KEY`, `CORS_ORIGINS`, `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET_NAME`, `R2_PUBLIC_URL_BASE`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `RESEND_API_KEY`, `RESEND_FROM_EMAIL`) — `src/config/env.ts` validates all of these with `zod` at import time and throws immediately if any required value is missing, so a misconfigured `.env` fails on startup rather than partway through a request. The five `R2_*` vars are read via `env.R2.ACCOUNT_ID` etc., `GOOGLE_*`/`RESEND_*` via `env.GOOGLE.*`/`env.RESEND.*` — not the flat names.
- `env.ts` loads env files by mode: `.env.${NODE_ENV}` first, then `.env` fills in anything not already set (dotenv never overwrites an existing `process.env` key). So `.env.development`/`.env.test`/`.env.production` are optional per-mode overrides layered on top of the shared `.env` — a missing mode-specific file is a silent no-op, not an error. All of them are gitignored; only `.env.example` is committed.
- Tests don't need a real `.env`: `vitest.config.ts`'s `test.env` injects dummy values for all required vars (`MONGODB_URI`, `ADMIN_API_KEY`, the five `R2_*` vars, `BETTER_AUTH_SECRET`/`BETTER_AUTH_URL`, `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`, `RESEND_API_KEY`/`RESEND_FROM_EMAIL`) directly into `process.env` for the whole run (Vitest also sets `NODE_ENV=test` itself, so `env.ts` would look for `.env.test` too — it doesn't need to exist, since the injected values already satisfy the `zod` schema before `dotenv.config()` would matter). Nothing in most of the test suite opens a real MongoDB connection or a real R2 bucket; `connectDB` and `r2.ts`'s `createPresignedPutUrl` are mocked wherever they're exercised — the one exception is `__tests__/auth/` (Issue #139), which overrides `MONGODB_URI` at runtime to point at a `mongodb-memory-server` instance instead (see Authentication (Buyer) above).

Test files: colocated `src/modules/<feature>/tests/*.test.ts` (or `src/<area>/tests/*.test.ts` for cross-cutting utilities, e.g. `src/utils/tests/apiResponse.test.ts`, `src/tests/index.test.ts`) for unit tests, workspace-root `__tests__/<feature>/*.test.ts` for Supertest integration tests. Both globs are wired in `vitest.config.ts`.
